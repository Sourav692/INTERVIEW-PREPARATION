🧩 Linked List Patterns — Interview Cheat Sheet

A few ideas cover the whole topic. Learn to spot which one a question wants.

🔁 Pointer Juggling with a Dummy

Move references around, using a stand-in head so the first node isn’t a special case.

The tell (how to spot it): You reshape a list — reverse, merge, remove, reorder.

How it works: Keep a dummy node before the head and carefully re-point `next` links, always saving the next node before you overwrite it.

Problems here that use it: Reverse Linked List Merge Two Sorted Lists Remove Nth Node From End

Say this in the interview:
“I’ll use a dummy head and re-point next pointers, saving each next node first — O(n), O(1) space.”

🏃 Fast & Slow Pointers

Two runners at different speeds reveal loops and middles.

The tell (how to spot it): You need a cycle, the middle, or an element a fixed distance from the end.

How it works: Advance one pointer by 1 and another by 2 (or open a fixed gap). They meet in a loop, or the slow one lands on the middle.

Problems here that use it: Linked List Cycle Remove Nth Node From End Reorder List

Say this in the interview:
“I’ll use fast/slow pointers to find the middle / detect a loop in one pass with O(1) memory.”

⛰️ Heap for k-Way Merge

Keep the current fronts in a heap and always pull the smallest.

The tell (how to spot it): You merge many sorted sources at once.

How it works: Push each list’s head into a min-heap; pop the minimum, append it, push its successor.

Problems here that use it: Merge k Sorted Lists

Say this in the interview:
“With k sorted lists I’ll keep their heads in a min-heap and pop the smallest each time — O(N log k).”

Talking through any Linked List problem

1. Draw it. Sketch nodes and arrows; linked-list bugs are almost always pointer order.

2. Use a dummy head whenever the head might change, to avoid special cases.

3. Save `next` before you overwrite it — the #1 way to lose the rest of the list.

4. Reach for fast/slow for middles, cycles, and "from the end".
