Binary Search

Binary search finds a target in a sorted sequence — or the flip point of any monotonic yes/no question — by repeatedly comparing the middle of what's left and throwing away the half that can't hold the answer. This page traces the classic index search and the more general "binary search on the answer" pattern step by step, and makes the invariant that keeps both of them correct explicit.

Why this matters

Database and index lookups

B-tree and B+tree nodes are searched with binary search internally — every key lookup in a sorted index is this exact loop, run at every level of the tree.

git bisect

git bisect finds the first bad commit by asking "good or bad?" at a candidate commit and halving the range — it is literally binary search on the answer, with commits as the sorted axis.

Resource-allocation interview questions

"Minimum capacity to ship packages in D days," "Koko eating bananas," "split array to minimize the largest sum" — all of these are binary search on the answer wearing a word-problem costume.

Instructor note: most candidates can recite the classic array search. Far fewer can recognize when a completely array-free word problem is secretly the same algorithm. That recognition — not the loop syntax — is the actual skill being tested.

What is binary search?

Simple definition

Binary search repeatedly looks at the middle of what's left, compares it to what it's looking for, and discards the half that provably cannot contain the answer. Repeat until the window closes.

The only real requirement

It does not require a literal array. It requires the search space to be monotonic: a sorted sequence, or a yes/no predicate whose answer flips from false to true (or true to false) at most once as you scan candidates in order.

Beginner shortcut: if you can promise "once this becomes true, it stays true" (or the false/true mirror of that) as you move through candidates in order, you can binary search it — even with no array anywhere in sight.

Step-by-step thinking process

1

Confirm the space is monotonic

Sorted array, or a predicate that flips at most once. Binary search on non-monotonic data runs to completion and returns a confidently wrong answer.

2

Define lo and hi

They must bound every possible answer — array indices for the classic search, or the smallest and largest candidate value for an answer search.

3

Compute mid and compare

mid = lo + (hi - lo) // 2, then compare arr[mid] to the target, or call predicate(mid).

4

Shrink toward the half that can still be right

Move lo or hi based on the comparison — never leave mid sitting unchanged inside the new window — and repeat.

How the input becomes the working structure

Beginners picture binary search as "an array with two fingers." That's only half the picture. What actually drives the algorithm is lo and hi — two numbers that bound the space of possible answers. For the classic search that space is array indices; for binary search on the answer, it's candidate values themselves.

Decide what "index" means

An array position, or a candidate answer value. This decision determines everything else.

Set lo to the smallest possible answer, hi to the largest

Too narrow silently rules out the real answer. Too wide only costs one extra comparison — when in doubt, go wide.

mid always sits inside [lo, hi]

mid = lo + (hi - lo) // 2 can never point outside the window you just built.

Every shrink step must remove at least one candidate

If a shrink step can leave lo and hi unchanged, the loop never terminates.

Critical point: binary search's entire correctness rests on lo and hi describing a space that shrinks by roughly half every iteration. Building that space correctly — and confirming it's sorted or monotonic — is the real first step, before any comparison happens.

Method 1: the classic index search

The classic version answers a concrete question about a literal array: does target exist, and if so at which index? At every iteration, one invariant holds: if the target is present in the array, it is always somewhere inside arr[lo..hi]. The loop condition (lo <= hi), the mid formula, and the shrink step (mid ± 1) all exist to keep that promise true.

def binary_search(arr, target): lo, hi = 0, len(arr) - 1 while lo <= hi: mid = lo + (hi - lo) // 2 if arr[mid] == target: return mid elif arr[mid] < target: lo = mid + 1 else: hi = mid - 1 return -1

Key mental model

Every comparison eliminates exactly the half of the array that provably cannot contain the target — that's why 7 elements take at most 3 comparisons, and a million elements take at most 20.

Common mistake

Writing lo = mid or hi = mid instead of mid + 1 / mid - 1. If mid is never excluded from the new window, the loop can revisit the same lo/hi pair forever.

Why the invariant matters

At every iteration, if the target exists, it is guaranteed to be inside [lo, hi]. The loop condition, the mid formula, and the shrink step are all written specifically to preserve that one promise.

Method 2: binary search on the answer

This is the generalization interviews actually test. There is no array — lo and hi are candidate answers themselves, and predicate(mid) replaces arr[mid] == target. The invariant shifts too: predicate(hi) is always true (or the initial bound), and everything strictly below lo is provably false — the loop is squeezing that flip point from both sides until lo == hi.

def binary_search_answer(lo, hi, predicate): while lo < hi: mid = lo + (hi - lo) // 2 if predicate(mid): hi = mid else: lo = mid + 1 return lo

Applied here to the "first bad version" pattern: FIRST_BAD = 37, is_bad_version(v) = v >= 37, searched over the range [1, 100].

Key mental model

hi always holds a value known to satisfy the predicate (or the initial upper bound); lo always holds the smallest value not yet ruled out. When lo == hi, that single point is the answer.

Common mistake

Copy-pasting the classic template's hi = mid - 1 into this shape. If predicate(mid) is true, mid might be the answer — excluding it throws away a value that still works.

Why hi = mid (not mid - 1) matters

Because mid itself could be the final answer, it has to stay inside the next window. hi = mid keeps it as a live candidate while the window still shrinks.

Edge cases you should test

Case A: target absent

arr = [1, 3, 5, 7, 9, 11, 13], target = 4

Answer = -1 (not found)

mid=3 (7>4) → hi=2. mid=1 (3<4) → lo=2. mid=2 (5>4) → hi=1. Now lo=2 > hi=1, the loop condition lo <= hi fails, and the function returns -1. This is exactly why the loop condition must be lo <= hi and not lo < hi — a single-element window (lo == hi) still needs to be checked before giving up.

Case B: target at the last index

arr = [1, 3, 5, 7, 9, 11, 13], target = 13

Answer = index 6

mid=3 (7<13) → lo=4. mid=5 (11<13) → lo=6. mid=6 (13==13) → found. Boundary elements are not a special case here — hi starting at len(arr)-1 guarantees the last index is always reachable.

Case C: duplicates — bisect_left vs bisect_right

a = [1, 3, 3, 3, 7], target = 3

bisect_left = 1 · bisect_right = 4

The classic binary_search above would return some index equal to 3 — which one depends on how the window happens to shrink, and it is not guaranteed to be the first or last one. bisect_left(a, 3) always returns the leftmost valid insertion point (1, before all the 3s); bisect_right(a, 3) always returns the rightmost (4, after all the 3s). bisect_right(a, x) - 1 is therefore the pattern for "the latest entry <= x" — useful for checkpoint-style queries where you want the most recent record at or before a given point.

Why mid = lo + (hi - lo) // 2? In Python, (lo + hi) // 2 gives the exact same value, because Python integers never overflow. But in a fixed-width-integer language, lo + hi can overflow before the division happens, silently wrapping into a negative number and corrupting the search — lo + (hi - lo) // 2 never adds two large numbers together, so it is safe everywhere. It's worth writing this form from muscle memory even in Python.

How to derive this in an interview

Reasoning path

Is the thing I'm searching sorted, or is there a monotonic predicate hiding in the wording? If neither, binary search doesn't apply yet.

Am I looking for an exact index/value in real data, or the smallest/largest value where some condition holds? The first is the classic template; the second is binary search on the answer.

What are the tightest correct lo and hi? Too narrow silently misses the answer; too wide only costs one extra comparison.

What does "true" mean at mid, and which side does it eliminate? Write this down in one sentence before coding — it decides every shrink step.

Does my shrink step always make progress? Match mid ± 1 to lo <= hi, or hi = mid / lo = mid + 1 to lo < hi — never mix the two shapes.

What to say out loud

  • "Is the thing I'm searching monotonic? If yes, I don't need a literal sorted array — I need lo/hi bounding the possible answers."
  • "I'll compute mid as lo + (hi - lo) // 2 to avoid overflow, even though it doesn't matter in Python."
  • "My invariant is: if the answer exists, it's always inside [lo, hi]. Every line I write has to preserve that."
  • "For an exact match I use lo <= hi with mid ± 1; for a boundary search I use lo < hi with hi = mid, so I never accidentally step over a valid answer."

Common beginner coding mistakes

Classic search mistakes

  • Writing hi = mid instead of hi = mid - 1 (or lo = mid instead of lo = mid + 1) — mid stays inside the new window forever, causing an infinite loop.
  • Using while lo < hi for an exact-match search — this can exit one comparison too early and miss a target sitting exactly at lo == hi.
  • Computing mid once outside the loop instead of re-deriving it every iteration — a stale mid silently breaks the comparison.
  • Forgetting the array must actually be sorted first — binary search does not check; it runs to completion and returns a confidently wrong answer.

Binary search on the answer mistakes

  • Copy-pasting the classic template's hi = mid - 1 into an answer search — this excludes mid even when predicate(mid) is true, skipping past a valid answer.
  • Using while lo <= hi in a while lo < hi shaped problem — lo and hi cross instead of converging, and the loop either infinite-loops or reads a stale mid.
  • Bounding lo/hi on the wrong axis — e.g. searching over array positions when the problem actually wants candidate capacities or values.
  • Forgetting to double-check the predicate is actually monotonic — if it isn't, binary search still converges to some flip point, just not necessarily the one you wanted.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Trace binary_search([2, 4, 6, 8, 10, 12], 10) by hand. What are lo, hi, and mid at each iteration, and what does it return?

Answer: Iteration 1 — lo=0, hi=5, mid=2, arr[2]=6 < 10 → lo=3. Iteration 2 — lo=3, hi=5, mid=4, arr[4]=10 == 10 → match. The function returns 4.

Practice 2 — A sorted array has duplicates: [5, 7, 7, 7, 7, 9]. Using only the classic binary_search template (no bisect), how would you find the leftmost index containing 7?

Answer: Change the found-case. When arr[mid] == target, don't return immediately — record mid as a candidate answer, then keep searching the left half (hi = mid - 1) to see whether an even earlier index also equals 7. Return the last recorded candidate once the loop ends. This is exactly the computation bisect_left performs internally.

Practice 3 — Given package weights and D days, find the minimum ship capacity so all packages are delivered within D days. What are lo, hi, and the predicate — and which template do you use?

Answer: This is binary search on the answer. lo = max(weights) (capacity must fit the single heaviest package), hi = sum(weights) (one day, ship everything at once). predicate(capacity) greedily packs a running day-load and starts a new day whenever the next package would exceed capacity, returning whether the whole shipment finishes within D days. Call binary_search_answer(lo, hi, predicate) — it returns the smallest capacity where the predicate is true.

Final takeaway

Binary search is one invariant wearing two costumes. Classic search: if the target exists, it's always inside [lo, hi] — so lo <= hi, mid ± 1, and an exact-match return all follow from that promise. Binary search on the answer: the flip point is always inside [lo, hi] — so lo < hi, hi = mid / lo = mid + 1, and return lo all follow from that one instead. Once you can state the invariant out loud, the loop condition, the mid formula, and the shrink step stop being things to memorize — they become the only lines that could possibly be correct.
