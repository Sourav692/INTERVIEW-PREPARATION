Hash Tables

A hash table turns "where is this key stored?" into a single arithmetic calculation instead of a search: compute hash(key) % capacity and land directly on a bucket. This page traces the two standard ways that bucket handles a collision — separate chaining and open addressing — and shows exactly why get/put/delete are O(1) on average, never guaranteed.

Canonical example

Why this matters

Every language's dict/set

Python's dict, JavaScript's Map/object, Java's HashMap — every one of them is a hash table. You use one every time you write d[key].

Caches and dedupe

An LRU cache's lookup table and a "have I already processed this ID" dedupe set both depend on O(1) average membership checks.

Database indexes

A hash index on a column answers "give me the row(s) with exactly this value" in one computed lookup instead of scanning every row.

Instructor note: this is not a niche structure to learn once and forget. It is the single most-reused idea in the rest of this repo — Two Sum's complement lookup, Group Anagrams' grouping, and every memoization cache all lean on the exact same computed-index trick you are about to trace.

What is a hash table?

Simple definition

A hash table stores key → value pairs in a plain array (the bucket array) by computing index = hash(key) % capacity. A hash function turns a key into an index, so a lookup skips the scan — it recomputes the same index instead of comparing against every stored key.

What you are actually computing

You are not searching for a match. You are computing an address. The hash function is deterministic, so the same key always recomputes to the same bucket — every time, on every call.

Beginner shortcut: collisions are not a bug — they are guaranteed. By the pigeonhole principle, a fixed number of buckets holding enough distinct keys must eventually put two different keys in the same bucket. What separates a working implementation from a broken one is only how gracefully it resolves that collision.

Step-by-step thinking process

1

Hash the key

Run the key through a deterministic hash function to get a large number.

2

Reduce mod capacity

index = hash % capacity turns that number into a valid array slot, 0 .. capacity-1.

3

Resolve the collision

If the slot is already taken by a different key: chain (append to a list) or probe (walk forward to the next free slot).

4

Watch the load factor

Once size / capacity crosses a threshold, resize before every operation degrades toward O(n).

How the input becomes a bucket array

This is where beginners lose the thread: the hash value itself is huge and mostly meaningless — only what survives the modulo matters.

Input keys

["cat", "dog", "bird", "fish"] capacity = 8
→

hash(key) % capacity

cat : 312 % 8 = 0 dog : 314 % 8 = 2 bird : 417 % 8 = 1 fish : 426 % 8 = 2 (collides with dog)

Hash "cat"

sum(ord(ch) for ch in "cat") = 312, then 312 % 8 = 0. Bucket 0 is free.

Hash "dog"

314 % 8 = 2. Bucket 2 is free.

Hash "bird"

417 % 8 = 1. Bucket 1 is free.

Hash "fish"

426 % 8 = 2 — the same remainder as dog. This is the collision both methods below have to resolve.

Critical point: the raw hash values (312, 314, 417, 426) are thrown away after the modulo. Only the remainder survives — that is exactly why two unrelated-looking keys (dog and fish) can still land on the same index.

Implementation note: Python's builtin hash() for strings is randomized per process (a security feature, PYTHONHASHSEED), so the same code would print different bucket indices on every run. Every trace on this page instead uses a small deterministic hash — sum(ord(ch) for ch in key) — purely so the diagrams below are reproducible. 16_hash_tables.ipynb uses hash(key) % capacity directly; for its integer-key example this is deterministic too, since hash(x) == x for small ints — only the string case needed a stand-in here.

Method 1: Separate chaining

Each bucket holds a small list of (key, value) pairs. A collision just means "append to this bucket's list" — nothing is evicted, and nothing is overwritten unless the key truly matches on a scan.

class HashTable: def __init__(self, capacity=8): self.capacity = capacity self.buckets = [[] for _ in range(capacity)] self.size = 0 def _hash(self, key): return sum(ord(ch) for ch in key) def _index(self, key): return self._hash(key) % self.capacity def put(self, key, value): i = self._index(key) bucket = self.buckets[i] for j, (k, _) in enumerate(bucket): if k == key: bucket[j] = (key, value) return bucket.append((key, value)) self.size += 1 def get(self, key, default=None): bucket = self.buckets[self._index(key)] for k, v in bucket: if k == key: return v return default

Key mental model

A bucket is never just "one slot" — it is a list. Insert always appends; lookup always scans until it finds a match or runs out of list.

Common chaining mistake

Assuming the bucket index alone identifies the key. Two different keys share a bucket's index — the loop must re-check the actual key, not just "we found the right bucket."

Why chain length matters

Chain length is exactly what separates the average case from the worst case: an evenly spread hash keeps every chain short (O(1)), but a bad hash — or an adversarial key set — can pile everything into one chain and degrade to O(n).

Method 2: Open addressing (linear probing)

There is no separate list — every key lives directly inside the bucket array. A collision means: don't evict, don't grow a list; instead walk forward (i+1, i+2, ...) until an empty slot is found.

EMPTY = None TOMBSTONE = object() # marks "deleted, but keep probing past me" def hash_index(key, capacity): return sum(ord(ch) for ch in key) % capacity def put(slots, keys, key, value, capacity): i = hash_index(key, capacity) start = i while slots[i] not in (EMPTY, TOMBSTONE): if keys[i] == key: slots[i] = value # update existing key return i = (i + 1) % capacity # linear probe: try the next slot if i == start: raise Exception("table full") slots[i] = value keys[i] = key def get(slots, keys, key, capacity, default=None): i = hash_index(key, capacity) start = i while slots[i] is not EMPTY: if slots[i] is not TOMBSTONE and keys[i] == key: return slots[i] i = (i + 1) % capacity if i == start: break return default def delete(slots, keys, key, capacity): i = hash_index(key, capacity) start = i while slots[i] is not EMPTY: if slots[i] is not TOMBSTONE and keys[i] == key: slots[i] = TOMBSTONE # NOT None -- keeps later probes alive return True i = (i + 1) % capacity if i == start: break return False

Key mental model

get() and delete() must retrace the exact probe path put() used. If put() had to walk two slots forward to insert a key, get() must walk the same two slots to find it again.

Common open addressing mistake

Deleting by setting the slot back to empty. That silently breaks the probe path for every key that collided through that slot — see steps 6-7 above.

Why open addressing matters

All the data lives in one contiguous array with no extra list-node objects, so open addressing has better cache locality than chaining — but it fills up faster and needs the tombstone discipline to delete safely.

Edge cases you should test

Case A: total collision (capacity = 4)

keys = ["a", "e", "i", "m"], capacity = 4

chain at bucket 1 has length 4 → get() degrades toward O(n)

hash("a")=97, hash("e")=101, hash("i")=105, hash("m")=109 — each exactly 4 apart, so every one reduces to index 1. With chaining, bucket 1's list grows to length 4, and a lookup for a missing key has to scan all four entries before giving up. With open addressing, inserting the 4th key means probing through 3 already-occupied slots first. This is the worst case, not a bug: a good hash function makes this rare, but it can never make it impossible — that is the pigeonhole principle again.

Case B: load factor crosses the resize threshold

Insert alice, bob, carol, then key0 .. key19 (23 keys total) into 16_hash_tables.ipynb's SimpleHashTable(capacity=4), whose put() resizes whenever size / capacity > 0.75.

capacity grows 4 → 8 → 16 → 32 as load factor repeatedly crosses 0.75

Real, run output: after carol, size/capacity = 3/4 = 0.75 — not greater than 0.75, so no resize yet. Inserting key0 pushes it to 4/4 = 1.00 > 0.75, triggering a resize to capacity 8. The same thing happens again at 7/8 = 0.88 (→ 16) and at 13/16 = 0.81 (→ 32). Final state: 23 keys in a capacity-32 table, load factor 0.72.

def _resize(self): old_buckets = self.buckets self.capacity *= 2 # double capacity self.buckets = [[] for _ in range(self.capacity)] self.size = 0 for bucket in old_buckets: # re-hash every existing key for k, v in bucket: self.put(k, v)

Resizing itself is O(n) (every key gets re-hashed and re-inserted), but it happens only O(log n) times as the table grows — the same doubling argument used for Python's dynamic arrays. That is why the average cost per insert stays O(1): the expensive resize is amortized, not free, and not guaranteed on any single call.

Case C: naive delete breaks open addressing

Table holds cat@0, bird@1, dog@2, fish@3 (fish collided with dog and probed forward to slot 3 — this is steps 6-7 vs. 9-11 in the Method 2 trace above).

delete('dog') the wrong way → get('fish') wrongly returns None even though fish is still in slot 3

Setting the deleted slot back to EMPTY makes get() stop probing there, because "empty slot" is the loop's only exit signal for "the key isn't here." Anything that had to probe past that slot to reach its real home becomes unreachable — not deleted, just lost. A tombstone fixes this: it still reads as "occupied" for probing purposes (so the walk continues) while reading as "not a real key" for matching purposes (so it doesn't falsely match a lookup). The tombstone only matters when the deleted slot lies on some other key's probe path — see Practice 3 below for the case where it doesn't matter at all.

How to derive this in an interview

Reasoning path

The question needs O(1) average lookup by key → reach for a hash table.

Two keys can land on the same index → I need a collision strategy.

Chaining is simplest to reason about (a list per bucket); open addressing has better cache locality but needs careful deletion.

What keeps this O(1) as the table grows? Load factor + resize: double capacity and rehash once size/capacity crosses roughly 0.75.

What's the actual worst case? O(n) if the hash function is bad enough that every key collides into the same bucket or chain.

What to say out loud

  • "I'll hash the key and reduce it mod capacity to get an O(1) average lookup instead of scanning."
  • "Collisions are guaranteed by the pigeonhole principle, so I need a resolution strategy — chaining is simplest, open addressing has better cache locality."
  • "I'll resize — double capacity, rehash everything — once the load factor crosses about 0.75, so the average stays O(1) even though a single resize is O(n)."
  • "Worst case is still O(n) if the hash function is pathological — that's why 'O(1) hash lookup' always comes with the word average attached."

Common beginner coding mistakes

Separate chaining mistakes

  • Comparing bucket-index equality instead of re-checking the actual key inside the bucket's list.
  • Forgetting to update an existing key in place (bucket[j] = (key, value)) and instead appending a duplicate entry.
  • Never checking the load factor, so a chain silently grows into an O(n) lookup.
  • Using a mutable object (a list, a dict, a set) as a key. Python raises TypeError: unhashable type because a mutable key's hash could change after insertion, which would corrupt every bucket it ever touched — always hash on something immutable, like a tuple or frozenset.

Open addressing mistakes

  • Deleting by setting the slot back to empty instead of a tombstone, silently breaking the probe path for every key that collided through that slot.
  • Forgetting the if i == start: break wraparound guard, causing an infinite loop once the table is completely full.
  • Not stopping get() at a genuinely empty slot — continuing to probe past it defeats the entire purpose of the probe sequence.
  • Relying on the order keys come back when iterating the table. A hand-rolled table's bucket order is not insertion order and can change after a resize — only Python's real dict guarantees insertion order as a documented feature (since 3.7).

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — With capacity = 8 and hash(key) = sum(ord(ch) for ch in key), which bucket does the key "ant" land in?

Answer: bucket 3. hash("ant") = 97 + 110 + 116 = 323, and 323 % 8 = 3.

Practice 2 — Insert cat, dog, bird, fish, owl in that order into a capacity-8 chaining table. What ends up in bucket 2, and does adding owl make lookups there suddenly slow?

Answer: bucket 2 ends up holding [('dog', 'bone'), ('fish', 'algae'), ('owl', 'hoot')] — owl hashes to 338 % 8 = 2, a third coincidental collision. A lookup that misses now costs 3 comparisons instead of 2, which is technically worse but still O(1) in the average-case sense: real hash tables keep chains short by resizing long before load factor lets any one chain grow large. This specific 3-way pileup is a deliberately constructed teaching coincidence, not typical behavior.

Practice 3 — Same open addressing table as the trace above: cat@0, bird@1, dog@2, fish@3. If you delete bird using a tombstone, does get('dog') still work? What if you deleted bird by setting its slot to None instead?

Answer: it works either way. dog hashes directly to slot 2 with zero probing (hash("dog") % 8 = 2, and slot 2 was empty when dog was inserted) — its probe path never touches slot 1 at all. The tombstone-vs-empty distinction only matters for keys whose probe path passes through the deleted slot. Deleting dog itself (which collided with fish) is the case that actually needs a tombstone, exactly as shown in steps 6-11 of the trace.

Final takeaway

A hash table's entire trick is turning "where is this?" into "let me compute that" — hash(key) % capacity. Collisions are inevitable by the pigeonhole principle, and the two standard fixes are chaining (a list per bucket) and open addressing (probe forward in the same array). Both are O(1) average, O(n) worst case, and both rely on resizing the table before the load factor gets out of hand — that resize is the "amortized" in "amortized O(1)."
