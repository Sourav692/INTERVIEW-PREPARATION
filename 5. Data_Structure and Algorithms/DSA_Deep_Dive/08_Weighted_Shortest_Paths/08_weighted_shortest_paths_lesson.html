Weighted Shortest Paths — Dijkstra & Bellman-Ford

BFS finds the path with the fewest edges. The moment edges carry different costs, "fewest edges" stops meaning "cheapest" — you need an algorithm that tracks total cost instead. This page traces two of them on the exact functions from the companion notebook: Dijkstra, a greedy algorithm that only works when every weight is non-negative, and Bellman-Ford, a slower algorithm that tolerates negative weights and can prove when a graph has no well-defined shortest path at all.

Why this matters

Maps and GPS routing

Road segments have real costs (time, distance, tolls). The "shortest route" is a Dijkstra run over the road network's weighted graph.

Network routing protocols

OSPF and similar link-state protocols run Dijkstra on link costs so every router agrees on the cheapest path to every other router.

Arbitrage detection

Model currency exchange rates as edge weights (via a negative log). A profitable arbitrage loop is exactly a negative cycle — the one thing only Bellman-Ford can detect.

Instructor note: both algorithms share one operation — relaxation: "does going through this edge beat the best cost I already know?" Everything else is just how aggressively and in what order that question gets asked.

What is a weighted shortest path?

Simple definition

The minimum total edge-weight needed to travel from a start vertex to another vertex, where each edge has its own cost — not just "1 hop" like in BFS.

What you are computing

A number dist[v] for every reachable vertex v: the cheapest possible total cost from start to v. Both algorithms build this same dist dictionary — they just fill it in differently.

Beginner shortcut: if every edge weighs the same (or exactly 1), Dijkstra degenerates into plain BFS — fewest edges really is cheapest. Weighted algorithms only start to matter once edge costs actually differ.

Step-by-step thinking process

1

Check the weights

Are all edge weights guaranteed non-negative? That single fact decides which algorithm is even legal to use.

2

Build the working structure

Dijkstra needs an adjacency list grouped by source vertex. Bellman-Ford just needs the raw flat edge list.

3

Relax, relax, relax

For every edge you examine: "does going through this edge beat what I already know?" If yes, update and keep going.

4

Know your stopping rule

Dijkstra stops when the heap is empty. Bellman-Ford stops after V-1 full rounds, plus one more to check for a negative cycle.

How the input becomes a working structure

Both algorithms start from the same directed, weighted edge list. Dijkstra reshapes it into an adjacency list keyed by source vertex — that is what lets it ask "who can I reach from here?" in O(1). Bellman-Ford does not reshape it at all: it just walks the flat list of edges, over and over, because it never tries to be clever about order.

Input edge list

edges = [ (A, B, 1), (A, C, 4), (B, C, 2), (B, D, 5), (C, D, 1), (D, E, 3), ]
→

Adjacency list (Dijkstra)

A: [(B,1), (C,4)] B: [(C,2), (D,5)] C: [(D,1)] D: [(E,3)] E: []

Read (A, B, 1), then (A, C, 4)

Both are appended as (neighbour, weight) pairs to A's list only.

Read (B, C, 2), then (B, D, 5)

Appended to B's list. C's list is untouched by this edge — the graph is directed.

Read (C, D, 1), then (D, E, 3)

Appended to C's and D's lists respectively. E ends with an empty list — it has no outgoing edges.

Critical point: unlike an undirected graph, each edge is added to only its source's list. There is no edge B → A just because A → B exists — direction matters, and it is exactly what the trace tables below track as "Relax u → v."

Method 1: Dijkstra — greedy with a min-heap

Always pop the closest unfinished vertex from a min-heap, lock in its distance for good, then relax its outgoing edges. Because every weight is non-negative, no path discovered later can ever beat the vertex you just popped — that guarantee is the entire algorithm, and it is also exactly the guarantee a negative edge would break.

import heapq def dijkstra(adj, start): dist = {start: 0} done = set() pq = [(0, start)] # (distance, vertex) min-heap while pq: d, u = heapq.heappop(pq) # closest unfinished vertex if u in done: continue # stale entry -- already finalized done.add(u) # lock in u's distance for good for v, w in adj[u]: if v in done: continue # never relax a finalized vertex nd = d + w if nd < dist.get(v, float("inf")): dist[v] = nd # relax: cheaper path found heapq.heappush(pq, (nd, v)) return dist

Key mental model

Once a vertex is popped, its distance is done forever — that is the greedy promise, and it only holds because no edge can ever make a path cheaper by going backwards through a bigger number.

Common Dijkstra mistake

Forgetting the stale-entry check (if u in done: continue) and assuming every heap pop is a brand-new vertex. C and D are each pushed twice in this trace — skip the check and you would re-process outdated distances.

Why the heap matters

Python's heapq has no cheap "decrease-key," so a cheaper path to a vertex pushes a brand-new heap entry instead of updating the old one. The stale-entry check is what makes that trade-off safe.

Method 2: Bellman-Ford — relax every edge, V-1 times

Don't be clever about order — just relax every edge, V-1 times in a row. After k rounds, every shortest path using at most k edges is already correct, and a simple shortest path never needs more than V-1 edges. One extra round then answers a question Dijkstra cannot even ask: is there a negative cycle?

def bellman_ford(vertices, edges, start): dist = {v: float("inf") for v in vertices} dist[start] = 0 for _ in range(len(vertices) - 1): # V-1 rounds for u, v, w in edges: if dist[u] + w < dist[v]: # relax every edge dist[v] = dist[u] + w # extra round: still improving => negative cycle neg = any(dist[u] + w < dist[v] for u, v, w in edges) return dist, neg

Key mental model

Bellman-Ford never locks a vertex in early. dist[A] changes on rounds 1 and 2 here — nothing is trustworthy until every round has run, which is exactly the opposite of Dijkstra's early-lock guarantee.

Common Bellman-Ford mistake

Stopping after fewer than V-1 rounds, or skipping the extra round entirely — without it, a negative cycle silently produces wrong-looking-but-plausible distances instead of an honest "undefined" answer.

Why the extra round matters

After V-1 rounds every simple shortest path is settled. If a V-th round still finds an improvement, that improvement can only be coming from a cycle — one with negative total weight.

Edge cases you should test

Case A: a node that can't be reached

adj = {A: [(B, 2)], B: [], C: []}, start = A

dist = {A:0, B:2} — C stays at infinity

C is never pushed onto the heap, so it is never even considered. dist.get('C', float('inf')) returns infinity forever — that is correct, because no path to C exists. Beginners sometimes expect a KeyError here; the code is written to avoid one on purpose with .get(...).

Case B: one negative edge, wrong Dijkstra answer

adj = {A: [(B,4),(C,5)], B: [], C: [(B,-3)]}, start = A

Dijkstra: dist[B] = 4 (WRONG) · Bellman-Ford: dist[B] = 2 (correct)

Dijkstra pops A(0), then B(4) — and finalizes B right there. The cheaper route A→C→B = 5 + (-3) = 2 is only discovered afterward, when C is popped, but B is already locked and the code explicitly skips relaxing a finalized vertex. Bellman-Ford has no such lock, so it finds the true answer.

Case C: a negative cycle

edges = [(A,B,1), (B,C,-1), (C,A,-1)] — the loop A→B→C→A sums to 1 + (-1) + (-1) = -1

Bellman-Ford: negative cycle detected — no shortest path is well-defined

Distances keep shrinking every round instead of settling (dist[A] goes 0 → -1 → -2 → ... and would never stop). The extra, V-th round still finds an improvement on edge A→B, which is exactly the signal Bellman-Ford uses to report "no answer exists" instead of returning a plausible-looking but meaningless number.

Every method builds the same kind of answer — a dist map from start to every vertex — using the same relaxation rule. They differ only in what order they're willing to apply it, and what that order costs and guarantees.

How to derive this in an interview

Reasoning path

Edges have different costs, so BFS's "fewest hops" guarantee breaks down.

The repeated operation everything reduces to is relaxation: can I reach v more cheaply through u?

Are weights guaranteed non-negative? If yes, I can be greedy: always expand the closest known vertex next, using a min-heap. That's Dijkstra.

If negative weights are possible, greedy breaks — a negative edge found later could undercut a vertex I already locked in.

So instead I relax every edge, blindly, for V-1 rounds — guaranteed enough for any simple shortest path. That's Bellman-Ford.

One more round tells me whether a negative cycle exists: if anything still improves, there is no bottom to the cost.

What to say out loud

  • "I need cheapest total cost, not fewest edges, so plain BFS is out."
  • "If weights are non-negative, Dijkstra's greedy pop is safe — the closest vertex found so far can never be beaten later, because nothing can subtract from a path."
  • "If weights can be negative, I can't trust a greedy lock-in, so I fall back to relaxing every edge for V-1 rounds — slower, but always correct."
  • "One extra round of relaxation is a cheap way to prove a negative cycle exists: if anything still improves, the answer is undefined, not just unfound."

Common beginner coding mistakes

Dijkstra mistakes

  • Running it on a graph with negative weights and trusting the answer without checking.
  • Forgetting the stale-entry check (if u in done: continue) and re-processing outdated heap entries.
  • Marking a vertex "done" the moment it's pushed onto the heap instead of when it's popped — a pushed value is only a candidate.
  • Using dist[v] directly instead of dist.get(v, float('inf')), causing a KeyError on an unreached vertex.

Bellman-Ford mistakes

  • Stopping after 1 round instead of V-1 — distances that need more hops to propagate haven't converged yet.
  • Forgetting the extra V-th round entirely, so negative cycles go undetected and wrong distances are returned silently.
  • Mutating dist during the negative-cycle check pass — that pass must only check, never apply, or you get false positives.
  • Assuming a "lucky" edge order converges in fewer than V-1 rounds — worst-case ordering genuinely needs every round.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — In the main Dijkstra trace, C is pushed onto the heap twice: once at distance 4 (via A), once at distance 3 (via B). What happens to the distance-4 entry, and is it a bug?

Answer: no bug. By the time (4, C) reaches the front of the heap, C has already been finalized at its true distance of 3 (popped as (3, C) one step earlier). The if u in done: continue check catches the stale duplicate and skips it — dist[C] is never touched again. This is exactly why lazy deletion is safe: a stale entry does nothing except get thrown away.

Practice 2 — A graph has 6 vertices and no negative weights. What's the maximum number of times heapq.heappush can run, and why isn't that bound simply "V"?

Answer: up to E times — once for every edge that turns out to be an improving relaxation — not V times. Python's heapq has no cheap "decrease-key," so a vertex that keeps getting cheaper paths before it is ever popped gets pushed again and again, rather than having one entry updated in place. That is exactly why the heap can hold more than V live entries at once, and why the stale-entry check on pop is mandatory, not optional.

Practice 3 — You run Dijkstra believing all weights are non-negative, but one edge is secretly -1. The output distances still look correct. Does that mean the negative edge was handled safely?

Answer: no — it got lucky. Whether the bug shows up depends entirely on whether the negative edge's discount would have reached a vertex that was already finalized before that edge got a chance to relax it. If the negative edge's target hasn't been popped yet when the edge is relaxed, the wrong assumption never actually gets exercised. You cannot know that in advance just by looking at the output — "looks right" and "is correct" are not the same guarantee once a negative weight is in play.

Final takeaway

Both algorithms answer the same question — "what is the cheapest way to reach each vertex?" — using the same core move: relaxation. Dijkstra earns its speed by being greedy: pop the closest unfinished vertex, lock it in, never look back. That lock is only safe because weights can't be negative. Bellman-Ford gives up the greedy shortcut and relaxes every edge, V-1 times, so it never has to trust an early guess — and one extra round turns that same patience into a proof that a negative cycle exists.
