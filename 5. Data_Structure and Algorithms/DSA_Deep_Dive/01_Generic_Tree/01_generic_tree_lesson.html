Generic (N-ary) Trees

A generic tree lets every node hold any number of children in a list, instead of a fixed left/right pair. This page traces two baseline walks over the exact same tree — a recursive pre-order DFS and an iterative level-order BFS — so you can see, step by step, what the call stack and the queue each look like in memory as the code runs.

Canonical example

Tree built with add_child: A → [B, C, D], B → [E, F], D → [G]

dfs_preorder(A) = [A,B,E,F,C,D,G] · bfs(A) = [A,B,C,D,E,F,G]

Why this matters

File systems

A folder can contain any number of files and subfolders. Printing a directory listing is a pre-order DFS; listing "everything at depth 2" is a BFS.

Org charts & comment threads

A manager can have any number of direct reports; a comment can have any number of replies. Both are generic trees, not binary ones.

Foundation for everything after

Binary trees, BSTs, tries, and heaps are all special cases of the generic tree. Own dfs_preorder and bfs here first — everything later is a variation.

Instructor note: the only structural difference from a binary tree is that node.children is a list instead of node.left / node.right. Every traversal idea you already know still applies — you just loop instead of hard-coding two branches.

What is a generic tree?

Simple definition

A generic (N-ary) tree is a hierarchy where every node has exactly one parent (except the root, which has none) and can have any number of children, stored as a list.

What you are computing

Both methods on this page produce a full visiting order across every node — the difference is only the order: depth-first plunges down one branch at a time, breadth-first sweeps row by row.

Beginner shortcut: if the question needs "top-down, node before its subtree" reach for pre-order DFS. If it needs "row by row" or "closest first," reach for BFS with a queue.

Step-by-step thinking process

1

Store children as a list

Every node gets a children list. Zero, one, or a hundred children are all handled by the same code — no special cases.

2

Pick the walk order you need

Pre-order (top-down, before children) and post-order (bottom-up, after children) for DFS; level-order for BFS.

3

DFS: recurse and loop

Record the node, then for child in node.children: recurse(child). The call stack does the bookkeeping for you.

4

BFS: queue and loop

Pop from the front, record it, push every one of its children to the back. Repeat until the queue is empty.

How the input becomes a tree

The notebook builds the canonical tree with add_child, which creates a node and appends it to the parent's children list. This is where beginners lose the thread coming from binary trees: there is no .left / .right to assign to — everything goes into one growing list per node.

Build calls

A = Node("A") B = add_child(A, "B") C = add_child(A, "C") D = add_child(A, "D") E = add_child(B, "E") F = add_child(B, "F") G = add_child(D, "G")
→

Children-list representation

A.children = [B, C, D] B.children = [E, F] C.children = [] D.children = [G] E.children = [] F.children = [] G.children = []

Create A, then add_child(A, "B")

A new node B is created and appended to A.children, which becomes [B].

add_child(A, "C"), then add_child(A, "D")

A.children grows to [B, C], then [B, C, D]. Nothing about A's node structure changes — only the list grows.

add_child(B, "E"), add_child(B, "F"), add_child(D, "G")

B.children becomes [E, F] and D.children becomes [G]. Node C never gets a call, so C.children stays [] — C is a leaf.

Critical point: because children live in a list, a node can have 0, 1, 2, or 20 children with zero changes to the traversal code — every DFS and BFS below already handles all of those cases with the same for child in node.children loop.

Method 1: DFS pre-order (recursive)

The intuition is that recursion already gives you a call stack for free. Pre-order simply records a node's value the instant its call frame is entered — before the code ever looks at that node's children.

def dfs_preorder(node, out=None): if out is None: out = [] if node is None: return out out.append(node.val) for child in node.children: dfs_preorder(child, out) return out

Key mental model

A node's value is recorded the instant its call frame opens, not when it closes. That single ordering choice is the entire difference between pre-order and post-order.

Common DFS mistake

Writing a fixed two-branch check like a binary tree instead of for child in node.children. A generic tree node can have any number of children — hard-coding two misses siblings or crashes on more.

Why the call stack matters

Recursion depth equals the tree's height, not its node count. That is cheap for a balanced tree but risky for a tall, skewed one — see the chain edge case below.

Method 2: BFS level-order (iterative, queue)

BFS explores ring by ring using a queue: pop from the front, record it, push every child to the back. Because the queue is FIFO, an entire level finishes before the next level starts.

from collections import deque def bfs(root): order = [] if root is None: return order q = deque([root]) while q: node = q.popleft() order.append(node.val) for child in node.children: q.append(child) return order

Key mental model

order.append happens immediately after popping. Because the queue is FIFO, every node at depth 1 leaves the queue before any node at depth 2 is ever popped.

Common BFS mistake

Calling q.pop() instead of q.popleft(). That removes from the same end you push onto, which silently turns your "BFS" into something closer to a reversed DFS.

Why the queue matters

The queue lives on the heap, not the call stack, so an extremely deep tree can never trigger a RecursionError the way the recursive DFS above could.

Method 3: DFS post-order (recursive)

Post-order asks the exact same call-stack question as pre-order — "when do I record this node?" — but answers it differently: wait until every child's subtree has fully finished, then record the node last. In code this is the same function as dfs_preorder with one change: the out.append(node.val) line moves from before the for loop to after it.

def dfs_postorder(node, out=None): if out is None: out = [] if node is None: return out for child in node.children: dfs_postorder(child, out) out.append(node.val) return out

Key mental model

Moving one line — out.append(node.val) — from before the for loop to after it is the entire difference between pre-order and post-order. Same recursion, same call stack, same children loop; only the moment of recording changes.

Common post-order mistake

Copy-pasting pre-order and forgetting to move the append line, then calling the result "post-order" anyway. If a node's value can be recorded before its children have returned, the code cannot depend on the children's results — which is exactly the ability post-order exists to provide.

Why post-order matters

Post-order is required whenever a node's answer depends on its children's answers first: computing subtree size or height, safely deleting a node (free children before the parent), or evaluating an expression tree bottom-up.

Method 4: build a tree from flat {id, parent_id} rows

Real trees rarely arrive pre-linked. A database table, a CSV export, or an API response usually hands you a flat list of rows, each carrying its own id and its parent's parent_id. build_from_rows rebuilds the exact same tree shape in two linear passes: first create every node and index it by id in a hash map (so any id is an O(1) lookup), then walk the rows again and attach each one to nodes[parent_id] — or, when parent_id is None, record it as a root. Because pass 1 always finishes before pass 2 starts, the rows can arrive in absolutely any order.

def build_from_rows(rows): # Pass 1: create every node first, index by id nodes = {} for r in rows: nodes[r["id"]] = Node(r["id"]) # Pass 2: link each row to its parent roots = [] for r in rows: pid = r["parent_id"] if pid is None: roots.append(nodes[r["id"]]) else: nodes[pid].children.append(nodes[r["id"]]) return roots

Key mental model

Two passes, not one. Pass 1 guarantees every id exists in the map before pass 2 ever runs — that is what makes the algorithm immune to row order. A single-pass version would crash or silently drop a node whenever a child row appears before its parent row.

Common mistake

Assuming parent rows always arrive before their children's rows and trying to link in one pass. Real data — a SQL dump, a CSV export, an API page — makes no such promise. The trace above deliberately links G to D (step 8) using nodes['D'], even though D's own row is not processed until step 13.

Why the hash map matters

Without nodes, finding a row's parent would mean scanning all rows for a matching id — O(n) work per row, O(n²) overall. The map turns "find node by id" into O(1), which is exactly what keeps the whole build at O(n).

Edge cases you should test

Case A: single node

root = Node("A"), no children

dfs_preorder = ['A'] · bfs = ['A']

A's children list is empty, so the DFS for loop never executes and the BFS queue empties after one pop. Both functions must handle "root is also a leaf" without any special-casing.

Case B: wide tree, one level deep

A with children [B, C, D, E], none of them have children

dfs_preorder = ['A','B','C','D','E'] · bfs = ['A','B','C','D','E']

When the tree is only one level deep, pre-order DFS and level-order BFS produce the identical sequence — the two traversal orders only diverge once there is a second level to choose between "go deeper" and "go sideways."

Case C: deep chain (A → B → C → ... , each with one child)

root = a chain of 5,000 single-child nodes

bfs survives · recursive dfs_preorder risks RecursionError

The recursive DFS adds one call-stack frame per level, so a chain deep enough can exceed Python's default recursion limit (~1000 frames) before it ever finishes. bfs's queue lives on the heap instead of the call stack, so it is unaffected by how tall or skewed the tree is — this is exactly why "how deep can this tree get" is a question worth asking before choosing recursive DFS in an interview.

The three traversals each visit every node exactly once because a tree has no cycles — the only thing that changes is the order they are visited in and where the "waiting" nodes are stored (call stack vs. queue). Building from flat rows is not a traversal at all — it is a two-pass construction step that has to run before any of the three traversals above can walk the result.

How to derive this in an interview

Reasoning path

Every node can have any number of children, so I loop over node.children instead of hard-coding two branches.

Do I need a node's value before or after its subtree is processed? Before → pre-order. After (need children's results first) → post-order.

Do I need "row by row" or "nearest first"? That is level-order — a queue, not recursion.

Is the tree potentially very deep or skewed? Prefer BFS, or an explicit-stack DFS, to avoid a recursion-depth failure.

What to say out loud

  • "Each node can have any number of children, so I'll loop over node.children rather than checking left/right."
  • "I need the value recorded before its subtree, so I'll append before the recursive calls — that's pre-order."
  • "I need row-by-row order, so I'll use a queue and pop from the front, push children to the back."
  • "If this tree could be very deep, I'd worry about the recursion limit and lean toward the queue-based BFS instead."

Common beginner coding mistakes

DFS mistakes

  • Treating node.children like a binary tree's left/right instead of looping over the whole list.
  • Appending to out after the recursive calls instead of before — that silently turns pre-order into post-order.
  • Forgetting the node is None base case, which crashes as soon as any subtree is empty.
  • Not threading the same out list through every recursive call — creating a fresh list per call loses everything a sibling branch already found.

BFS mistakes

  • Using q.pop() instead of q.popleft(), which pops from the wrong end and breaks the FIFO order.
  • Forgetting to push every child — only pushing the first one silently drops entire subtrees.
  • Using a plain Python list instead of deque as the queue — list.pop(0) is O(n), which quietly kills performance on a large tree.
  • Confusing "depth" with "position in the queue" when a problem asks for level numbers explicitly — depth has to be tracked alongside the node, it isn't free.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — What is height(A) for the canonical tree, and why does the notebook define an empty tree's height as -1 instead of 0?

Answer: 2. The longest path from A down to a leaf is two edges (A → B → E or A → D → G). The -1 sentinel for an empty (None) tree exists so the formula 1 + height(child) still produces the right answer uniformly: if a leaf's single "virtual" empty child were treated as height 0, the formula would report height 1 for a leaf instead of the correct 0.

Practice 2 — If node D had two children, [G, H], instead of one, where would H appear in dfs_preorder(A) relative to G?

Answer: immediately after G's entire subtree finishes. for child in node.children processes D's children strictly in list order, and each child's full recursive call (including all of its own descendants) completes before the loop moves to the next sibling. Since G and H are both leaves here, the output becomes [..., 'C', 'D', 'G', 'H'].

Practice 3 — You need the path of values from the root down to a node holding a target value. Which traversal do you adapt, and what extra state do you carry?

Answer: adapt the DFS pre-order walk into a choose/recurse/un-choose pattern: append the current node's value to a running path list before recursing into each child, return immediately once node.val == target is found, and pop the value back off if that subtree did not contain the target (backtrack). BFS can tell you the target exists, but without extra parent-pointer bookkeeping it does not naturally hand you the root-to-node path the way DFS's call stack already does.

Final takeaway

A generic tree is exactly a binary tree with the left/right restriction removed: every node holds a list of children instead of two fixed slots. DFS pre-order's call stack records a node the moment it is entered, walking one branch fully before backing up. BFS's queue records a node the moment it is popped, guaranteeing every node at one depth finishes before the next depth starts. Once you can write dfs_preorder and bfs from memory, binary trees, BSTs, and tries are all just this same idea with extra constraints layered on.
