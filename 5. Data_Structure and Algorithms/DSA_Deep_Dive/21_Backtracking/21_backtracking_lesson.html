Backtracking

Backtracking is DFS over a tree of decisions instead of a tree of nodes. At every step you choose one option, explore what follows from it, and then un-choose it so the next option starts from a clean slate. This page traces that template through three real problems and shows the seven-pattern family it generates.

Why this matters

Configuration search

Trying every valid combination of settings, ingredients, or team assignments under hard constraints — feature flags, product bundles, seating charts.

Puzzle and game solvers

Sudoku, N-Queens, crosswords, and maze solving all place one piece, recurse, and undo the piece if the branch fails — the same template every time.

Interview reuse

Ten Blind 75 / NeetCode 150 problems — Subsets, Permutations, Combination Sum, Word Search, N-Queens and more — are all small edits to one template.

Instructor note: do not memorize seven separate algorithms. Memorize one skeleton — choose, explore, un-choose — and learn to recognize which one-line edit each new problem needs.

What is backtracking?

Simple definition

Backtracking is depth-first recursion where the recursive call mutates one shared piece of state on the way down, and undoes that exact mutation on the way back up before trying the next option.

What you are building

Either every valid arrangement that satisfies the problem (all subsets, all permutations, all paths) or the first one that does (does this word exist on the board, can four queens be placed safely).

The recursion tree: picture the calls as a tree. The root is the empty state. Each edge is one choice. Each node is one partial arrangement. Leaves are complete arrangements you record, or dead ends you prune. The shape of this tree — how many nodes it has — is exactly what determines the running time.

Beginner shortcut: if a problem says "find all ways to..." or "does there exist a way to...", and a greedy rule or a DP table cannot see far enough ahead to know if a choice is safe, reach for backtracking.

Step-by-step thinking process

1

Name the shared state

What single mutable object — a list called path, a used array, the board itself — represents "the arrangement so far"?

2

Write the base case

When is the state complete? Length equals n? Remaining sum hits zero? Every row has a queen?

3

List the choices, then prune

What are the legal next moves from here, and which ones can be rejected before recursing at all?

4

Write the un-choose as an exact mirror of the choose

Every line that mutates state in the choose step gets one matching line that reverses it, in the opposite order, right after the recursive call returns.

How the input becomes the recursion tree of decisions

Backtracking does not transform the input into a separate data structure the way graph traversal builds an adjacency list. The input list is the set of choices at every level — the transformation beginners miss is realizing that the recursion calls themselves trace out a tree, and that tree is the real "structure" being built as the code runs.

Input list

nums = [1, 2, 3]
→

Recursion tree of decisions

[] ├─ [1] ── [1,2] ── [1,2,3] │ └─ [1,3] ├─ [2] ── [2,3] └─ [3]

Call backtrack(0)

The root of the tree. path = [] is recorded, then the loop considers index 0, 1, and 2 in turn as the root's three children.

Choosing index 0 descends one level

path.append(1) then backtrack(1) creates the edge [] → [1] and enters a new call frame whose own loop considers indices 1 and 2.

Returning un-does the edge, not the node

path.pop() after the recursive call returns removes the value from path, but the node already recorded into out stays recorded forever — only the live path shrinks.

Critical point: the recursion tree is not drawn ahead of time and then walked — it is discovered one edge at a time, exactly in the order the recursive calls happen. That is what the interactive trace below shows growing in real time.

Method 1: Subsets (LC 78) — the start-index loop

Every node visited is itself a subset, not just the leaves. start guarantees the loop only ever moves forward, so [1, 2] and [2, 1] can never both appear — order does not matter for subsets, and forward-only indices are what enforce that.

def subsets(nums): out, path = [], [] def backtrack(start): out.append(path[:]) # record on ENTRY -- every prefix is a subset for i in range(start, len(nums)): path.append(nums[i]) # CHOOSE backtrack(i + 1) # EXPLORE -- only indices after i path.pop() # UN-CHOOSE backtrack(0) return out

Key mental model

Every node in the tree is recorded the instant it is entered, not just the leaves. That is why subsets includes the empty set and every partial prefix, not only the full [1, 2, 3].

Common mistake

Recursing with i instead of i + 1 would let the same index be chosen twice in a row — that is the reuse pattern from Combination Sum, not subsets.

Why start matters

start is what turns an n-way choice at every level into a tree with exactly 2^n nodes instead of n! — each element is either still ahead of start (a live choice) or already behind it (never reconsidered).

Method 2: Combination Sum (LC 39) — reuse and the sorted break

Same start-index loop, a different base case: record only when remaining hits exactly zero. Two new ideas appear here that Subsets did not need: recursing with i instead of i + 1 to allow reusing a candidate, and a break that exploits sorted input to prune every later sibling at once.

def combination_sum(candidates, target): candidates = sorted(candidates) out, path = [], [] def backtrack(start, remaining): if remaining == 0: out.append(path[:]); return for i in range(start, len(candidates)): if candidates[i] > remaining: break # PRUNE: sorted, so nothing later fits either path.append(candidates[i]) # CHOOSE backtrack(i, remaining - candidates[i]) # EXPLORE -- reuse allowed (i, not i + 1) path.pop() # UN-CHOOSE backtrack(0, target) return out

Measured on the notebook's larger example — combination_sum_counted([2, 3, 5, 7], 20, mode): no prune, only bailing out once remaining < 0, costs 246 recursive calls; skipping over-large candidates with continue costs 133; stopping with break the moment one candidate is too large also costs 133. All three find the same 18 answers. Honestly: the prune is what does the work, cutting calls roughly in half — break and continue skip exactly the same branches on sorted input, because once one candidate is too large every later one is too. break is still the better choice because it also skips the leftover loop iterations for free, instead of visiting and rejecting each one.

Key mental model

Passing i instead of i + 1 to the recursive call is the entire difference between "each candidate once" and "unlimited reuse" — nothing else in the function changes.

Common mistake

Using continue instead of break still gives a correct answer on sorted input, but wastes time re-checking every later candidate that is guaranteed to also be too large.

Why sorting first matters

The break prune is only valid because candidates is sorted — on unsorted input, one large value early in the list would wrongly cut off smaller valid values sitting after it.

Method 3: N-Queens (LC 51) — constraint sets

One queen per row; the choice at each row is which column. Three sets — cols, diag (r - c), anti (r + c) — turn "is this square attacked?" into three O(1) lookups instead of rescanning the board. Four pieces of state must be un-chosen, not one.

def solve_n_queens(n): out, cols, diag, anti = [], set(), set(), set() board = [["."] * n for _ in range(n)] def backtrack(r): if r == n: out.append(["".join(row) for row in board]); return for c in range(n): if c in cols or (r - c) in diag or (r + c) in anti: continue # PRUNE: attacked by a queen above cols.add(c); diag.add(r - c); anti.add(r + c); board[r][c] = "Q" # CHOOSE backtrack(r + 1) # EXPLORE cols.remove(c); diag.remove(r - c); anti.remove(r + c); board[r][c] = "." # UN-CHOOSE backtrack(0) return out

Why r - c and r + c? Every cell on the same "\" diagonal shares one value of r - c (move one row down and one column right and both go up by 1, so the difference is unchanged). Every cell on the same "/" diagonal shares one value of r + c (move one row down and one column left and the sum is unchanged). Two queens attack each other diagonally exactly when one of those two numbers matches, so remembering the numbers already in use is enough to check safety without touching the board.

Key mental model

Every dead end above looks the same: scan all n columns in the current row, find every one attacked, and return without ever calling backtrack(r + 1) — the recursion never even descends into a doomed row.

Common mistake

Un-choosing only three of the four pieces of state (forgetting board[r][c] = ".", say) leaves a stale queen drawn on the board for branches that never actually placed one there.

Why three sets beat rescanning

Checking safety by scanning the whole board is O(n) per candidate column; checking three set memberships is O(1) — for n columns across n rows that is the difference between O(n^3) and O(n^2) work just to place one full board.

Reading down the "what must be un-chosen" column is the fastest way to spot the bug in a broken solution: count how many pieces of state the choose line touches, then confirm the un-choose line touches exactly the same pieces, in reverse.

Edge cases you should test

Case A: empty input

subsets([])

Answer = [[]]

backtrack(0) still records the empty path once, then the loop range(0, 0) never runs. One subset — the empty set itself — not zero subsets.

Case B: input with duplicates

subsets_with_dup([1, 2, 2])

Answer = [[], [1], [1,2], [1,2,2], [2], [2,2]]

Sort first so the two 2s sit adjacent, then skip a candidate when i > start and nums[i] == nums[i-1]: the sibling right before it in this same loop already explored that value, so trying it again would only rebuild the exact same subset. Without the sort-and-skip rule, the plain subsets function treats the two 2s as distinguishable and returns all 8 combinations, only 6 of which are distinct.

Case C: target no combination can reach

combination_sum([2, 4, 6], 7)

Answer = []

Every candidate is even, so every reachable sum is even — 7 is odd and can never be hit. Every branch eventually either overflows into the sorted break or the loop simply runs out of candidates; no path ever reaches remaining == 0, so out stays empty. The function must return [] cleanly, not raise an error or return a partial answer.

How to derive this in an interview

Reasoning path

Do I need every valid arrangement, or just the first one that works? Find-all records and continues; find-one returns True up the chain and short-circuits.

Does order matter? If not (subsets, combinations), a start index that only moves forward is enough. If it does (permutations), every level needs to consider every unused element via a used array.

Can I reuse a choice? Recursing with i allows reuse; recursing with i + 1 forbids it.

What can I prune before I even choose? Sorted-and-additive problems get a break; duplicate inputs get a sort-and-skip; grid and constraint problems get an O(1) feasibility check.

What to say out loud

  • "This wants every arrangement, so I will write a backtracking function that records on a valid base case and keeps going, rather than returning early."
  • "Order doesn't matter here, so I'll use a start index to avoid generating the same combination twice in different orders."
  • "The input can repeat, so I need a used array instead of a start index, and I have to remember to reset it on the way back up."
  • "Once I sort the input, any candidate too large to fit means every later candidate is too large too, so I can break instead of just continuing."

Common beginner coding mistakes

State and recording mistakes

  • Missing un-choose: without path.pop(), every sibling inherits the previous sibling's choice instead of starting clean.
  • Recording a reference: out.append(path) stores the same list every time; by the end every recorded answer is empty, because the shared list has been popped back down.
  • Forgetting to reset used: in Permutations, popping path but leaving used[i] = True starves every other branch after the first full permutation is found.

Pruning mistakes

  • continue where break was possible: correct on sorted, additive input, but slower — it still visits and rejects every later candidate instead of skipping them all at once.
  • Wrong dedup condition: writing if nums[i] == nums[i-1]: continue without the i > start guard also skips a duplicate value that is legitimately the first choice at this level, silently dropping valid subsets.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Why does Permutations (LC 46) need a used array instead of a start index?

Answer: a start index only ever looks at elements from start onward, which is exactly what forces the order-independent shape of subsets and combinations. Permutations need [2, 1, 3] and [1, 2, 3] to both appear, which means every level must be able to pick any element not currently on the path, including ones with smaller indices than a choice made earlier. A start index physically cannot go backward; a used array can mark and unmark any index regardless of order.

Practice 2 — Why does Word Search (LC 79) restore the cell even on failure?

Answer: board[r][c] = saved runs unconditionally after the four recursive calls, whether or not any of them returned True. If the cell were only restored on success, a failed path from one starting cell would leave the board permanently mutated with "#" markers, corrupting every subsequent search from a different starting cell — including the very next candidate in the outer loop over (r, c). The un-choose has to be unconditional because the choose was unconditional.

Practice 3 — What does the not used[i-1] clause do in Permutations II (LC 47)?

Answer: without it, if i > 0 and nums[i] == nums[i-1]: continue would also block a duplicate value from ever being placed anywhere in the permutation once its twin has been placed, which is wrong — twins are allowed to both appear, just not interchangeably. not used[i-1] narrows the skip to exactly one case: the identical value just before i is currently sitting idle (already tried and popped back off at this same level), meaning this position would only rebuild a permutation already produced by trying that earlier twin first. If the earlier twin is still on the path, this is a genuinely different position for the current one, so it is allowed.

Final takeaway

One skeleton — choose, explore, un-choose — generates every problem on this page. Subsets is that skeleton with a start index. Combination Sum is the same skeleton with a different base case, reuse via i, and a sorted break. N-Queens is the same skeleton with four pieces of state instead of one and three sets doing the safety check in O(1). The un-choose line is never optional and never approximate — it is an exact mirror of the choose line, every time.
