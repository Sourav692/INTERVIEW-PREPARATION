Minimum Spanning Tree — Kruskal & Prim

A Minimum Spanning Tree connects every vertex of a weighted graph using the cheapest possible set of edges, with no cycles. This page traces two different greedy algorithms — Kruskal (sort edges, skip anything that would cycle) and Prim (grow one tree outward, always take the cheapest edge leaving it) — on the exact same graph, line by line, so you can see them arrive at the same total weight through two different orders of edge selection.

Why this matters

Network infrastructure

Wiring every office, data center, or house to a network for the least total cable — no redundant loops, every site reachable.

Circuit board design

Connecting every pin on a board with the shortest total trace length is literally a minimum spanning tree problem.

Clustering

Single-linkage clustering builds an MST over data points, then cuts its most expensive edges to reveal natural groups.

Instructor note: MST is one of the cleanest examples of a greedy algorithm that is provably optimal — not "usually good," but always correct, for a reason you can state precisely (the cut property, covered below).

What is a Minimum Spanning Tree?

Three words, three requirements

Spanning — touches every one of the V vertices, none left out. Tree — no cycles, which for a connected structure over V vertices forces exactly V - 1 edges. Minimum — among every possible spanning tree, the one whose edge weights sum to the least.

What you are actually building

You start with a graph that may have many redundant connections (cycles) and many possible ways to link everything up. You are selecting a subset of exactly V - 1 edges that keeps the graph connected at the lowest possible total cost.

Beginner shortcut: if a graph has V vertices and is connected, its MST always has exactly V - 1 edges — no more, no fewer. Count your accepted edges as you go; when you hit V - 1, you are done, even if edges remain unprocessed.

Step-by-step thinking process

1

Confirm the graph is connected

If it isn't, no spanning tree exists at all — there's no set of edges that can reach every vertex.

2

Pick edge-centric or vertex-centric

Sparse graph, edges easy to sort → Kruskal. Dense graph, want to grow outward from one point → Prim.

3

Repeatedly take the cheapest safe edge

"Safe" means it doesn't create a cycle (Kruskal) or its far endpoint isn't already in the tree (Prim).

4

Stop at V - 1 edges

That is a complete spanning tree. Any further edges would only create a cycle.

How the input becomes a working structure

Both algorithms start from the same raw fact — a list of weighted edges — but each reshapes it differently before it can run.

Input: weighted edge list

edges = [ (1, A, C), (2, B, C), (3, D, E), (4, A, B), (5, B, D), (6, C, E) ]
→

Kruskal needs: sorted edge list

Input: weighted edge list

edges = [ (1, A, C), (2, B, C), (3, D, E), (4, A, B), (5, B, D), (6, C, E) ]
→

Prim needs: adjacency list

A: [(C,1), (B,4)] B: [(C,2), (A,4), (D,5)] C: [(A,1), (B,2), (E,6)] D: [(E,3), (B,5)] E: [(D,3), (C,6)]

Sorting once, up front (Kruskal)

Because Kruskal always wants "the next cheapest edge overall," sorting the whole list once at the start means every later step is just "read the next item" — no repeated searching.

Building both directions (Prim)

The graph is undirected, so each edge (w, u, v) is added to both adj[u] and adj[v] — from either endpoint you need to be able to see the edge.

Same graph, two different "next" questions

Kruskal's "next" is a position in a sorted array. Prim's "next" is whatever sits at the top of a min-heap of edges leaving the current tree. Different bookkeeping, same underlying graph.

Critical point: neither structure by itself prevents cycles. Kruskal pairs its sorted list with Union-Find; Prim pairs its heap with a visited set. The structure only decides which edge to look at next — a separate check decides whether to keep it.

Method 1: Kruskal — sort edges, skip anything that cycles

Consider every edge from cheapest to most expensive. Add it if and only if its two endpoints are currently in different Union-Find groups — that is exactly the same question as "would this edge create a cycle?"

The cycle-check engine: Union-Find

Kruskal calls uf.union(u, v) on every edge. It returns True (safe, groups merged) if u and v were in different groups, or False (would create a cycle) if they already shared a group.

class UnionFind: def __init__(self, n): self.parent = list(range(n)) self.rank = [0] * n def find(self, x): while self.parent[x] != x: self.parent[x] = self.parent[self.parent[x]] x = self.parent[x] return x def union(self, a, b): ra, rb = self.find(a), self.find(b) if ra == rb: return False if self.rank[ra] < self.rank[rb]: ra, rb = rb, ra self.parent[rb] = ra if self.rank[ra] == self.rank[rb]: self.rank[ra] += 1 return True
def kruskal(n, edges): uf = UnionFind(n) mst, total = [], 0 for w, u, v in sorted(edges): if uf.union(u, v): mst.append((u, v, w)) total += w if len(mst) == n - 1: break return mst, total

Key mental model

Sorting turns "find the globally cheapest remaining edge" into "read the next item." Union-Find turns "would this create a cycle?" into one near-O(1) comparison of two roots.

Common Kruskal mistake

Forgetting the len(mst) == n - 1 stop condition and processing every edge anyway. It still gives the right answer, but on a large graph it wastes work — and if you forget it entirely on a disconnected graph, the loop simply runs out of edges without ever reaching a full tree.

Why Union-Find matters

Without it, checking "are A and D already connected?" would mean a fresh DFS/BFS from A on every single edge — O(V+E) per check instead of near-O(1).

Method 2: Prim — grow one tree, always take the cheapest frontier edge

Start at any vertex. Keep a min-heap of every edge leaving the current tree. Repeatedly pop the cheapest one; if its far endpoint is already in the tree, discard it — otherwise add that vertex and push its outgoing edges as new candidates.

def prim(adj, start=0): visited = {start} pq = [(w, start, v) for v, w in adj[start]] heapq.heapify(pq) mst, total = [], 0 while pq and len(visited) < len(adj): w, u, v = heapq.heappop(pq) if v in visited: continue visited.add(v) mst.append((u, v, w)) total += w for nxt, w2 in adj[v]: if nxt not in visited: heapq.heappush(pq, (w2, v, nxt)) return mst, total

Key mental model

The heap always surfaces the cheapest edge leaving the current tree. Prim never has to scan every frontier edge to find the minimum — the heap already did that work.

Common Prim mistake

Forgetting the if v in visited: continue check. Stale heap entries like A-B(4) in step 3 are expected and harmless — but only if you actually discard them instead of re-adding an already-visited vertex.

Why the heap matters

Without it, finding the cheapest frontier edge would mean scanning every edge touching the tree on every iteration — O(V) or worse per step instead of O(log V) per heap operation.

Edge cases you should test

Case A: disconnected graph

vertices = A, B, C, D with edges only among {A, B} and none touching {C, D}

No spanning tree exists

Kruskal will run out of edges with len(mst) < n - 1 and just stop — it will not raise an error, it will silently return an incomplete tree. Prim's visited set will never reach len(adj) and the heap will empty out first. Always check len(mst) == n - 1 before trusting the result.

Case B: tied edge weights

triangle A-B(2), B-C(2), A-C(2)

Total weight = 4 either way, but the edge SET can differ

With a tie, sorted()'s stable order (or the order edges were pushed to the heap) decides which two of the three equal edges get kept. Two different valid MSTs can result — same total weight, different edges — and that is not a bug in either algorithm. If all weights in a graph are distinct, the MST is provably unique.

Case C: single vertex or two vertices

n = 1 (no edges) or n = 2 with one edge A-B(7)

n=1: 0 edges, total=0 · n=2: 1 edge, total=7

A single vertex is trivially its own spanning tree with zero edges. With two vertices and one connecting edge, that edge is forced — there is no choice to make, and both algorithms return it immediately.

How to derive this in an interview

Reasoning path

We need to connect everything at minimum total cost, with no redundant cycles.

Greedy — always take the cheapest available option — is tempting, but does it actually give the optimal total?

The cut property: split the vertices into any two groups. The cheapest edge crossing that split can never be wrong to include — a cheaper alternative crossing the same split would already have been the cheaper edge.

Kruskal applies this globally, one sorted edge at a time. Prim applies it locally, around the frontier of one growing tree. Both are legal because the cut property holds for every possible cut.

What to say out loud

  • "I need every vertex connected at minimum cost with no cycles — that's a spanning tree, and I want the cheapest one."
  • "Greedy is actually optimal here because of the cut property: the cheapest edge crossing any split of the vertices is always safe to include in some MST."
  • "Given the graph is sparse, I'll sort the edges and use Union-Find to reject anything that would cycle — that's Kruskal, O(E log E)."
  • "If it were dense instead, I'd grow one tree with a min-heap of frontier edges — that's Prim, O((V+E) log V), similar shape to Dijkstra."

Common beginner coding mistakes

Kruskal mistakes

  • Comparing vertices directly (u == v) instead of comparing their roots (find(u) == find(v)) to detect a cycle.
  • Forgetting to sort the edges first — the whole algorithm depends on always looking at the cheapest remaining edge.
  • Not stopping at V - 1 edges, or forgetting to check whether it was ever reached (silently wrong on a disconnected graph).
  • Implementing Union-Find without path compression or union by rank, quietly degrading it from near-O(1) to O(V) per call.

Prim mistakes

  • Forgetting to check if v in visited: continue after popping — this is what discards stale heap entries safely.
  • Only pushing edges from the start vertex once, instead of pushing every newly-added vertex's outgoing edges too.
  • Using a plain list and scanning for the minimum instead of a heap, turning an O(log V) operation into O(V).
  • Assuming the heap only ever holds valid frontier edges — it can and will hold stale entries pointing at vertices already in the tree.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — A graph has two edges tied for cheapest: A-B(3) and C-D(3), touching completely different vertices. Does the order Kruskal considers them in change the final total weight?

Answer: No. Since the two edges don't share any vertex, both will always be accepted regardless of which is processed first — neither can create a cycle relative to the other. Ties only matter for the final edge set when the tied edges compete for the same connection; the total weight of the MST is unaffected either way.

Practice 2 — You run kruskal(6, edges) on a graph where vertex 5 has no edges at all. What does the function return, and how would you catch the problem?

Answer: The loop will never accept an edge touching vertex 5, so mst will end with only 4 edges instead of the required n - 1 = 5. The function returns normally with no error — you must explicitly check len(mst) == n - 1 after the call to detect that the graph was disconnected.

Practice 3 — Partway through Prim, the tree is {A, B, C} and the heap holds (4,A,B), (5,B,D), (6,C,E). Which edge gets processed next, and is it accepted?

Answer: The heap always pops the smallest weight first, so (4,A,B) comes out next. But both A and B are already in {A, B, C}, so v=B in visited is true and it is skipped as a stale entry — the next real addition will be (5,B,D).

Final takeaway

Kruskal and Prim are not two different answers — they are two different orders of discovery for the same guarantee. Kruskal asks a global question, cheapest edge first, and leans on Union-Find to reject cycles. Prim asks a local question, cheapest edge leaving the current tree, and leans on a heap to find it fast. Both are correct because of the same cut property, and on this page's graph both land on total weight 11 — just by picking edges in a different order.
