Graph Traversal — BFS & DFS on Graphs

Trees never loop back on themselves. Graphs do — and that one fact changes everything: every traversal here needs a visited set, marked the instant a vertex is discovered, or the walk never terminates. This page traces the exact same six-vertex graph through both BFS (a queue, finds the fewest-hop path) and DFS (a stack, finds structure), step by step, so you can see exactly what the visited set is protecting you from.

Canonical example

edges = [(A,B),(A,D),(B,C),(B,E),(C,F),(D,E),(E,F)]

BFS(A) order = A, B, D, C, E, F · dist(A→F) = 3 hops

Why this matters

Social graphs

"How many people separate you from a stranger" (degrees of separation) is literally BFS's distance map — the number of hops, nothing else.

Network routing

Roads and routers are graphs full of cycles on purpose — redundant paths mean resilience. BFS finds the fewest-hop route; DFS finds some reachable route fast.

Dependency graphs & crawlers

Package managers and web crawlers walk graphs that loop back on themselves constantly. Skip the visited set here and the program hangs, not just runs slow.

Instructor note: unlike a tree, a graph can hand you the same vertex twice through two different edges. Every idea in this lesson — BFS's queue, DFS's stack, the visited set — exists to make sure that vertex still only gets processed once.

What is graph traversal?

Simple definition

Graph traversal means visiting every vertex reachable from a start vertex by following edges, while guaranteeing each vertex is processed exactly once — even when edges loop back on themselves.

What you are computing

BFS computes a visit order plus the fewest-edges distance from the source to every vertex. DFS computes a visit order plus structure — reachability, connected components, or where a cycle closes.

Beginner shortcut: if the question says "shortest," "fewest," "minimum hops," or "nearest," reach for BFS. If it just says "reachable," "connected," or "does a path exist," either works — DFS's stack or recursion is usually less code to write.

Step-by-step thinking process

1

Build the adjacency list

Turn the edge list into a {vertex: [neighbors]} map. For an undirected graph, every edge is written in both directions.

2

Pick a start, seed the state

Choose a starting vertex, mark it visited, and place it in the container — a queue for BFS, a stack for DFS.

3

Choose the container that fits

"Shortest / fewest hops" needs a queue (BFS). "Does a path exist / explore everything" fits a stack or recursion (DFS).

4

Mark visited at discovery

Mark a vertex the instant it is first seen, not when it is finally processed — this is what keeps a shared vertex off the queue twice.

How the input becomes an adjacency list

Before either BFS or DFS can run, the raw edge list has to become a lookup table of neighbors. Neighbor lists are sorted afterward so the traversal order below is deterministic and reproducible.

Input edges

edges = [ ("A","B"), ("A","D"), ("B","C"), ("B","E"), ("C","F"), ("D","E"), ("E","F"), ]
→

Adjacency list

A: [B, D] B: [A, C, E] C: [B, F] D: [A, E] E: [B, D, F] F: [C, E]

Read edge (A,B), then (A,D)

Add B and D to A's list, and add A back onto B's and D's lists — every undirected edge is written twice.

Read (B,C), (B,E), (C,F), (D,E), (E,F)

Same rule, five more times. By the time all seven edges are read, vertex E already has three neighbors: B, D, and F.

Sort every neighbor list

Purely for reproducibility — it guarantees the exact same visit order every time this page (or the notebook) runs the traversal below.

Critical point: this is not a tree — vertex E can be reached from A two different ways (through B, or through D), and following edges from E long enough leads right back to A. That loop is exactly why the visited set below has to exist.

Method 1: BFS — fewest-hop distance from a source

BFS explores the graph ring by ring using a queue. Every vertex is marked seen the moment it is enqueued, not when it is dequeued — that single ordering choice is what stops the shared vertex E from being queued twice by both of its cycles.

def bfs(adj, start): seen = {start} # mark on ENQUEUE so nothing is queued twice dist = {start: 0} q = deque([start]) order = [] while q: u = q.popleft() # oldest waiting vertex (FIFO -> wide) order.append(u) for v in adj[u]: if v not in seen: seen.add(v) dist[v] = dist[u] + 1 # one edge further than u q.append(v) return order, dist

Key mental model

The first time BFS reaches any vertex, it is guaranteed to be via the fewest edges — the queue's FIFO order does that work for free, without ever comparing candidate paths.

Common BFS mistake

Marking a vertex seen when it is dequeued instead of when it is enqueued. On a cyclic graph, that lets the same vertex sit in the queue more than once before it is ever processed.

Why the queue matters

The queue lives on the heap, not the call stack, so it is unaffected by very long or skewed graphs — see the disconnected and cycle edge cases below for what the visited set is actually preventing.

Method 2: DFS — explicit stack, marks visited on pop

DFS follows one branch as deep as it can before backtracking, using an explicit stack instead of the queue. This version marks a vertex seen when it is popped, not when it is pushed — so a duplicate can sit on the stack for a while, and the if u in seen: continue guard is what makes that safe.

def dfs_iterative(adj, start): seen, order, stack = set(), [], [start] while stack: u = stack.pop() # LIFO -> depth-first if u in seen: continue seen.add(u) order.append(u) for v in reversed(adj[u]): # reversed so the smallest neighbour pops first if v not in seen: stack.append(v) return order

Key mental model

A stack dives one branch as deep as it goes before backing up — same six vertices as BFS, completely different order, because LIFO explores depth instead of breadth.

Common DFS mistake

Expecting if v not in seen: push to fully prevent duplicates. It does not — seen is not updated until pop time, so the pop-time if u in seen: continue guard is what actually keeps this correct (see steps 4, 7, and 8).

Why the guard matters

Drop the if u in seen: continue line and this same graph — which has a real cycle — starts re-processing vertices forever instead of just wasting a little stack space on a duplicate.

Method 3: Connected components — count the islands

BFS and DFS above both assumed the graph was one connected piece — start at A and every other vertex is reachable. Real graphs are often not: they arrive as several separate pieces, and some pieces are a single vertex with no edges at all. Counting connected components answers "how many separate pieces does this graph have?" by wrapping the same DFS-with-an-explicit-stack from Method 2 in a for loop over every vertex, sorted for a deterministic order. Whenever that loop lands on a vertex that is still unvisited, that vertex cannot belong to any component already flooded — so the count goes up by one and a fresh flood-fill starts right there.

Canonical graph for this trace: adj = {"G":["H"], "H":["G","I"], "I":["H"], "J":["K"], "K":["J","L"], "L":["K"], "M":[]}, with vertices = sorted(adj) = [G, H, I, J, K, L, M]. It has three components on purpose: {G, H, I}, a separate {J, K, L}, and {M} — a single vertex with zero edges, included specifically because it proves the outer loop cannot be driven by the edge list.

def connected_components(adj, vertices): """Each fresh start that finds new ground is one more component.""" seen, count = set(), 0 for start in vertices: # try EVERY vertex, not just the ones with edges if start not in seen: count += 1 # a fresh, never-before-seen island stack = [start] while stack: # flood everything reachable from start u = stack.pop() if u in seen: continue seen.add(u) stack.extend(adj[u]) return count

Key mental model

A single BFS or DFS from one start only ever finds the vertices reachable from that start — it can never discover a vertex sitting in a different, disconnected part of the graph. Wrapping the traversal in a for loop over every vertex, and only re-flooding when a vertex is still unvisited, is what turns "traverse from one place" into "count every component in the whole graph."

Common mistake

Driving the outer loop off the edge list instead of the full vertex list. Vertex M has zero edges, so it never appears in any edge tuple — if the loop only visits vertices mentioned in edges, an isolated vertex like M is silently skipped and the component count comes out one short.

Why this pattern matters

This exact shape — loop over every cell or vertex, skip the ones already visited, flood-fill the rest — is Number of Islands, Provinces, and Accounts Merge under different names. The flood-fill (BFS or DFS) never changes; only what counts as a "neighbor" does: grid adjacency, a same-city matrix, or a shared email address.

Edge cases you should test

Case A: disconnected graph

edges + [("G","H")] adds a second island untouched by the rest of the graph.

BFS(A) never reaches G or H — dist has no entry for either

dist (or seen) is an honest record of what is reachable from the start — an entry simply never appears for a vertex in a different component. To cover the whole graph, restart the traversal from every still-unvisited vertex; that repeated restart is exactly how counting connected components works.

Case B: the cycle this graph actually has

Delete the line if v not in seen: from bfs and re-run it on this exact graph.

With the check: BFS finishes in 6 pops. Without it: the queue never empties.

Every pop of B would push A right back onto the queue (B's neighbor list includes A), and every later pop of A pushes B back again — around the A-B-E-D-A cycle forever. The queue length grows without bound and the loop never terminates. This single check is the whole difference between "graph traversal" and "tree traversal" — a tree never needs it because it has no cycle to walk back into.

Case C: single node with a self-loop

edges = [("I","I")] — building the adjacency list still writes the edge in "both directions," so I: [I, I].

order = [I], dist = {I: 0} — I is visited exactly once

When BFS pops I, it scans I's neighbor list [I, I] — but I is already in seen, marked the instant it was enqueued as the start vertex, so both self-references are skipped. The visited set does the same job here it does everywhere else: process each vertex exactly once, no matter how many edges point at it.

All three rely on the same truth: once a vertex is marked visited, it is never processed again — that is what turns a graph with cycles into something that finishes in O(V + E) instead of running forever.

How to derive this in an interview

Reasoning path

"shortest / fewest edges / minimum hops / nearest" → BFS.

"can I reach X" or "explore everything reachable" → either BFS or DFS; DFS's recursion is usually less code.

Graph could be very deep or skewed, worried about recursion → prefer BFS, or an explicit-stack DFS.

Does this graph have cycles? Unless told it is a tree or a DAG, assume yes — a visited set is mandatory, marked at discovery time.

For BFS specifically: mark on enqueue, not on pop — otherwise the same vertex can flood the queue before it is ever processed.

What to say out loud

  • "I need the vertex with the fewest edges from the source, so I will use BFS — the first time it reaches any vertex is guaranteed to be via the shortest unweighted path."
  • "This graph is not a tree, so it can have cycles — I need a visited set, and for BFS I have to mark a vertex visited the moment I enqueue it, or the same vertex could get queued more than once."
  • "I do not need the shortest path, just reachability, so I will use DFS — recursion keeps it short, or an explicit stack if the graph could be very deep."
  • "If the input is a plain edge list, I build the adjacency list first, writing each undirected edge in both directions before I traverse anything."

Common beginner coding mistakes

BFS mistakes

  • Marking a vertex visited when it is dequeued instead of when it is enqueued — on a cyclic graph this lets the same vertex get pushed onto the queue more than once before it is ever processed.
  • Forgetting to build the adjacency list in both directions for an undirected graph, silently making some edges one-way.
  • Using dist[v] = dist[u] + 1 correctly but not initializing the source's own distance to 0 in that same dict.
  • Assuming BFS gives the shortest path on a weighted graph — it only works unweighted; use Dijkstra otherwise.

DFS mistakes

  • Recursing on a very large or very deep graph without an explicit-stack fallback, risking RecursionError.
  • In the iterative version, expecting if v not in seen: push to fully prevent duplicates on the stack — it does not, since seen is not updated until pop time.
  • Forgetting the pop-time if u in seen: continue guard entirely when hand-rolling an iterative DFS, which turns a real cycle into an infinite loop.
  • Confusing "no shortest-path guarantee" with "wrong answer" — DFS still finds every reachable vertex correctly, it just does not guarantee the fewest-edges path to get there.

Practice questions

Try these first in your head against the same six-vertex graph. Then open the answer only after you commit to a guess.

Practice 1 — Run BFS starting from D instead of A. What is dist[C], and what does the visit order look like?

Answer: dist[C] = 3. D's neighbors A and E go to distance 1; from there B and F reach distance 2; C is discovered from B at distance 3 (there is also a same-length path D-E-F-C). Full order: [D, A, E, B, F, C].

Practice 2 — Why does removing if v not in seen: from bfs turn this specific graph into an infinite loop, even though it only has six vertices?

Answer: because of the cycle A-B-E-D-A (and B-C-F-E-B), a vertex like B keeps re-discovering A, and A keeps re-discovering B, every time either is popped. The queue keeps growing forever instead of shrinking to empty — a finite graph does not guarantee a finite run without the visited check, because a cycle gives the walk somewhere to go back to. A tree never has this problem, because it has no cycle to walk back into.

Practice 3 — Swap the queue in bfs for a stack (use stack.pop() instead of q.popleft()) but keep marking visited on push. Do you still get a shortest-path guarantee? What do you get instead?

Answer: no shortest-path guarantee. Marking on push still keeps the traversal correct and terminating — no vertex gets processed twice — but LIFO order dives deep before spreading wide, so the first time you reach a vertex is no longer necessarily via the fewest edges. You get a valid DFS-shaped traversal, not a distance map. This is exactly why BFS specifically needs a FIFO queue, not just "any container plus a visited set."

Final takeaway

Every graph traversal answers the same underlying question: starting from some vertex, what can you reach, and — for BFS — how many edges does it take? The queue-versus-stack choice decides whether "first reached" means "fewest edges" or just "some path." But in both cases the real engine is the visited set: mark a vertex the instant it is discovered, and a graph riddled with cycles becomes exactly as safe to walk as a tree.
