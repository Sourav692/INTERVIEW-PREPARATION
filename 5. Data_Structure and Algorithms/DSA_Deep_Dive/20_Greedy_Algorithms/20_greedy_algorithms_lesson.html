Greedy Algorithms: Interval Scheduling & Partitioning

A greedy algorithm commits to the locally best choice at every step and never reconsiders. This page teaches two greedy algorithms that actually work — and, just as importantly, the exchange-argument reasoning that tells you when a greedy rule is safe and when it silently fails.

Core idea: sort by the right key, then scan once Interactive interval-scheduling trace Interactive interval-partitioning trace Includes a real greedy failure case

Canonical example

meetings = [(1,3),(2,4),(3,5),(0,6),(5,7),(8,9)]

Answer = 4 non-overlapping meetings

Why this matters

Meeting room booking

Given a pile of requested time slots, pick the maximum number that can happen in one room without overlapping.

CPU / job scheduling

The same accept-or-reject scan decides which jobs a single machine can run back to back.

Court, room, and machine allocation

When you can't reject anything and must serve every request, the question flips to: how many rooms/machines/courts do I need at minimum?

Instructor note: both problems on this page share the same skeleton — sort the input by one key, then make a single pass. That skeleton is not an accident; it is the entire content of the algorithm. The hard part is never the loop, it's proving which key is correct.

What is a greedy algorithm?

Simple definition

At every step, take the choice that looks best right now, and never go back to reconsider it. No backtracking, no trying alternatives — one pass, one decision at a time.

Fast, but only sometimes correct

That single-pass discipline is what makes greedy fast — usually O(n log n) from the sort, then one linear scan. It is also exactly why greedy can be wrong: a locally good choice can box you into a globally bad outcome, and nothing in the algorithm itself checks for that.

Beginner shortcut: if you can finish the sentence "swapping in the greedy choice never makes an optimal solution worse," greedy is safe. If you can't finish that sentence — or you can think of a case where it's false — greedy is guessing, not proving.

Step-by-step thinking process

1

Name the choice

At each step of the scan, what decision is actually being made? For scheduling it's accept/reject; for partitioning it's reuse/open-new.

2

Choose the sort key

This is the algorithm. Sort by end time for scheduling, by start time for partitioning — pick wrong and the rest of the code runs perfectly and still gives the wrong answer.

3

Apply the greedy test

One comparison per item, decided immediately and never revisited: does this pass the test right now, given what's already been chosen?

4

Prove it — or find a counterexample

Write the one-sentence exchange argument. If you can't, try to break your own rule with a small adversarial input before you trust it.

How the input becomes the working structure

This is where the algorithm is actually decided. Before any scanning happens, the raw list is sorted by one key — and that choice of key is not a minor implementation detail, it is the whole strategy.

Raw input

meetings = [ (1, 3), (2, 4), (3, 5), (0, 6), (5, 7), (8, 9) ]
→ sort by end time →

Working order (scan left to right)

(1, 3) end = 3 (2, 4) end = 4 (3, 5) end = 5 (0, 6) end = 6 (5, 7) end = 7 (8, 9) end = 9

Why end time, not start time

Finishing earliest leaves the most room for everything scheduled after it. An interval that starts early but runs long (like (0,6)) can block far more future picks than one that starts late but ends soon.

Proof by contrast: sorting by start time instead

Running the exact same accept/reject loop but sorted by start time on these six meetings gives only 2 accepted meetings, not 4 — sorting by start time picks (0,6) first because it starts earliest, which then blocks everything from 1 to 6. Same loop, wrong key, worse answer.

The scan itself is trivial

Once sorted by end time, the loop is a single pass with one comparison: does this interval start after the last one we kept ends? That's it — no backtracking, no lookahead. All of the intelligence lives in the sort key.

Critical point: almost every correct greedy algorithm starts with "sort by ___." Choosing that key correctly is the algorithm — everything after it is bookkeeping.

Method 1: Interval scheduling — max_non_overlapping

Sort by end time. Walk the sorted list once. Keep an interval whenever its start is at or after the end of the last interval you kept — that's the entire algorithm.

Key mental model

last_end is the only memory the algorithm needs. Every decision is just "does this start late enough to clear that one number?"

Common mistake

Sorting by start time instead of end time. It looks equally reasonable but on this exact input it gives 2 instead of 4 — a 50% worse answer from one wrong sort key.

Why the >= matters

(3,5) is accepted right after (1,3) even though they touch at 3. Touching is not overlapping — using > instead of >= would wrongly reject back-to-back meetings.

Method 2: Interval partitioning — min_resources

A different question: instead of rejecting anything, every interval must be scheduled somewhere. Sort by start time, and reuse whichever resource frees up earliest if it's already free — otherwise open a new one. A min-heap gives O(log n) access to "which resource frees up soonest."

import heapq def min_resources(intervals): intervals = sorted(intervals, key=lambda iv: iv[0]) # sort by START time heap = [] # end times of resources in use for start, end in intervals: if heap and heap[0] <= start: # earliest-freeing resource is free by now heapq.heappop(heap) heapq.heappush(heap, end) return len(heap) # resources still "in use" at the end = the peak count

Key mental model

The heap answers exactly one question fast: "which resource frees up soonest?" That is the only information the greedy rule needs to decide reuse vs. open-new.

Common mistake

Popping the heap unconditionally instead of checking heap[0] <= start first. That silently reuses a resource that is not actually free yet.

Why the answer equals peak overlap

The heap only grows past its current size when no resource is free — which happens exactly when intervals genuinely overlap. So the peak heap size is the maximum simultaneous overlap. On this input both equal 2.

Edge cases you should test

Case A: greedy fails — coin change with denominations {1, 3, 4}, target 6

The naive greedy rule — repeatedly take the largest coin that still fits — works for US coins {25,10,5,1}, but it is not universally safe. There is no exchange argument for it: swapping a large coin into an optimal solution can make things worse.

Greedy takes 4 + 1 + 1 = 3 coins True optimum: 3 + 3 = 2 coins

Traced run: greedy_coin_change([1,3,4], 6) → takes 4 first (largest that fits), leaving 2, then two 1s. That's a valid answer (sums to 6) but not the minimum-count one. Compare to US coins: greedy_coin_change([25,10,5,1], 30) → 25 + 5, which happens to be optimal — the same rule, correct on one input and wrong on another, which is exactly why "it worked on my example" is not a proof.

Case B: ties in the sort key

intervals = [(1,4), (2,4), (4,6)] — the first two both end at 4.

Answer = 2, regardless of tie order

Traced run: processing [(1,4),(2,4),(4,6)] gives count 2, and processing the tied pair reversed as [(2,4),(1,4),(4,6)] also gives count 2. Whichever of the two tied-end intervals is scanned first gets accepted; the other is rejected because its start is always less than the shared end. Only one interval from a tied-end group can ever be kept, so tie-breaking order does not change the final count — you don't need a tie-breaking rule for this problem.

Case C: empty or single-element input

intervals = [] and intervals = [(2,5)], run through both methods.

max_non_overlapping: 0, then 1 — min_resources: 0, then 1

Traced run: max_non_overlapping([]) = 0, max_non_overlapping([(2,5)]) = 1, min_resources([]) = 0, min_resources([(2,5)]) = 1. Both functions handle these without a special case in the code — float("-inf") as the starting last_end and an empty heap already do the right thing on an empty or singleton list. If your implementation needs an if not intervals: return 0 guard, that's a sign your initial values are wrong, not that the guard is necessary.

Method comparison

Method Time Space When it's correct
Greedy — interval scheduling (sort by end)O(n log n)O(1) extraProvably optimal — the exchange argument holds: swapping in the earliest-finishing interval never leaves less room.
Greedy — interval partitioning (sort by start + heap)O(n log n)O(n) for the heapProvably optimal — the answer is bounded below by peak overlap, and the heap reuse rule always hits that bound.
Greedy — coin change (largest coin first)O(n log n)O(1) extraNot always correct. No exchange argument exists for arbitrary denominations — see the counterexample above.
DP — coin change (bottom-up over amounts)O(target × coins)O(target)Always correct, for any denominations — the "always right, slower" fallback greedy can't safely replace.

The lesson underneath the table: when a greedy exchange argument holds, it matches or beats DP on speed with far less code. When it doesn't hold, DP is the safety net — slower, but correct on every input, not just the ones you happened to test.

How to derive this in an interview

Reasoning path

What am I actually optimizing? Maximum count of non-overlapping intervals.

My first instinct is to sort — the question is by which key. Start time feels natural; let me not commit yet.

Let me test my greedy rule against a small adversarial case before I commit — a long interval that starts early but blocks everything.

Sorting by start lets that long interval get picked first and it wrecks the count. Sorting by end time avoids that: whichever interval frees up soonest leaves the most room for the rest.

Can I state the exchange argument in one sentence? "Any optimal solution's first choice can be swapped for the earliest-finishing interval without losing room." Yes — so greedy is safe here.

Land on: sort by end time, single pass, O(n log n).

What to say out loud

  • "This smells like a greedy problem — I need to pick the right sort key, not just any sort key."
  • "Let me test my greedy rule against a small adversarial case before I commit — for example, one long interval that starts first."
  • "I can justify sorting by end time with an exchange argument: it never leaves less room than any other optimal first choice."
  • "If I can't construct that sentence confidently — like with coin change on arbitrary denominations — I say so out loud and fall back to DP instead of hoping greedy works."

Common beginner mistakes

Interval scheduling mistakes

  • Sorting by start time instead of end time — looks equally natural, is provably worse.
  • Using > instead of >= in the overlap test, which wrongly rejects meetings that only touch.
  • Initializing last_end to 0 instead of float("-inf"), which breaks on negative-start intervals.
  • Confusing "maximum count of intervals" with "minimum number of intervals to remove" — same problem, easy to answer the wrong question.

General greedy mistakes

  • Sorting by end time for interval partitioning — that's the other problem's key; partitioning needs start time.
  • Popping the heap before checking heap[0] <= start, which reuses a resource that isn't actually free yet.
  • Assuming a locally-sensible rule (like "take the biggest coin") is automatically correct without writing the exchange argument first.
  • Applying the sort-and-scan template to a problem where no exchange argument exists, then debugging the code instead of questioning the approach.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — max_non_overlapping([(0,2), (2,4), (1,3)])

Answer: 2. Sorted by end time: (0,2), (1,3), (2,4). Accept (0,2) (last_end=2), reject (1,3) since 1 < 2, accept (2,4) since 2 >= 2. Two meetings fit.

Practice 2 — what happens if you sort by duration (end - start) instead of end time, on the canonical meetings list?

Answer: it collapses to 1 accepted meeting, down from 4. Sorting by duration picks the shortest interval, (8,9), first — but that tells you nothing about how much room it leaves for the rest of the timeline, since it happens to sit at the very end and blocks nothing before it in duration-order but everything after it is now compared against last_end = 9, rejecting all five remaining meetings. Shortest-first sounds greedy-friendly but has no exchange argument behind it — this traced run is the proof.

Practice 3 — min_resources([(1,4), (2,5), (3,6)])

Answer: 3. All three intervals pairwise overlap (each starts before the previous one ends), so no resource ever frees up in time to be reused — three separate resources are opened, and the peak overlap really is 3.

Final takeaway

Greedy is not "the obvious idea that happens to work" — it's a claim that needs a proof. When you can state the exchange argument in one sentence, as with sorting intervals by end time or by start time plus a heap, greedy is fast and correct. When you can't — as with coin change on arbitrary denominations — greedy will still run, still return an answer, and still be wrong. The sort key is the algorithm; the exchange argument is what tells you whether to trust it.
