Binary Trees

A binary tree is a tree where every node has at most two children, always labeled left and right. That one restriction unlocks two completely different ways to store the same shape: a flexible linked structure of TreeNode objects, and — when the tree is complete — a pointer-free array-packed layout where child positions are pure index arithmetic. This page traces both, step by step, against the real functions from the notebook.

Canonical example

root = TreeNode(1, TreeNode(2, TreeNode(4), TreeNode(5)), TreeNode(3, None, TreeNode(6)))

size = 6 · height = 2 · diameter = 4

Why this matters

Expression & parse trees

Compilers and calculators build binary trees where every internal node is an operator with exactly two operands — a full tree by construction.

Heaps & priority queues

A binary heap is the array-packed representation: left=2i+1, right=2i+2, no pointers, cache-friendly.

Interview reuse

Once you own height()'s "solve left, solve right, combine" shape, Diameter, Balanced Tree, and Max Path Sum become small edits, not new algorithms.

Instructor note: the single most reusable idea in this notebook is "return one value up, track a different answer in a side variable." height() only returns a height — but diameter() reuses that exact recursion while quietly recording left_h + right_h at every node in a nonlocal variable, because the longest path doesn't have to pass through the root.

What is a binary tree?

Simple definition

A tree where every node has at most two children, and those children are distinct and ordered: a left child is never interchangeable with a right child.

What you are computing

Method 1 computes height — the longest path down from a node, in edges — by combining the heights of both children. Method 2 reconstructs pointer links from array positions using nothing but arithmetic.

Beginner shortcut: an empty subtree (None) reports height -1, so a leaf naturally computes to 1 + max(-1, -1) = 0. If you instead let empty report 0, every leaf would wrongly come out to 1.

Step-by-step thinking process

1

Identify the base case

An empty subtree (node is None) is the recursion's floor — decide what it should report before writing anything else.

2

Solve the left subtree

Recurse into node.left and trust the recursion to give you a correct answer for that half.

3

Solve the right subtree

Recurse into node.right the same way — same function, same trust.

4

Combine, and return

1 + max(left, right) combines both halves into this node's answer. Some problems also stash a second answer in a side variable here.

How the input becomes a linked tree

Before any recursion can run, nested TreeNode(...) constructor calls have to wire up .left and .right pointers. This is the structure every Method 1 step below walks.

Constructor calls

TreeNode(1, TreeNode(2, TreeNode(4), TreeNode(5)), TreeNode(3, None, TreeNode(6)))
→

Linked pointers

1.left = 2 1.right = 3 2.left = 4 2.right = 5 3.left = None 3.right = 6

Build the leaves first

TreeNode(4), TreeNode(5), and TreeNode(6) are evaluated first because Python evaluates constructor arguments before the outer call — each starts with left=None, right=None.

Attach them to node 2 and node 3

TreeNode(2, TreeNode(4), TreeNode(5)) wires 4 and 5 as 2's children. TreeNode(3, None, TreeNode(6)) wires 3's left explicitly to None and right to 6.

Attach 2 and 3 to the root

TreeNode(1, ..., ...) finally wires 1.left = 2 and 1.right = 3, completing the tree.

Critical point: None is a real, explicit value here — 3's left child is None on purpose, not "unset." Every recursive helper (size, height, invert) must treat None as its base case, not skip it.

Method 1: linked-tree recursion — height()

Height is the longest path down from a node, counted in edges. The recursion is the classic binary-tree shape: solve left, solve right, combine. An empty subtree reports -1 so that a leaf — whose left and right are both empty — computes 1 + max(-1, -1) = 0, exactly right for "zero edges below a leaf."

def height(node): if not node: return -1 left_h = height(node.left) right_h = height(node.right) return 1 + max(left_h, right_h)

Key mental model

This is a post-order walk in disguise: a node's EXIT step — where it combines and returns — only happens after both children's EXIT steps have already happened.

Common height() mistake

Returning 0 instead of -1 for an empty subtree. That single off-by-one makes every leaf report height 1 instead of 0, and cascades upward.

Why the call stack matters

Stack depth equals the recursion depth, which equals the tree's height. On a skewed tree (see edge cases below) that depth is n, not log n — the recursion itself becomes the bottleneck.

Method 2: array-packed complete tree — from_array()

For a complete tree stored level-order in an array, child positions are pure arithmetic — no pointers required to know the shape. from_array still builds real TreeNode pointer links (so the rest of the codebase can use it normally), but it derives every link from left = 2i+1, right = 2i+2 instead of following any existing pointer.

def from_array(arr): if not arr: return None nodes = [TreeNode(v) if v is not None else None for v in arr] for i, node in enumerate(nodes): if node is None: continue li, ri = 2*i + 1, 2*i + 2 if li < len(arr): node.left = nodes[li] if ri < len(arr): node.right = nodes[ri] return nodes[0]

Key mental model

Once you know an index i, its children's indices are 2i+1 and 2i+2 — that arithmetic is the entire "traversal." No queue, no stack, no recursion needed to know the shape.

Common array-packing mistake

Omitting explicit None placeholders for missing children. Without them, later indices silently shift and the arithmetic attaches the wrong node as a child — see edge case C below.

Why the bounds check matters

li < len(arr) is what naturally stops assigning children once you're at the last level — the same way BFS's queue emptying naturally ends a traversal, here a simple index comparison ends the construction.

Method 3: recursive mirror — invert()

Inverting a tree means swapping every node's left and right child, all the way down. The "work" at each node is a single swap — the interesting part is when that swap happens. node.left, node.right = invert(node.right), invert(node.left) only assigns once both recursive calls on the right-hand side have returned, so a node's own swap always lands after its whole subtree has already been recursed into. That makes this a post-order-ish walk, even though it is written as one line. One quirk worth noticing: Python evaluates a tuple's right-hand side left to right, so invert(node.right) actually runs before invert(node.left) — recursion visits the right subtree first at every node.

def invert(node): if not node: return None node.left, node.right = invert(node.right), invert(node.left) return node

Key mental model

The recursion visits right before left at every node (that is just how Python evaluates the tuple), but a node's own swap still only lands after both of its children have already been fully recursed into and returned — it is still fundamentally a "children first, then this node's work" walk.

Common invert() mistake

Writing the swap as two separate lines — node.left = node.right then node.right = node.left — destroys the original left value before the second line can read it. A tuple assignment (or a temp variable) evaluates the whole right-hand side first, which is why this code is safe.

Why the invisible swaps matter

Steps 4, 8, and 10 swap two None children and produce no visible change — but the recursive call still genuinely ran. Skipping the call on a None child instead of hitting the base case is a common way to silently miss inverting a subtree that starts one level deeper.

Method 4: longest path — diameter() (reuses Method 1's recursion)

The diameter is the longest path between any two nodes — and that path does not have to pass through the root. Because of that, diameter cannot simply be the value a recursive call returns: whatever gets returned up has to be usable by a parent call to keep combining, so it must stay a height-like number. The fix is the same trick called out in the instructor note above — return one value, track another. The nested depth() function here is the exact same "solve left, solve right, combine" recursion as height() in Method 1, walking this tree in the identical order and taking the identical 12 steps. The only differences: its base case reports 0 instead of -1, and one extra line updates a side variable best — declared in diameter() and reached into with nonlocal — every time a node's left + right beats the running best.

def diameter(root): best = 0 def depth(node): nonlocal best if not node: return 0 L = depth(node.left) R = depth(node.right) best = max(best, L + R) return 1 + max(L, R) depth(root) return best

Key mental model

depth() reuses the exact same "solve left, solve right, combine" shape as height() from Method 1 — same recursion, same traversal order, same 12 steps over this tree. The only two differences: the base case returns 0 instead of -1 (so a leaf reports 1, not 0), and one extra line updates best before returning.

Common diameter() mistake

Making diameter() return whatever depth(root) returns forces the longest path to pass through the root. Here the true longest path (4-2-1-3-6) happens to touch the root anyway, but step 7 already found best = 2 entirely inside node 2's own subtree — a different tree could hide its longest path there and never reach the root at all.

Why the side variable matters

best lives in the enclosing diameter() and is reached into with nonlocal so all six recursive depth() calls update the same variable — not six separate local copies that would each disappear the moment their own call returned.

Edge cases you should test

Case A: single node

root = TreeNode(1)

size = 1 · height = 0

Both children are None, so height hits its base case twice and returns 1 + max(-1, -1) = 0 — a lone node has zero edges below it.

Case B: skewed chain (all left children)

root = TreeNode(1, TreeNode(2, TreeNode(3, TreeNode(4))))

size = 4 · height = 3 (= n − 1)

A skewed tree is a linked list in disguise, so height hits the worst case n − 1. The recursion also goes n frames deep — on a tree with thousands of nodes, this is exactly the shape that risks Python's recursion limit, which is why the README calls balance "the whole game": most tree operations cost O(h), and only a balanced tree keeps h = O(log n).

Case C: missing-child gap in array packing

from_array([1, None, 2]) → root.left = None, root.right.val = 2 (correct)

from_array([1, 2]) (the None omitted) → root.left.val = 2, root.right = None — wrong tree

Explicit None placeholders are not optional

Omitting the placeholder shifts every later index left by one, so index arithmetic silently attaches node 2 as the left child instead of the right child. Array packing only works if the array faithfully reflects every gap in the level-order layout.

Both rely on the same underlying node count n. Which one you reach for depends entirely on whether the tree is guaranteed complete — a heap is, an arbitrary binary tree is not.

How to derive this in an interview

Reasoning path

The problem asks about a node's relationship to its subtrees (height, size, balance) → this is recursive.

A node's answer depends on both children's answers → write "solve left, solve right, combine."

Decide what an empty subtree should report first — get the base case right before anything else.

If the real answer (like diameter) doesn't equal what gets returned up, return the report value and track the real answer in a side variable.

If the tree is explicitly stated to be complete (a heap, a level-order array), skip pointers entirely — use 2i+1 / 2i+2 arithmetic instead.

What to say out loud

  • "This node's answer depends on both children, so I'll recurse left, recurse right, then combine."
  • "I need height in edges, so an empty subtree returns -1 — that makes a leaf correctly compute to 0."
  • "The longest path might not pass through the root, so I can't just return it — I'll track it in a side variable while still returning height up."
  • "Since this is guaranteed complete, I don't need pointers at all — index i's children live at 2i+1 and 2i+2."

Common beginner coding mistakes

Linked-tree recursion mistakes

  • Returning 0 instead of -1 for an empty subtree in height, which makes every leaf report 1 instead of 0.
  • Forgetting the base case entirely and hitting AttributeError on None.left.
  • Computing an aggregate like diameter as the function's return value instead of a side variable, so it silently only considers paths through the root.
  • Assuming recursion is free — a deep skewed tree can exceed the call-stack limit.

Array-packing mistakes

  • Omitting explicit None entries for missing children, which shifts every later index and attaches the wrong node.
  • Using array packing on a tree that is not complete — the array ends up mostly empty slots, wasting memory.
  • Forgetting the bounds check (li < len(arr)) and indexing past the end of the array.
  • Mixing up the parent formula — it is (i-1)//2, not i//2.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — For root = TreeNode(1, TreeNode(2), TreeNode(3)), what do size(root) and height(root) return?

Answer: size = 3 (three real nodes), height = 1. Both children are leaves (height 0), so height(root) = 1 + max(0, 0) = 1.

Practice 2 — Why must height(None) be -1 rather than 0?

Answer: height counts edges, not nodes. A leaf has zero edges below it, so it must compute to 0. Since a leaf's recursion is 1 + max(height(left), height(right)) with both children None, the only way to land on 0 is if height(None) = -1, because 1 + max(-1, -1) = 0.

Practice 3 — For a complete tree stored as an array with n = 10 elements, what are the left child, right child, and parent of index 4?

Answer: left = 2*4+1 = 9 (valid, since 9 < 10), right = 2*4+2 = 10 (invalid, since 10 ≥ 10 — index 4 has no right child), parent = (4-1)//2 = 1.

Final takeaway

A binary tree is one shape, but two completely different ways to hold it in memory. Linked TreeNode recursion handles any shape at all, at the cost of one call-stack frame per level of depth. Array packing with 2i+1 / 2i+2 replaces every pointer with arithmetic, but only stays honest when the tree is genuinely complete. Once you can write height() from memory and reason about the index formulas, most binary-tree problems become a diff against one of these two baselines, not a new algorithm.
