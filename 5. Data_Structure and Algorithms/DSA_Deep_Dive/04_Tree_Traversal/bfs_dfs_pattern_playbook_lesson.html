BFS & DFS Pattern Playbook — Trees

Almost every tree problem is a small, predictable edit to one of a handful of baseline functions. This page teaches you those baselines directly: one BFS walk (queue, level by level) and one DFS walk (recursion, choose/recurse/un-choose), traced step by step so you can see exactly what changes in memory as the code runs — and how to tell, from the wording of a problem, which one to reach for.

Why this matters

File systems

Listing a directory tree level by level (BFS) vs. printing every full file path (DFS) are the same two shapes.

Org charts

"Who is the nearest manager with role X" is a BFS minimum-depth question; "list every reporting chain" is a DFS path question.

Interview reuse

Once you own min_depth and binary_tree_paths, roughly a dozen LeetCode problems become small edits, not new algorithms.

Instructor note: the goal is not to memorize a generic "tree traversal engine." It is to own two concrete, complete functions well enough that you can diff a new problem against them in your head.

What are BFS and DFS on a tree?

BFS — breadth-first search

Explores the tree ring by ring using a queue: everything at depth 1, then everything at depth 2, and so on. The first time BFS reaches a target, that is guaranteed to be the closest way to reach it.

DFS — depth-first search

Plunges down one branch as far as possible using recursion (or an explicit stack) before backing up. It naturally combines a node's answer from its children's answers, or builds up a root-to-leaf path as it goes.

Beginner shortcut: if the question mentions "shortest," "minimum," or "nearest," reach for BFS. If it mentions "every path," "sum along a path," or "compute something from this node's children," reach for DFS.

Step-by-step thinking process

1

Read the shape of the answer

Does the problem want a shortest distance, a level-by-level view, an aggregated value, or a full path?

2

Match it to a baseline

"Nearest/shortest" → BFS. "Combine children" → DFS-compute. "Enumerate paths" → DFS-backtrack.

3

Write the baseline in full

Don't reach for a generic template. Write the complete, concrete function for the simplest version of the problem.

4

Edit, don't redesign

Most variants are a one- or two-line diff: a sentinel value, an extra piece of state, a different base case.

How the input becomes a tree

LeetCode hands you a level-order list. Before either BFS or DFS can run, that list has to become linked TreeNode objects.

Input list

[3, 9, 20, null, null, 15, 7]
→

Linked tree

3.left = 9 3.right = 20 20.left = 15 20.right = 7

Read 3

Becomes the root node and is pushed onto a build queue.

Read 9, then 20

Attached as 3.left and 3.right, then each is pushed onto the build queue in turn.

Read 15, then 7

Attached as 20.left and 20.right. Node 9 has no more values waiting for it, so it stays a leaf.

Critical point: this build step is itself a BFS (it uses a queue to attach children left-to-right, level by level) — you are looking at BFS before you even reach the "real" algorithm.

Method 1: BFS baseline — Minimum Depth (LC 111)

BFS explores ring by ring, so the first leaf it dequeues is guaranteed to be the nearest one. No need to check every path and keep a running minimum the way DFS would have to — the queue order does that work for free.

def min_depth(root): if not root: return 0 q = deque([(root, 1)]) while q: node, depth = q.popleft() if not node.left and not node.right: return depth if node.left: q.append((node.left, depth + 1)) if node.right: q.append((node.right, depth + 1))

Key mental model

The very first leaf dequeued is the nearest one — BFS never has to compare candidates because the queue order already guarantees this.

Common BFS mistake

Checking if not node instead of if not node.left and not node.right. A node with exactly one child is not a leaf.

Why the queue matters

The queue lives on the heap, not the call stack, so it never risks a RecursionError on a very tall tree — see the skewed-tree edge case below.

Method 2: DFS baseline — Binary Tree Paths (LC 257)

Choose a child, recurse into it with that child appended to the running path, then un-choose it (pop) once that branch is fully explored. Record the finished path only when a leaf is reached.

def binary_tree_paths(root): if not root: return [] out, path = [], [str(root.val)] def backtrack(node): if not node.left and not node.right: out.append("->".join(path)) return for nxt in (node.left, node.right): if nxt: path.append(str(nxt.val)) backtrack(nxt) path.pop() backtrack(root) return out

Key mental model

path grows on the way down and shrinks on the way back up — at any moment it is exactly the branch currently being explored.

Common DFS mistake

Forgetting path.pop() after the recursive call. Without the un-choose step, a sibling branch inherits nodes from a path it was never actually on.

Why choose/recurse/un-choose matters

This is the same skeleton behind Path Sum II, Sum Root to Leaf Numbers, and Smallest String From Leaf — only the record condition and what gets pushed onto path change.

Edge cases you should test

Case A: single node

root = [1]

min_depth = 1 · paths = ["1"]

The root itself has no children, so it is immediately a leaf. Both functions must handle "no recursion needed at all" cleanly.

Case B: skewed / chain tree (height 5000, all left children)

root = left_chain(5000)

BFS survives · naive recursive DFS raises RecursionError

A recursive walk adds one call-stack frame per level, so a tall skewed tree can exceed Python's recursion limit (~1000 frames). min_depth's queue lives on the heap, not the call stack, so it is completely unaffected — this is why "deep/skewed tree" is its own row in the BFS-vs-DFS decision table, not about which answer is correct but about which one survives being asked at all.

Case C: one-sided branch

root = [1, null, 2]

min_depth = 2, not 1

Node 1 has only a right child, so it is not a leaf even though its left side is empty. The code must check not node.left and not node.right together — checking either side alone would wrongly report a minimum depth of 1.

Method comparison table

MethodTimeSpaceBest for
BFS (e.g. Minimum Depth)O(n)O(w) — widest levelShortest path, nearest node, level-by-level info
DFS — compute a value (Max Depth, Balanced, Diameter, Path Sum)O(n)O(h) — call stackCombining children's answers, or threading state downward
DFS — backtrack along paths (Binary Tree Paths, Path Sum II, Smallest String)O(n) (up to O(n·h) if paths are copied)O(h)Enumerating or building actual root-to-leaf paths
DFS — inorder on a BST (Validate BST, Kth Smallest)O(n)O(h)Anything that relies on sorted order

All four rely on the same truth: a tree has no cycles, so once you pick a walk order, every node is visited exactly once.

How to derive this in an interview

Reasoning path

"shortest / minimum depth / fewest hops" → BFS.

"level by level / nearest to root" → BFS.

A step needs a direction the tree doesn't hand you for free (e.g. parent) → still BFS/DFS, just widen the set of neighbors.

Deep/skewed tree, worried about the call stack → prefer BFS or an explicit-stack DFS.

"Combine this node's answer from its children" → DFS, compute-a-value shape.

"List every path / sum along a path" → DFS, backtracking shape.

Anything about sorted order on a BST → DFS, inorder shape.

What to say out loud

  • "I need the nearest match, so I'll use BFS — the first hit at any given depth is guaranteed to be the closest."
  • "This node's answer depends on its children's answers, so I'll write a DFS that returns a value and combines it on the way back up."
  • "I need actual paths, not just an aggregate, so I'll backtrack: append before recursing, pop after."
  • "It's a BST question about order, so I'll do an inorder DFS and track one small piece of running state."

Common beginner coding mistakes

BFS mistakes

  • Forgetting to carry depth (or level) alongside each node in the queue.
  • Checking if not node instead of if not node.left and not node.right for "is this a leaf."
  • Not pushing both children when both exist — silently dropping a whole subtree.
  • Using recursion for a BFS "just because," and reintroducing the call-stack risk BFS was chosen to avoid.

DFS backtracking mistakes

  • Forgetting path.pop() after the recursive call, so state leaks into sibling branches.
  • Recording a path before actually confirming the node is a leaf.
  • Appending path by reference instead of path[:] when a snapshot must survive future mutation.
  • Popping in the wrong place — it must happen after recursion, unconditionally, whether or not a path was recorded.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Given a target node, how would BFS find every node exactly distance k away in the tree?

Answer: this is LC 863. A TreeNode only gives you .left/.right, so first do one pass building a child → parent map. Then run BFS starting from target (not the root), and at each pop explore three neighbors instead of two: left, right, and parent.get(node). Instead of returning at the first match, collect every node whose distance equals k and keep going.

Practice 2 — Diameter of Binary Tree reuses the exact height() recursion from Max Depth. Why does it need a nonlocal variable if height already returns a value?

Answer: the longest path in the tree doesn't have to pass through the root, so it can't be the function's return value (which is always "height from this node down"). Instead, at every node the code computes left_height + right_height and keeps a running best in a nonlocal variable as a side effect, while the return value keeps behaving exactly like Max Depth.

Practice 3 — Kth Smallest in a BST reuses the same inorder walk as Validate BST. What is the one piece of state that changes?

Answer: Validate BST tracks a running prev value and requires it to strictly increase. Kth Smallest instead tracks a visit count and stops the instant count == k, recording that node's value — because inorder already visits a BST's values in ascending order, the k-th node visited is the k-th smallest value, with no sorting required.

Final takeaway

BFS and DFS are not two competing algorithms to memorize in the abstract — they are two concrete walking orders, each with one owned baseline function. BFS's queue guarantees "first found is nearest." DFS's recursion naturally combines children's answers or builds up a path as it goes. Once you can write min_depth and binary_tree_paths from memory, most tree problems become a diff against one of the two, not a new algorithm.
