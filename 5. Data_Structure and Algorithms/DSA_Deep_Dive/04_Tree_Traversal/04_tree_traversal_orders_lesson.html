Tree Traversal Orders — Preorder, Inorder, Postorder & Level-Order

This page is about the walk orders themselves, not about which one to pick for a given problem (that's the companion BFS/DFS Pattern Playbook page). Here you watch preorder, inorder and postorder fall out of the exact same three-line recursive body just by moving one statement — and then you watch the iterative inorder version make the call stack, which was invisible the whole time, into something you can actually see change.

Core idea: same walk, different visit point Interactive combined DFS trace Interactive explicit-stack trace Interactive reconstruction trace Code synced with steps

Canonical example

root = [1, 2, 3, 4, 5, 6, 7]

pre=[1,2,4,5,3,6,7] · in=[4,2,5,1,6,3,7] · post=[4,5,2,6,7,3,1] · level=[1,2,3,4,5,6,7]

Why this matters

Serialize or copy a tree

Preorder's first value is always the root, so a preorder list is a self-describing build order — read it left to right and you can reconstruct or clone the exact same tree.

Sorted output from a BST

On a binary search tree, inorder emits values already sorted. That one fact powers validate-BST, kth-smallest, and BST-to-sorted-array.

Bottom-up computation and cleanup

Postorder finishes both children before touching the parent, so it's the only safe order to free/delete nodes, and the natural order to compute height, sum, or "is this balanced" from the bottom up.

Instructor note: preorder, inorder, and postorder are not three algorithms to memorize separately. They are one algorithm with the visit statement in three different places. Level-order (BFS) is the one genuinely different shape — it answers anything about depth: shortest path to a node, level-by-level view, minimum depth.

What is a traversal order?

Simple definition

A traversal order is the rule that decides, out of the three things a recursive call can do at a node — visit it, recurse left, recurse right — which one happens first.

What actually changes between them

Every DFS order runs the same base case (if not node: return) and makes the same two recursive calls. The only difference is where the one "record this node" line sits relative to those two calls.

Preorder — N L R

Visit before either recursive call. The node is recorded the instant its frame starts.

Inorder — L N R

Visit between the two calls. The node waits until its left subtree is fully done.

Postorder — L R N

Visit after both calls. The node waits until both children are completely finished.

Level-order — BFS

Not a variant of the same body at all — no recursion, a queue instead of a stack, visiting ring by ring.

Beginner shortcut: the name already tells you the answer. "N" is spelled where it is visited relative to "L" and "R" — preN means N first, iN the middle means N between, postN means N last. You never have to memorize which is which; read the name.

Step-by-step thinking process

1

Recognize the shared skeleton

Base case, then a call on node.left, a call on node.right, and one "record" line — always these four pieces.

2

Decide where "record" goes

Need root first for rebuilding? Preorder. Need sorted order on a BST? Inorder. Need children finished first? Postorder.

3

Write it recursively first

Get correctness with the natural call-stack version before worrying about converting it to a loop.

4

Convert to iterative if needed

If the tree could be deep/skewed, or you need to watch the walk happen, swap the call stack for an explicit one.

How the input becomes the working structure

LeetCode hands you a level-order list. build_tree turns that flat list into linked TreeNode objects using a queue — itself a small BFS — before any DFS or BFS traversal can run on it.

Input list

[1, 2, 3, 4, 5, 6, 7]
→

Linked tree

1.left = 2 1.right = 3 2.left = 4 2.right = 5 3.left = 6 3.right = 7

Read 1

Becomes the root and is pushed onto a build queue.

Read 2, then 3

Attached as 1.left and 1.right, then each is pushed onto the build queue in turn.

Read 4, 5, 6, 7

Dequeue 2, attach 4 and 5 as its children. Dequeue 3, attach 6 and 7. The build queue is now empty and the tree is complete.

Critical point: the level-order input list and the level-order traversal output (BFS below) are the same shape but not automatically identical — the input list can contain null gaps for missing children; the traversal output only ever contains real nodes.

Method 1: recursive DFS — one walk, three orders

Instead of writing three separate functions, this single dfs appends to all three output lists in one pass — to preorder on arrival, to inorder between the two recursive calls, and to postorder after both return. Watch how the three lists fill at different moments even though the walk itself only happens once.

def preorder_inorder_postorder(root): preorder, inorder, postorder = [], [], [] def dfs(node): if not node: return preorder.append(node.val) # N first dfs(node.left) # L inorder.append(node.val) # N middle dfs(node.right) # R postorder.append(node.val) # N last dfs(root) return preorder, inorder, postorder

Key mental model

The call stack column is the ancestor path from the root to whatever node is active. Every recursive traversal is secretly maintaining that exact list for you — you just can't see it.

Common mistake

Assuming the append position doesn't matter. Moving postorder.append to before the two recursive calls doesn't give you "postorder a bit early" — it silently turns the function into preorder.

Why this matters for Method 2

The "call stack" column above is exactly what Method 2 makes explicit. Watch it shrink from [1,2,4] back to [1,2] at step 6 — that's a frame returning, the same event an explicit stack's pop() represents.

Method 2: iterative inorder — the stack made visible

Same result as recursive inorder, but the ancestor path that recursion tracked for free is now an explicit list you push and pop by hand: dive left (push every node on the way down), pop (its left subtree is now provably finished), record, then go right and repeat.

def inorder_iterative(root): out, stack = [], [] node = root while node or stack: while node: stack.append(node) node = node.left node = stack.pop() out.append(node.val) node = node.right return out

Key mental model

The stack always holds nodes whose left subtree is not yet provably finished. Popping one is the code's way of saying "your left side is done, your turn."

Common mistake

Writing while stack: instead of while node or stack:. Once the stack empties mid-walk (it does, at step 8 and step 12 above), that drops every remaining right subtree silently.

Why this survives a deep tree

stack is a Python list living on the heap. Recursion instead consumes one call-stack frame per level and can hit Python's ~1000-frame RecursionError limit on a very tall tree — see the skewed-tree edge case below.

Method 3: reconstruct a tree from preorder + inorder

Both walks above assume a tree already exists. This one runs the idea backwards: given only the two output lists, rebuild the exact tree that produced them. The trick is that preorder and inorder answer two different questions about the same node — preorder says which value is the root, inorder says which values are left of it and which are right of it — and combining those two answers, one recursive call at a time, is enough to pin down the whole shape uniquely.

def build_tree(preorder, inorder): if not preorder or not inorder: return None root_val = preorder[0] root = TreeNode(root_val) mid = inorder.index(root_val) left_inorder = inorder[:mid] right_inorder = inorder[mid + 1:] left_preorder = preorder[1:1 + len(left_inorder)] right_preorder = preorder[1 + len(left_inorder):] root.left = build_tree(left_preorder, left_inorder) root.right = build_tree(right_preorder, right_inorder) return root

Key mental model

Preorder's first element is always the current subtree's root — no exceptions, that's what "N first" guarantees. Finding that value's position inside the matching inorder slice splits it into "everything left of the root" and "everything right of it" — which are the left and right subtrees. Their sizes then tell you exactly how to cut the preorder slice too: the next len(left_inorder) values after the root belong to the left subtree, the rest to the right.

Common mistake — assuming preorder + postorder is enough

It is not, for a general binary tree. Preorder [1,2] and postorder [2,1] match both "1 with a left child 2" and "1 with a right child 2" — postorder can't tell which side a lone child is on because L,R,N never records where the single child sat relative to a sibling that doesn't exist. Inorder breaks that tie ([2,1] vs [1,2]), which is exactly why it must be one of the two traversals you use.

The O(n) optimization: an index map

The code above calls inorder.index(root_val) on every recursive call — a linear scan each time, O(n) work repeated for each of the n nodes, so O(n2) overall. Precomputing val_to_index = {v: i for i, v in enumerate(inorder)} once up front turns that scan into a single O(1) dictionary lookup per call, dropping the whole reconstruction to O(n).

Edge cases you should test

Case A: single node

root = build_tree([5])

pre = in = post = level = [5]

With no children, all four orders visit exactly one node and produce the same one-element list. This is the case that proves the base case (if not node: return) is correct: no recursion beyond it is ever needed.

Case B: left-skewed chain

root = left_chain(3) — 1.left = 2, 2.left = 3, no right children anywhere

preorder = [1,2,3] · inorder = postorder = [3,2,1]

With every right child empty, postorder's L R N collapses to just L N — identical to inorder. And because the walk only ever goes one direction, inorder is exactly preorder reversed. At left_chain(5000) — the notebook's actual stress test — recursive inorder raises RecursionError while the iterative version, whose stack lives on the heap, returns cleanly. Depth is the real danger here, not correctness.

Case C: empty tree

root = build_tree([]) → root = None

pre = in = post = level = []

Every function must check for None before touching .val, .left, or .right. Recursive versions do it with if not node: return; iterative versions do it with if not root: return [] before the loop even starts.

OrderWhat it's forTimeSpace (recursive)Space (iterative)
PreorderSerialize / clone a tree — the root is always firstO(n)O(h) call stackO(h) explicit stack
InorderSorted order on a BST — validate-BST, kth-smallestO(n)O(h) call stackO(h) explicit stack (O(1) with Morris threading)
PostorderCompute a value bottom-up from children; the only safe order to free/delete nodesO(n)O(h) call stackO(h) explicit stack
Level-order (BFS)Anything about depth: shortest hops to a node, level-by-level view, minimum depthO(n)N/A — no natural recursive formO(w) queue, widest level
Reconstruct (pre + in)Rebuild the unique tree from two traversals — needs one of them to be inorderO(n2) naive .index() · O(n) with an index mapO(h) call stackO(n) index map (optimized version only)

h = tree height (worst case n on a skewed tree, log n balanced). w = widest level (up to ~n/2 on a perfect tree). All four traversal orders still touch every node exactly once — they only differ in when/how. Reconstruction is the odd one out: it does n total recursive calls but each one's .index() scan can cost up to O(n), which is what the index-map optimization removes.

How to derive this in an interview

Reasoning path

Does a node's answer depend on its children, or do I just need to walk in a specific value order?

If it's about sorted VALUE order on a BST → inorder, sorted for free.

If I need to rebuild, serialize, or clone → root has to come first → preorder.

If I'm computing something from children (height, sum, balance) or freeing memory → children before parent → postorder.

If the question says nearest / shortest / level-by-level → none of the three DFS orders fit; I need a queue, not a stack → BFS.

If the tree could be very deep or skewed → say out loud that recursion risks RecursionError, and I'd use the explicit-stack version instead.

What to say out loud

  • "All three DFS orders are the same body — I just need to decide where the visit line goes relative to the two recursive calls."
  • "This is a BST and I need sorted order, so inorder gives me that for free — no separate sort step."
  • "I need every child fully resolved before the parent, so I'll record the node after both recursive calls — that's postorder."
  • "If I'm worried about a deep or skewed input, I'll convert to the iterative version so the walk lives on the heap, not the call stack."

Common beginner coding mistakes

Recursive DFS mistakes

  • Assuming the append position doesn't matter — swapping it changes which traversal you actually have, silently.
  • Forgetting the base case (if not node: return) — leads to an AttributeError on None.val, not infinite recursion (Python trees terminate at leaves regardless).
  • Believing "inorder is sorted" applies to any binary tree — it is only true on a binary search tree.
  • Returning a value from the inner helper instead of appending to a closure list, then losing results between recursive calls.

Iterative stack mistakes

  • Using while stack: instead of while node or stack: — the walk stops the moment the stack empties mid-tree, silently dropping whatever comes next.
  • Pushing left before right for preorder — a stack reverses whatever you push, so right must go on first to make left pop next.
  • Popping and recording immediately in inorder the way preorder does it — inorder can only record a node once its left subtree is provably finished, which is exactly when the dive-left loop pops it.
  • Forgetting node = popped.right after recording in inorder — without it the loop never explores right subtrees and the walk ends early.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Given preorder = [1, 2, 4, 5, 3, 6, 7], what is the very first element guaranteed to be, and why?

Answer: the root. Preorder appends node.val before either recursive call runs, so the outermost call — the one on the root — is always the first thing recorded, no matter the tree's shape.

Practice 2 — Trace inorder_iterative by hand on a right-skewed chain 1 → 2 → 3 (all right children, no left children anywhere). How does the stack behave differently than on the left-skewed case above?

Answer: the stack never holds more than one element. Each node has no left child, so the inner "dive left" loop pushes it and immediately falls through (node.left is None); the very next line pops it right back off and records it, then moves to node.right and repeats. Compare that to the left-skewed case, where the whole chain piles onto the stack before a single pop happens — the stack's peak size is the tree's height, and that height is entirely determined by how many left pointers are chained together.

Practice 3 — In preorder_inorder_postorder, what happens if you move postorder.append(node.val) from after both recursive calls to before both of them?

Answer: you get preorder again — a second copy of it, appended before dfs(node.left). This is the whole point of the "one skeleton, three positions" idea: there is nothing structurally special about postorder's code, only about where its one line sits. Move the line, and you've moved the traversal.

Final takeaway

Preorder, inorder, and postorder are one walk, not three. The base case and the two recursive calls never change — only where the "record this node" line sits relative to them. Recursion gives you that walk for free by using the call stack as scratch space; the iterative inorder version just takes that same scratch space and hands it to you as a Python list you can inspect at every step. Level-order breaks the pattern on purpose: swap the stack for a queue and you get a completely different question answered — depth, not subtree structure.
