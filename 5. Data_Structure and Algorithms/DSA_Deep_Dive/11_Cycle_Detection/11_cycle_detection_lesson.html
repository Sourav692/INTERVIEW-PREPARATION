Cycle Detection in Graphs

A cycle is a path that returns to where it started. Finding one sounds like a single algorithm, but it is actually two different rules wearing the same DFS costume: an undirected graph needs you to remember your parent, and a directed graph needs you to remember what is still on the recursion stack. Confuse the two and you get false positives or false negatives on almost every graph you test.

Canonical example

edges = [(0,1), (1,2), (2,0)] — a triangle

Undirected 0–1–2–0: cycle · Directed 0→1→2→0: cycle

Why this matters

Deadlock detection

Process A waits on a lock held by B, B waits on C, C waits on A. That "waits-for" graph is directed, and a deadlock is exactly a directed cycle in it.

Dependency loops

Package managers and build systems (npm, Bazel, Make) model "depends on" as a directed edge. A circular dependency is a cycle that makes the build unschedulable.

Spreadsheet circular references

Cell A references B, B references C, C references A. Spreadsheet engines run cycle detection on the formula graph before they can compute anything.

Instructor note: notice all three examples are directed. That is not an accident — in practice, directed-cycle detection (deadlocks, dependencies, references) comes up far more often than the undirected version, which mostly shows up as a helper inside Union-Find and Kruskal's MST. Learn both, but expect directed to be the one you reach for most.

What is cycle detection?

Simple definition

A cycle is a path of one or more edges that starts and ends at the same vertex, without immediately retracing the single edge you just walked.

What you are computing

Just a yes/no answer: does any cycle exist anywhere in the graph? You are not counting cycles, and you are not finding the shortest one — the first one you confirm is enough to return True.

Beginner shortcut — the one idea this whole page is built around: during a DFS, running into an already-visited vertex is not automatically a cycle, in either graph type. In an undirected graph it might just be the parent you arrived from. In a directed graph it might be a vertex that finished through a completely different branch. Each direction needs one extra piece of state — a parent pointer, or an on-stack flag — before "visited" can be trusted to mean "cycle."

Step-by-step thinking process

1

Check: directed or undirected?

This single fact decides which extra state you need to carry. Get it wrong and the whole algorithm gives wrong answers.

2

Pick the extra state

Undirected → carry the parent you came from. Directed → carry a three-way colour (or an explicit on-stack set).

3

DFS every unvisited vertex

Loop over all vertices from the outside, not just vertex 0 — a graph can have several disconnected pieces, each needing its own DFS.

4

Apply the direction-specific check

Only when you hit an already-seen vertex: is it the parent (undirected, skip) or still on the stack (directed, cycle)?

How the input becomes an adjacency list

Before any DFS can run, the raw edge list has to become an adjacency list. For an undirected graph, every edge is added in both directions, because you can walk it either way.

Input edges

edges = [(0,1), (1,2), (2,0)]
→

Undirected adjacency list

0: [1, 2] 1: [0, 2] 2: [0, 1]

Read edge (0,1)

Add 1 to node 0's list, and add 0 to node 1's list — both directions.

Read edge (1,2)

Add 2 to node 1's list, and add 1 to node 2's list.

Read edge (2,0)

Add 0 to node 2's list, and add 2 to node 0's list. Node 0 now lists both of its triangle neighbours.

Critical point: for a directed graph, the same edge (0,1) would only add 1 to node 0's list — never the reverse. That one-line difference in the build step is the entire reason the two DFS traversals need different cycle rules: the undirected adjacency list secretly contains a "fake" edge back to the parent that was never really a second connection.

Both traces below iterate each vertex's neighbour list in sorted (ascending) order, so the walk order is fully deterministic and reproducible.

Method 1: Undirected — DFS remembering your parent

In an undirected graph, the edge u–v lets you walk straight back from v to u. That backward step is not a new connection — it is the same edge, seen from the other side. So while exploring from u, DFS carries along the vertex it just came from (parent) and ignores exactly that one neighbour. Any other already-visited neighbour is a real, second way back to that vertex — a genuine cycle.

def has_cycle_undirected(n, adj): seen = [False] * n def dfs(u, parent): seen[u] = True for v in sorted(adj[u]): if not seen[v]: if dfs(v, u): return True elif v != parent: return True return False for s in range(n): if not seen[s] and dfs(s, -1): return True return False

Key mental model

At any moment, the recursion stack is exactly the path from the outer-loop start down to the current node. A cycle is a second edge that lands on any vertex still open on that stack.

Common undirected mistake

Checking only if seen[v]: return True without the parent guard. That flags every single edge as a cycle, because you always immediately see the vertex you just came from.

Why the outer loop matters

DFS from vertex 0 alone would miss a cycle sitting in a disconnected second component. Looping for s in range(n) restarts DFS on every unvisited vertex.

Method 2: Directed — the 3-colour DFS (back edges)

In a directed graph the parent trick breaks, because arrows are one-way — you can never walk straight back along the edge you arrived on. Instead, every vertex gets one of three colours: white (never touched), grey (visited, and still on the current recursion stack — an ancestor of where you are now), or black (fully finished, every descendant explored). A cycle exists exactly when an edge points to a grey vertex — a back edge to an ancestor. An edge to a black vertex is completely normal.

def has_cycle_directed(n, adj): WHITE, GREY, BLACK = 0, 1, 2 color = [WHITE] * n def dfs(u): color[u] = GREY for v in sorted(adj[u]): if color[v] == GREY: return True if color[v] == WHITE and dfs(v): return True color[u] = BLACK return False for s in range(n): if color[s] == WHITE and dfs(s): return True return False

Key mental model

Grey means "an ancestor of the node I'm at right now." Only an edge to a grey vertex closes a loop back onto the current path — an edge to black is just a second, unrelated way to reach an already-finished branch.

Common directed mistake

Using one boolean visited flag instead of three colours. That collapses grey and black together, so reaching vertex 2 a second time (once it is black) gets wrongly reported as a cycle.

Why the early return matters

Notice in the trace above that 2, 3, and 4 never reach color[u] = BLACK — they return True early and stay grey forever. That is fine: the algorithm is about to stop entirely, so no later code ever reads their colour again.

Edge cases you should test

Case A: a self-loop

adj = {0: [0], 1: []} — vertex 0 has an edge back to itself.

Answer = cycle found (both directions)

Undirected: dfs(0, parent=-1) sees neighbour 0, which is seen and is not equal to the sentinel parent -1 → cycle. Directed: dfs(0) colours 0 GREY, then immediately examines the edge 0→0 and finds color[0] == GREY → cycle. A self-loop is the smallest possible cycle in either graph type.

Case B: a duplicate edge in an undirected graph — this IS a cycle

adj = {0: [1, 1], 1: [0, 0]} — the edge (0,1) is listed twice.

Answer = cycle found

The first pass into 1 and back correctly skips 0 (it is the parent). But dfs(0,-1) then reaches the second copy of neighbour 1 in its own list. By then 1 is seen, and 1 is not equal to 0's parent (-1) — so this correctly reports a cycle. Two parallel edges between the same pair of vertices really do form a 2-edge cycle; the parent guard only protects against the single edge you are currently walking, not against a second, separately-listed one.

Case C: a directed shared successor — this looks like a cycle but is NOT

adj = {0: [1, 2], 1: [2], 2: []} — both 0 and 1 point to 2.

Answer = no cycle

DFS visits 0 → 1 → 2, finishes 2 (BLACK), then finishes 1 (BLACK). Back in dfs(0), the edge 0 → 2 is examined: color[2] is now BLACK, not GREY, so nothing happens. A beginner using a plain visited flag would see "2 already visited" and wrongly flag a cycle — the 3-colour check correctly recognises this as two unrelated paths converging, not a loop.

Kahn's topological sort (directed alt.)O(V + E)O(V) in-degree array + queueIf the output order has fewer than V vertices, the leftovers are stuck in a cycle.

All four rely on the same core truth: an already-visited vertex only counts as a cycle once you know it is still "open" (the parent link, or the recursion stack) rather than merely "seen before."

How to derive this in an interview

Reasoning path

First question: are the edges bidirectional or one-way? That single fact decides everything downstream.

If undirected: a plain "visited" check is not enough, because every edge you walk immediately shows you your own parent as "visited." I need to carry parent and exempt it.

If directed: a plain "visited" check is also not enough, but for a different reason — it cannot tell a back edge (ancestor, real cycle) from a cross edge (a finished, unrelated branch). I need a third state.

Either way it is one DFS pass, O(V + E), plus an outer loop over every vertex so disconnected pieces are not missed.

If asked for a non-recursive alternative: Union-Find for undirected, Kahn's topological sort for directed.

What to say out loud

  • "First I'll check whether this graph is directed or undirected — the cycle rule is different for each, so I don't want to guess."
  • "For undirected, seeing a visited neighbour is not a cycle if it's the parent I arrived from — I'll pass that parent down through the recursion."
  • "For directed, seeing a visited neighbour is not a cycle if that vertex has already finished — I need a third state, on-stack, not just visited, so I'll use white/grey/black."
  • "I'll still loop over every vertex from the outside so I don't miss a cycle sitting in a disconnected part of the graph."

Common beginner coding mistakes

Undirected mistakes

  • Flagging a cycle on any seen neighbour without excluding the parent — this reports every edge as a cycle.
  • Passing the wrong parent into the recursive call (e.g. always 0 instead of the actual calling vertex u).
  • Forgetting the outer for s in range(n) loop, so a cycle in a second, disconnected component is never found.
  • For Union-Find: comparing raw vertex ids instead of their find() roots, or forgetting to call find() before checking equality.

Directed mistakes

  • Using a single visited boolean instead of white/grey/black — this flags a normal edge to a finished (black) vertex as a cycle.
  • Colouring a vertex BLACK too early, before all of its neighbours are actually checked — this can hide a real back edge.
  • Assuming any repeated vertex means a cycle, instead of specifically checking "is it still on the current recursion stack (grey)?"
  • For Kahn's: forgetting to compare the number of vertices actually output to V — silently returning "no cycle" when vertices are stuck.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Undirected, n = 4, edges = [(0,1), (1,2), (2,3)]

Answer: no cycle. This is a straight path (a tree with 3 edges and 4 vertices). At every step, DFS's only seen neighbour is the parent it just came from, so the elif branch never triggers.

Practice 2 — Directed, adj = {0: [1], 1: [2], 2: [3], 3: [1]}

Answer: cycle found. DFS colours 0, 1, 2, 3 all GREY in turn. When it examines edge 3 → 1, vertex 1 is still GREY (an ancestor on the current stack), so this is a back edge — a cycle: 1 → 2 → 3 → 1. Vertex 0 is not part of the cycle itself; it just happened to be where the DFS started.

Practice 3 — Directed, adj = {0: [1, 2], 1: [2], 2: []}

Answer: no cycle. This is the same "shared successor" shape from the edge cases above. DFS reaches vertex 2 twice — once via 0 → 1 → 2 (finishing it to BLACK) and once via the direct edge 0 → 2 (by which point 2 is BLACK, not GREY). Two paths converging on the same finished vertex is completely normal in a DAG; it is exactly the case a plain "visited" flag gets wrong.

Final takeaway

Cycle detection is not one algorithm — it is one instinct (DFS) paired with two different extra pieces of state. Undirected: carry your parent, and only ignore that one exempted edge. Directed: carry a three-way colour, and only an edge to a still-open (grey) vertex counts. Every beginner mistake on this page traces back to the same root cause — treating "visited" as if it already meant "cycle," when really it is just the first half of the question.
