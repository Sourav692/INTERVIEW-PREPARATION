Heaps and Priority Queues

A priority queue always hands you the most important item next — the smallest or the largest — no matter what order things were added in. A heap is the specific structure that makes both "add an item" and "remove the best item" cost only O(log n), by giving up full sorted order in exchange for just enough order to guarantee the root is always correct. This page traces the sift-up / sift-down mechanics on a real array, then the bounded min-heap pattern that solves top-K problems in interviews.

Canonical example

Push 5, 1, 8, 3, 9, 2, 7 one at a time into an empty min-heap.

array = [1, 3, 2, 5, 9, 8, 7] · root = 1 (the minimum)

Why this matters

Schedulers & event queues

An OS scheduler or timer system always needs "what runs next" — the soonest deadline, not a fully sorted list of every future event.

Dijkstra & Prim

Both algorithms repeatedly ask "which unvisited vertex is cheapest to reach right now?" A heap answers that in O(log n) every time a distance improves.

Top-K & streaming medians

Keep only the K best items — or a running middle value — seen so far in a stream, without ever re-sorting everything on every new arrival.

Instructor note: a heap is deliberately not a sorted array. That trade is the entire idea: give up full order, keep only "parent is at least as good as its children," and that weaker guarantee is still enough to make the root always correct in O(1) and to restore it in O(log n) after any change.

What is a heap?

Priority queue — the interface

A contract with three operations: push(x) add an item, pop() remove and return the best item, peek() look at the best item without removing it. Nothing here says how it's built.

Heap — the implementation

A complete binary tree (every level full, last level filled left-to-right) obeying the heap property: in a min-heap, every parent is ≤ both of its children, so the smallest value always sits at the root.

Because the tree is complete, it packs perfectly into a plain array with no pointers at all. For any node at index i:

Index math

parent(i) = (i - 1) // 2 left(i) = 2*i + 1 right(i) = 2*i + 2
↔

Array = tree

index: 0 1 2 3 4 5 6 value: [1, 3, 2, 5, 9, 8, 7]

Beginner shortcut: if you can compute an index, you already know its parent and both children. There is nothing to "follow" — a heap has no .left / .right / .parent references, just arithmetic on a position in a list.

Step-by-step thinking process

1

Decide min or max

What counts as "best" here — the smallest distance, the soonest deadline, the largest score? That decides whether the parent rule is ≤ or ≥.

2

Keep it complete

Always insert at the very end and always remove by pulling the last element into the empty root slot — never leave a hole anywhere else in the array.

3

Restore the property

A single insert or removal can only break the heap property along one root-to-leaf path. Sift that one element up or down until parent ≤ children holds again.

4

Trust index math, not pointers

i, 2i+1, 2i+2, (i-1)//2 replace every .left / .right / .parent lookup you'd write for a linked tree.

How the input becomes a heap array

You don't always build a heap by pushing one item at a time. Given a whole unordered list up front, heapify converts it into a valid heap in-place in O(n) — faster than n individual pushes, which would cost O(n log n).

Raw list

[9, 4, 7, 1, 3, 8, 2]
→

Heapified array

[1, 3, 2, 4, 9, 8, 7]

heapify walks every internal node from the bottom up (starting at index n // 2 - 1) and sifts each one down. Leaves need no work — a single value is already a valid heap of size one.

i = 2, value 7

Children are index 5 (value 8) and index 6 (value 2). The smaller child is 2, and 2 < 7, so swap: [9, 4, 2, 1, 3, 8, 7]. Index 6 has no children, so this node stops.

i = 1, value 4

Children are index 3 (value 1) and index 4 (value 3). The smaller child is 1, and 1 < 4, so swap: [9, 1, 2, 4, 3, 8, 7]. Index 3 has no children, so this node stops.

i = 0, value 9

Children are index 1 (value 1) and index 2 (value 2). The smaller is 1, so swap: [1, 9, 2, 4, 3, 8, 7]. Now at index 1, value 9: children are index 3 (value 4) and index 4 (value 3); smaller is 3, so swap: [1, 3, 2, 4, 9, 8, 7]. Index 4 has no children — done.

Critical point: heapify never even looks at the leaves (roughly half the array) as a starting point for sifting — only internal nodes can possibly violate the heap property, since a leaf has no children to compare against. That's why the total work is O(n), not O(n log n).

Method 1: push and pop mechanics — sift-up and sift-down

This is the engine underneath every heap operation. push appends at the end (keeps the tree complete) and bubbles the new value up past parents that are bigger than it. pop removes the root, moves the very last element into the empty root slot (keeps the tree complete), and bubbles that value down past children that are smaller than it. Watch the tree and the array below — they are always showing the exact same object, just two views of it.

def push(heap, x): heap.append(x) i = len(heap) - 1 while i > 0: parent = (i - 1) // 2 if heap[i] < heap[parent]: heap[i], heap[parent] = heap[parent], heap[i] i = parent else: break def pop(heap): top = heap[0] last = heap.pop() if heap: heap[0] = last i, n = 0, len(heap) while True: small, l, r = i, 2*i + 1, 2*i + 2 if l < n and heap[l] < heap[small]: small = l if r < n and heap[r] < heap[small]: small = r if small == i: break heap[i], heap[small] = heap[small], heap[i] i = small return top

Key mental model

The tree diagram and the array diagram above are not two representations of two different things — they are one object drawn twice. Index i in the array is the node at that position in the tree.

Common mistake

Forgetting to guard child indices with l < n / r < n before comparing — on the last level a node may have zero, one, or two children, and indexing past the end crashes.

Why sifting stops early

Both loops break the instant the heap property holds locally. A value never has to travel further than the tree's height, which is why push and pop are O(log n), not O(n).

Method 2: bounded min-heap for top-K

You only need the K largest values out of n, not a full sort of everything. Keep a min-heap capped at size K: push every value, and the instant the heap grows past K, pop the smallest. Whatever survives is always "the K largest seen so far," because the weakest candidate is discarded the moment a stronger one arrives. This is the exact pattern behind Confluence Word Count's topWords_heap and File System's top_collections.

def top_k(nums, k): h = [] for x in nums: heapq.heappush(h, x) if len(h) > k: heapq.heappop(h) return sorted(h, reverse=True)

Key mental model

The heap always holds "the best K candidates seen so far, in no particular order beyond the heap property." Its root is always the weakest of those K — exactly the one to evict next.

Common mistake

Using a max-heap here. A max-heap puts the strongest candidate at the root, which tells you nothing about who to evict — you'd need O(k) to find the weakest instead of O(1).

Why this beats sorting

Sorting all n values costs O(n log n) and needs O(n) memory. The bounded heap costs O(n log k) and only ever holds k items — a real win when k is small and n is huge.

Edge cases you should test

Case A: Python's heapq is min-only

heapq.heappush(h, -x) then -heapq.heappop(h)

largest of [5, 1, 3] → push [-5, -1, -3] → pop returns -5 → negate → 5

There is no built-in max-heap in Python. Negating every value on the way in flips "smallest" and "largest," so the most negative number (the original largest) always surfaces first. Negate again on the way out to get the real value back. This is purely a comparison trick — no new data structure is needed.

Case B: duplicate priorities and tuple tie-breaking

heapq.heappush(pq, (2, "task-B")); heapq.heappush(pq, (2, "task-A"))

Same priority 2 → heapq compares the next tuple element to break the tie

When two entries share a priority, heapq falls back to comparing the rest of the tuple — here, the strings, so "task-A" would sort before "task-B". That's harmless for strings and numbers, but if the second element is an object without < defined (or another tuple that can't be compared), Python raises a TypeError the moment two priorities tie. The fix is to add a strictly increasing counter as a middle tiebreaker: (priority, counter, item) — the counter is always unique, so the comparison never has to look at item at all.

Case C: heapq cannot update an arbitrary entry's priority

A leaderboard entry's score changes — you cannot fix its position in O(log n).

No decrease-key in heapq → use lazy deletion

heapq gives no way to find an arbitrary entry's index or re-sift it in place. The standard workaround, lazy deletion: push a brand-new entry with the updated priority and leave the stale one sitting in the heap. Keep a side dictionary of each key's current, authoritative value. When an entry is popped, check it against the dictionary — if it's stale (doesn't match), silently discard it and pop again. This is exactly why a heap is the wrong tool for something like Content Popularity Tracker, where scores change constantly.

How to derive this in an interview

Reasoning path

"I need the current best item repeatedly, not a one-time answer."

A sorted array gives fast peek but slow insert; an unsorted array gives fast insert but slow peek — I need both to be fast.

A heap trades full order for the minimum guarantee that still makes the root correct: parent ≤ children.

Because the tree is complete, I can pack it into a plain array with index math instead of pointers.

If I only need the best K, not a full ranking, I bound the heap to size K instead of letting it grow to n.

What to say out loud

  • "I don't need a full sort — a heap gets me O(log n) insert and remove for the price of just enough ordering."
  • "Because the tree is complete, I don't need TreeNode objects — index i, 2i+1, 2i+2, (i-1)//2 give me the whole structure in a plain list."
  • "For top-K, I'll bound the heap to size K and pop the weakest whenever it overflows — O(n log k) instead of sorting everything."
  • "heapq is min-only, so for a max-heap I'll negate values on the way in and out."

Common beginner coding mistakes

push / pop mechanics mistakes

  • Computing the parent as i - 1 instead of (i - 1) // 2.
  • Indexing a child without checking l < n / r < n first — crashes once the array runs out of that level.
  • Swapping values but forgetting to update i to the new position, so the loop keeps comparing at the old spot.
  • Assuming the array is fully sorted after building a heap — it isn't; only parent ≤ children holds.

top-K bounded heap mistakes

  • Using a max-heap to find the K largest — you want a min-heap so the weakest survivor is disposable at the root.
  • Popping unconditionally instead of only when len(h) > k, which throws away a value that should have stayed.
  • Sorting the entire input first "to be safe," which throws away the whole O(n log k) benefit.
  • Forgetting that the surviving heap is not itself sorted — you still need one final sorted() call if the output order matters.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Starting from [1, 3, 2, 5, 9, 8, 7] (the array after all seven pushes above), what does the array look like after push(6)?

Answer: [1, 3, 2, 5, 9, 8, 7, 6]. 6 is appended at index 7. Its parent is (7-1)//2 = 3, which holds 5. Since 6 < 5 is false, the sift-up stops immediately — no swap happens at all.

Practice 2 — Why does the top-K pattern use a MIN-heap to find the K LARGEST values, not a MAX-heap?

Answer: a min-heap of size K keeps the weakest of the current K survivors at the root, visible in O(1). The moment a new value arrives, you compare it against that weakest survivor and evict it if the new value is bigger — an O(log K) operation. A max-heap of size K would put the strongest value at the root, which is useless for deciding who to evict; you'd have to scan all K items to find the weakest one instead.

Practice 3 — A leaderboard needs to re-prioritize a player whose score just changed. Why can't you just update their existing heap entry?

Answer: heapq has no way to locate an arbitrary entry's index or fix its position in O(log n) — there's no index-by-value lookup, and moving one entry can require sifting through unrelated ones. The standard fix is lazy deletion: push a fresh (new_score, player) entry and leave the stale one sitting in the heap. Keep a side dictionary mapping each player to their current score; when a popped entry's score doesn't match the dictionary, it's stale — discard it and pop again instead of using it.

Final takeaway

A heap is one array wearing a tree costume. The array and the tree are the same object — index i is a node, 2i+1/2i+2 are its children, (i-1)//2 is its parent, and no pointer is ever needed. push restores order by sifting up; pop restores it by sifting down. Bound the heap to size K and the same machinery solves top-K in O(n log k) instead of sorting everything.
