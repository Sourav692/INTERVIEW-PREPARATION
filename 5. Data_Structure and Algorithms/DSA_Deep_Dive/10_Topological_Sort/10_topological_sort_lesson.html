Topological Sort on a DAG

This page explains topological sort like an instructor would: what a valid order actually means, how the edge list becomes an adjacency list and an in-degree map, how Kahn's algorithm peels off ready tasks one by one, how DFS builds the same kind of order by finishing nodes and reversing, and how to reason about cycles and non-uniqueness in an interview.

Why this matters

Build systems

A source file can only compile after every file it imports has compiled. The dependency graph must be sorted before the compiler runs a single step.

Course prerequisites

You cannot register for "Algorithms II" before "Algorithms I." A degree plan is a topological order of the prerequisite graph.

Task scheduling

Package installers, spreadsheet recalculation, and CI pipeline stages all need "do this before that" resolved into one runnable sequence.

Instructor note: the underlying question is always the same — given a set of "before" rules, is there any order that satisfies all of them, and if so, what is one? Topological sort answers both at once.

What is a topological sort?

Simple definition

A topological sort is a linear ordering of a directed graph's vertices such that for every edge u → v, u appears before v in the ordering.

What you are computing

You are not computing a shortest path or a single number. You are producing an entire sequence — one that respects every "before" constraint in the graph at once.

Beginner shortcut: lay your answer out left to right. If you can draw every edge as an arrow pointing only rightward, never backward, the order is valid. This only works at all when the graph is a DAG — Directed, Acyclic, Graph. A cycle means no valid order exists.

Step-by-step thinking process

1

Confirm it's a "before" graph

Each edge u → v means u must come before v. That is the signal to reach for topological sort.

2

Build adjacency list + in-degree map

Every edge adds a neighbor to adj[u] and adds one prerequisite to indeg[v].

3

Peel off ready nodes, or finish-then-reverse

Kahn's algorithm repeatedly outputs any vertex with no remaining prerequisites. DFS instead finishes the deepest vertices first, then reverses.

4

Watch for a cycle

Kahn: fewer than n vertices got output. DFS: an edge points to a vertex still on the call stack.

How the input becomes a working structure

Both algorithms below start from the exact same setup. Before any sorting logic runs, the edge list is converted into an adjacency list and an in-degree count for every vertex — this is the part beginners skip past too quickly.

Input edges

n = 5 edges = [(0,1), (0,2), (1,3), (2,3), (3,4)]
→

Adjacency list + in-degree map

adj = {0:[1,2], 1:[3], 2:[3], 3:[4], 4:[]} indeg = {0:0, 1:1, 2:1, 3:2, 4:1}

Read edges (0,1) and (0,2)

Both start at 0, so adj[0] = [1, 2]. Each edge also adds one prerequisite: indeg[1] = 1 and indeg[2] = 1.

Read edges (1,3) and (2,3)

Both point into 3, so indeg[3] becomes 2 — vertex 3 needs both 1 and 2 finished before it can run.

Read edge (3,4)

adj[3] = [4] and indeg[4] = 1. Vertex 4 has exactly one prerequisite: vertex 3.

Critical point: only vertex 0 starts with indeg = 0. That is not a coincidence for this example — it is the definition of "ready to run right now," and it is exactly what seeds both algorithms below.

Method 1: Kahn's algorithm (BFS-based)

A vertex is ready the moment its in-degree hits 0 — it has no unmet prerequisites left. Kahn's algorithm keeps a queue of ready vertices, pops one, outputs it, and "removes" it by decrementing every neighbor's in-degree. Any neighbor that drops to 0 just became ready and joins the queue.

from collections import deque def topo_sort_kahn(n, edges): """n vertices 0..n-1; edges = (u, v) meaning u must come before v. Returns a valid order, or None if there is a cycle.""" indeg = [0] * n adj = [[] for _ in range(n)] for u, v in edges: adj[u].append(v) indeg[v] += 1 # v gains a prerequisite q = deque(i for i in range(n) if indeg[i] == 0) # everything ready now order = [] while q: u = q.popleft() order.append(u) # no prerequisites left -> output it for v in adj[u]: indeg[v] -= 1 # u done -> v loses a prerequisite if indeg[v] == 0: q.append(v) # v just became ready return order if len(order) == n else None # short -> a cycle blocked some tasks

Key mental model

The in-degree map is the live state that drives everything. A vertex enters the queue the instant its count reaches exactly 0 — not before.

Common Kahn mistake

Checking cycle-freedom with anything other than len(order) == n. If some vertices never reach in-degree 0, they simply never get output — that shortfall is the cycle signal.

Why in-degree matters

A vertex with two prerequisites, like 3 in this example, must wait for both to finish. That is exactly what "decrement, then check for zero" enforces — one decrement is not enough.

Method 2: DFS-based topological sort

Run a normal DFS. The moment a vertex finishes — every one of its outgoing edges has been fully explored — push it onto a list. A vertex with no remaining unexplored descendants finishes before the vertex that called it, so the finish list ends up backwards. Reversing it gives a valid topological order.

def topo_sort_dfs(n, edges): adj = [[] for _ in range(n)] for u, v in edges: adj[u].append(v) visited = [0] * n # 0 unseen, 1 in-progress, 2 done order, ok = [], True def dfs(u): nonlocal ok visited[u] = 1 # on the recursion stack for v in adj[u]: if visited[v] == 1: # edge back to an in-progress node -> cycle ok = False elif visited[v] == 0: dfs(v) visited[u] = 2 # finished order.append(u) # push on finish for i in range(n): if visited[i] == 0: dfs(i) return order[::-1] if ok else None # reverse of finish order

Key mental model

Vertices finish in the reverse of the order that makes sense for the answer — the deepest, most-depended-on vertex (4) finishes first. Reversing the finish list undoes that.

Common DFS mistake

Using a 2-state visited set (seen / unseen) instead of 3 states. Without a separate "in-progress" state, DFS cannot tell "currently on the stack" from "already fully done" — and cycle detection silently breaks.

Why "in-progress" matters

Step 9 hits vertex 3 a second time via a different path, but visited[3] == 2 (done), not 1 (in-progress) — so it is correctly recognized as safe, not a cycle.

Edge cases you should test

Case A: a cycle means no valid order exists

n = 3, edges = [(0,1), (1,2), (2,0)]

topo_sort_kahn(3, edges) = None · topo_sort_dfs(3, edges) = None

Kahn's: every vertex starts with indeg = 1, so the queue is empty from the very first step — nothing is ever output, and len(order) = 0 < n confirms a cycle immediately. DFS: dfs(0) → dfs(1) → dfs(2), then edge 2 → 0 is checked while visited[0] is still 1 (in-progress, not done) — that back-edge to a node still on the call stack is the cycle.

Case B: topological order is not unique

n = 5, edges = [(0,1), (0,2), (1,3), (2,3), (3,4)] — the canonical example above.

Kahn's gives [0, 1, 2, 3, 4] · DFS gives [0, 2, 1, 3, 4] · both are correct

1 and 2 do not depend on each other, so either can legally come first — only their relationship to 0 and 3 is constrained. Kahn's processes them in the order they entered the queue (1 before 2); DFS finishes them in the opposite order it entered them (2's branch happens to finish and reverse ahead of 1's here). Both orders keep every edge pointing forward, so both are valid. There is no single "the" answer to check against — only "is every edge satisfied."

Case C: a disconnected DAG with several ready roots

n = 5, edges = [(0,1), (1,2), (3,4)]

topo_sort_kahn(5, edges) = [0, 3, 1, 4, 2]

This graph is really two separate chains: 0→1→2 and 3→4. Both 0 and 3 start at indeg = 0, so the queue seeds with [0, 3] and Kahn's naturally interleaves the two independent chains as it pops from the front. Neither algorithm needs any special handling for disconnected components — every vertex with no prerequisites, wherever it lives in the graph, is ready immediately.

How to derive this in an interview

Reasoning path

"Task X must happen before task Y" is a directed edge, not an undirected one.

I need one linear order where every edge points forward — that's topological sort, and it only makes sense on a DAG.

Which vertices are safe to place next? Any vertex with no remaining prerequisites — in-degree 0. Repeatedly peeling those off is Kahn's algorithm, which is really BFS.

Alternatively, I can recurse to the bottom of each chain first and push each vertex the moment it finishes, then reverse that list.

How do I know it's impossible? Kahn's: some vertices never reach in-degree 0. DFS: an edge points back to a vertex still on the call stack.

What to say out loud

  • "Edges mean 'before', so I'll build an adjacency list plus an in-degree count for every vertex."
  • "I'll repeatedly output any vertex with in-degree 0 and decrement its neighbors — that's Kahn's algorithm, and it's basically BFS."
  • "If I run out of ready vertices before outputting everyone, the graph has a cycle and no valid order exists."
  • "Alternatively, DFS can push each vertex onto a list the instant it finishes; reversing that list also gives a valid order."
  • "There's no single correct answer — any order that keeps every edge pointing forward is valid."

Common beginner coding mistakes

Kahn's algorithm mistakes

  • Forgetting to compute in-degree for every vertex before seeding the queue, so a ready vertex gets missed.
  • Decrementing a neighbor's in-degree but forgetting the == 0 check before enqueueing — a vertex with two prerequisites would get enqueued twice, once too early.
  • Detecting a cycle by inspecting the in-degree array instead of comparing len(order) to n.
  • Assuming the queue's output is "the" answer instead of "a" valid answer — the order depends on tie-breaking, not just the graph.

DFS-based mistakes

  • Using a 2-state visited set (seen/unseen) instead of 3 states — without "in-progress," a legitimate re-visit of a finished node looks identical to a cycle.
  • Forgetting to reverse the finish order before returning it — the raw finish list is backwards.
  • Marking a vertex "done" before its neighbor loop finishes, which can hide a real cycle.
  • Appending to the output list before recursing into children (pre-order) instead of after (post-order) — topological order needs the push to happen on finish, not on entry.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — n = 4, edges = [(0,1), (0,2), (1,3), (2,3)]. What does topo_sort_kahn return?

Answer: [0, 1, 2, 3]. Vertex 0 seeds the queue alone. Popping it makes both 1 and 2 ready at once; they get popped in queue order (1 then 2), and only once both are done does 3's in-degree reach 0. [0, 2, 1, 3] would be an equally valid order — 1 and 2 don't depend on each other.

Practice 2 — edges = [(0,1), (1,2), (2,3), (3,1)], n = 4. Does a topological order exist?

Answer: No. 1 → 2 → 3 → 1 is a cycle. Kahn's: only vertex 0 ever reaches in-degree 0 (1 needs both 0 and 3 to finish, but 3 needs 1 to finish first), so the queue empties after outputting just [0] — len(order) = 1 < 4. DFS: exploring from 0 eventually reaches edge 3 → 1 while visited[1] is still 1 (in-progress) — cycle detected. Both return None.

Practice 3 — If adj[0] were built as [2, 1] instead of [1, 2] for the canonical example, would the DFS-based result still be a valid topological order?

Answer: Yes. The neighbor visiting order changes which branch DFS finishes first, so the finish list — and therefore the reversed output — comes out differently (e.g. a different interleaving of 1 and 2). But every edge in the graph still points forward in the new order, because neither traversal order changes what the graph's actual dependencies are. This is the same lesson as edge case B: there is no single correct output to memorize, only the property "every edge points forward" to check.

Final takeaway

Topological sort answers one question: is there an order that respects every "before" rule, and if so, what is one of them? Kahn's algorithm answers it by repeatedly peeling off whatever has no prerequisites left — a queue-driven BFS. DFS answers it by finishing the deepest dependencies first and reversing. Both detect a cycle as a side effect of trying: Kahn's when vertices get stuck below in-degree 0's queue, DFS when an edge loops back onto the call stack. Neither algorithm's output is the answer — only a valid one.
