Binary Search Trees

A BST is binary search wearing a tree's clothing. One rule — everything left of a node is smaller, everything right is larger, recursively — is enough to give you search, insert, and delete in O(height) time, and sorted output for free. This page traces the real search, insert, and delete functions from the companion notebook, step by step, on one concrete tree.

Canonical example

Why this matters

Ordered maps and sets

std::map, Java's TreeMap, and database indexes all lean on this exact idea: keep keys ordered so lookup, insert, delete, and "give me everything sorted" are all fast.

Range and neighbor queries

"Smallest value ≥ x" (ceiling), "largest value ≤ x" (floor), and "what comes right after this value" all fall out of the same left/right walk — no extra data structure needed.

Interview reuse

Validate BST, Kth Smallest, Lowest Common Ancestor in a BST, and Convert Sorted Array to BST are all small edits to the same two functions traced on this page.

Instructor note: a BST is not a new algorithm to memorize — it is binary search, generalized from a sorted array onto a linked structure. Every technique here is that one idea applied to search, insert, and delete.

What is a Binary Search Tree?

Simple definition

For every node, everything in its left subtree is smaller, and everything in its right subtree is larger. This holds recursively — at every node, not only the root.

What you are actually computing

At each node you throw away half the remaining tree: smaller than me → forget the right side entirely; bigger → forget the left. That halving is where O(log n) comes from — it is binary search, on a tree.

Beginner shortcut: at any node, ask one question — is my target smaller, larger, or equal? Smaller → go left. Larger → go right. Equal → you found it (search) or that's where you stop comparing (delete).

Step-by-step thinking process

1

Compare

Compare the target value to the value at the current node.

2

Decide a direction

Smaller → left. Larger → right. Equal → stop here (found, or this is the node to modify).

3

Recurse or loop

Repeat the same comparison one level down. Every step discards the other half of the remaining tree.

4

Stop condition

Search/insert stop at a match or an empty slot. Delete stops at a match, then branches on child count.

Both compare against 8 first (go left), then against 3: 1 < 3 goes left, 6 > 3 goes right.

Each one repeats the same walk from the root. 4 and 7 land under 6; 14 lands under 10; 13 lands under 14 because 13 < 14.

Critical point: the invariant holds at every node, not only the root — {1,4,6,7} are all smaller than 3's parent path where required, and {4,7} stay correctly split around 6. That recursive property is what beginners miss when they only check immediate children.

Method 1: Search & Insert — the shared walk

search and insert are the same walk with different stop conditions. Both compare the target to the current node and go left or right; search stops at a match or falls off the tree, while insert stops at a match (ignored) or an empty slot, where it hangs a new node.

def insert(root, val): if root is None: return TreeNode(val) if val < root.val: root.left = insert(root.left, val) elif val > root.val: root.right = insert(root.right, val) return root def search(root, target): node = root while node: if target == node.val: return True node = node.left if target < node.val else node.right return False

Key mental model

Search and insert are the same function in spirit: insert is just a search that is allowed to fail, and the failure point (an empty slot) is exactly where the value belongs.

Common search/insert mistake

Forgetting to reassign the return value: root.left = insert(root.left, val). Without the reassignment, a brand-new node is built and immediately thrown away.

Why the comparison order matters

Using if / elif (not two independent ifs) guarantees exactly one branch runs per call — that is what keeps the walk to a single root-to-leaf path.

Method 2: Delete — the three cases

Deleting must preserve the invariant. A leaf is just removed. One child means splicing the parent straight to that child. Two children is the hard case: swap in the in-order successor's value, then delete that successor — which is guaranteed to have at most one child, so it falls back into the easy case.

def delete(root, val): if root is None: return None if val < root.val: root.left = delete(root.left, val) elif val > root.val: root.right = delete(root.right, val) else: if root.left is None: return root.right if root.right is None: return root.left succ = root.right while succ.left: succ = succ.left root.val = succ.val root.right = delete(root.right, succ.val) return root

Key mental model

The successor search always walks node.right then all-the-way-left — by construction it lands on a node with no left child, so removing it can never be the hard two-children case.

Common delete mistake

Copying succ.val into the node but forgetting the second delete() call. Without it, the value 4 exists in the tree twice — the old leaf never gets removed.

Why every call reassigns

root.left = delete(root.left, val) — delete's return value must be reassigned by every caller, or a deleted subtree stays wired into the tree.

Method 3: Validate a BST — carry a (low, high) range

The trap: checking only node.left.val < node.val < node.right.val is not enough. A node several levels down must still be smaller (or larger) than ancestors far above its own parent. is_valid_bst fixes this by carrying an allowed (low, high) window down the recursion — going left tightens the ceiling, going right tightens the floor — so every node is checked against every ancestor that matters, not just its parent.

def is_valid_bst(node, low=float("-inf"), high=float("inf")): if node is None: return True if not (low < node.val < high): return False return (is_valid_bst(node.left, low, node.val) and is_valid_bst(node.right, node.val, high))

Why a naive parent-only check is not enough

The common wrong version only compares a node to its immediate parent — node.left.val < node.val and node.right.val > node.val. Run both checks against this tree, where 6 sits in 10's right subtree but is smaller than 10:

bad = 10(left=5, right=15(left=6, right=None)) naive_is_valid(bad) = True # WRONG — only checks 6 < 15, its immediate parent is_valid_bst(bad) = False # CORRECT — 6 must be in (10, 15), but 6 < 10

6 passes the naive check because 6 < 15 holds. But 6 is in 10's right subtree, so the real rule requires 10 < 6 < 15 — and 6 fails that lower bound. This is exactly the ancestor-not-just-parent gap the (low, high) window closes: at node 6, low is inherited from 10, two levels up, not from 15, the immediate parent.

Key mental model

Each recursive call inherits its window from its parent call, not from the tree shape directly — going left tightens the ceiling, going right tightens the floor. The window is the accumulated memory of every ancestor's decision, not just the immediate parent's value.

Common validate mistake

Checking only node.left.val < node.val < node.right.val. This passes the counterexample above even though the tree is not a valid BST, because it never checks a node against ancestors further up than its own parent.

Why this pattern matters

Carrying inherited state down the recursion instead of re-deriving it from scratch at every node is the same trick behind Kth Smallest in a BST and Lowest Common Ancestor in a BST.

Method 4: In-order walk — sorted output for free

An in-order traversal visits left subtree, then the node itself, then right subtree. On a BST that ordering is not incidental: because every node's left subtree is entirely smaller and its right subtree entirely larger, visiting in that order emits every value in ascending order. This is also the direct reason the naive validate check is wrong — the same recursive left-then-node-then-right structure is what makes a node's relationship to every ancestor, not just its parent, the thing that has to hold.

def inorder(node, out=None): out = [] if out is None else out if node: inorder(node.left, out) out.append(node.val) inorder(node.right, out) return out

Key mental model

A value is appended only after its entire left subtree is fully appended and before its entire right subtree begins. Applied recursively at every node, that ordering is what produces ascending output — it is a direct consequence of the BST invariant, not a separate trick.

Common in-order mistake

Appending node.val before recursing left (pre-order, not sorted), or creating a new list instead of passing the same out list into both recursive calls — either mistake silently breaks the sorted guarantee.

Why this pattern matters

This is the basis for Kth Smallest in a BST (stop after k appends instead of collecting everything) and for converting a BST back into a sorted array in O(n) with zero extra sorting work.

Edge cases you should test

Case A: sorted insert order degenerates the tree

Insert 1, 2, 3, 4, 5, 6, 7, 8, 9 into an empty BST, in that order.

search(skewed, 9) = 9 comparisons · search(balanced, 9) = 3 comparisons

Every new value is larger than everything before it, so each one attaches as a right child of the previous node — the tree becomes a 9-node linked list with height 8. Inserting the same 9 values as [5, 3, 8, 2, 4, 7, 9, 1, 6] keeps the tree short (height 2), and search_steps() confirms it: 9 comparisons vs. 3 for the identical target, purely from insert order. This is the single most important BST caveat: a plain BST is only O(log n) if it stays balanced. Sorted (or nearly sorted) input makes it O(n) — no better than a linked list. Production code reaches for a self-balancing variant (AVL, Red-Black) specifically to prevent this. The gap holds for other targets too, measured the same way with search_steps(): target 1 takes 1 comparison in the skewed tree (an early hit near the root) but 4 comparisons in the balanced tree (1 sits four levels down as a leaf); target 5 takes 5 comparisons skewed but only 1 comparison balanced (5 is the balanced tree's root). Same nine values every time — only the insert order changes, and the comparison count swings by 4-9x.

Case B: delete a leaf (0-children case)

delete(root, 1) on the canonical tree — node 1 is a leaf.

Result: 8(3(_, 6(4, 7)), 10(_, 14(13, _)))

Node 1 has no children, so root.left is None is true immediately and the function returns root.right, which is also None. The parent (node 3) receives None back and its left pointer is simply cleared. This is the simple case the two-children delete traced above deliberately reduces itself down to.

Case C: searching for a value that is not present

search(root, 9) on the canonical tree — 9 was never inserted.

Result: False, after 2 comparisons

At node 8: 9 > 8 → go right to 10. At node 10: 9 < 10 → go left, but 10.left is None, so the loop variable node becomes None and the while-loop exits, returning False. Notice this is exactly the spot insert(root, 9) would have attached a new node — search and insert fail (or succeed) at the same empty slot.

How to derive this in an interview

Reasoning path

The problem needs ordered lookups, inserts, and deletes — a BST gives all three in O(h) via one shared rule.

State the invariant out loud: left < node < right, recursively — write it before any code.

Search and insert are the same walk; insert just keeps going until it finds an empty slot instead of a match.

Delete needs a case split on child count — 0/1 child is a splice, 2 children needs the in-order successor.

Mention balance: sorted input degenerates a plain BST to O(n) — call that out and name AVL/Red-Black as the fix.

What to say out loud

  • "I'll walk down comparing the target to the current node — smaller goes left, larger goes right, discarding half the remaining tree each step."
  • "Insert is the same walk, but landing on None means I create the node there instead of failing."
  • "For delete, I first find the node. 0 or 1 child, I splice it out directly. 2 children, I swap in the in-order successor's value and delete that successor instead — it's guaranteed to have at most one child."
  • "In-order traversal gives me sorted order for free — that's the single most useful consequence of the invariant."
  • "None of this is O(log n) unless the tree stays balanced. I'd call that out and mention AVL/Red-Black, or a hash map if I don't need ordering."

Common beginner coding mistakes

Search / Insert mistakes

  • Using <=/>= instead of strict </>, which silently changes duplicate handling.
  • Forgetting root.left = insert(root.left, val) — insert must rebuild the pointer chain on the way back up, not just recurse.
  • Writing two independent ifs instead of if / elif, which can process an equal value on both branches.
  • Assuming search is always O(log n) — it is O(h), and h can be n.

Delete mistakes

  • Copying the successor's value without also calling delete() on it — leaves a duplicate value in the tree.
  • Assuming the successor is always node.right itself — only true when that node has no left child.
  • Deleting the successor by value from the subtree instead of via a fresh recursive call — risks detaching part of that subtree.
  • Forgetting the caller must reassign delete's return value — the old subtree stays wired in otherwise.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Insert 1..9 into an empty BST in order, then insert the same 9 values as [5, 3, 8, 2, 4, 7, 9, 1, 6] into a second empty BST. How many comparisons does search(tree, 9) take in each?

Answer: 9 comparisons in the sorted-insert tree (it degenerates into a 9-node right-leaning chain, height 8) versus 3 comparisons in the second tree (height 2). Same 9 values, same target — the 3x difference comes entirely from insert order, which is why real systems use self-balancing BSTs.

Practice 2 — On the canonical tree, what does delete(root, 8) — deleting the root — produce?

Answer: 10(3(1, 6(4, 7)), 14(13, _)). Root 8 has two children, so its successor is the leftmost node of its right subtree — node 10 itself, since 10 has no left child. Root's value becomes 10, then delete(root.right, 10) removes the original node 10 by returning its right child (the 14-subtree), which becomes the new root's right child.

Practice 3 — The two-children delete case guarantees the in-order successor never has a left child. Why is that always true, and why does it matter?

Answer: the successor search is succ = node.right; while succ.left: succ = succ.left — by definition, that loop only stops when succ.left is None. It matters because it collapses the "hard" two-children deletion into the "easy" 0-or-1-child case for the nested delete(node.right, succ.val) call — no additional case logic is ever needed for the successor itself.

Final takeaway

A Binary Search Tree is one invariant — left < node < right, recursively — applied consistently to search, insert, and delete. Search and insert are literally the same walk with different stop conditions. Delete is the same walk plus one extra idea: when a node has two children, swap in its in-order successor and let the easy case clean up the rest. None of it is fast unless the tree stays short — that single caveat is worth saying out loud in every interview.
