Two Pointers and Sliding Window

Both techniques replace an O(n²) nested loop with two indices that only ever move forward. This page traces the real code step by step: converging pointers that close in on a sorted array from both ends, and a variable-size window that expands right and shrinks left — and explains why a loop that looks nested is still only O(n) total work.

Why this matters

Pair-matching on sorted data

Two-sum on a sorted leaderboard, matching merged log timestamps, or Container With Most Water all reduce to the same converging-pointer shape.

Constraint-bound substrings/subarrays

Longest substring without repeats, minimum window substring, and longest subarray with at most K distinct values are all one sliding window with a different validity rule.

Interview reuse

Once you own these two shapes, 3Sum, Trapping Rain Water, and Minimum Size Subarray Sum become small edits, not new algorithms.

Instructor note: the reason these problems feel different from a brute force is not cleverness — it is a proof about how many times each index can possibly move. Learn that proof once and it applies to both patterns.

What are two pointers and sliding window?

Two pointers — converging from both ends

One pointer starts at index 0, the other at the last index. Each step looks at both values together and moves exactly one pointer inward, based on a comparison that a sorted array makes decisive.

Sliding window — variable-size, moving right

Both pointers start at the left. right expands the window to include more; left shrinks it only when the window becomes invalid. Neither pointer ever moves backward.

Beginner shortcut — eligibility: converging pointers need a sorted array (or one you sort first) — that is what makes "move the wrong side" a forced, correct decision instead of a guess. A sliding window needs a monotone validity condition: once the window is valid, growing it never breaks it, and once it is invalid, shrinking is the only fix. If either property is missing, the technique does not apply.

Step-by-step thinking process

1

Identify the shape

Is it "find a pair/triple in sorted data" (converging pointers) or "find the best contiguous run under a constraint" (sliding window)?

2

Name the forced decision

For converging pointers: what does the sorted order tell you about which side to move? For a window: what condition makes it invalid?

3

Write a loop that only advances

Never reset a pointer backward and never rescan. One comparison decides exactly one pointer move.

4

Keep the running state in sync

Update the sum, the seen-map, or the counter the instant a pointer moves — never recompute it from scratch.

How the input becomes the working structure

Beginners often picture these techniques as "two loops," but nothing is nested in the way a brute force is. The input becomes a pair of positions plus a small piece of running state that travels with them.

Sorted array → two ends

lo starts at index 0, hi starts at the last index. Both are valid starting candidates because sorted order guarantees a direction to move.

Raw string → empty window

left and right both start at index 0. The running state (seen) starts empty because nothing has been read yet.

Each step reads exactly one new fact

For converging pointers, one comparison decides which single pointer moves. For the window, right always advances and left advances only while the window is invalid.

State updates travel with the pointers

The sum comparison and the seen map are always current for wherever the pointers are right now — nothing is ever re-derived from index 0.

Critical point: the "window" is never rebuilt from scratch. It is edited by exactly one element at a time — one value enters when a pointer advances, at most one value leaves when the other pointer catches up.

Method 1: Two pointers — converging from both ends (Two Sum on a sorted array)

Because arr is sorted, the current sum tells you everything you need: too big means the right value must shrink, too small means the left value must grow. There is never a reason to try both at once.

def two_sum_sorted(arr, target): """arr is SORTED. Find two indices whose values sum to target.""" lo, hi = 0, len(arr) - 1 while lo < hi: s = arr[lo] + arr[hi] if s == target: return [lo, hi] elif s < target: lo += 1 # sum too small -> need a bigger left value else: hi -= 1 # sum too big -> need a smaller right value return []

Key mental model

Sorted order means the current sum tells you, with certainty, which single pointer is wrong — you never need to try both.

Common mistake

Running this on an unsorted array. Without sorted order, "sum too big → move hi" is not guaranteed to preserve the true answer.

Why O(n), not O(n²)

Every step moves exactly one pointer inward by one, and lo and hi can each move at most n times before they meet — total movement is bounded by n, not n².

Method 2: Sliding window — variable size (Longest Substring Without Repeating Characters)

right expands the window by one character every iteration. The moment that character has already been seen inside the current window, the window is invalid — left jumps forward just far enough to fix it, then the best length is updated.

def longest_substring_without_repeat(s): seen = {} # char -> most recent index left = best = 0 for right, ch in enumerate(s): if ch in seen and seen[ch] >= left: left = seen[ch] + 1 # shrink: jump left past the previous occurrence seen[ch] = right best = max(best, right - left + 1) return best

Key mental model

The window never resets to empty on a repeat — left jumps to exactly one past the earlier occurrence, so no valid substring is skipped.

Common mistake

Checking ch in seen alone without seen[ch] >= left. A character seen before the current window started is stale and must not trigger a shrink.

Why O(n), not O(n²)

right advances exactly n times; left also only ever advances, and across the whole run it moves at most n times total — not n times per step of right.

Edge cases you should test

Case A: no valid answer exists

two_sum_sorted([1, 2, 4, 7, 11, 15], target=100)

Answer = []

lo keeps advancing (every sum is still too small) until lo == hi, and the loop exits without ever returning. The function must explicitly return [] after the loop — there is no pair to find.

Case B: the whole input is the answer

longest_substring_without_repeat("abcdef")

Answer = 6

Every character is unique, so the shrink condition (ch in seen and seen[ch] >= left) never fires. left stays at 0 for the whole run and the window grows to cover the entire string.

Case C: all-identical elements

longest_substring_without_repeat("bbbbb")

Answer = 1

Every new b is a repeat of the one right before it, so left jumps forward on every single step. The window never grows past length 1 — this is the case that most exposes an if-instead-of-correct-jump bug.

All three non-brute-force methods rely on the same truth: once you can prove a pointer never needs to move backward, the total number of pointer moves is bounded by n, not n².

How to derive this in an interview

Reasoning path

Start with the brute force: nested loops checking every pair or every substring. This is the safe, obviously-correct baseline.

Notice the redundant work: fixing a left index and rescanning the rest re-derives the same "too small / too big" information over and over.

Ask whether moving one side ever lets you safely skip the other — sorted order answers this for two-sum; a monotone validity rule answers it for a window.

Replace the nested loop with two indices that only ever advance — same correctness, O(n) instead of O(n²).

State out loud why no valid pair or window is ever skipped — this is the part interviewers actually probe.

What to say out loud

  • "My brute force is O(n²) because for every left index I rescan the rest of the array or string — that's wasted, repeated work."
  • "The array is sorted, so I know moving lo right only grows the sum and moving hi left only shrinks it — that determinism is what lets me discard one comparison per step instead of keeping every pair on the table."
  • "For the window, once it's invalid, shrinking is the only fix, and once it's valid, growing is always safe — that monotonic property is what lets a while loop replace a full rescan."
  • "Each pointer moves at most n times total across the whole run, so total work is O(n), not O(n²), even though there's a loop inside a loop."

Common beginner coding mistakes

Sliding window mistakes

  • Shrinking with if instead of while — one if only fixes a single violation; some constraints need repeated shrinking to become valid again.
  • Forgetting to update the running state (the seen map or a counter) the moment a pointer moves — the validity check then silently goes stale.
  • Comparing for the "best" answer before updating the window's state for this step, so the score reflects the previous window instead of the current one.
  • Resetting the window to empty on a repeat instead of jumping left to exactly one past the earlier occurrence — this quietly turns O(n) into O(n²).

Two-pointer mistakes

  • Using converging two pointers on unsorted data — without sorted order, "sum too big → move hi" has no guarantee of correctness.
  • Moving both pointers on the same step instead of exactly one — this can step over the actual answer.
  • Using lo <= hi instead of lo < hi, letting a pointer compare an index against itself.
  • Forgetting to handle "no answer" — the loop just ends when the pointers meet; it does not signal that on its own.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Trace two_sum_sorted([1, 3, 4, 5, 7, 10, 11], target=9) by hand. What indices does it return?

Answer: [2, 3]. Trace: lo=0(1),hi=6(11) sum 12 > 9 → hi--; hi=5(10) sum 11 > 9 → hi--; hi=4(7) sum 8 < 9 → lo++; lo=1(3),hi=4(7) sum 10 > 9 → hi--; hi=3(5) sum 8 < 9 → lo++; lo=2(4),hi=3(5) sum 9 == 9 → return [2, 3] (4 + 5 = 9).

Practice 2 — What does longest_substring_without_repeat("dvdf") return, and why isn't the answer "dvd" reset from scratch at the second d?

Answer: 3 (the substring "vdf"). At right=2 the character d repeats (last seen at index 0), so left jumps to exactly 1 — one past the stale d — not back to 0 and not forward to 3. That precise jump is what lets the algorithm find "vdf" at right=3 instead of undercounting or overcounting the window.

Practice 3 — Why doesn't converging two pointers need a while-style shrink loop the way sliding window does?

Answer: because each iteration compares exactly one pair of values and resolves it with exactly one pointer move — there is no notion of a "currently invalid window" that might need several fixes in a row. The outer while lo < hi already is the only loop needed; nesting another loop inside it would just repeat work the single comparison already settled.

Final takeaway

A loop inside a loop is not automatically O(n²) — what matters is how many times each index can possibly move. Converging pointers and sliding windows both guarantee that every index enters and leaves consideration at most once across the whole run, so total pointer movement is bounded by n. That single proof is why both techniques replace a brute-force nested scan with genuinely O(n) work.
