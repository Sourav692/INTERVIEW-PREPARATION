Sorting Algorithms

Sorting is the most-used subroutine in computer science, and the property beginners forget to ask about is stability — whether equal elements keep their original order. This page traces two real, hand-written sorts on the same seven-element array: merge sort's two-pointer merge, and quicksort's index-by-index partition, so you can see exactly what changes in memory at every step.

Canonical example

a = [5, 3, 8, 1, 9, 2, 7]

sorted(a) = [1, 2, 3, 5, 7, 8, 9]

Why this matters

Every "sort by column" UI

Spreadsheets, issue trackers, and admin dashboards all rely on a stable sort so that sorting by a second column doesn't scramble ties from the first.

Unlocks binary search

Once data is sorted, you can search it in O(log n), merge two datasets in one linear pass, or find duplicates by scanning adjacent pairs.

Interview reuse

Merge sort's two-pointer merge is the same skeleton behind Merge Intervals and Merge K Sorted Lists. Quicksort's partition is the same skeleton behind Kth Largest Element (quickselect).

Instructor note: almost nobody asks you to hand-roll a sort in a real interview. They ask you to reason about which sort, its complexity, and — most often — whether Python's built-in sorted() already solves the problem with the right key= function.

What is sorting?

What it costs

Any sorting algorithm that only compares elements pairwise cannot beat O(n log n) in the worst case. There are n! possible orderings of n elements, and each comparison narrows the possibilities by at most half — so you need at least log2(n!) = O(n log n) comparisons to tell every ordering apart. This is a hard floor, not an implementation detail.

Stability, defined plainly

A sort is stable if two elements that compare equal keep the same relative order they had before sorting. Merge sort is stable because its merge step takes from the left side on ties. Quicksort is not, because swaps during partitioning can jump an equal element past another one.

Beginner shortcut: if the interviewer says "sort by status, then by assignee, independently" — that is a stability question, not a comparator question. Sort once per column, least significant column first, and let stability carry the earlier order through as the tiebreak.

Step-by-step thinking process

1

Decide: build it, or call sorted()?

If the interviewer just needs sorted data as a step toward something else, use sorted() and spend your time on the key= function.

2

Pick a strategy

Divide the array and merge sorted halves back together, or pick a pivot and partition around it. Same goal, two different mechanics.

3

Nail the base case

An array of length 0 or 1 is already sorted by definition — every recursive sort bottoms out here.

4

Track what moves

Merging appends without ever reordering equal ties. Partitioning swaps in place, which is exactly what breaks stability.

How the input becomes the working structure

Both algorithms start from the same flat array. Merge sort's recursion repeatedly halves it by index until every piece is a single element — that recursion tree is the shape both traces below are built on.

Input array

a = [5, 3, 8, 1, 9, 2, 7] idx 0 1 2 3 4 5 6
→

Recursion tree of splits

Level 1: split at mid = 7 // 2 = 3

a[0:3] = [5,3,8] goes left, a[3:7] = [1,9,2,7] goes right.

Level 2: split each half again

[5,3,8] → [5] and [3,8]. [1,9,2,7] → [1,9] and [2,7].

Level 3: reach base cases

[3,8] → [3],[8], [1,9] → [1],[9], [2,7] → [2],[7]. Every leaf is length ≤ 1 — already "sorted" by definition.

Now merge back up

The recursion unwinds and every pair of sibling leaves gets merged, then those results get merged, all the way back to one sorted array of 7. This unwind is exactly what Method 1 traces below.

Critical point: quicksort never builds this tree explicitly — it partitions the array in place and only recurses into the two resulting sides. Same "divide" idea, opposite mechanics: merge sort does the work on the way back up, quicksort does the work on the way down.

Method 1: Merge sort — split, sort halves, merge

Split the array in half recursively until every piece is a single element (already sorted), then merge sorted pieces back together two at a time. All the real work — every comparison — happens in merge(), using two pointers that each walk one sorted half.

def merge(left, right): result, i, j = [], 0, 0 while i < len(left) and j < len(right): if left[i] <= right[j]: result.append(left[i]); i += 1 else: result.append(right[j]); j += 1 return result + left[i:] + right[j:] def merge_sort(a): if len(a) <= 1: return a mid = len(a) // 2 return merge(merge_sort(a[:mid]), merge_sort(a[mid:]))

Key mental model

Two pointers, i into left and j into right, only ever move forward. Each comparison places exactly one element into the result — the merge never revisits a decision.

Common merge sort mistake

Using < instead of <= in the comparison. That single character is what makes merge sort stable — with strict <, ties would start pulling from right instead of left, breaking original order.

Why the extra space matters

Each merge builds a brand-new list rather than shuffling in place — that's the O(n) auxiliary space cost, and it's exactly what makes stability possible. Quicksort skips this cost by swapping in place, but loses stability as a result.

Method 2: Quicksort — partition around a pivot

Pick a pivot (here, the last element), and rearrange the array in one linear pass so that everything <= pivot ends up left of it and everything else ends up right of it — then recursively partition each side. No merge step: the array is sorted in place, and the pivot lands in its final position the moment its partition call finishes.

def partition(a, lo, hi): pivot = a[hi] i = lo - 1 for j in range(lo, hi): if a[j] <= pivot: i += 1 a[i], a[j] = a[j], a[i] a[i + 1], a[hi] = a[hi], a[i + 1] return i + 1 def quicksort(a, lo=0, hi=None): if hi is None: hi = len(a) - 1 if lo < hi: p = partition(a, lo, hi) quicksort(a, lo, p - 1) quicksort(a, p + 1, hi) return a

Key mental model

i is the boundary of "confirmed <= pivot" territory. Every time j finds a small-enough element, i advances by one and that element gets swapped into the confirmed zone.

Common quicksort mistake

Forgetting the final swap (a[i+1], a[hi] = a[hi], a[i+1]). Without it, the pivot never actually moves out of index hi into its true sorted position.

Why the pivot choice matters

Picking the last element is simple but fragile: on an already-sorted array it always produces the most lopsided possible split, which is exactly the worst case below.

Edge cases you should test

Case A: already-sorted input, naive last-element pivot

a = [1, 2, 3, 4, 5, 6, 7]

Quicksort degrades to O(n²) · merge sort stays O(n log n)

With pivot = last element, every partition call picks the largest remaining value as pivot. The "left of pivot" side always contains everything except the pivot itself, so the recursion depth is n instead of log n — this is exactly the case the notebook tests with already_sorted = list(range(50)). Median-of-three or random pivot selection avoids this; merge sort is completely unaffected because its split point never depends on the data.

Case B: all duplicate values

a = [4, 4, 4, 4, 4, 4]

Quicksort partitions everything to one side · merge sort unaffected, and still stable

Because the condition is a[j] <= pivot, every element counts as "belongs on the left," so i advances on every iteration and the pivot always lands at the very last index — the same lopsided shape as the sorted-input case. Merge sort doesn't care: it still splits by position, not by value, and its stability guarantee means five equal 4's keep whatever order they started in.

Case C: single element or empty array

a = [7] and a = []

Both return immediately, unchanged

merge_sort hits len(a) <= 1 and returns a as-is. quicksort hits lo < hi as false (for a single element, lo == hi; for empty, there's no valid hi to even reach the check) and returns immediately. Every recursive call in both algorithms eventually bottoms out here — it's worth tracing by hand once.

Timsort's O(n) best case comes from detecting already-sorted "runs" in the data; it extends short runs with insertion sort, then merges them the way merge sort does — a hybrid that inherits merge sort's stability without merge sort's guaranteed O(n) space in the common case.

How to derive this in an interview

Reasoning path

First question: do I actually need to hand-roll a sort, or just sorted data? Nine times out of ten, it's sorted(data, key=...).

If they want an implementation, ask: does order of equal elements matter? If yes, merge sort. If no, quicksort is usually faster in practice and uses less memory.

If they push on worst case: quicksort with a bad pivot on sorted/duplicate-heavy input degrades to O(n²) — mention random or median-of-three pivots as the fix.

If it's a "sort by multiple columns" question, that's a stability question — sort least-significant key first, most-significant key last.

What to say out loud

  • "Unless you need me to implement it, I'd just call sorted() here and focus on getting the key= function right."
  • "Merge sort guarantees O(n log n) and is stable, at the cost of O(n) extra space for the merge buffers."
  • "Quicksort is in-place and fast on average, but a naive last-element pivot is O(n²) on sorted or duplicate-heavy input — I'd randomize the pivot to avoid that."
  • "Since I need to sort by status then by assignee independently, I'll rely on stability: sort by assignee first, then by status."

Common beginner coding mistakes

Merge sort mistakes

  • Using < instead of <= in the merge comparison, which silently breaks stability.
  • Forgetting the leftover-append (left[i:] + right[j:]) — one side almost always finishes before the other.
  • Recomputing len(a) or mid inside the loop instead of once, wasting work on every call.
  • Assuming the base case is len(a) == 0 only — a single-element array must also return immediately.

Quicksort mistakes

  • Forgetting the final swap that moves the pivot from a[hi] into its true position at a[i+1].
  • Recursing on (lo, p) and (p, hi) instead of (lo, p-1) and (p+1, hi) — that re-includes the already-placed pivot and causes infinite recursion.
  • Always picking the last element as pivot in production code, ignoring the sorted-input O(n²) trap.
  • Assuming quicksort is stable because it "looks like" it preserves order on small examples — the in-place swaps can and do reorder equal elements.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Merging left = [2, 4, 6] and right = [1, 3, 5], what are the first three values appended to result?

Answer: 1, 2, 3. Compare 2 vs 1 → take 1 (right). Compare 2 vs 3 → take 2 (left). Compare 4 vs 3 → take 3 (right). The two pointers only ever move forward, one comparison per step.

Practice 2 — Why does quicksort with a "pivot = last element" strategy become O(n²) on a = [1, 2, 3, 4, 5]?

Answer: on sorted input, the last element is always the largest remaining value, so every element satisfies a[j] <= pivot and the pivot always lands at the very end of its current range. Every partition call only removes one element (the pivot) from further recursion, giving n recursive levels instead of log n — O(n) work per level times n levels is O(n²).

Practice 3 — You sort a list of dicts by "score" (ascending), then by "team" (ascending), using sorted() twice. Does the score order survive within a team?

Answer: Yes — because sorted() is stable (Timsort). The first pass establishes ascending score order; the second pass reorders by team but never disturbs the relative order of elements that share the same team, so within each team the entries stay in the score order the first pass produced. This is the exact multi-key trick: sort least-significant key first, most-significant key last.

Final takeaway

Merge sort and quicksort both divide the array, but the work happens on opposite ends of the recursion: merge sort does its work on the way back up — two pointers walking two already-sorted halves, stable because ties always take from the left. Quicksort does its work on the way down — one pass partitioning around a pivot, in place, fast on average but not stable and vulnerable to a bad pivot. In practice, reach for sorted() first and argue about the key= function; reach for these two only when an interviewer explicitly asks you to build the sort itself.
