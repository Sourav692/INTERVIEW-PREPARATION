Graph Fundamentals

A graph is just vertices and the edges between them. This page traces the real Graph class from the notebook: building an adjacency list edge by edge with add_edge, reading structure off it with degree / in_degree / out_degree, and answering "can I reach it at all" with path_exists — an iterative DFS that needs something a tree traversal never did: a visited set.

Canonical example

edges = [("A","B"),("A","D"),("B","C"),("B","E"),("C","F"),("D","E"),("E","F")]

6 vertices · 7 edges · degree(B) = 3 · path A → F: True

Why this matters

Social and friend graphs

People are vertices, "is friends with" is an undirected edge. degree(you) is literally your friend count.

Road and network maps

Intersections are vertices, roads are edges. "Can I drive from A to F" is exactly path_exists.

Dependency graphs

Courses, tasks, or build targets are vertices; "must finish before" is a directed edge — now in-degree and out-degree mean different things.

Instructor note: a tree is a connected, acyclic graph — a special case with extra rules. Everything you learned about tree traversal still applies here, except now the structure can loop back on itself, and that single fact is what drives every design decision below.

What is a graph?

Simple definition

A graph is a set of vertices (the things) and a set of edges (the connections between pairs of things). Nothing more is required for something to qualify as a graph.

What you're computing

You're building an adjacency list — a map from each vertex to the set of vertices it's directly connected to — then reading two things off that map: degree (how many neighbours a vertex has) and reachability (can you walk from one vertex to another at all).

Beginner shortcut: if you can draw dots with lines between them, you already have a graph. Undirected means each line can be walked in either direction — so storing it needs two pointer insertions per edge, one for each end. Directed means the line is an arrow — store it once, but now "edges touching me" splits into "edges I point to" (out-degree) and "edges pointing at me" (in-degree).

Step-by-step thinking process

1

Read the edge list

Decide up front: is this relationship mutual (undirected) or one-way (directed)? That single choice changes how add_edge behaves.

2

Build the adjacency list

Call add_edge once per pair. Undirected edges update both endpoints' neighbour sets; directed edges update only one.

3

Read structure off the map

degree(u) is len(adj[u]) — free once the list exists. in_degree(u) has no shortcut; it has to scan every other vertex's list.

4

Ask reachability questions with a visited set

Walk from a start vertex with DFS or BFS. Unlike a tree, a graph can have cycles — so you must remember every vertex you've already left.

How the input becomes an adjacency list

The notebook hands you a flat list of pairs. Before degree or path_exists can run, that list has to become a dictionary of neighbour sets — this is the step beginners skip past too quickly.

Input edges

edges = [ ("A","B"), ("A","D"), ("B","C"), ("B","E"), ("C","F"), ("D","E"), ("E","F") ]
→

Adjacency list

A: {B, D} B: {A, C, E} C: {B, F} D: {A, E} E: {B, D, F} F: {C, E}

Read ("A","B")

Add B to A's set, and add A to B's set — the undirected branch fires on every single edge.

Read ("A","D"), ("B","C"), ("B","E")

Each new pair either adds a neighbour to an existing vertex or introduces a brand-new one. By the third edge, B already has two neighbours.

Read ("C","F"), ("D","E"), ("E","F")

The last three edges close the shape into a 2×3 grid: every vertex now has either 2 or 3 neighbours, and no vertex is left isolated.

Critical point: because the graph is undirected, every add_edge(u, v) call is really two writes — adj[u].add(v) and adj[v].add(u). Forget the second one and the graph silently becomes directed.

Method 1: building the adjacency list and reading degree

Every edge is processed once. Because the graph is undirected, add_edge writes both directions. Once every edge has been added, degree(u) is nothing more than len(g.adj[u]) — the size of the neighbour set built during construction.

from collections import defaultdict class Graph: def __init__(self, directed=False): self.directed = directed self.adj = defaultdict(set) def add_edge(self, u, v): self.adj[u].add(v) if not self.directed: self.adj[v].add(u) def degree(g, u): return len(g.adj[u]) g = Graph(directed=False) edges = [("A","B"), ("A","D"), ("B","C"), ("B","E"), ("C","F"), ("D","E"), ("E","F")] for u, v in edges: g.add_edge(u, v) for v in sorted(g.adj): print(f"degree({v}) = {degree(g, v)}")

Key mental model

add_edge doesn't record one fact — for an undirected graph it always records two: "u sees v" and "v sees u." Skip the second write and the graph becomes silently directed.

Common mistake

Confusing "edges in the input list" with "entries written to the adjacency list." Seven edges produced fourteen set insertions — two per edge — because the graph is undirected.

Why the data structure matters

A set, not a list, backs each vertex's neighbours. That's what makes add_edge idempotent — adding the same edge twice never inflates degree() — and what makes degree() an O(1) len() call instead of a scan.

Method 2: path_exists — DFS with an explicit stack and a visited set

To answer "can I get from start to goal," push start onto a stack and pop until you either find goal or run out of vertices to try. The neighbours of a popped vertex go straight onto the stack — including vertices already seen. That's exactly why the if u in seen check has to happen on pop, not on push.

Reproducibility note: the real g.adj[u] is a Python set, whose iteration order isn't guaranteed. For this trace, neighbours are expanded in sorted order (stack.extend(sorted(g.adj[u]))) purely so the walk is deterministic on the page. Either order still finds a valid path when one exists — only the specific path found can differ.

def path_exists(g, start, goal): seen, stack = set(), [start] while stack: u = stack.pop() if u == goal: return True if u in seen: continue seen.add(u) stack.extend(g.adj[u]) return False

Key mental model

seen is checked exactly once, right after a vertex is popped, before its neighbours get pushed. That single check is the only thing standing between this function and an infinite loop.

Common mistake

Checking seen before pushing instead of after popping. Checking on pop is simpler and is exactly what this code does — a vertex can be pushed many times, but it only ever gets processed once.

Why the visited set matters

Trees never needed this set — a tree has exactly one path between any two nodes, so DFS can never walk back to a node it already left. This graph has two cycles (A-B-E-D-A and B-C-F-E-B), so without if u in seen: continue, the traversal would keep re-expanding the same vertices along those cycles forever.

Method 3: the vocabulary tour — degree, path, cycle

Every graph term you'll ever use is answerable by reading the same adjacency list a different way. degree(u) counts entries in one neighbour set. A path is a sequence of vertices where every consecutive pair is a real edge — v in adj[u], checked over and over. A cycle is exactly that same kind of chain, except the last vertex has to be the first vertex again. This trace steps through all three on the canonical grid graph so you see what the words mean instead of just reading a definition.

adj = { "A": {"B", "D"}, "B": {"A", "C", "E"}, "C": {"B", "F"}, "D": {"A", "E"}, "E": {"B", "D", "F"}, "F": {"C", "E"}, } vertices = sorted(adj) edges = [("A","B"), ("A","D"), ("B","C"), ("B","E"), ("C","F"), ("D","E"), ("E","F")] degree_B = len(adj["B"]) # neighbours: A, C, E path = ["A", "B", "E", "F"] for u, v in zip(path, path[1:]): assert v in adj[u] # every step is a real edge cycle = ["A", "B", "E", "D", "A"] for u, v in zip(cycle, cycle[1:]): assert v in adj[u] # every step is a real edge assert cycle[0] == cycle[-1] # returns to start

Key mental model

Degree, path, and cycle aren't three different data structures — they're three different questions you can ask of the same adjacency list: "how many neighbours does this vertex have," "is there a chain of real edges between these two vertices," and "does that chain loop back to where it started."

Common mistake

Treating the highlighted path or cycle as the only one. A → B → E → F is one valid path from A to F on this graph — A → D → E → F is a different, equally valid one. "A path exists" and "this is the path" are two different claims; path_exists in Method 2 only answers the first.

Why the data structure matters

Because adj[u] is a set, checking whether the next hop is a real edge — v in adj[u] — is an O(1) lookup. That single check is exactly what both the path loop and the cycle loop above are built from, and it's the same check path_exists uses internally on every pop.

Graph types: undirected → directed → weighted

Same six vertices, same seven connecting pairs — three different graphs, because add_edge and the neighbour sets it writes change shape each time. Watch what happens to the same canonical graph as it goes from undirected to directed to weighted.

Undirected

Each line is mutual — add_edge(u, v) writes both adj[u].add(v) and adj[v].add(u).

Directed

Same pairs, now one-way — add_edge(u, v) writes only adj[u].add(v). In-degree and out-degree can now differ.

Weighted

Each edge now carries a cost — adj[u].add((v, weight)) stores a tuple instead of a bare vertex. "Shortest" means cheapest total weight, not fewest edges.

When you'd use each: undirected for mutual relationships (friendships, two-way roads — degree() is symmetric). Directed for one-way relationships (follows, prerequisites, one-way streets — now in_degree and out_degree can differ). Weighted whenever the connection itself has a cost (distance, latency, price) and "shortest" has to mean cheapest, which is what pulls Dijkstra or Bellman-Ford into the picture instead of plain BFS.

DAG — directed + acyclic

The directed diagram above happens to have zero cycles — every arrow goes from an earlier letter to a later one, so nothing ever points back. That makes it a DAG: it can be topologically sorted into a valid order (here, simply A, B, C, D, E, F), which is exactly the shape of a build pipeline or a course-prerequisite chart.

Bipartite

A graph is bipartite if its vertices split into two groups with edges only crossing between the groups, never within one. This canonical graph actually is: group {A, C, E} and group {B, D, F} — every one of the 7 edges connects one group to the other. Useful for matching problems and 2-colouring.

Sparse vs dense

6 vertices means a spanning tree needs 5 edges (the minimum to stay connected) and a complete graph would need 15 (V(V−1)/2). This graph has 7 — just 2 above the minimum, nowhere near the 15-edge maximum. That's sparse, and it's exactly why the whole page stores it as an adjacency list rather than a V×V matrix.

Edge cases you should test

Case A: directed graph — in-degree vs out-degree

dg = Graph(directed=True), edges [("X","Y"),("Y","Z"),("Z","X")] — a pure 3-cycle of one-way arrows.

out(X)=1 · in(X)=1 · every vertex: out=1, in=1

Because the graph is directed, add_edge only writes one direction, so out_degree(u) = len(g.adj[u]) is free — but in_degree(u) has no reverse index to read from. It has to scan every other vertex's neighbour set looking for u, which is O(V + E) instead of O(1). That asymmetry is the entire reason directed graphs get two separate degree functions.

Case B: disconnected graph — an unreachable vertex

g2.add_edge("P","Q"), then g2.adj["Z"] is touched directly (so Z exists in the adjacency list with zero neighbours).

path_exists(g2, 'P', 'Z') = False (after 3 steps, 1 seen-skip)

The DFS explores every vertex actually reachable from P — that's just P and Q — then the stack empties and the function returns False. Z exists as a key in the adjacency list (via defaultdict), but "exists in the structure" and "reachable from P" are not the same thing.

Case C: a cycle forces the visited set to fire repeatedly

On the canonical graph, path_exists(g, "A", "Q") where Q was never added — the goal can never match, so DFS must exhaust the entire component.

Returns False after 15 pops · 9 of them skipped by the visited-set guard

This run walks both cycles in the grid (A-B-E-D-A and B-C-F-E-B). Vertex B alone gets pushed onto the stack three separate times. Every one of those 9 "already seen" skips is the if u in seen: continue line doing its job — delete that line, and this exact graph would re-expand B, D, E, A, C, F over and over, forever.

How to derive this in an interview

Reasoning path

The problem gives me pairs of related things — that's an edge list.

I need fast neighbour lookups, and most real graphs are sparse, so I'll use an adjacency list (dict of sets), not a matrix.

Is the relationship mutual or one-directional? Undirected: write both directions in add_edge. Directed: write once, and now in-degree ≠ out-degree.

Do I need "is X connected to Y at all"? That's DFS or BFS from X with a visited set.

Could I ever revisit a vertex without that visited set? Yes — that's exactly what happens on any graph with a cycle. That's why the check is not optional.

What to say out loud

  • "I'll store this as an adjacency list — a dict from vertex to its set of neighbours — because most real graphs are sparse, and this gives O(1) neighbour lookups without wasting O(V²) space on a matrix."
  • "Since the graph is undirected, every add_edge call has to update both endpoints, or half the graph becomes invisible from the other side."
  • "For reachability, I'll do an iterative DFS with an explicit stack, but the visited set is not optional — trees never needed one because they have no cycles, but this graph does, so without it the traversal can walk in circles forever."

Common beginner coding mistakes

Building the graph — mistakes

  • Only calling adj[u].add(v) for an undirected graph and forgetting the reverse write — half the graph becomes invisible from the other direction.
  • Using a list instead of a set for neighbours, so re-adding the same edge twice silently inflates degree().
  • Confusing degree() (undirected) with out_degree() — they only happen to be equal because this particular class reuses the same len(g.adj[u]) logic.
  • Computing in_degree(u) by reading adj[u] directly — that only gives what u points to, not what points to u; it requires scanning every OTHER vertex's list.

path_exists / DFS — mistakes

  • Forgetting the visited set entirely — on a graph with a cycle, this causes the traversal to loop forever instead of terminating.
  • Checking if u in seen only when pushing, not when popping — a vertex can (and will) be pushed multiple times before it's ever popped; the check has to happen on pop.
  • Assuming path_exists returning False means the whole graph is disconnected — it only means goal isn't reachable from this particular start; a different pair in the same graph might still be connected.
  • Checking if u == goal after the seen check instead of before it — order matters, especially for the edge case where start == goal.

Practice questions

Try these first in your head. Then open the answer only after you commit to a guess.

Practice 1 — Given the undirected edges [("A","B"), ("B","C")], what is degree("B")?

Answer: 2. Each edge is undirected, so add_edge("A","B") gives B the neighbour A, and add_edge("B","C") gives B the neighbour C. adj["B"] = {A, C}, so degree(B) = len({A, C}) = 2.

Practice 2 — On the canonical grid graph, does path_exists(g, "C", "D") return True? Roughly how many pops does it take?

Answer: True, in 5 pops (1 of them a seen-skip). Run for real: pop C (new, push [B,F]) → pop F (new, push [C,E]) → pop E (new, push [B,D,F]) → pop F again (already seen, skip) → pop D, which equals the goal → return True. The whole graph is one connected component (it's a 2×3 grid with no isolated vertex), so every pair of vertices is mutually reachable.

Practice 3 — Suppose add_edge only ever ran self.adj[u].add(v), even for an undirected graph. After add_edge("A","B") and add_edge("C","A"), what would degree("A") report?

Answer: 1, not 2 — even though two edges visually touch A. add_edge("A","B") writes adj[A].add(B), so adj[A] = {B}. But add_edge("C","A") writes adj[C].add(A) — A is the second argument, so nothing is ever written to adj[A] for that edge. Without the "if not self.directed" reverse write, a vertex's degree becomes "how many edges I was listed first in," not "how many edges actually touch me." This is exactly the bug the undirected branch exists to prevent.

Final takeaway

A graph is nothing more than vertices and edges — but two decisions shape everything you build on top of it: directed or undirected (does add_edge write one direction or two?), and does it have cycles (do you need a visited set to avoid walking in circles forever?). Trees answered "no" to that second question by definition. Graphs don't get that guarantee for free — path_exists earns it with one line: if u in seen: continue.
