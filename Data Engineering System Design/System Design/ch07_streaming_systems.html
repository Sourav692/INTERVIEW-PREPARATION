Streaming Systems

Streaming isn't "batch, but faster." It's a different set of promises — about which clock you trust, how late data is allowed to be, and what happens when something fails partway through.

Printed as "Chapter Six" in the book's own running heads — see the numbering note in Chapter 3. This guide cites it as Chapter 7.
The Simple Version, First

Think of the difference between a live sports scoreboard (updates the second a goal is scored) versus a newspaper box score (printed once, the next morning). That's batch vs. streaming.

Streaming isn't just "batch, but faster." It's a completely different set of promises about which clock you trust, how late data can be, and what happens on failure. Picking it because it sounds impressive — without understanding those promises — is how teams end up maintaining something complicated for a problem batch could've solved more cheaply.

Why Two Teams Both Say They Built "Streaming" — But Only One Did

Two teams both need real-time analytics. Both ship. Both have dashboards that refresh every few seconds. Both call what they built "streaming."

Team A runs a small job every 30 seconds and has the dashboard read the latest result. Works great — until data gets bigger or someone needs faster updates.

Team B built something where data flows through continuously, a processing engine keeps a running tally per key, and results save the instant they're ready. Harder to build and debug — but it can handle far more data and update in well under a second.

Neither team is wrong. The real question is whether the team understood what they signed up for. That's what this chapter is about.

Idea 1: There Are Three Different Clocks, and They Disagree

Imagine watching a hockey game on a 30-second broadcast delay. Something happens on the ice at 8:00:00 PM. It reaches your TV at 8:00:30 PM. You notice it at 8:00:32 PM, because you were getting a snack. Three different points in time, for the exact same event.

Most business questions mean event time — when it actually happened. Most naive implementations accidentally use processing time instead, because it's easier to code. That mismatch is where a lot of subtly wrong dashboards come from.

Idea 2: A Watermark Is Just an Honest Promise About How Late You'll Wait

Imagine hosting a potluck: "food starts at 7 PM." At 7:05, two people say they're running a little late. Do you wait? You draw a line: "we'll wait until 7:15, then start without you." That line is a watermark — your system saying "I'm willing to wait this long for late data, and after that, I'm moving on."

Four ways to decide "how long do I wait"

StrategyPlain descriptionDownsideUse it when
Bounded lateness"I'll wait up to N seconds for stragglers" — the defaultMust be set conservatively for your worst sourceDisorder has a predictable upper limit
PunctuatedSender tells you "I'm done sending for this period"Only works if sender cooperates reliablyProducer can reliably mark "end of batch"

Three choices when something does arrive late:

  • Drop it — fastest option, fine for rough estimates.
  • Update the result later — keep the door open, recalculate if late data shows up. More correct, more expensive.
  • Set it aside separately — send it to a "review later" pile instead of dropping or blocking. Right choice when you legally can't just lose data.
🚩 FAANG Signal

When you say "I'd aggregate the last 5 minutes," the interviewer wants you to immediately clarify: last 5 minutes of what clock? And they want a specific watermark policy — "5 seconds of expected lateness, 10 seconds of grace period, drop after that" — not just "we'd handle late data."

✅ Say this out loud

"Event time, processing time, and ingestion time are three different clocks. My watermark is a bet about how wrong one of them is."

Idea 3: "Exactly-Once" Is Three Different Promises Wearing One Name

Think of a package delivery service claiming "guaranteed delivery." That could mean the courier attempts delivery once, or the warehouse scans it once, or — the one you actually care about — you receive exactly one package, no duplicates, no matter what went wrong upstream.

Streaming has the same three layers:

  1. Exactly-once delivery — sender to receiver, exactly once. Basically impossible to fully guarantee; most systems give you "at least once" instead.
  2. Exactly-once processing — your program computes each event exactly once. Achieved via checkpoints: crash, rewind to last checkpoint, reprocess.
  3. End-to-end exactly-once — the one people actually mean. No duplicates at the final destination, no matter what broke along the way. Requires the destination to cooperate, not just the processing engine.

Two ways to actually achieve layer 3: two-phase commit (destination and engine coordinate so a write only counts once both agree), or idempotent writes with a stable key (writing the same result twice has no extra effect — an UPSERT keyed by a stable ID just overwrites with the same value).

❌ Anti-Pattern

Saying "the broker gives us exactly-once delivery" and stopping there. It doesn't. You have at-least-once delivery, and your destination needs to handle duplicates gracefully.

✅ Say this out loud

"Exactly-once is a semantics claim, not a delivery claim. The guarantee lives in the sink, not the broker."

Idea 4: Streaming Programs Remember Things — and That Memory Needs Rules

Streaming programs often keep a running memory of things: a customer's rolling average spend, a session's click count so far. This is called state — the program's own private notebook, updated as events arrive.

The problem: if you never clean up that notebook, it grows forever. The fix: give every piece of memory an expiration date, called a TTL. If a customer hasn't shown up in 36 hours, forget their average — they'll get tracked fresh if they return.

Streaming also needs to periodically save its progress, called a checkpoint — otherwise a crash loses everything. The more state you hold, the longer each checkpoint takes. Rule of thumb: a checkpoint should take no more than 10–20% of the time between checkpoints. More than that, and the job slowly falls behind and may never catch up.

⚠️ War Story

A fraud detection team kept per-card rolling averages in memory with no expiration date. It worked fine in testing. In production, months of accumulated state — including cards unused for over a year — bloated checkpoint size until checkpoints took longer than the time between them. The job fell permanently behind. The fix was one line: a TTL on the state. This exact mistake — memory with no expiration date — is the most common real-world streaming incident.

✅ Pattern

Every piece of state gets a TTL. No exceptions. If you can't immediately answer "how long does this need to be remembered," you haven't finished designing the system yet.

Idea 5: Should You Even Use Streaming? (Lambda vs. Kappa)

Before picking a streaming framework, ask a more basic question: do you need full streaming at all, or would "batch, but frequent" be good enough? Toggle between the two older architecture ideas below.

Interactive — compare the two approaches

Kappa is the modern default — modern streaming engines handle joins, aggregations, and corrections well enough that a separate batch path usually isn't needed anymore. Lambda tends to show up when a team picked the wrong streaming tool first, hit a wall, and bolted on a batch path to compensate.

And sometimes the right answer is neither — just a more frequent batch job. If results can be "up to 1 minute old," a small job running every minute is usually far cheaper to build than full streaming, for basically the same outcome. Streaming earns its cost specifically when you need sub-10-second freshness or a genuinely continuous per-event computation that a periodic job can't express.

A Real Interview, Walked Through Simply

The fraud-detection example — a favorite prompt at any payments company, because every idea in this chapter shows up in the answer.

Interviewer

Design a real-time fraud detection system for a payments company. Thousands of transactions per second at peak. The decision has to come back within 100 milliseconds.

Candidate

(pauses) Before I draw anything — is this decision blocking, meaning the transaction doesn't complete until the fraud check returns? Or advisory, with a reversal later if needed?

Interviewer

Blocking.

Candidate

That changes everything — every step now has a slice of that 100ms budget, and that's the dimension I'd expect to break first. Next: how are transactions spread across merchants?

Interviewer

Very uneven — top 1% of merchants make up 40% of volume.

Candidate

So uneven load is a first-class problem here too. Last question: if the same transaction retries, does it need the exact same decision both times?

Interviewer

Yes — same transaction, same decision. The gateway retries on timeout.

Candidate

Okay — so scoring needs to be deterministic, plus a way to recognize "this is a retry" at the final decision point.

Here's the shape: the gateway writes each transaction into a stream, split by card ID. A processing job reads it, pulls in relevant facts (recent spending, risk scores), scores it, and writes the decision to a second stream. The gateway reads that and responds.

Interviewer

What if the merchant risk lookup takes too long?

Candidate

I'd set a hard budget — say 50ms. If it's not back in time, don't block. Flag it "needs enrichment," fall back to a conservative rules-only decision immediately, and reconcile the full analysis afterward, asynchronously.

Interviewer

And if the ML model goes down entirely?

Candidate

Never stall the pipeline. A circuit breaker: if more than ~5% of calls fail in a short window, stop calling it and fall back to rules-only — more false alarms, zero downtime. Once it's healthy again, reprocess anything scored conservatively in the meantime.

Interviewer

How would you know this design hasn't silently drifted out of correctness?

Candidate

A quarterly audit comparing current traffic against the original design assumptions — is merchant concentration still the same shape? Is the 100ms budget still realistic given current lookup times? Drift in either is a signal to revisit before it becomes an incident.

Common Mistakes People Make

  1. Mixing up "delivered once" with "exactly one correct result." The broker can't promise the first. Only a correctly-built destination can promise the second.
  2. Using "when my program saw it" instead of "when it happened" for time windows. Most business questions mean event time, not processing time.
  3. Giving memory (state) no expiration date. It grows forever until checkpoints slow down and the job falls behind — the most common real-world streaming incident.
  4. Reaching for full streaming when frequent batch would do. "Every minute" is not the same requirement as "every second."
  5. Proposing Lambda (dual pipelines) unprompted. Signals you haven't actually run the simpler Kappa approach in production.
Cheat Sheet
Built to be photographed before your interview.

The Three Clocks

  • Event time — when it actually happened
  • Ingestion time — when it arrived at your system
  • Processing time — when your program got to it

Watermark Formula

watermark = latest event time seen − how long you'll wait for stragglers

Set the wait time from your own measured lateness, not a default.

Late-Data Options

  • Drop it (rough estimates)
  • Update the result later (audits/finance)
  • Set aside for review (can't lose data)

"Exactly-Once," Three Layers

  • Delivery — not really achievable, assume at-least-once
  • Processing — via checkpoints
  • End-to-end — needs the destination to cooperate

Healthy State Management

  • Every piece of state gets a TTL — no exceptions
  • Checkpoint time ≤ 10–20% of interval
  • Practice recovery from your largest real checkpoint

Should You Even Stream?

Sub-10-sec freshness needed → streaming. "Every minute or so" → frequent batch is cheaper. Kappa (one pipeline) is the modern default over Lambda (two pipelines).

Three Lines Worth Memorizing

  • "Event time, processing time, and ingestion time are three different clocks."
  • "Exactly-once lives in the sink, not the broker."
  • "Every piece of streaming state gets a TTL. No exceptions."
A Couple of Extra Ideas — from the older 2025 edition
  • Choosing Flink over Spark for fast, continuously-evolving calculations: if a feature needs to evolve per event (like a time-decayed score), a true streaming engine using a KeyedProcessFunction gives control a micro-batch tool isn't built for — lower latency, but more hands-on state management.
  • Graceful degradation instead of stalling: if a slow dependency can't respond in time, don't block the pipeline — flag it "needs enrichment," apply a safe default immediately, reconcile asynchronously once it catches up.
  • Autoscaling isn't magic: only helps if scaling on real pressure signals (consumer lag, processing time), and only if partitions can actually support more parallel workers.
