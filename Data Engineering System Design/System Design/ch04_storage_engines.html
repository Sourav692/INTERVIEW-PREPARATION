System Design for Data Engineers · Chapter 4

Storage Engines

Every downstream decision in a data pipeline inherits constraints from the storage engine underneath, which is why experienced candidates pick the engine first and the query plan second.

Printed as "Chapter Three" in the book's own running heads — see the numbering note in Chapter 3. This guide cites it as Chapter 4.
The Simple Version, First

Two ways to organize a filing cabinet of employee records: staple each employee's whole file together, or keep separate drawers for "all addresses," "all salaries," "all start dates." One is fast for "look up one employee." The other is fast for "average salary across everyone."

That one choice — how you physically organize data on disk — is one of the most consequential decisions in the platform, because you can't easily change your mind once you've picked.

What you'll be able to say by the end (the book's own scripted lines)
The storage engine is the one pipeline decision I can't renegotiate. Before I name the engine, I name the three axes: row or column, LSM or B-tree, local disk or object store.
Row stores optimize for access patterns I know. Columnar stores optimize for the ones I don't know yet.
LSM accepts write amplification in exchange for sequential writes; B-trees accept random I/O for read locality. I pick whichever one is cheaper at my scale.
Compression isn't an afterthought. Three-times compression on a petabyte is two petabytes of disk I don't have to buy.
S3 isn't a filesystem. Rename, list, and append all have different cost and consistency semantics, and the design that ignores this breaks at scale.

Why Two Similar Teams Ended Up With Completely Different Years

Two data teams both need to pick a storage layer for their event pipeline. Both say the exact same sentence: "a few hundred million events, analytical workload, two-year retention." One picks a traditional row-based database. The other picks a columnar file format on cheap cloud storage with a lightweight bookkeeping layer.

A year later, the first team is rebuilding the whole thing. The second is adding new use cases every quarter. The difference wasn't the engineers — it was the storage engine, and once you've picked the foundation, you can't easily renegotiate it.

Byte-read cost: row vs. column, for the same query

Row-major — aggregate one column

Reads every row's full bytes to get one 40-byte field out of a 300-byte row. Slow — throws away 4/5 of what it read.

Column-major — aggregate one column

Reads just that one column's bytes, compressed. Roughly 50x fewer bytes read for the same aggregation.

🚩 FAANG Signal

When you mention LSM trees in an interview, the interviewer's next question is almost always about compaction tuning. The answer they want isn't "the system handles it." It's "tiered compaction for append-heavy workloads, leveled when the same keys get rewritten, and I'd tune the level multiplier and target file size based on the write pattern."

Idea 2: Object Storage Has Its Own, Very Different Rules

  • Rename = copy + delete (~150ms for 100MB) vs. sub-millisecond on a normal filesystem.
  • List = paginated API, ~1,000 keys per call.
  • Append doesn't exist — every "append" creates a brand new object.
  • Tail latency is 10-100x local disk, and the worst case is worse still.
  • Prefix rate limits — roughly 3,500 writes/sec and 5,500 reads/sec per prefix on S3.
❌ Anti-Pattern

Treating S3 (or any object store) like a regular filesystem. A design that assumes instant renames, cheap directory listings, and in-place appends breaks the very first time someone tries to replace a single file in place at real scale.

✅ Say this out loud

"S3 isn't a filesystem. Rename, list, and append all cost differently, and the design that ignores this breaks at scale."

Idea 3: Compression Isn't a Bonus Feature — It's Load-Bearing

Columnar layouts compress 5 to 10 times better than row layouts, because adjacent values in a column tend to be similar (timestamps only increase, country codes repeat) — exactly what run-length, dictionary, and delta encoding exploit well.

✅ Say this out loud

"Compression isn't an afterthought. Three-times compression on a petabyte is two petabytes of disk I don't have to buy."

Idea 4: Three Anti-Patterns Under Interview Pressure

❌ Anti-Pattern

Picking the engine to match the vendor, not the workload. "We use Snowflake, so the storage layer is Snowflake" treats the engine as a given. Vendor lock-in is an operating reality; vendor-first thinking is an interview tell.

An Interview Transcript — the 10 Petabyte Warehouse

Interviewer

Design the storage layer for a 10 petabyte analytical warehouse. Daily load of about 50 terabytes of new data. A mix of ad-hoc interactive queries and scheduled reports. Two-year retention.

Candidate

Before picking any tool, three axes. Row-major or column-major? Analytical workload, so column-major. LSM or B-tree? Bulk nightly loads, not small random writes, so LSM-style fits. Local disk or object store? At 10 petabytes, disk-attached storage runs into the hundreds of thousands of dollars before even counting I/O charges — object storage is the answer unless interactive latency has to be sub-second at the tail.

Interviewer

Latency target is a few seconds for ad-hoc, minutes for scheduled reports.

Candidate

Good, that confirms object storage. Columnar data on object storage with a bookkeeping layer on top is the lakehouse pattern.

✅ Pattern

When you pick a storage engine in an interview, state the three axis positions out loud first, then name the engine that satisfies them. The interviewer grades the decomposition, not the final name.

Common Mistakes People Make

  1. Defaulting to a row database for analytics. Fine at 100 GB, wrong at 10 TB.
  2. Picking a write-once columnar format for transactional workloads. Can't serve update-heavy patterns without an expensive metadata layer.
  3. Treating object storage as a filesystem. Breaks on first contact with real scale.
  4. Ignoring compaction on an LSM-based system. A future incident waiting to happen.
  5. Letting lakehouse metadata grow unbounded. Causes mystery slowdowns a year later.
Cheat Sheet
Built to be photographed before your interview.

The Three Axes

Row-major vs. column-major · LSM tree vs. B-tree · Local disk vs. object store

Bytes Read, Rule of Thumb

  • Row: rows × row_bytes
  • Columnar: cols × rows × compressed bytes (5-10x compression)
  • Aggregating one column: ~1/50th the row-scan cost

Object Storage Gotchas

  • Rename = copy + delete (~150ms)
  • List = paginated, ~1,000 keys/call
  • Append = new object every time
  • Prefix limits: ~3,500 PUT/s, ~5,500 GET/s

Write Amplification

B-tree: 1.5x-3x. LSM (leveled, default): ~10x at depth 7.

Lakehouse Maintenance

Expire snapshots · rewrite small files · compact manifests · remove orphan files — mandatory, not optional.

A Couple of Extra Ideas — from the older 2025 edition
  • File format inside the lakehouse depends on data movement, not just querying: Parquet wins for analytics; Avro makes more sense for individual events through a message system, since each is read as a whole record.
  • Illustrative storage pricing: standard object storage ~$23/TB/month; cold-tier roughly a fifth of that; block storage considerably more plus IOPS; API charges a common surprise for high-frequency small-object writers.
