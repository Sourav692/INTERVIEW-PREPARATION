Data Contracts & Governance

Every schema your pipeline reads is already a contract, whether anyone wrote it down or not. The only real question is whether someone can break it silently, or whether the system stops them before it ships.

Printed as "Chapter Eleven" in the book's own running heads — see the numbering note in Chapter 3. This guide cites it as Chapter 12.
The Simple Version, First

Imagine a group project with a shared spreadsheet where everyone quietly agreed what each column means — but nobody wrote it down. One day, someone decides a column should hold something slightly different, and doesn't tell anyone. Everyone else's work that depended on it quietly breaks.

A data contract just makes that unwritten agreement explicit and impossible to break by accident. Every schema is already a contract. The question is only whether it's enforced.

What you'll be able to say by the end (the book's own scripted lines)
A schema is a contract whether I document it or not. The question is only whether the producer can break it silently.
Forward compatibility is the producer's promise; backward compatibility is the consumer's. Mix them and you get outages.
Lineage isn't a compliance checkbox. It's the tool that tells the on-call which table to roll back when the Monday dashboard goes red.
PII at scale isn't a late-stage add-on. Once it touches a pipeline, retrofit costs an order of magnitude more than separation at ingest.
Contract enforcement goes in CI, not in the dashboard. If a contract only breaks when the consumer notices, it isn't a contract.

Why Two Teams Who "Both Have Documentation" Get Very Different Outcomes

Two data teams at similarly-sized companies. Both have schemas written down in a wiki. Both say the right things about "taking schema evolution seriously."

Team A's contract is a wiki page last edited 18 months ago. Team B's is an actual schema file checked into the producer's code, with an automated check that blocks any change that would break things or accidentally drop a privacy tag.

Six months later, Team A has paged their on-call four times this quarter. Team B: zero. The difference isn't the schema — it's enforcement. Team A has "contract as a hope." Team B has "contract as something the code cannot ship without satisfying."

Idea 1: Every Schema Is Already a Contract — the Only Question Is Enforcement

You already have contracts, whether you call them that or not. The moment a producer writes data somewhere and a consumer reads it, there's an implicit agreement about what fields mean, which can be empty, and which contain sensitive personal information.

💡 The one idea to remember

The question was never "should we have contracts?" It was always: is the agreement enforced, or can it be broken without anyone noticing until a downstream dashboard catches fire?

Three properties separate "a contract that holds" from "a contract that's just a suggestion":

  • Lives with the code, not in a wiki. A schema file checked into the producer's own repo, versioned with their code.
  • Compatibility is enforced automatically, before shipping. Not manually reviewed — automated, applied to every change, failing fast.
  • Violations get caught at the producer's door, not the consumer's. The moment they try to ship — not at 2 AM when someone notices a broken dashboard.

Idea 2: Every Production Incident Is a Contract Violation Wearing a Disguise

Three common incidents. Each looks different at first — each is the same problem underneath.

  • The silent rename — a field gets renamed on a Thursday. By Friday, 17 downstream jobs fail because the old name no longer exists. Nobody was told.
  • The silent type widening — an ID field's type gets quietly widened. Values still fit for now. Six months later, values finally exceed the old type, and every downstream system still expecting it starts silently writing wrong numbers.
  • The silent privacy leak — a phone number field gets added with no privacy tag. It lands in an open analytics area. Two weeks later it ends up in an external export.

All three are contract violations, invisible to the producer because nothing ever asked them to check.

❌ Anti-Pattern

Treating a contract as documentation — a wiki page nobody reads before shipping and nobody updates after changing the schema. If it isn't enforced automatically before a change ships, it isn't a contract. It's a suggestion.

# Backward-compatibility checker. Runs in the producer's own CI,
# fails the PR on any breaking change.
from dataclasses import dataclass
from typing import List

@dataclass(frozen=True)
class Field:
    name: str
    type: str
    required: bool = False
    has_default: bool = False
    pii: bool = False

def check_backward_compat(old: List[Field], new: List[Field]) -> List[str]:
    errors: List[str] = []
    old_by = {f.name: f for f in old}
    new_by = {f.name: f for f in new}

    for f in new:
        if f.name not in old_by:
            if f.required and not f.has_default:
                errors.append("BREAKING: required field added without default")

    for f in old:
        nf = new_by.get(f.name)
        if nf is None:
            errors.append("BREAKING: field dropped")
            continue
        if nf.type != f.type:
            errors.append("BREAKING: field type changed")
        if f.pii and not nf.pii:
            errors.append("BREAKING: field lost PII tag")
    return errors

⚠️ War Story

A team had a schema registry with a solid compatibility rule enforced. A producer merged a change widening a required field's number type. By the registry's own rules this was technically safe — old readers could still parse the wider values as long as they still fit the smaller type. It shipped. Three months later, a downstream ML feature store that converted the field back to the smaller type started silently overflowing once IDs passed that limit. Nobody noticed for six weeks. The root cause: the consumer's own internal assumption had never been registered as something the contract system tracked — only the producer's side was covered. The fix: consumer expectations became a declared contract too. Contracts are a two-way promise, and mixing up the two directions is exactly how outages like this happen.

Idea 4: Handling Sensitive Personal Data — Separate It Early, or Pay 100x Later

Every pipeline that touches user data eventually touches personal information. The decision: keep it mixed in with regular data, or route it to its own separate, tightly controlled area from the start.

Cost comparison

✅ Separated at ingestion

~1 engineer-month
  • Sensitive columns routed to a restricted zone from day one
  • ~5% more compute, one extra week of upfront design
  • Makes the "accidentally-shared export" failure structurally impossible

❌ Retrofit after 18 months mixed together

6–12 months, $1M–$5M
  • Find every table containing it (weeks)
  • Rebuild or retire those tables (months)
  • Rebuild every query that referenced them (months)
  • Re-verify every downstream consumer (months)

The ratio is roughly 100x. This decision gets made on day one, whether anyone realizes it or not.

Three structural patterns, in increasing cost:

  • Token vault — sensitive fields replaced with meaningless tokens; a separate service holds the real mapping. Standard at payment companies.
  • Field-level encryption — cheaper than a vault, but leakier; watch key rotation carefully.
  • Differential privacy — statistical noise so individuals can't be re-identified. Right for public aggregates, overkill for internal analytics.

A Real Interview, Walked Through Simply

The classic governance prompt: roll out contracts across an organization with existing pipelines, without breaking anything. Watch the candidate design a phased rollout — and catch a flaw in their own tiering plan mid-answer.

Interviewer

Roll out a data contract system across a 40-team organization without breaking existing pipelines.

Candidate

Three questions first. What do we have today? How are incidents distributed — are some teams hit more often? Is there organizational appetite for asking producers to do extra work?

Interviewer

Schemas live in a wiki, inconsistently maintained. Incidents cluster around platform and revenue teams — they consume a lot of upstream data and get burned by upstream changes. There's executive sponsorship pushing this.

Candidate

Good — that tells me who the first consumers and producers should be. I'd roll this out in three phases over 9 to 12 months: dogfooding on our own tables first, then five "lighthouse" producer teams whose downstream pipelines cause the most pain, then org-wide rollout to the remaining 35, tiered by criticality.

(pauses) Actually, let me revise that tiering plan. Asking 40 teams to self-label their own tables as "most critical" turns into a political negotiation — every team calls their own table the most important one. Better: default everything to a middle tier, then use actual usage data — reads per day, downstream job count, revenue-dashboard dependency, sensitive-data content — to automatically promote or demote tables based on objective signals. Let the data decide the tier, not each team's self-assessment.

Interviewer

What about existing schemas — how do you handle "here's where we currently stand"?

Candidate

Scan and seed. Auto-generate each producer's initial contract from their current schema. They review it, tag anything sensitive, and merge it as their starting point. From then on, every schema change is a pull request against that contract.

Interviewer

What about sensitive personal data specifically?

Candidate

That's the subtle one. If it's already mixed in across existing tables, separating it is its own 6-to-12-month project — not part of this rollout. New fields get tagged from day one; existing sensitive data gets a separate, year-long remediation track. Doing both at once is too much organizational change to absorb.

Interviewer

What breaks first?

Candidate

Lineage freshness. If the graph lags behind actual deployments, the on-call trusts it and misses a downstream consumer during an incident. Investing in keeping it fresh pays for itself by the third real incident.

Common Mistakes People Make

  1. Treating a contract as documentation. A wiki page a producer can break silently was never actually enforced.
  2. Having a registry with no automated testing layer. It catches structural breaks, not semantic changes or privacy-tag drops.
  3. Letting lineage go stale. Freshness is operational, not a nice-to-have.
  4. Waiting to separate sensitive data. Retrofitting costs roughly 100x what separating from day one would.
  5. One enforcement level for 200 tables. Either too strict or too lax — tier by actual criticality.
Cheat Sheet
Built to be photographed before your interview.

Three Layers

  • Schema Registry — structural rules
  • Contract Tests in CI — semantic rules
  • Lineage Graph — blast radius, impact analysis

Compatibility, Two Directions

Forward — new data readable by old consumers (producer's promise). Backward — new consumers can read old data (consumer's promise). Mixing these up causes outages.

Enforcement Tiers

Highest — blocks + validates at ingest + weekly lineage audit. Middle — blocks + monthly audit. Lowest — warns only, on-demand lineage.

The PII Principle

Separate at ingestion: ~1 engineer-month. Retrofit later: 6–12 months, $1M–$5M. Roughly a 100x ratio.

PII Separation Patterns

  • Token vault — standard for payments/regulated
  • Field-level encryption — cheaper, watch key rotation
  • Differential privacy — public aggregates only

Four Breaks a Registry Won't Catch

  • Value-range changes
  • Silent nullability changes
  • Meaning changes (same name/type)
  • Privacy-tag drops

Three Lines Worth Memorizing

  • "Contracts are build artifacts, not wiki pages."
  • "Enforce at the producer's CI, not the consumer's dashboard."
  • "Separate PII at ingestion. The retrofit ratio is 100x."
A Couple of Extra Ideas — from the older 2025 edition
  • Where contracts live in the pipeline lifecycle: defined before code is written, published to a registry that auto-rejects incompatible versions, validated again at ingestion (since even a compatible schema doesn't guarantee the actual data follows the rules), and enforced downstream via dbt tests or Great Expectations — turning a downstream test from "defensive, just in case" into "assertive, because we know this holds."
  • What a breaking change looks like beyond the tooling: dual-writing old and new fields for a release cycle, communicating ahead of time, coordinating with ML teams (feature stores break silently on missing fields) and BI teams (semantic layers need remapping) — invisible work until it's skipped.
  • Real incident examples: a payments system changing cents-as-integer to dollars-as-float doubled revenue on dashboards overnight; a ride-share app sending empty route data for six hours caused driver overpayments; an e-commerce platform receiving null currency codes silently defaulted to the wrong currency. Contracts wouldn't have prevented all of these — but each would have become a visible, immediate violation instead of silent corruption discovered days later.
