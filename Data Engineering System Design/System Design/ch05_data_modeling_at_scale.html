Data Modeling at Scale

At scale, your schema is a contract with every downstream team and every future query you can't see yet. The shape determines which queries are cheap, and the SCD choice determines which historical questions you can still answer three years from now.

Printed as "Chapter Four" in the book's own running heads — see the numbering note in Chapter 3. This guide cites it as Chapter 5.
The Simple Version, First

Two people organize the same pile of receipts. One files things into labeled folders and cross-references. The other just staples everything to each receipt directly — faster to read, but six months later, answering "which vendors changed category last quarter" means going through every single receipt by hand.

How you model your data determines which future questions are cheap to answer and which ones require a rebuild.

What you'll be able to say by the end (the book's own scripted lines)
Star schemas aren't legacy. They're an answer to "how do you make analytics fast without knowing which queries I'll ask," which is still the hardest question in DE.
Wide tables win when compression and columnar pruning are free. Narrow tables win when I need partial updates without write amplification.
Slowly Changing Dimensions are a modeling problem disguised as a history problem. Getting the SCD type wrong costs three years of rework.
Denormalize for the query path that dominates. Normalize for the one I might break.
Schema migrations are interface changes. I treat them like API versioning: additive by default, breaking changes with deprecation cycles and explicit consumer buy-in.

Why Two Teams Who Started Identically Ended Up Nowhere Near Each Other

Two teams both need to model 10 billion transactions a year. Both talk to the same stakeholders. Both land on a schema in week two.

Team A builds a star schema — a central fact table with foreign keys to separate dimension tables. Team B builds one wide, denormalized table with everything inlined.

At year one, both are shipping fine. At year two, Team B has rebuilt most of the pipeline. The wide table served the first dashboard beautifully but couldn't serve the thirty new kinds of analysis year two demanded. Team A, on the star schema, just adds a join.

Idea 1: A Schema Is Three Separate Contracts

  • A contract with downstream queries — the shape determines which queries are cheap.
  • A contract with producer teams — adding a column is free; renaming or retyping one silently breaks consumers.
  • A contract with history — the SCD type answers "what do we know when this record changes?"

❌ Anti-Pattern

Designing a schema for the dashboard you have, not the unknown queries you'll need. A schema that only serves the first dashboard is a schema you'll rebuild within eighteen months.

Idea 3: Wide Tables — a Specialization, Not a Default

Wide tables win on three fronts: columnar compression closes the storage gap, projection pushdown means extra columns aren't extra scan cost, and BI tooling handles them natively. They fail on two: update cost (one changed attribute rewrites every row carrying that key) and query rigidity (a genuinely new pattern either runs slowly or forces a rebuild).

⚠️ War Story

A fintech startup modeled user_plan (Free, Pro, Enterprise) as SCD Type 1, overwriting the plan on every upgrade. Two years later, the CFO asked for plan-level revenue history by quarter to support a pricing-change pitch. Answering it required reconstructing plan history from the billing system's event log, cross-referencing user accounts, and reconciling with support's notes. It took six months and one senior data engineer — roughly $200k in salary and overhead. The day-one Type 2 choice would have added roughly 0.1 percent to dimension storage.

🚩 FAANG Signal

When you mention SCD, the interviewer isn't testing whether you know Type 1 through 4. They're testing whether you can pick the right type per attribute. "Type 2 for user_plan because finance queries it historically, Type 1 for display_name because no one cares what it used to be" signals you've done this before. "I'd use Type 2 for everything" signals you haven't.

An Interview Transcript — the Product Analytics Platform

Watch the candidate walk through all three contracts and catch themselves on one derived attribute.

Interviewer

Model the dataset for a product analytics platform. About 100 million daily active users, 100 events per user per day, 100 concurrent SQL authors, mostly schema-change requests. Two-year retention.

Candidate

What are the dominant query patterns? How often do plan, country, or tier actually change? What do the schema-change requests usually look like?

Interviewer

90% is aggregation by user attribute. Plan changes a few times a year, country rarely, tier is derived nightly. Mostly adding event types; breaking changes have caused incidents.

Candidate

Star schema confirmed. Plan needs SCD Type 2 — finance queries it historically. Country too — cohort analyses ask "where were these users at signup?" Tier is interesting — derived, so I could track it as Type 2 or recompute it.

(pauses) Wait. Type 4 feels right at first, but it introduces a second source of truth for a value I can always derive from the fact table. The rule: SCD is for attributes I can't reconstruct. Plan and country qualify; tier doesn't.

Actually, let me revise — I wouldn't store tier history at all. I'd recompute it on demand, with yesterday's snapshot cached in a daily rollup for the common case.

Interviewer

What breaks first at this scale?

Candidate

The SCD Type 2 nightly update. A naive full outer join on 100 million rows every night doesn't scale. I'd use CDC on the user table to surface only changed rows, then apply SCD logic to that subset — turning a 100-million-row scan into something proportional to actual change volume.

Common Mistakes People Make

  1. Wide table by default. Fine for a small, stable workload. Wrong as a starting point for a platform that will evolve.
  2. Implicit SCD Type 1. Happens by accident, and the lost history costs years to recover from.
  3. Treating a rename as free. Renames need a deprecation cycle, not just a PR approval.
  4. Confusing 3NF with modeling discipline. Analytics wants lightly denormalized dimensions, not full normalization.
  5. Modeling the current state only. Always name the SCD choice explicitly, even if the answer is Type 1.
Cheat Sheet
Built to be photographed before your interview.

Three Contracts

Query shape · Producer evolution · History (SCD)

Four Modeling Patterns

  • Star — default, unknown queries
  • Wide — known, stable, dominant pattern
  • Data Vault — regulated, audit-heavy
  • OBT — single named consumer

SCD Types, Per Attribute

  • Type 1 — overwrite, cheap, history lost
  • Type 2 — new row per change, full history
  • Type 3 — current + previous only
  • Type 4 — history sidecar table

Schema Change Tiers

  • Additive → ship without coordination
  • Rename → deprecation cycle, ~3 months
  • Breaking → sign-off + migration plan

The Default Decision

Star schema unless a specific, stable, dominant pattern justifies a wide table. Don't SCD what you can recompute from the fact table.

Three Lines Worth Memorizing

  • "Denormalize for the query path that dominates. Normalize for the one I might break."
  • "SCD types are decided per attribute, not per table."
  • "Schema migrations are interface changes. Deprecation cycles, not surprises."
A Couple of Extra Ideas — from the older 2025 edition
  • Schema changes are, at their core, a contract-review problem — the same discipline as API versioning. A PR-level review asking "is this field always non-null?" catches ambiguity before it leaks downstream.
  • Breaking changes get managed through people, not just tooling — Slack threads, tickets, change windows, deprecation timelines, dual-write periods, and often a platform lead mediating between teams.
  • Real examples of what happens without a contract: a currency field silently switched from integer cents to floating-point dollars, doubling reported revenue overnight; an app release sending empty route data for six hours, causing a pricing model to overpay; a vendor sending null currency codes, silently defaulting to the wrong currency.
