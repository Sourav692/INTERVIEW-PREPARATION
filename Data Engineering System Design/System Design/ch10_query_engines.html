Query Engines

A query engine doesn't charge you for how many rows come back. It charges you for how much raw data it had to look through to answer you. Almost everything else in this chapter is just "how to help it look through less."

The Simple Version, First

Two people cook the exact same recipe, in the exact same kitchen. One finishes in 12 minutes; the other takes two hours. Same ingredients, same stove — but one person knew exactly which shortcuts the kitchen allowed.

Two teams can write nearly identical SQL and one query finishes 600x faster — not from a better computer, but from one tiny difference in how the question was phrased. You're charged for bytes scanned, not rows returned. Everything else follows from that.

Why the Same Question, Written Two Ways, Can Take 600x Longer

Two teams each own a slow dashboard. Both queries run against the same 50 terabyte table, split up by day. Both do the exact same thing: add up daily revenue by customer plan.

Team A's query runs in 12 seconds. Team B's runs in two hours. The SQL is nearly identical — the difference is a single function call in the filter.

Team B wrote "reformat this date column, then compare the reformatted text to '2024-06-15.'" Team A wrote "compare the raw date column directly to a date range." Those sound similar, but to the engine they're completely different instructions. Team A's version skips 729 of 730 days without opening them. Team B's version has to open and read every single day first, because the engine can no longer tell which day is being asked for.

💡 The one idea to remember

Query engines are where the shape of your data meets the intent of your question. The engine's whole job is translating your intent into the smallest possible read, given the shape. A strong candidate can predict, just from reading the SQL, whether that translation will go smoothly.

Idea 1: You're Charged for What Was Read, Not What Came Back

In a regular app database, asking for "the one row where ID = 42" uses an index to jump straight there — like flipping to the right page using a book's index. The cost is about the lookup, not the size of the book.

In a big analytics warehouse, that shortcut mostly doesn't exist. A column-level index on a 10 TB table would itself be roughly a 10 TB index. Instead, the engine relies on folder structure, summary statistics, and how columns are physically stored. The cost of a query is how many bytes it scanned — not how many rows survived the filter.

  • "Just add an index" doesn't help here. The engine uses folder structure and stored statistics instead — reaching for an index is applying the wrong mental model.
  • Fewer columns matters more than fewer rows. A well-organized (columnar) format skips reading unrequested columns entirely, for free. SELECT * throws that away.
  • Which folders you touch is the single biggest lever. Data split into daily folders lets a query skip essentially the whole rest of the table — but only if the engine can tell which folder your filter maps to.

Idea 2: "Pushdown" Is Just "Skip Stuff Before Even Opening the File"

Think of sorting mail. If the zip code is printed clearly on the outside of the envelope, a mail carrier sorts without opening anything. If it's scribbled in code somewhere inside, they have to open every envelope first. Same information, wildly different amount of work.

Three levels of pushdown, in order of typical impact:

  1. Skip whole folders (partition pruning) — the biggest lever, shown above.
  2. Read fewer columns (projection pushdown) — free in columnar storage.
  3. Skip files by contents (predicate pushdown) — stored min/max notes per file let non-matching files get skipped entirely.

One blind spot: min/max doesn't help much for a specific ID lookup on unsorted data, since the range spans almost everything. Parquet bloom filters (optional, 1–5% extra storage) close that gap.

Idea 3: The One Mistake That Breaks Everything

Wrapping a column in a function before comparing it — reformatting a date, uppercasing text, converting a type — hides your real intent from the engine. It can no longer tell you're asking about one specific day; it sees a filter on a function's output, not the actual column.

❌ Before — function wraps the column

WHERE DATE_FORMAT(event_ts, 'yyyy-MM-dd')
      = '2024-06-15'
Scans all 730 folders — 50 TB read

✅ After — raw column, direct range

WHERE event_ts >= '2024-06-15'
  AND event_ts <  '2024-06-16'
Scans 1 folder — ~70 GB read

The fix is always the same shape: move the transformation to the other side of the comparison, so the stored column stays untouched.

sql-- src/code-examples/ch09/query_tuning_pushdown.sql
-- BEFORE: reformatting hides the filter from the planner.
SELECT u.plan_tier, SUM(t.amount) AS revenue
FROM fact_transactions t
JOIN dim_user u ON t.user_id = u.user_id
WHERE DATE_FORMAT(t.event_ts, 'yyyy-MM-dd') = '2024-06-15'
  AND u.country = 'US'
GROUP BY u.plan_tier;

-- AFTER: a plain range comparison on the raw column. Folder-skipping
-- fires; the scan touches one folder instead of 730.
SELECT u.plan_tier, SUM(t.amount) AS revenue
FROM fact_transactions t
JOIN dim_user u ON t.user_id = u.user_id
WHERE t.event_ts >= TIMESTAMP '2024-06-15 00:00:00'
  AND t.event_ts <  TIMESTAMP '2024-06-16 00:00:00'
  AND u.country = 'US'
GROUP BY u.plan_tier;
⚠️ War Story

A team at a financial services company ran a daily revenue-reconciliation query that took two hours and blocked the morning refresh of eight dashboards. The SQL had been written by a senior engineer who understood data modeling well. The two hours came from a single function call: wrapping the date column in a type conversion before comparing it to "yesterday." That one wrapper silently disabled folder-skipping on a table split into daily folders. A five-minute rewrite — comparing the raw column to a plain date range — dropped runtime to four minutes. The lesson: the engineer had a perfectly correct mental model of data modeling and zero mental model of how the engine's shortcuts actually work. Those are two different skills.

❌ Anti-Pattern

Wrapping a partition or filter column in any function before comparing it. This is the single most damaging habit in analytics SQL — it silently disables every shortcut the engine could have used.

Idea 4: Pre-Computing Results — and Their Three Ways of Breaking

A materialized view is a stored, pre-computed answer to a specific query — think of it as a cache. It can be a huge speedup, but it breaks in three common ways:

  • Drift — the query pattern it was built for slowly changes; it keeps costing compute but serves fewer of the actual queries.
  • Staleness — it only refreshes on a schedule, so consumers can see outdated data without a clear per-view freshness expectation.
  • Chains — views built on other views mean a broken link anywhere silently poisons everything downstream.
✅ Pattern

Track materialized view usage and freshness from day one. A view with no consumers is compute you're paying for with zero benefit.

A Real Interview, Walked Through Simply

The classic query-tuning prompt: a specific slow query, a specific speedup target, no business-logic changes allowed. Watch the candidate read the plan, fix one thing at a time, and check progress against the target rather than guessing everything at once.

Interviewer

This query runs in 20 minutes against fact_transactions. Your team wants it in 30 seconds. Business logic can't change.

Candidate

First, I'd run the engine's "explain" command and read the plan bottom-up. I'd expect a full scan, because reformatting the date column before comparing it is probably preventing any folder-skipping.

Interviewer

Confirmed. The scan reads 50 TB across 730 daily folders.

Candidate

That's the primary cost. I'd rewrite the filter as a plain range directly on the raw date column. That lets the engine skip to one folder — 50 TB becomes roughly 70 GB.

Interviewer

Done. Runtime drops to four minutes.

Candidate

(thinking) Real progress, but still about 8x off target. The folder-skip was the big lever — whatever's left is probably in columns read or the join. What's the plan doing after the scan — how many columns is it reading, and what join approach?

Interviewer

Reading all 30 columns. The join reshuffles the full data across the network on user_id.

Candidate

Two more fixes. Ask for only the columns we need — two out of 30 — which drops the read to about 7 GB with columnar storage. And the other table is probably only a few GB — filter it to US users, then switch the join to broadcast: copy the small, filtered table to every worker instead of reshuffling the giant table to match it. That avoids the network shuffle entirely.

Interviewer

Runtime drops to 45 seconds.

Candidate

Close — and that's usually where I'd check whether 45 seconds actually meets the target, or whether there's a specific number I'm still missing.

Common Mistakes People Make

  1. Reaching for "add an index." Doesn't help at analytics scale — folder structure and stored statistics do that job instead.
  2. Using SELECT * in analytics. Reads every column even when the query only needs a few — a free optimization thrown away.
  3. Wrapping a partition or filter column in a function. The single most damaging habit in analytics SQL.
  4. Materialized views with no usage tracking. Quietly become compute you're paying for with no benefit.
  5. Picking an engine by reputation instead of workload shape. Choosing a tool because it sounded fast at a conference, not because it fits interactive vs. batch needs.
Cheat Sheet
Built to be photographed before your interview.

The Cost Model

Bytes read, not rows returned. Every tuning move reduces that number.

Four Pushdown Levers, in Order of Impact

  1. Skip whole folders (partition pruning) — biggest lever
  2. Read fewer columns (projection pushdown) — free
  3. Skip files by contents (predicate pushdown)
  4. Bloom filters — closes the point-lookup gap, ~1–5% storage

The One Anti-Pattern

A function on the partition or filter column kills pruning. Always compare the raw stored column directly.

Tuning Workflow

  1. Run "explain," read bottom-up
  2. Find the stage where bytes read is highest
  3. Check what was pruned vs. not
  4. Rewrite to unlock the missing pushdown
  5. Re-run "explain" to confirm

Materialized Views

Track usage and freshness per view, per consumer. Avoid long chains built on other views.

Engine by Workload Shape

Interactive sub-second: Trino, DuckDB. Batch minutes-to-hours: Spark SQL. Managed middle ground: Snowflake.

Three Lines Worth Memorizing

  • "Bytes read is the cost model. Rows returned is the rounding error."
  • "Explain first. Rewrite second."
  • "Functions on partition columns kill pushdown. Always."
A Couple of Extra Ideas — from the older 2025 edition
  • Warehouse vs. lake isn't either/or: most real systems use both — a cheap raw copy in a lake for ad-hoc exploration, and a cleaned, structured subset in a warehouse for BI and reporting.
  • File format depends on how the data will be read: columnar formats (Parquet, ORC) win for analytics; row-based formats (Avro) make more sense for passing individual records through a message system like Kafka.
  • Managed vs. self-hosted applies to query engines too: managed services reduce operational burden for smaller teams or unpredictable workloads; self-hosting can pay off at large, predictable scale where customization or cost control matters more.

Further Reading
