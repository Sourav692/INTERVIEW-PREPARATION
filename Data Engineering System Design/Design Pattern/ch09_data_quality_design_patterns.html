Data Quality Design Patterns

Trust is a mutual transaction between data producer and consumer. This chapter covers the checkpoints that keep that transaction honest — from pipeline-level audits to schema contracts to ongoing observation of datasets that never stop changing.

Quality Enforcement Schema Consistency Quality Observation
Chapter Framing

Where This Chapter Sits

Even with ingestion, error handling, idempotency, value-add, flow, security, and storage patterns all correctly in place, a dataset can still be irrelevant to its consumers — or worse, silently wrong — if data quality issues go unnoticed. This chapter groups its patterns into three categories, each solving a different piece of the trust problem, before handing off to Chapter 10 (Data Observability) for monitoring and alerting on top of these guards.

🧩 Case Study

Across this chapter, examples run on the blog analytics platform's visits pipeline — the same dataset introduced in Chapter 1. The AWAP pattern's opening scenario (a false 50% visitor-drop alarm that triggered a real marketing decision) is the book's central, recurring illustration of what happens when quality enforcement is missing.

Category 1 of 3

Quality Enforcement

Stop an incomplete, inconsistent, or inaccurate dataset from ever reaching downstream consumers.

01
Pattern

Audit-Write-Audit-Publish (AWAP)

📌 Note

AWAP evolves the Write-Audit-Publish (WAP) pattern, originated by Michelle Ufford at DataWorks Summit 2017. AWAP's addition: an earlier audit gate on the raw input, not just the transformed output.

Problem

A daily batch ETL job generates user-visit statistics. Unique visitors dropped 50% over a week — the product team believed it and launched a marketing campaign in response. It later turned out the aggregation itself was miscomputed, not a real traffic drop. The team demanded this could never happen silently again.

Solution

Add explicit audit gates at two points: an input audit (lightweight — format, size, schema-presence checks) before transformation, and an output audit (row- and dataset-level business rules, like unit tests running on live data) after. Click each gate below to see what it checks.

An audit failure needn't be a hard stop — the book allows data dispatching (promote valid rows, park invalid ones separately) and nonblocking audit (publish anyway, but annotate the dataset with a quality summary).

✅ Say this out loud

"AWAP extends unit tests onto real production data — tests are a static snapshot, but datasets evolve, so AWAP is how we keep validating against the dataset's current shape, not just what it looked like when we wrote the tests."

Consequences
GotchaDetail & Mitigation
Compute costMetadata checks are cheap; row-level validation is expensive — an accepted cost of guaranteed quality.
Rules coverageToday's rules may miss tomorrow's dataset shape. Never treat AWAP-controlled pipelines as 100% reliable — pair with Quality Observation.
Streaming latencyAsserting something like a NULL-distribution within a window delays delivery by the window's accumulation period.
An issue may not be an issueA volume spike or drop isn't automatically a bug (e.g., a legitimate viral traffic spike). Not every audit failure needs to be critical — some should just alert.

02
Pattern

Constraints Enforcer

Problem

A batch pipeline processing visits has run cleanly for months but has started producing random NULL values in required fields. The job is already complex — the ask is to fail the load declaratively, without adding validation code to the pipeline.

Solution

Delegate validation to the database or storage format. Identify the attributes needing rules, then assign constraints from four categories:

Constraint categories
TypeWhat It Guarantees
TypeEvery value for an attribute is always the same type — backbone of Schema Consistency.
NullabilityAttribute is always present, or explicitly allowed to be missing.
ValueValue must satisfy a comparison, e.g. x <= NOW(), x BETWEEN 1901 AND 2000.
IntegrityA referenced value must exist in another table (common in normalized/relational schemas).

Supported natively by Delta Lake's CHECK operator, and by serialization formats like Protobuf (type constraints natively; value constraints via protovalidate).

Consequences
GotchaDetail & Mitigation
All-or-nothing semanticsTransactional constraints reject the whole batch if any row fails, and databases usually stop at the first error — multiple round trips needed to find every issue.
Data producer shiftConstraints are producer-oriented. A field nullable in the DB may still be required for some consumers, who then need their own extra checks.
Constraints coverageNot all rule types are supported everywhere (e.g., integrity constraints in table file formats) — AWAP-style code checks fill the gap.
Examples
SQL · Delta Lake — type, nullability & value constraints
CREATE TABLE default.visits (
  visit_id STRING NOT NULL,
  event_time TIMESTAMP NOT NULL
) USING delta;

ALTER TABLE default.visits ADD CONSTRAINT
  event_time_not_in_the_future CHECK (event_time < NOW() + INTERVAL "1 SECOND")
Protobuf · protovalidate — type & value constraints
message Visit {
  string visit_id = 1 [(buf.validate.field).string.min_len = 5];
  google.protobuf.Timestamp event_time = 2 [
    (buf.validate.field).timestamp.lt_now = true,
    (buf.validate.field).required = true];
  string user_id = 3 [(buf.validate.field).required = true];
  string page = 4 [(buf.validate.field).cel = {
    message: "Page cannot end with an html extension"
    expression: "this.endsWith('html') == false"
  }, (buf.validate.field).required = true];
}

Pattern

Schema Compatibility Enforcer

Problem

A sessionization job ran fine for months. Then the upstream team removed fields they assumed were "obsolete," and the job failed repeatedly for a month. The ask: prevent any schema-breaking change from happening in the first place.

Compatibility modes
ModeAllowed ActionsSemantics
BackwardDelete field, add optional fieldNewer-schema consumer can read older-schema data
ForwardAdd field, delete optional fieldOlder-schema consumer can read newer-schema data
FullAdd/delete optional fieldBoth directions hold simultaneously
📌 Note — Transitive vs. Non-Transitive

Transitive compatibility must hold across all past/future versions, not just adjacent ones. Worked example: Order(v0) has order_id only; v1 adds amount DOUBLE DEFAULT 0.0 (fine); v2 makes amount required. v1→v2 is fine non-transitively, but v0→v2 breaks transitively — a v2 consumer can't safely read v0 data.

Consequences
GotchaDetail & Mitigation
Interaction overheadAn external registry adds a validation round trip to every write.
Schema evolutionEvery change must satisfy the compatibility level — a simple rename can require "add new + deprecate old" (solved by Schema Migrator, next).

04
Pattern

Schema Migrator

Problem

Fields have been added over time without ever bothering consumers, resulting in a message with up to 60 attributes scattered with no grouping. Consumers want related attributes grouped (e.g., login, email, age → a single user entity) — a genuine breaking change the team wants to make safely.

Solution

Schema Compatibility Enforcer only blocks incompatible changes — it can't help you perform one. Three scenarios:

ScenarioWhen It Applies
RenameAn attribute name is wrong or confusing.
Type changeSimplifying after multiple changes, or optimizing (e.g., text date-time → epoch).
RemovalOnly when 100% certain no downstream consumers use the attribute.

For rename/type-change: create the new field alongside the old, agree a transition grace period during which both are populated, then drop the old field once the deadline passes.

⚠️ Warning

The Schema Migrator requires non-transitive compatibility. Transitive compatibility guarantees consistency across every version, which makes field removal or renaming impossible by definition.

📌 Note

To confirm an attribute is actually unused before removing it, the book points to the Fine-Grained Tracker pattern (Chapter 10) for data lineage.

Consequences
GotchaDetail & Mitigation
Size impactRunning old + new fields during the grace period costs storage, network, and I/O. Protobuf's "Proto Best Practices" warns against hundreds of fields — each, even unpopulated, costs at least 65 bytes, risking Java compilation limits.

Category 3 of 3

Quality Observation

Enforcement rules reflect what you knew at the time you wrote them. Observation patterns keep them honest as the dataset evolves.

05
Pattern

Offline Observer

Problem

A new pipeline has had few quality issues so far. Experience says this won't last as the upstream dataset evolves. The ask: monitor value distributions and null counts per column, without blocking the main pipeline.

Solution

Build a separate observability job that runs independently — potentially on a completely different schedule (e.g., generators run all day, observability runs at night to avoid resource contention).

📌 Note — Observability ≠ Auditing

An audit is blocking — it can halt the pipeline. Observability is nonblocking — it surfaces issues without preventing the pipeline from continuing.

Consequences
GotchaDetail & Mitigation
Time accuracySince it can run on any schedule, insight may arrive after downstream consumers already processed the flawed dataset.
Compute resourcesRunning less often than the generator means a bigger backlog per run — can cost more compute than frequent small runs. Sampling trades completeness for cost.
Examples
SQL · idempotent state tracking (Airflow + PostgreSQL)
-- record_new_observation_state: track first/last row IDs for idempotency
INSERT INTO dedp.visits_monitoring_state (execution_time, first_row_id, last_row_id)
SELECT
  '{{ execution_date }}' AS execution_time,
  MIN(id) AS first_row_id, MAX(id) AS last_row_id
FROM dedp.visits_output
WHERE id > COALESCE(
  (SELECT last_row_id FROM dedp.visits_monitoring_state WHERE
   execution_time = '{{ prev_execution_date }}'::TIMESTAMP),
  0
)

Python · lag detection
def get_last_offsets_per_partition(self) -> Dict[str, int]:
    last_processed_offsets = self._read_last_processed_offsets()
    last_available_offsets = self._read_last_available_offsets()
    offsets_lag = {}
    for partition, offset in last_available_offsets.items():
        lag = offset - last_processed_offsets[partition]
        offsets_lag[partition] = lag
    return offsets_lag

06
Pattern

Online Observer

Problem

Analytics colleagues found an unexpected format in the zip_code field — a regression upstream. The Offline Observer did detect it, but only ran weekly, so consumers found out first. The ask: shrink that detection-to-discovery gap.

Solution

Keep the same observation-metrics job, but embed it directly into the data generation pipeline so insight is available immediately, not on a delayed schedule.

Choice"} PS -->|"Parallel Split"| P1["Load Dataset"] PS -->|"Parallel Split"| P2["Observation Job"] PS -->|"Local Sequencer"| L1["Load Dataset"] --> L2["Observation Job"] style T fill:#1B2430,stroke:#1B2430,color:#F7F4EC style PS fill:#F3E3D2,stroke:#B5652B,color:#8A4A1E style P1 fill:#E1EDE9,stroke:#3D7068,color:#26463F style P2 fill:#E1EDE9,stroke:#3D7068,color:#26463F style L1 fill:#E1EDE9,stroke:#3D7068,color:#26463F style L2 fill:#E1EDE9,stroke:#3D7068,color:#26463F

In streaming, observation logic must be embedded inside the same job — it can't run as a fully separate pipeline. Sampling offsets the risk of observation logic destabilizing the job.

📌 Note

Observability isn't limited to data — it also covers technical metadata (CPU, memory, disk usage), typically near-real-time and therefore naturally at home in the Online Observer pattern.

Consequences
GotchaDetail & Mitigation
Extra delaysLocal Sequencer adds the observation step to the critical path, delaying pipeline completion.
Parallel splitsRunning observation and loading concurrently risks reading a partially-valid dataset mid-load, producing a misleading quality read.

Synthesis

Trade-Off Comparisons

Quality Enforcement — AWAP vs. Constraints Enforcer
PatternWhen to UseTrade-off
AWAPCustom, flexible, code-level business-rule validation; you control the pipeline logicCompute cost scales with checks; rules go stale; streaming adds window latency
Constraints EnforcerDeclarative validation delegated to DB/storage format, no pipeline codeAll-or-nothing rejection; producer-oriented; some constraint types unsupported everywhere
Schema Consistency — Compatibility Enforcer vs. Migrator
PatternWhen to UseTrade-off
Schema Compat. EnforcerPrevent any incompatible schema change outrightEvery change constrained by compatibility level; renames awkward under transitive rules
Schema MigratorPerform a breaking change safely, with a consumer grace periodRequires non-transitive compatibility; dual-field period costs storage/network/I/O
Quality Observation — Offline vs. Online Observer
PatternWhen to UseTrade-off
Offline ObserverMonitoring must never touch production resources; some delay is acceptableTime-accuracy lag; infrequent runs raise per-run compute cost
Online ObserverNear-real-time detection neededAdds critical-path latency, or risks partial-data reads; streaming failures can hit the whole job
