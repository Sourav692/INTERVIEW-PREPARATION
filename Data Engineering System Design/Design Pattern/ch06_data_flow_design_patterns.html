Data Flow Design Patterns

How pipeline steps are wired together — sequencing, merging, splitting, and controlling how many instances run at once. Eight named patterns, organized into four families, drawn from the book's blog-analytics-platform case study.

Chapters 2–5 covered what happens to data as it moves through the pipeline (ingestion, error handling, idempotency, enrichment). Chapter 6 covers how the pieces are wired together — the dependency and execution topology. Three families, in order of increasing structural complexity: Sequence (steps that run one after another), Fan-In / Fan-Out (branches that merge or split), and Orchestration (how many whole-pipeline instances can run at once). The chapter hands off to Chapter 7 — once data flows correctly, the next concern is protecting it.

01 Sequence Patterns

Steps that must run in a fixed order because one depends on another's output. The question these two patterns answer: should that order live in the orchestration layer, or inside a single processing job?

PatternLocal Sequencer

Problem

A single data processing job has grown from dozens to hundreds of lines, with transformations tripling over time. It fails often, and every failure forces a restart from the very beginning. Business logic can't be removed — only the structure can change.

Solution

Decompose one large component into smaller, connected steps run sequentially, ordered by actual data dependency. Example: full data ingestion (Ch. 2) as a Readiness Marker task followed by a Full Loader task — either as two dependent orchestration tasks, or one processing-layer unit.

Three criteria decide orchestration-layer vs. processing-layer:

  • Separation of concerns — if naming the single task is hard, you've bundled too much together.
  • Maintainability — one combined task re-runs everything on backfill/retry (e.g. 10 paid API calls re-billed on every retry).
  • Implementation effort — combining tasks forfeits the orchestrator's built-in abstractions (run a query, call an API).

Consequences

⚠ Warning — Boundaries

No universal rule for where to split. Over-splitting hurts readability as much as under-splitting hurts maintainability.

Examples

input_data_sensor >> load_data_to_table >> expose_new_table

aws emr add-steps --cluster-id j=cluster_id --steps Type=Spark,Name="Spark Program",\
ActionOnFailure=TERMINATE_CLUSTER,Args=[--class com.waitingforcode.DataPublisher]

A Local Sequencer shows the power of a real orchestrator over plain CRON when building advanced logic — but CRON is still valid for an isolated use case with no dependencies.

✅ Say this out loud

"I split this into orchestration-layer tasks rather than one processing job, because backfilling a paid-API readiness check inside a monolith would re-trigger billed calls on every retry — the split directly controls cost and blast radius."

PatternIsolated Sequencer

Problem

Your team cleans and enriches raw datasets for a data visualization team. Both teams agree the dashboard-specific transformation shouldn't be folded into your team's pipeline — your team won't own that logic. The visualization team wants only the cleansed, enriched dataset.

Solution

Connect two physically separate pipelines. Draw the boundary either by team ownership (you provide to a different team → two isolated pipelines), or by pipeline complexity when you're both provider and consumer of your own output.

Two mechanisms shown:

  • Data-dependency (implicit) — sensors watching for upstream output.
  • Trigger-based (explicit) — ExternalTaskMarker (upstream) + ExternalTaskSensor (downstream); the marker auto-propagates backfills.

Consequences

⚠ Warning

The book names Scheduling and Communication as the gotcha categories — cross-team pipelines need explicit coordination since implicit in-DAG signals don't cross pipeline boundaries. [verify against source page — full prose not fully returned by search]

Examples

    external_task_id='downstream_trigger_sensor',

02 Fan-In Patterns

Branches that merge back together at a common point.

🧩 Case Study — running example for both Fan-In patterns

Your pipeline generates a daily aggregate of blog visits from raw visit events, but the dataset is partitioned hourly to fit most other use cases. Processing the whole day at once wastes that partitioning — you want to leverage it to keep each job small.

PatternAligned Fan-In

Problem

Compute a daily aggregate from 24 hourly partitions, using hourly partitioning to keep each job small, then merge the 24 results into one daily output.

Solution

Define separate branches (one per hour) that all merge into a common merge task. Two merge models at the processing layer:

  • UNION — vertical alignment; same columns, more rows.
  • JOIN — horizontal alignment; more columns, fewer rows than UNION.

Two advantages over one monolithic job: faster feedback (a broken hour surfaces sooner than a full-day failure) and cheaper recovery (replay only the failed hour, not all 24).

Consequences

⚠ Infrastructure spikes

24 simultaneous jobs need elastic provisioning, or you must cap concurrency / run branches incrementally.

⚠ Scheduling skew

The merge task waits for the slowest parent — its trigger time is bound by the longest-running branch.

⚠ Scheduling overhead

Overly granular pipelines force the orchestrator to spend most resources on scheduling, not work.

⚠ Complexity

More decoupling → longer, harder-to-read DAGs. Ask: "What tasks belong to a single unit of execution?" and "What operations should be backfilled individually?"

Examples

python · Apache Airflow
clear_context = PostgresOperator(...)
generate_trends = PostgresOperator(...)

for hour_to_load in [f"{hour:02d}" for hour in range(24)]:
    file_sensor = FileSensor(
        task_id=f'wait_for_{hour_to_load}',
        filepath=input_dir + '/date={{ ds_nodash }}/hour=' + hour_to_load + '/dataset.csv'
    )
    visits_loader = PostgresOperator(
        task_id=f'load_hourly_visits_{hour_to_load}',
        params={'hour': hour_to_load}
    )
    clear_context >> file_sensor >> visits_loader >> generate_trends
python · PySpark
input_dataset_1: DataFrame = ...
input_dataset_2: DataFrame = ...
output_dataset = input_dataset_1.unionByName(input_dataset_2)
sql
-- Position-based UNION pitfall: combines a+c, b+b, c+a by POSITION, not name
SELECT a, b, c FROM abc
UNION
SELECT c, b, a FROM cba
-- unionByName() in PySpark combines by column name instead.

PatternUnaligned Fan-In

Problem

The Aligned Fan-In hourly pipeline works well but can't handle a partially-failed hour gracefully — a failed hour blocks the whole daily aggregate. The team decides a partial dataset, filled in later, beats blocking entirely.

Solution

Relax "all parents must succeed." The child task can run even when some parents fail:

  • If enough parents succeed and remaining failures are acceptable → trigger the child anyway (partial dataset).
  • If all parents fail → trigger a different failure-path task (fallback / error handler) instead.

Implementation relies on the orchestrator's trigger condition — Airflow's trigger_rule set to "all done" rather than the default "all success."

Consequences

⚠ Readability

Two downstream branches (success-path, failure-path) make execution flow hard to see from the DAG graph alone. Mitigation: use the orchestrator's dedicated failure handling — Airflow's on_failure_callback, or Step Functions' Catch field.

⚠ Partial data

Publishing from partial parents requires communicating incompleteness, via a completeness table (e.g. 12/24 succeeded → 50%), metadata tags, a notification, or keeping the dataset private until 100% complete.

Examples

python · Apache Airflow
clear_context = PostgresOperator(...)
generate_cube = PostgresOperator(
    # ...
    trigger_rule=TriggerRule.ALL_DONE
)

for hour_to_load in [f"{hour:02d}" for hour in range(24)]:
    file_sensor = FileSensor(
        task_id=f'wait_for_{hour_to_load}',
        filepath=input_dir + '/date={{ ds_nodash }}/hour=' + hour_to_load + '/dataset.csv'
    )
    visits_loader = PostgresOperator(
        task_id=f'load_hourly_visits_{hour_to_load}',
        params={'hour': hour_to_load}
    )
    clear_context >> file_sensor >> visits_loader >> generate_cube

Identical to the Aligned Fan-In example except trigger_rule=TriggerRule.ALL_DONE — the rule stays hidden in code and won't appear in the visual DAG graph.

✅ Say this out loud

"I'd default to Aligned Fan-In unless a partial-but-timely result genuinely beats a complete-but-delayed one — and if I relax it, I always publish a completeness signal so consumers never silently assume 100%."

03 Fan-Out Patterns

One task feeds multiple downstream tasks — useful when one dataset serves multiple teams or purposes.

PatternParallel Split

Problem

A legacy C# processing framework is being retired with no surviving documentation. After reverse-engineering, you're rewriting it in Python — but since the rewrite might not be perfect, you keep the old pipeline running too, writing the processed dataset to two places during migration.

Solution

One parent task feeds at least two child tasks that run in parallel, since their logic is isolated. At the processing layer, three concerns:

  • Read once — materialize the shared dataset once (SQL temp table, or Spark's .persist()), not per branch.
  • Isolate branches — shared/global variables must be read-only or have compatible concurrent writes.
  • Resource allocation — dedicated compute or auto-scaling for time-sensitive work.

Consequences

⚠ Blocked execution

Time-dependent pipelines gate on the slowest branch — a failure blocks all subsequent runs. Mitigation: export the slow branch to its own pipeline via an Isolated Sequencer dependency.

⚠ Hardware

Differently-resourced branches (CPU-heavy vs. memory-heavy) sharing one job can't both get ideal hardware. Mitigation: split like Local Sequencer — generate the intermediary dataset first, then run branches separately on dedicated hardware.

Examples

python · Apache Airflow
file_sensor = FileSensor(#...
    task_id='input_dataset_waiter')
for output_format in ['delta', 'csv']:
    load_job_trigger = SparkKubernetesOperator(# ...
        task_id=f'load_job_trigger_{output_format}',
        params={'output_format': output_format}
    )
    load_job_sensor = SparkKubernetesSensor(#...
        task_id=f'load_job_sensor_{output_format}')
    file_sensor >> load_job_trigger >> load_job_sensor

PatternExclusive Choice

Problem

The Parallel Split migration works well. Now the new job version should run only from January 1, 2024 — backfills for prior days should still run the old version — without creating a new pipeline (to preserve execution history).

Solution

Like Parallel Split, declare at least two downstream branches — but add a condition evaluator task before branching so only one path executes. Airflow uses a branch operator; Azure Data Factory uses an if-condition activity. Also applies at the processing layer via ordinary if/else.

Consequences

⚠ Complexity factory

Branching feels natural (like application-code if/else), but each orchestration-layer condition is a real execution branch. Heuristic: rubber duck debugging — explain the pipeline to an imaginary new teammate; if it's not concise, it's too complex.

⚠ Hidden logic

Processing-layer-only branches are easy to forget weeks later. Mitigation: surface the choice at the orchestration layer too, so it's visible in the DAG.

⚠ Heavy conditions

Data-based conditions add real execution time — prefer metadata-based conditions, and avoid re-reading the full dataset each time when data-based logic is unavoidable.

Examples

04 Orchestration Patterns

How many whole-pipeline instances are allowed to run at once.

PatternSingle Runner

Problem

A sessionization pipeline (Incremental Sessionizer, Ch. 5) was a manually-run POC with no formal orchestration. Moving toward release, it needs real orchestration — and since the logic is incremental (sequential), more than one instance can't safely run at once.

Solution

Guarantee at most one execution at a time. Both Airflow and Azure Data Factory support a concurrency attribute settable to 1. Without native support, implement a Readiness Marker that waits for the prior run — this doesn't stop future runs from queuing behind it.

Consequences

⚠ Backfilling

Sequential-only execution makes backfilling slow — and this can't be relaxed, since single concurrency is a correctness requirement, not a performance choice. Only lever: check whether the whole pipeline truly needs to backfill, or just part of it.

⚠ Latency

A milder case than backfilling: stragglers. An hourly job that normally takes 30 min creeping to 1.5h compounds delay run over run, and every downstream consumer inherits it. Mitigation: add compute power or improve the processing logic on scalable infrastructure.

Examples

python · Apache Airflow
with DAG('visits_trend_generator', max_active_runs=1, default_args={
    'depends_on_past': True,
    # ...
📌 Note

AWS EMR exposes StepConcurrencyLevel for cluster-wide concurrency. Azure Data Factory's Concurrency setting queues excess runs (up to 100) rather than blocking — once full, scheduling returns HTTP 429.

PatternConcurrent Runner

Problem

A data ingestion team pulls external at-rest data every 30–60 minutes, sometimes longer. Running under Single Runner, every subsequent delivery is delayed behind a slow one — even though the ingested datasets are actually independent.

Solution

Since datasets don't depend on each other, set concurrency higher than 1 — the Concurrent Runner pattern. The orchestrator picks up the next scheduled run as soon as capacity allows. "With great power comes great responsibility" — balance the ceiling against overall infrastructure capacity.

Consequences

⚠ Resource starvation

In multitenant orchestrators, several high-concurrency pipelines backfilling simultaneously can starve other teams' capacity. Mitigation: workload management — allocate dedicated capacity per team so one team can't exceed its threshold. Serverless orchestrators (e.g. Step Functions, up to 10,000 parallel child executions) may avoid this entirely.

⚠ Shared state

Touching a shared component under concurrent, nondeterministic execution causes unexpected side effects — e.g. the Dynamic Late Data Integrator (Ch. 4) could trigger backfilling multiple times, or not at all for some dates.

Examples

python · Apache Airflow
with DAG('devices_loader', max_active_runs=5,
    default_args={
        'depends_on_past': False,
        # ...

◆ Trade-Off Tables

Fan-In: Aligned vs. Unaligned

PatternWhen to UseTrade-Off
Aligned Fan-In All branch inputs are equally required for a correct, complete result. Simpler, single output — but one failed branch blocks the merge entirely; gated by the slowest parent; infra spikes under simultaneous branches.
Unaligned Fan-In Timely partial results beat a complete-but-delayed result; gaps can be backfilled later. Requires explicit completeness tracking or consumers silently assume 100%; dual success/failure branches reduce DAG readability.

Fan-Out: Parallel Split vs. Exclusive Choice

PatternWhen to UseTrade-Off
Parallel Split Multiple consumers genuinely need the same upstream data at the same time (e.g. dual-write migration). All branches share one hardware profile unless split further; blocks on the slowest branch; must guard against duplicate writes on retry.
Exclusive Choice Only one of several paths should execute per run (e.g. cut-over date routing). Easy to over-branch into a "complexity factory"; hidden processing-layer logic is easy to forget; data-driven conditions add runtime cost.

Orchestration: Single Runner vs. Concurrent Runner

PatternWhen to UseTrade-Off
Single Runner Pipeline logic is incremental/stateful — correctness depends on the previous run's output. Backfilling is slow (can't parallelize — correctness-driven); stragglers compound latency for every downstream consumer.
Concurrent Runner Runs are independent of each other (e.g. unrelated external datasets). Risk of resource starvation in multitenant orchestrators without workload management; shared mutable state causes nondeterministic bugs.

Cheat Sheet — five minutes before the interview

Local Sequencer
Problem: One bloated job, hard to debug/maintain.
Solution: Ordered, dependency-driven steps.
Gotcha: No universal split boundary.
Isolated Sequencer
Problem: Two teams must hand off data, not merge ownership.
Solution: Data- or trigger-based cross-pipeline dependency.
Gotcha: Cross-boundary scheduling & comms overhead.
Aligned Fan-In
Problem: Need one daily result from 24 hourly partitions.
Solution: Branch per hour, merge via UNION/JOIN when all succeed.
Gotcha: Slowest parent gates everything.
Unaligned Fan-In
Problem: Aligned Fan-In blocks entirely on one failed hour.
Solution: trigger_rule=ALL_DONE + completeness metric.
Gotcha: Must signal incompleteness explicitly.
Parallel Split
Problem: Write the same data to two destinations.
Solution: Materialize once (.persist()), fan out.
Gotcha: Slowest branch blocks subsequent runs.
Exclusive Choice
Problem: Only one job variant should run per condition.
Solution: Router/branch task before splitting.
Gotcha: Over-branching → unreadable complexity factory.
Single Runner
Problem: Incremental logic breaks under concurrent instances.
Solution: max_active_runs=1.
Gotcha: Slow, non-parallelizable backfilling.
Concurrent Runner
Problem: Independent datasets needlessly serialized.
Solution: Raise concurrency above 1.
Gotcha: Resource starvation & shared-state bugs.

Special Notes

  • Apache Airflow: >> for sequencing; BranchPythonOperator for Exclusive Choice; trigger_rule=ALL_DONE for Unaligned Fan-In; ExternalTaskMarker/ExternalTaskSensor for Isolated Sequencer; max_active_runs + depends_on_past for runner control; on_failure_callback for clean failure handling.
  • AWS EMR: Step API for sequencing; StepConcurrencyLevel for cluster-wide concurrency; ActionOnFailure=TERMINATE_CLUSTER avoids silently exposing partial data.
  • Azure Data Factory: if-condition activity for Exclusive Choice; Concurrency setting queues (not blocks) excess runs up to 100, then returns HTTP 429; no task-based dependency support.
  • Delta Lake: txnVersion/txnAppId give idempotent, retry-safe writes — directly relevant to Parallel Split.
  • Cross-reference: the Factory software-engineering pattern used in the Exclusive Choice example.
