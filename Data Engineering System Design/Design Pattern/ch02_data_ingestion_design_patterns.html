Chapter 2 — Data Ingestion Design Patterns

How to bring data acquired from external producers, other pipelines, and other teams into your system — full and incremental loading, replication, compaction, readiness, and event-driven triggers — built around the book's blog analytics case study.

Patterns covered: 7 Category: Ingestion → Bronze Layer Design note: editorial reference-manual aesthetic — ink navy, parchment page, brass accent

Chapter Framing

Data engineering systems are rarely data generators — their first stage is almost always data acquisition from producers you don't control: other pipelines, other teams, or entirely different organizations. Each producer comes with its own constraints, and you have to adapt or you simply won't get the data you need.

This chapter covers how much to load (Full vs. Incremental), how to copy data as-is or transformed (Replication), and the operational mechanics around ingestion that aren't about moving data at all: readiness, compaction, and event-driven triggering.

🧩 Case Study

The book's running example is a blog analytics platform. Most visit events arrive in real time via a streaming broker, but some legacy producers still write to a transactional database — this exact split motivates the Incremental Loader and, later, Change Data Capture.

01 / FULL LOAD

Pattern: Full Loader

Problem

You're setting up the Silver layer. A transformation job needs extra device information from an external provider. The dataset changes only a few times a week, is slowly evolving, and never exceeds one million rows — but the provider defines no "last updated" attribute to detect which rows changed.

Solution

The absence of a delta signal makes Full Loader the ideal fit. The simplest implementation is a two-step extract and load (EL) job — also called a passthrough job — using native store commands for homogeneous stores. For heterogeneous stores, add a thin transformation layer, turning it into an ETL job on a processing framework with native connectors.

Consequences
Data volume. Usually a scheduled batch job with roughly constant compute needs — but a dataset that doubles overnight can slow or fail a statically provisioned job. Mitigate with auto-scaling.
Data consistency. A naive drop-and-insert overwrite risks (1) consumers seeing partial/zero data mid-run, and (2) losing the ability to roll back. Use transactions, a view-swap abstraction, or a time-travel format (Delta Lake, Iceberg, BigQuery).
⚠️ Warning

Although framed around ingestion, every pattern here directly impacts downstream analytics and data science workloads, since they're the ones loading data into the system.

✅ Say this out loud

"We chose Full Loader because the provider gives us no delta signal — but we protect consumers from partial reads with a view-swap so ingestion never blocks or half-exposes the dataset."

Examples
bash 
aws s3 sync s3://input-bucket s3://output-bucket --delete
python

input_data.write.format("delta").save("s3://master/devices")
sql

sql

02 / INCREMENTAL LOAD

Pattern: Incremental Loader

Problem

Most visit events stream in real time, but some legacy producers still write to a transactional database. Ingestion should only integrate visits added since the last execution as volume continuously grows. Each visit is immutable.

Solution

Two implementations, by input structure:

  • Delta column — a column (typically ingestion_time) marks new rows since the last run. Requires remembering the last-processed value.
  • Time-partitioned datasets — the job targets a whole new partition each run (e.g., a job at 11:00 targets the previous hour). No state needed; pair with Readiness Marker to confirm the partition is safe to ingest.
Figure 2-2 — Two implementations of Incremental Loader
flowchart TD subgraph DeltaCol["Delta Column"] direction LR A1[Remember last ingestion_time] --> A2[WHERE ingestion_time > last_value] --> A3[Ingest new rows] end subgraph PartitionBased["Partition-Based"] direction LR B1[Resolve partition from execution time] --> B2[Wait for Readiness Marker] --> B3[Ingest whole partition] end
⚠️ Warning — Be aware of real-time issues

Using event time as a delta column is risky: your ingestion process might miss records if the producer emits late data for an event-time value you already processed.

Consequences
Hard deletes. A physically deleted row leaves no trace in a delta-column read. Mitigate with soft deletes (producer marks rows via UPDATE) or insert-only tables that shift reconstruction responsibility to consumers.
Backfilling. Backfilling a delta-column pipeline can silently become a full load. Mitigate by bounding the window: delta_column BETWEEN ingestion_time AND ingestion_time + INTERVAL '1 HOUR' — predictable volume, and safe concurrent backfill jobs. Partition-based loaders avoid this if they process one partition at a time.
✅ Say this out loud

"We limit the ingestion window explicitly during backfills so a replay never silently turns into a full load — that keeps compute needs predictable and lets us parallelize backfill jobs safely."

03 / INCREMENTAL LOAD

Pattern: Change Data Capture (CDC)

Problem

Legacy visit events integrated via Incremental Loader now need lower latency: the ingestion job must capture each database change within 30 seconds and publish it to a central streaming topic.

Solution

Incremental Loader's job-scheduling and query overhead make 30-second latency hard to hit. CDC reads continuously from the database's commit log — an append-only structure recording every row operation — for lower-level, faster access. A CDC consumer streams changes to a broker; consumers can keep full history or just the latest value per row. CDC intercepts all operations, including hard deletes, so soft deletes are no longer required upstream.

Figure 2-3 — Debezium-style CDC flow (commit log → topic)
sequenceDiagram participant DB as Database (commit log) participant CDC as CDC Consumer (Debezium) participant Topic as Kafka Topic participant Cons as Downstream Consumer DB->>DB: INSERT / UPDATE / DELETE row DB->>CDC: Append change to commit log CDC->>Topic: Stream change (op type, time, columns) Topic->>Cons: Consume change event Note over Cons: Data-at-rest has become data-in-motion
Consequences
Complexity. Unlike the loaders, CDC often needs operations-team involvement (enabling the commit log on database servers).
Data scope. Depending on the client, you may only capture changes from client-start onward — combine with another pattern for history.
Payload. Records carry extra metadata (operation type, modification time, column type) consumers must learn to filter.
Data semantics. CDC output is data-in-motion. A JOIN against two streaming sources returning nothing may just mean the data hasn't arrived yet — don't treat it as static data-at-rest.
📌 Note

Lake-native formats support CDC more simply than a full Debezium setup — Delta Lake's built-in change data feed (CDF) can be enabled per-session or per-table.

Comparison — Full Loader vs. Incremental Loader vs. CDC
PatternWhen to UseTrade-off
Full Loader No delta/last-updated signal exists; small-to-moderate, slowly evolving dataset Simple, but costly at scale — needs auto-scaling and a consistency strategy
Incremental Loader Continuously growing, append-mostly dataset with a usable delta column or partitions Cheaper, but struggles with hard deletes and can balloon during backfills
Change Data Capture Low-latency requirement (seconds); need native hard-delete support Lowest latency, full operation coverage — highest setup complexity

Replication

📌 Note — Data Loading vs. Replication

Replication moves data between the same type of storage and ideally preserves all metadata (primary keys, stream offsets). Loading is more flexible and doesn't require homogeneous environments.

04 / REPLICATION

Pattern: Passthrough Replicator

Problem

Three environments — dev, staging, production — share a reference device-parameters dataset loaded daily from a third-party API. The API is not idempotent, so replaying the loading pipeline per environment won't reproduce the same data. You need the exact same data everywhere.

Solution

A non-idempotent provider plus cross-environment consistency needs is the textbook case for Passthrough Replicator:

  • Compute-level (EL job) — read then write, copying as-is, no transformation, avoiding quality issues like type coercion or rounding.
  • Infrastructure-level — a replication policy document configuring input/output locations, letting the storage provider replicate for you.
Consequences
Keep it simple. Use the simplest mechanism available; prefer raw text APIs over JSON I/O APIs to avoid silent reinterpretation.
Security and isolation. Prefer push over pull to avoid destabilizing the source environment.
PII data. If the dataset carries PII, switch to Transformation Replicator.
Latency. Infra-based implementations add latency — check your provider's SLA.
Metadata. Don't ignore metadata — replicating only the Parquet files of a Delta Lake table isn't enough.
Examples
python 
events_to_replicate = (input_data_stream
    .selectExpr('key', 'value', 'partition', 'headers', 'offset'))

def write_sorted_events(events, batch_number):
    (events.sortWithinPartitions('offset', ascending=True).drop('offset').write
        .format('kafka').option('kafka.bootstrap.servers', 'localhost:9094')
        .option('topic', 'events-replicated').option('includeHeaders', 'true').save())

write_data_stream = (events_to_replicate.writeStream
    .option('checkpointLocation', f'{get_base_dir()}/checkpoint-kafka-replicator')
    .foreachBatch(write_sorted_events))

05 / REPLICATION

Pattern: Transformation Replicator

Problem

Before a release, you want to test against real data — synthetic generators can't replicate real data-quality issues. But the production dataset contains PII not accessible outside production, ruling out a plain Passthrough Replicator job.

Solution

Transformation Replicator adds a transformation layer between the read and write steps — a custom mapping function (Spark, Flink) or a SQL SELECT. It either replaces disallowed attributes (e.g., with Anonymizer) or removes them entirely.

🧩 Case Study — Not only PII

PII is only the most common case; protected health information (PHI) and intellectual property (IP) data need the same treatment.

Consequences
Transformation risk for text formats. A datetime format mismatch can silently drop timestamp columns and fail staging. Keep ambiguous columns as plain strings rather than typed dates.
Desynchronization. Privacy fields change over time — new PII attributes appear, old ones get reclassified. Rely on a governed data catalog / data contract so transformation logic stays automated.
✅ Say this out loud

"We route PII removal through governance-tagged fields rather than a hardcoded column list, so a newly-classified PII attribute doesn't silently leak into staging."

Examples
sql 
SELECT * EXCEPT (ip, latitude, longitude)
python

users_no_pii = input_delta_dataset.drop('ip', 'latitude', 'longitude')
sql

Data Compaction

06 / COMPACTION

Pattern: Compactor

Problem

A real-time pipeline syncs events to an object store within a 10-minute target. It's a simple passthrough job — until, three months later, batch jobs spend 70% of execution time listing files and only 30% processing data, due to accumulated small files.

Solution

The small-files problem has existed since the Hadoop era. Many small files mean longer listing operations and heavier I/O. Compactor merges small files into bigger ones. Implementation varies: Iceberg uses a rewrite data file action; Delta Lake uses OPTIMIZE; Hudi merges row-format changes into columnar storage; Kafka's log compaction (config-driven) keeps only the latest entry per key, actually overwriting data rather than reorganizing files.

Consequences
Cost vs. performance trade-off. No one-size-fits-all frequency — running rarely saves compute but denies uncompacted jobs the optimization in the meantime.
Consistency. Compaction rewrites existing data; far safer in ACID formats (Delta Lake, Iceberg) than raw formats (JSON, CSV).
Cleaning. Compaction may preserve original small files — you need a follow-up VACUUM job, and a careless retention window can break time travel.
⚠️ Warning

Compaction and cleaning are two separate jobs. Skipping cleanup leaves the small-files problem partially unsolved even after compaction runs.

Examples
python 
devices_table = DeltaTable.forPath(spark_session, table_dir)
devices_table.optimize().executeCompaction()
python 
devices_table = DeltaTable.forPath(spark_session, table_dir)
devices_table.vacuum()

Data Readiness

07 / READINESS

Pattern: Readiness Marker

Problem

An hourly Silver-layer job feeds ML models and BI dashboards for other teams — who frequently complain about incomplete datasets and want a way to know when it's safe to consume.

Solution

Since logically dependent but physically isolated pipelines can't trigger each other directly, mark the dataset ready:

  • Flag file — created after successful generation. Native to some layers (Spark's _SUCCESS, Delta Lake's commit log) or added as a final orchestration task.
  • Partition convention — for time-partitioned data, the appearance of partition N+1 implies partition N is complete.
Consequences
Lack of enforcement. Both implementations rely on pull semantics and convention — nothing stops a consumer reading mid-write. Communicate the readiness conditions clearly.
Reliability for late data. Late data breaks the "next partition means previous is done" convention. Treat partitions as immutable once closed, or explicitly share mutability rules and notify consumers of corrections separately.
📌 Note

The readiness marker should always be generated as the last step in a pipeline, after the final transformation.

Examples
python 
dataset = (spark_session.read.schema('...').json(f'{base_dir}/input'))
dataset.write.mode('overwrite').format('parquet').save('devices-parquet')
# _SUCCESS file written automatically after data files complete
python

    filepath=f'{input_data_file_path}/_SUCCESS',
    mode='reschedule',
)
python

    shutil.rmtree(dataset_dir, ignore_errors=True)

@task

    ...  # processing, omitted for brevity

    with open(f'{dataset_dir}/COMPLETED', 'w') as marker_file:

delete_dataset() >> generate_dataset() >> create_readiness_file()
📌 Note

mode='reschedule' on the FileSensor matters: it frees the worker slot between checks instead of blocking it, so the orchestration layer isn't occupied just waiting on data.

Event Driven

08 / EVENT DRIVEN

Pattern: External Trigger

Problem

The backend team releases features irregularly (Monday–Thursday, at most weekly). The refresh job runs daily regardless of whether anything changed, wasting compute. The team already sends a notification event on every release.

Solution

Readiness Marker relies on pull semantics; event-driven data favors push semantics. External Trigger has three steps:

  • Subscribe to a notification channel.
  • React — an event handler decides whether to trigger a pipeline or job, optionally filtering event types.
  • Trigger the ingestion pipeline or job — typically one event to one pipeline, though fan-out to several is possible.
📌 Note — Not only trigger

If there's no separate job to trigger, you can run the ingestion logic directly inside the notification handler — simply called event-driven data ingestion.

Figure 2-4 — External trigger flow
flowchart LR P[Backend Team
publishes feature] -->|event| Bus[Message Bus] Bus --> Handler[Event Handler
Lambda] Handler -->|POST /dagRuns| Orchestrator[Airflow DAG
schedule_interval=None] Orchestrator --> Bronze[(Bronze Layer)] Handler -.on failure.-> DL[Dead-Letter]
Consequences
Push versus pull. A pull-based trigger polls at short intervals — wasteful, since most polls find nothing new. Push-based is better: the source notifies the endpoint directly, spinning up a short-lived consumer.
Execution context. Don't let the trigger degenerate into a bare ping. Enrich it with metadata (trigger version, notification envelope, processing time, event time) for monitoring and debugging.
Error management. Events are the sole driver of the pipeline — design for failure so events are never silently dropped, typically via Dead-Letter (Chapter 3).
Examples
python 
with DAG('devices-loader', max_active_runs=5, schedule_interval=None,
         default_args={'depends_on_past': False}) as dag:
    pass  # pipeline just copies the file from the trigger
python 
def lambda_handler(event, ctx):
    payload = {
        'event': json.dumps(event),
        'trigger': {
            'function_name': ctx.function_name,
            'function_version': ctx.function_version,
            'lambda_request_id': ctx.aws_request_id
        },
        'file_to_load': (urllib.parse.unquote_plus(
            event['Records'][0]['s3']['object']['key'], encoding='utf-8')),
        'dag_run_id': f'External-{ctx.aws_request_id}'
    }
    trigger_response = requests.post(
        'http://localhost:8080/api/v1/dags/devices-loader/dagRuns',
        data=json.dumps({'conf': payload}), auth=('dedp', 'dedp'), headers=headers)
    if trigger_response.status_code != 200:
        raise Exception(f"Couldn't trigger the `devices-loader` DAG. "
                         f"{trigger_response} for {payload}")
    else:
        return True
⚠️ Warning

The example above hardcodes credentials for readability only. In real pipelines, apply the Chapter 7 data security patterns (e.g., Secretless Connector, Secrets Pointer) instead.

Gotchas — By Pattern

Full Loader
  • Rapidly growing datasets can outpace static compute — use auto-scaling.
  • Drop-and-insert overwrites risk consumer-visible partial data and loss of rollback.
Incremental Loader
  • Delta-column implementations can't see hard deletes — use soft deletes or insert-only tables.
  • Backfilling can silently become a full load — bound the ingestion window explicitly.
Change Data Capture
  • Requires operations-team-level setup — heavier than the loaders.
  • CDC output is data-in-motion — joins behave differently than on data-at-rest.
  • Client may only capture changes from start-time forward — combine with another pattern for history.
Passthrough Replicator
  • Any transformation risks quality issues — prefer raw copy commands.
  • Pull-based replication risks destabilizing the source environment — prefer push.
  • Cannot be used if the dataset carries PII.
Transformation Replicator
  • Schema-based transformations can silently drop or corrupt columns.
  • PII definitions drift over time — tie transformation to a governed field list.
Compactor
  • No universally correct compaction frequency — a deliberate cost-vs-performance choice.
  • Compaction without cleanup (VACUUM) leaves the original small files in place.
Readiness Marker
  • Convention-based readiness is not enforced — a consumer can read mid-write.
  • Late data breaks the partition convention unless immutability or mutability rules are explicit.
External Trigger
  • Pull-based (polling) triggers waste resources — prefer push.
  • A trigger with no execution context becomes hard to debug — always pass metadata.
  • The pipeline lives or dies by event delivery — plan for dead-lettering failed invocations.
