Chapter 4
Idempotency Design Patterns

Overwriting · Updates · Database-native guarantees · Immutable datasets — a field reference for interviews and design reviews.

▤ 7 patterns · 4 families

Chapter Framing

Errors are inevitable, and Chapter 3's error-management patterns handle most of the fallout — but not all of it. A retried task or job can replay writes that already succeeded. Best case: duplicates a consumer can filter out. Worst case: duplicates indistinguishable from the original records.

Idempotency is the fix — the guarantee that no matter how many times a job runs (retry, backfill, manual replay), the output stays consistent. The book anchors this in the absolute() function: absolute(-1) == absolute(absolute(absolute(-1))). Credit goes to Maxime Beauchemin's 2018 article for popularizing the concept in data engineering.

02 Pattern-by-Pattern Breakdown

Fast Metadata Cleaner

Overwriting

Problem

A daily batch job processes between 500 GB and 1.5 TB of visits data events. Idempotency is guaranteed with two steps: a DELETE that removes all rows added by the previous run, then an INSERT of the newly processed rows. This worked fine for three weeks, but as the table grew, the DELETE task's performance degraded considerably.

Solution

DELETE is often a two-step operation: identify rows, then rewrite affected data files — slow at scale. TRUNCATE TABLE and DROP TABLE are metadata operations that skip the table scan entirely.

📌 Note

TRUNCATE TABLE table_a is semantically equivalent to DELETE FROM table_a without conditions, but doesn't perform a table scan — hence it's a metadata operation.

Think of the dataset as multiple physically isolated tables (e.g., weekly tables) exposed through a single logical view. The idempotency granularity is the physical unit that metadata operations clean and repopulate. Implementation needs three orchestration steps:

  1. Decide the branch — analyze the execution date to start a new granularity or continue the current one (Exclusive Choice pattern).
  2. Create the idempotency environment — TRUNCATE (often preceded by table creation) or DROP (followed by re-creation).
  3. Update the exposition layer — refresh the view/union; optionally remove the table from the view before dropping it, to avoid reader errors.
🧩 Case Study

The blog analytics platform stores 52 weekly visits tables, unioned through a single view. The idempotency (and backfill) granularity is one week.

The pattern also applies to fully loaded tables — simply re-create the table each load, or fall back to Data Overwrite.

Consequences

Granularity and backfilling boundaryReplay must start from the task that creates the partitioned table. Backfilling one day inside a week means rerunning that whole week's creation step. Fine-grained (per-user) backfills aren't supported — metadata ops act on whole tables.
Metadata limitsWarehouses cap partitions/tables (BigQuery: 4,000 partitions; Redshift: 200,000 tables). Mitigate with a freezing step that turns mutable tables immutable on a longer cadence. Only works on stores supporting metadata ops — not object stores.
Data exposition layerThe dataset no longer lives in one place; end users typically want a single access point (a view).
Schema evolutionNew optional fields need a separate backfill pipeline. New required fields piggyback naturally since replaying past runs re-triggers processing.
✅ Say this out loud

TRUNCATE and DROP skip the table scan that makes DELETE slow at scale — but the idempotency granularity they create also becomes my backfill granularity, so partition size has to be chosen carefully.

Data Overwrite

Overwriting

Problem

You need a data-removal / idempotency approach that works even where metadata-only operations (TRUNCATE/DROP) aren't supported — e.g., an object store, or where a single full-table INSERT OVERWRITE-style replace is preferable to managing multiple physical tables. [verify against source page for the book's exact framing]

Solution

Where Fast Metadata Cleaner works at the logical level, Data Overwrite works at the physical data level — it actually rewrites files. The classic approach is DELETE then INSERT; a more concise alternative is INSERT OVERWRITE, which replaces the whole table with the SELECT's result (no row-level selectivity, unlike DELETE+INSERT).

📌 Note

INSERT doesn't require literal values — you can insert from a SELECT against another table, e.g. INSERT INTO visits (id, v_time) SELECT visit_id, visit_time FROM visits_raw.

Some stores support native overwrite loading (BigQuery's LOAD DATA OVERWRITE); others need a preceding TRUNCATE. Stores with time travel (table file formats, BigQuery, Snowflake) keep old blocks until retention expires or vacuum runs.

Consequences

Data overheadBig, unpartitioned tables get slower to overwrite over time. Mitigate with partitioning to reduce volume touched per overwrite.
Vacuum needDELETE may not remove data from disk immediately; dead blocks persist (inaccessible but present) until a vacuum process reclaims space.
⚠️ Warning

Spark's overwrite save mode is not transactional by itself — the guarantee depends entirely on the target format. Modern table file formats fix this because the delete becomes a new commit; data files stay untouched until commit succeeds.

✅ Say this out loud

INSERT OVERWRITE is simpler than DELETE+INSERT, but it's a full-table replace with no row-level selectivity — on unpartitioned big tables the data-level rewrite is the real cost, which is why I'd pair it with partitioning.

Examples

sql — INSERT OVERWRITE
INSERT OVERWRITE INTO devices SELECT * FROM devices_staging WHERE state = 'valid';
bash — BigQuery load with replace
bq load dedp.devices gs://devices/in_20240101.csv ./info_schema.json --replace=true
python — PySpark overwrite
input_data.write.mode('overwrite').text(job_arguments.output_dir)

Merger

Updates

Problem

A pipeline manages a stream of changes synchronized from an Apache Kafka topic via Change Data Capture. A new batch pipeline must replicate all changes into an existing Delta Lake table so the table fully reflects the source at any moment — no duplicates allowed.

Solution

When the full dataset isn't available each run, you need to combine new and existing rows — implemented with the MERGE (a.k.a. UPSERT) command supported by most modern frameworks, table file formats, and warehouses.

📌 Note

Idempotent processing for fully available datasets is simpler via an overwriting pattern. Merger is for incremental datasets where delete-and-replace isn't viable.

Define uniquely-identifying attributes, then define behavior per scenario:

  • Insert — new record absent from the current dataset.
  • Update — record exists in both; new dataset likely has an updated version.
  • Delete — trickiest case. Merger has no native delete; a missing record does nothing. Must be expressed as a soft delete (is_deleted flag).
sql — soft-delete MERGE
MERGE INTO dedp.devices_output AS target
USING dedp.devices_input AS input
ON target.type = input.type AND target.version = input.version
WHEN MATCHED AND input.is_deleted = true THEN
  DELETE
WHEN MATCHED AND input.is_deleted = false THEN
  UPDATE SET full_name = input.full_name
WHEN NOT MATCHED AND input.is_deleted = false THEN
  INSERT (full_name, version, type) VALUES (input.full_name, input.version, input.type)
⚠️ Warning

The is_deleted = false condition on INSERT is essential — without it, a first run could insert already-removed records you can never get rid of.

Consequences

UniquenessMust have immutable attributes to safely identify each record — otherwise backfills can insert duplicates instead of updating.
I/OData-block-level operation, more compute intensive than metadata patterns; mitigated by stores consulting metadata statistics to skip irrelevant files.
Incremental datasets with backfillingBackfilling from an earlier point starts from the most recent dataset version, so consumers can briefly see rows that shouldn't exist yet, until later runs catch up. Solved by Stateful Merger.
✅ Say this out loud

Merger handles insert/update naturally through MERGE, but deletes have to be modeled as soft deletes — a missing row in an incremental feed is invisible to the merge logic, so hard deletes just can't be expressed.

Examples

sql — load then merge
CREATE TEMPORARY TABLE changed_devices (LIKE dedp.devices);
COPY changed_devices FROM '/data_to_load/dataset.csv' CSV DELIMITER ';' HEADER;

MERGE INTO dedp.devices AS d USING changed_devices AS c_d
ON c_d.type = d.type AND c_d.version = d.version
WHEN MATCHED THEN
  UPDATE SET full_name = c_d.full_name
WHEN NOT MATCHED THEN
  INSERT (type, full_name, version) VALUES (c_d.type, c_d.full_name, c_d.version)

Stateful Merger

Updates

Problem

Changes were synced between two Delta Lake tables using the Merger pattern. A week later, an issue was found in the merged dataset, and business users need a backfill — but restored first to the last valid version, since they care about consistency. Plain Merger doesn't support this.

Solution

Extend Merger with a state table tracking, per execution time, which table version was produced. The pipeline gains a restore step at the start (backfill-only) and a state update step at the end.

sql — state table
CREATE TABLE IF NOT EXISTS `default`.`versions`
(execution_time STRING NOT NULL, delta_table_version INT NOT NULL)

Restore logic (backfill mode only):

  • No version for prior execution time → truncate the table.
  • Recorded version differs from current latest → roll back to that version.
  • Otherwise → normal run, do nothing.
📌 Note

Without a versioned store, adapt the pattern: load raw data into a history table stamped with execution time; detect backfill mode via rows with a future execution time; rebuild using the Windowed Deduplicator pattern instead of a version rollback.

Consequences

Versioned data storesRequires a versioned store (Delta Lake, Iceberg) or the raw-history-table adaptation.
Vacuum operationsRetention periods remove old files the state table points to. Mitigate by increasing retention (costs more storage) or accepting backfill limits.
Metadata operationsNo-data operations like compaction still create a new version. Using "the previous run's recorded version" naively misses compactions between runs — fix by using (current execution's version − 1) instead.
✅ Say this out loud

Merger alone can't recover cleanly from backfilling because it only tracks the merge action, not table history. Stateful Merger adds a state table mapping execution time to table version, so a backfill can roll back before re-merging — as long as I account for no-data commits like compaction consuming a version number.

Examples

last_merge_version = (spark.sql('DESCRIBE HISTORY default.devices')

Keyed Idempotency

Database-native

Problem

A streaming pipeline processes visit events to generate user sessions, buffering messages per user in a time window and writing to a key-value store. Retries must not create duplicate sessions.

Solution

For key-based stores, idempotency comes from the key generation logic: generate the same key for the same logical entity every time, regardless of retries.

Start with immutable attributes to key on. If the natural key would collapse multiple sessions into one, use a composite key — but event time is mutable: late data can shift the derived key across restarts.

⚠️ Warning

Using a mutable timestamp (event time) in key generation is a trap. If a job restarts and a late record has since arrived, the recomputed key differs from the original — a new session gets created instead of resuming the old one.

Fix: key on an immutable timestamp — the broker's append time (Kafka: append time; Kinesis: approximate arrival timestamp; at-rest stores: added/ingestion/insertion time). This value never changes after the fact.

sql — window keyed on ingestion_time
SELECT ... OVER (PARTITION BY user_id ORDER BY ingestion_time ASC, visit_time ASC)

The same strategy extends to file outputs: name daily job output by execution time so replays always produce the same filename — applies to partitions or whole tables too.

Consequences

Database dependentWorks cleanly on key-based NoSQL (Cassandra, ScyllaDB, HBase). On relational DBs, duplicate primary key inserts error — need MERGE instead of INSERT. On Kafka, duplicates can be visible until async compaction catches up (though sharing the same key aids identification).
Mutable data sourceCompaction can expire old events. If the original keying record gets compacted away before a restart, the job derives its key from the next available record — logically breaking idempotency (though arguably reasonable, since the data genuinely changed shape).
✅ Say this out loud

The idempotency guarantee lives entirely in the key-generation logic — key on an immutable attribute like Kafka's append time, not event time, because event time can shift under late data and silently produce a different key on restart.

Examples

sql — ScyllaDB sessions table
CREATE TABLE sessions (
  session_id BIGINT,
  user_id BIGINT,
  pages LIST<TEXT>,
  ingestion_time TIMESTAMP,
  PRIMARY KEY(session_id, user_id));

Transactional Writer

Database-native

Problem

A batch job runs on a cloud provider's unused compute capacity — 60% infrastructure savings. But whenever the provider reclaims a node, running tasks fail and retry elsewhere, rewriting data already written. Downstream consumers see duplicates and incomplete records. The job must never expose partial data.

Solution

Lean on native database transactions: in-progress, uncommitted changes stay invisible to downstream readers until commit.

  1. Initialize — START TRANSACTION / BEGIN, explicit or implicit.
  2. Write — changes recorded but private to the transaction.
  3. Commit to publish, or rollback to discard.

Two shapes depending on processing model:

  • Standalone/ELT at the storage layer (BigQuery, Redshift, Snowflake) — transaction is declarative, fully store-managed.
  • Distributed ETL — either a local (task-based) transaction (fine without retries, risky with them) or a whole-job transaction (opens before any task runs, commits once all finish — stronger, harder).
⚠️ Warning

Even with writer-side transactions, a reader using read uncommitted isolation can still see records from a transaction that later rolls back — a classic dirty read.

Supported by table file formats (Delta Lake, Iceberg, Hudi), Kafka, warehouses (Redshift, BigQuery), and RDBMSes — but framework support is uneven: Kafka transactional producers are Flink-only, not available in Spark.

Consequences

Commit stepTwo extra steps (open + commit) plus conflict resolution add latency. Transactional formats only become visible once the commit log entry is written — consumers wait for the slowest task.
Distributed processingSupport isn't universal — e.g., Kafka transactional producers aren't available in Spark, significantly limiting scope.
Idempotency scopeGuarantee is limited to the transaction itself. A job restart or backfill opens a new transaction and can happily re-commit already-successful data.
✅ Say this out loud

Transactions give all-or-nothing visibility — a partial write never becomes visible — but the idempotency only covers a single transaction's scope. A retry or backfill gets a brand-new transaction that can duplicate already-successful data. This solves partial-data visibility, not duplicate prevention across retries.

Examples

sql — two operations, one transaction
CREATE TEMPORARY TABLE changed_devices_file1 (LIKE dedp.devices);
COPY changed_devices_file1 FROM '/data_to_load/dataset_1.csv' CSV DELIMITER ';' HEADER;

-- ... omitted for brevity

CREATE TEMPORARY TABLE changed_devices_file2 (LIKE dedp.devices);
COPY changed_devices_file2 FROM '/data_to_load/dataset_too_long_type.csv' CSV DELIMITER ';' HEADER;
MERGE INTO dedp.devices AS d USING changed_devices_file1 AS c_d
-- ... omitted for brevity
COMMIT;

Proxy

Immutable Dataset

Problem

A batch job generates a full dataset each run; historically only the most recent version was kept by overwriting the previous one. Legal now requires every past version retained — the mutable overwrite approach no longer works. The pipeline must keep every copy while exposing only the latest from a single access point.

Solution

Named after the classic saying: "We can solve any problem by introducing an extra level of indirection." The Proxy sits between end users and physical storage, like a network proxy.

  1. Guarantee immutability — load new data into a different location each run (timestamped/versioned table). Remove write permissions immediately after creation, so it's writable only once. On object stores, strengthen with native WORM locks (AWS S3 Object Lock, Azure Blob immutability policies, GCP object holds / bucket locks).
  2. Create a single access point — a passthrough view exposing the most recent table, with no transformation logic.

Consequences

Database supportNot every database has a convenient view abstraction; a manifest file can substitute but is more cumbersome to read.
Immutability configurationOrchestration-level enforcement alone isn't enough — typically needs infrastructure-level enforcement too (object-store locks, revoked write permissions), likely requiring the infra team.
PermissionsThe user managing tables must be scoped to only create tables — otherwise they could accidentally delete an internal table and break the immutability guarantee.
✅ Say this out loud

Proxy gives write-once semantics by never writing to the same physical location twice — each run gets its own versioned table with write permissions revoked right after creation — and a passthrough view is the single stable access point clients query, so consumers never need to know the internal versioning scheme.

Examples

python — Airflow pipeline: load then refresh view
load_data_to_internal_table = PostgresOperator(
    sql='/sql/load_devices_to_weekly_table.sql'
)
refresh_view = PostgresOperator(  # ...
    sql='/sql/refresh_view.sql'
)
load_data_to_internal_table >> refresh_view

04 Gotchas — by Pattern

Fast Metadata Cleaner

  • Backfill granularity is locked to the idempotency (partition) granularity — no fine-grained per-user backfills.
  • Partition/table count limits (BigQuery 4,000 partitions, Redshift 200,000 tables) — mitigate with a freezing step.
  • Only works where metadata operations exist — not on object stores.
  • Optional schema fields need a dedicated backfill pipeline; required fields piggyback on replays.

Data Overwrite

  • Large, unpartitioned tables slow down over time; mitigate with partitioning.
  • Deleted data can occupy disk until vacuum runs.
  • Spark's overwrite mode isn't transactional by itself — depends on target format.

Merger

  • Requires a genuinely unique key, or backfills can insert duplicates instead of updating.
  • Data-block-level operation — more compute-intensive (though modern stores optimize with statistics).
  • Deletes must be modeled as soft deletes; true deletes aren't natively expressible.
  • Backfilling from an old point transiently shows inconsistent rows — fixed by Stateful Merger.

Stateful Merger

  • Requires a versioned/time-travel-capable store, or a raw-history-table workaround.
  • Vacuum/retention limits how far back you can restore.
  • Compaction consumes a version number — must offset by one rather than trusting the previous run's recorded version.

Keyed Idempotency

  • Works cleanly on key-based NoSQL; needs MERGE on relational DBs; Kafka duplicates visible until compaction.
  • Keying on mutable event time breaks idempotency under late data and restarts.
  • Compaction can expire the original keying record, changing the derived key on restart.

Transactional Writer

  • Extra open/commit latency; consumers wait for the slowest task's commit.
  • Uneven framework support (e.g., Kafka transactional producers only via Flink).
  • Idempotency scope limited to the transaction — retries/backfills can still duplicate committed data.
  • Read-uncommitted isolation can still expose dirty reads.

Proxy

  • Not every database has a convenient view abstraction; manifest-file fallback is more cumbersome.
  • Immutability must be enforced at the infrastructure level too, not just in orchestration logic.
  • Permission scoping matters — delete rights on internal tables can break the immutability guarantee.

Generate keys from immutable attributes (append time)
Biggest gotcha
Keying on mutable event time breaks under late data

Transactional Writer

Problem
Retried tasks expose partial/duplicate writes
Solution
Wrap writes in BEGIN...COMMIT/ROLLBACK
Biggest gotcha
Idempotency scope = one transaction only, not across retries

Proxy

Problem
Dataset must be write-once (immutable) for compliance
Solution
Versioned tables + write-once locks + passthrough view
Biggest gotcha
Requires infra-level immutability enforcement, not just orchestration
