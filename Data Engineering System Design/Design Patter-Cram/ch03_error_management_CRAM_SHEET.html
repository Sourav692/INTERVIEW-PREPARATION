P·01

Dead-Letter

ProblemBad/unparseable records crash the whole pipeline instead of failing on just that one record.
SolutionTry-catch (or if-else for error-safe functions) routes bad records to a separate dead-letter store + metadata; main pipeline keeps running.
GotchaReplaying dead-lettered records can trigger a snowball backfill downstream; also hides real failures unless you alert on volume.
📌 Note

Transient errors self-heal (retry). Nontransient errors (poison pills) need Dead-Letter.

✅ Say this out loud

"Dead-Letter trades pipeline uptime for hidden-error risk — I always pair it with volume-based alerting so a spike still pages someone."

🎯 FAANG pointer

Common follow-up: "what if dead-lettered records need reprocessing?" → optional replay pipeline, but flag the snowball backfill risk to consumers first.

🧱 Databricks

Delta Lake handles this cleanly — write valid vs. invalid rows to two separate Delta tables (book's own is_valid flag example). No dedicated "dead-letter" product feature; it's just a write pattern on Delta.

P·02

Windowed Deduplicator

ProblemAt-least-once delivery + producer retries = duplicate records reaching the table.
SolutionBatch → DISTINCT / ROW_NUMBER() over the dataset. Streaming → dedup key held in a state store for a bounded time window.
GotchaShort window = cheap but may miss dupes; long window = catches more but costs more state. Dedup ≠ exactly-once delivery.
📌 Note

3 state store types: Local (fast, no fault tolerance), Local+fault-tolerant (balanced), Remote (safe, slower).

✅ Say this out loud

"Deduplication solves exactly-once processing, not exactly-once delivery — for the latter I'd add an idempotency pattern from Chapter 4."

🎯 FAANG pointer

Classic: "how do you dedup an unbounded stream?" → you can't fully; bound it with a time window and accept the trade-off.

🧱 Databricks

Spark's native dropDuplicates() works as-is (batch and Structured Streaming with withWatermark). Delta Lake's MERGE INTO is a common idempotent-upsert alternative.

P·03

Late Data Detector

ProblemUsers go offline, buffer events, then flush late — pipeline needs to tell "late" from "on time."
SolutionTrack event time per partition with MAX (never MIN). watermark = MAX(event time) − allowed lateness. Before the watermark = late.
GotchaMIN per-partition → stuck-in-the-past risk. MAX across skewed sources → can wrongly drop a genuinely slow-but-valid source.
📌 Note

Event time (when it happened) ≠ processing time (when you saw it). Processing time is never late.

✅ Say this out loud

"I always use MAX for per-partition watermarking to guarantee monotonic progress — MIN risks getting permanently stuck on one slow partition."

🎯 FAANG pointer

Whiteboard favorite — draw the watermark formula, walk one "on time" and one "late" example. They're testing the *why* behind MAX, not just the formula.

🧱 Databricks

.withWatermark("event_time", "1 hour") is native in Structured Streaming and works the same on Databricks. Capturing dropped late records into a separate sink is not natively exposed in Spark (Flink is stronger here) — not sure Databricks has closed that gap.

P·04

Static Late Data Integrator

ProblemLate data has a known fixed delay (e.g., "up to 15 days") but you don't want 15 separate backfill jobs.
SolutionEvery run automatically replays a fixed N-day lookback window as part of the same pipeline.
GotchaWastes resources when nothing needs backfilling; naive multi-day replay overlaps — only the latest execution needs rerunning.
📌 Note

Switching to processing-time partitions "solves" this too easily — it hides the event-time problem instead of fixing it.

✅ Say this out loud

"Static Integrator is simple but wasteful — it always pays the backfill cost even when there's nothing to backfill."

🎯 FAANG pointer

Probe: "why not just rerun the whole 15-day pipeline daily?" → overlapping runs reprocess the same data redundantly; only rerun the latest execution.

🧱 Databricks

Airflow's Dynamic Task Mapping (expand()) is the book's example — orchestration-layer, so it behaves the same whether triggered by Databricks Jobs, Airflow, or another scheduler. Not Databricks-specific.

P·05

Dynamic Late Data Integrator

ProblemStatic's fixed window isn't enough — business wants all late data included, even beyond 15 days.
SolutionState table (partition, last_processed_time, last_update_time). Backfill only where last_update_time > last_processed_time.
GotchaConcurrent runs can double-trigger without an Is processed flag; very late data in stateful pipelines can still force a long re-execution chain.
📌 Note

If you can isolate exactly which entities changed, overwrite just those instead of full partitions — more efficient, more complex.

✅ Say this out loud

"Dynamic Integrator only backfills what actually changed, but that state table adds real scheduling complexity and a concurrency hazard I have to explicitly lock against."

🎯 FAANG pointer

Great trade-off to volunteer unprompted — Static (simple, wasteful) vs. Dynamic (efficient, complex) is a textbook system-design answer.

🧱 Databricks

Maps naturally to Delta Lake table versions — the book's own example tracks lastProcessedVersion per partition via Delta version history instead of timestamps. Genuine Databricks/Delta strength.

P·06

Filter Interceptor

ProblemFiltered-out volume jumps (e.g., 15% → 90%) after a code change, but the optimizer collapses filter conditions into one — can't tell which one is guilty.
SolutionWrap each filter condition with its own counter (accumulator in code, or a CASE-based column in SQL).
GotchaSmall runtime overhead; much harder to implement cleanly in SQL than a programmatic API; streaming may force a stateful implementation.
📌 Note

"Stay pragmatic" — use SQL or the programmatic API, whichever the job actually calls for.

✅ Say this out loud

"When filter selectivity spikes, the query plan won't tell you which rule is responsible if the optimizer merged them — Filter Interceptor isolates that with per-condition counters."

🎯 FAANG pointer

Good to mention for "how do you debug a silent data quality regression?" — it's a diagnostic pattern, not a prevention one.

🧱 Databricks

Spark accumulators work the same on Databricks — no special product feature. For ad hoc debugging you could also just run df.filter(cond).count() per condition, though that re-scans the data each time.

P·07

Checkpointer

ProblemA long-running streaming job would reprocess everything from scratch after a crash.
SolutionPersist offset position + computed state to durable storage on a cadence — framework-managed (Spark/Flink) or manual (custom Kafka consumer commits).
GotchaFrequent checkpoints = slower job, less reprocessing on failure — and either way, it's only an "exactly-once feeling," not real exactly-once delivery.
📌 Note — 3 delivery modes

Exactly once (needs Ch.4 idempotency) · At-least-once (checkpoint after write → dupes possible) · At-most-once (checkpoint before write → data loss possible).

✅ Say this out loud

"Checkpointing alone gives an exactly-once feeling — a task can fail mid-write after processing but before committing the checkpoint, so a retry reprocesses. Real exactly-once needs idempotency on top."

🎯 FAANG pointer

The #1 gotcha question — tests whether you actually understand delivery semantics vs. just knowing the checkpoint config flag.

🧱 Databricks

Fully native — checkpointLocation in Structured Streaming (stored in DBFS/cloud storage) is a first-class, battle-tested Databricks capability. Strongest Databricks fit in this whole chapter.

Before you close the laptop tonight

Every pattern here is a risk reducer, not a guarantee. If you can say out loud why each pattern doesn't fully solve the problem — not just what it does — you're ready.
