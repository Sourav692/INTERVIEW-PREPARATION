The Connecting Thread

This chapter is about pipeline topology, not logic. Sequence patterns decide one job vs. many. Fan-in patterns decide how branches merge back (all-or-nothing vs. partial). Fan-out patterns decide how one task spawns others (all branches vs. one). Orchestration patterns decide how many whole-pipeline instances run at once. Get the topology right and readability, backfill cost, and correctness fall out of it.

P·01

Local Sequencer

ProblemA monolithic job (hundreds of lines, tripled transforms) fails often and every retry restarts from scratch.
SolutionDecompose into steps run in strict data-dependency order — orchestration-layer tasks or one processing unit, chosen by naming clarity, backfill cost, and lost abstractions.
GotchaNo fixed rule for the split boundary — over-splitting hurts readability as much as under-splitting hurts maintainability.
📌 Note

CRON is still valid for a genuinely isolated task with zero dependencies.

✅ Say this out loud

"I split this at the orchestration layer because backfilling a paid-API check inside a monolith would re-trigger billed calls on every retry."

🎯 FAANG pointer

"How would you decide whether to split this?" — name the three book criteria: separation of concerns, maintainability, implementation effort.

🧱 Databricks

No dedicated feature — this is Databricks Workflows task dependencies, not a Delta capability.

P·02

Isolated Sequencer

ProblemYour team's cleansed dataset feeds a separate team's dashboard pipeline; both must stay owned and run independently.
SolutionConnect two physically separate pipelines via implicit data-dependency sensors, or explicit ExternalTaskMarker (upstream) + ExternalTaskSensor (downstream) — the latter auto-propagates backfills.
GotchaScheduling and communication overhead across the boundary. [verify against source page]
📌 Note

Draw the boundary by team ownership, or by pipeline complexity if you're both provider and consumer.

✅ Say this out loud

"I'd use ExternalTaskMarker/Sensor so a backfill upstream auto-propagates downstream, instead of relying on manual team coordination."

🎯 FAANG pointer

"How do you avoid two teams' pipelines drifting out of sync?" — answer with the marker/sensor auto-propagation, not "we'd talk."

🧱 Databricks

No dedicated feature — cross-pipeline triggering stays an orchestrator concern (Airflow sensors, or Databricks Workflows job-to-job triggers via the Jobs API).

P·03

Aligned Fan-In

ProblemCompute one daily aggregate from 24 hourly partitions without reprocessing the whole day at once.
SolutionBranch per hour; merge via UNION (vertical) or JOIN (horizontal) — only once ALL 24 branches succeed.
GotchaMerge task gated by the slowest parent (scheduling skew), plus infra spikes and DAG complexity.
📌 Note

SQL UNION is position-based by default and silently misaligns mismatched columns; Spark's unionByName() avoids this.

✅ Say this out loud

"A true daily total requires every hour present — a partial merge would be wrong, not just incomplete."

🎯 FAANG pointer

"What happens if hour 14 fails?" — the whole merge blocks; you only replay the failed hour, not all 24.

🧱 Databricks

No dedicated feature — Databricks Workflows all-upstream-success dependencies feeding a MERGE/UNION notebook task.

P·04

Unaligned Fan-In

ProblemAligned Fan-In blocks the whole daily output when just one hour fails; team wants a partial dataset released instead.
SolutionRelax the trigger (trigger_rule=ALL_DONE) so merge runs despite some parent failures; publish a completeness signal alongside the partial result.
GotchaConsumers assume 100% completeness unless you explicitly publish a completeness metric.
📌 Note

The trigger-rule relaxation is invisible in the DAG graph — lives only in code, so document it.

✅ Say this out loud

"If I relax to Unaligned Fan-In, I always publish a completeness percentage so consumers never silently assume 100%."

🎯 FAANG pointer

"How do consumers know the data is incomplete?" — name a concrete tracking mechanism, not "we'd document it."

🧱 Databricks

No dedicated feature — a completeness flag column or companion Delta table is the practical pattern, not a first-class primitive.

P·05

Parallel Split

ProblemMigrating a legacy framework requires writing the same processed dataset to two destinations during transition.
SolutionOne parent feeds multiple parallel children; materialize the shared dataset once (.persist() or a temp table) so it isn't re-read per branch.
GotchaTime-dependent pipelines block on the slowest branch — a failure blocks all subsequent runs.
📌 Note

Mismatched hardware needs (CPU vs. memory heavy) can't both get ideal resources from one job.

✅ Say this out loud

"I persist the shared input once to avoid duplicate reads, and use Delta's txnVersion/txnAppId to make writes idempotent on retry."

🎯 FAANG pointer

"How do you avoid processing the same data twice?" — answer: .persist()/temp-table materialization plus retry-safe writes.

🧱 Databricks

Confirmed: Delta Lake's txnVersion/txnAppId write options give idempotent, retry-safe appends — directly solves this pattern's duplicate-write risk.

P·06

Exclusive Choice

ProblemA new job version should run only from a cutover date forward; backfills for prior dates use the old version, without a new pipeline.
SolutionAdd a router/condition task before branching (BranchPythonOperator, ADF if-condition) so only one declared branch executes.
GotchaOver-branching → "complexity factory." Heuristic: rubber-duck debugging — if you can't explain it concisely, it's too complex.
📌 Note

Prefer metadata-based routing over data-based — reading the dataset to decide a route adds real runtime cost.

✅ Say this out loud

"I route on execution-date metadata rather than reading the dataset, so the branching decision itself adds no processing time."

🎯 FAANG pointer

"Why not just an if/else inside the job?" — hidden processing-layer logic is easy to forget; surface it at the orchestration layer instead.

🧱 Databricks

No dedicated feature — Databricks Workflows conditional "Run if" task dependencies, or plain if/else inside a notebook task.

P·07

Single Runner

ProblemAn incremental sessionization pipeline gives wrong results if two instances execute concurrently.
SolutionCap concurrency at exactly 1 (max_active_runs=1); without native support, use a Readiness Marker to wait on the prior run.
GotchaBackfilling is inherently slow and can't be parallelized — a correctness constraint, not a tunable trade-off.
📌 Note

Straggler runs (30 min creeping to 1.5h) compound delay for every downstream consumer, even outside backfill.

✅ Say this out loud

"Single concurrency here isn't a performance choice — it's correctness, because the logic depends on the prior run's output."

🎯 FAANG pointer

"How would you speed up backfilling under Single Runner?" — honest answer: mostly you can't; check if the *whole* pipeline truly needs to re-run.

🧱 Databricks

No dedicated feature — enforced via Databricks Workflows job concurrency settings (max concurrent runs = 1).

P·08

Concurrent Runner

ProblemIndependent, unrelated dataset ingestions are needlessly serialized under Single Runner, compounding latency.
SolutionRaise the concurrency ceiling above 1 so the next run starts without waiting — balanced against overall infrastructure capacity.
GotchaIn multitenant orchestrators, several high-concurrency pipelines backfilling at once can starve other teams' scheduling capacity.
📌 Note

Shared mutable state under concurrency is a distinct risk — e.g. Dynamic Late Data Integrator could double-trigger or skip backfilling.

✅ Say this out loud

"I'd only relax to Concurrent Runner once datasets are confirmed independent, paired with workload management so one team can't starve another."

🎯 FAANG pointer

"What could go wrong with high concurrency?" — name both resource starvation *and* shared-state nondeterminism, not just infra cost.

🧱 Databricks

No dedicated feature — workload isolation via Databricks Workflows concurrency limits per job plus cluster policies/pools.

Before You Close the Laptop

Sequence → Fan-In → Fan-Out → Orchestration is the chapter's own build order. If you remember one thing per family: Aligned/Single Runner favor correctness over speed; Unaligned/Concurrent Runner favor speed but require you to explicitly manage the honesty gap that creates — completeness metadata, workload isolation. That trade-off is what an interviewer is really testing.
