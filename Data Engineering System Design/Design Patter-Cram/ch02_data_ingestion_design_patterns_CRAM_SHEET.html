Chapter 2 — Data Ingestion Design Patterns

Last-minute recall: 8 patterns, one line each for Problem / Solution / Gotcha, plus interview-ready lines.

1 Full Loader 2 Incremental Loader 3 CDC 4 Passthrough Repl. 5 Transformation Repl. 6 Compactor 7 Readiness Marker 8 External Trigger
The Connecting Thread

Ingestion is where you stop controlling the data. Every pattern here exists because a producer you don't own — a legacy DB, a third-party API, an irregular event stream — hands you data on its own terms. The chapter moves from how much to load (Full → Incremental → CDC), to how to copy it safely (Replication), to the operational plumbing that makes ingestion trustworthy: readiness, compaction, and reacting to unscheduled arrivals.

P·01

Full Loader

ProblemDevice reference dataset has no last-updated column, so you can't detect changed rows.
SolutionReload the entire dataset every run via a two-step EL job (or ETL for heterogeneous stores).
GotchaNaive drop-and-insert exposes consumers to partial reads and destroys rollback unless you use a view-swap or time-travel format.
📌 Note

EL jobs are also called "passthrough jobs" — data just passes through unmodified.

✅ Say this out loud

"We chose Full Loader because the provider gives us no delta signal — but we protect consumers from partial reads with a view-swap so ingestion never half-exposes the dataset."

🎯 FAANG pointer

Expect "what happens to readers while you're overwriting?" — correct shape: transactions or a view/table-swap abstraction, not "just overwrite it."

🧱 Databricks angle

Delta Lake's time-travel (table version history) gives the rollback safety net this pattern needs, without hand-building a view-swap.

P·02

Incremental Loader

ProblemLegacy visit events land in a transactional DB; ingest only what's added since the last run.
SolutionDelta column (e.g. ingestion_time) filter, or target a whole new time-partition each run.
GotchaHard deletes are invisible to delta-column reads; unbounded backfills silently become full loads.
📌 Note

Partition-based implementations need no memory of state — the partition is implicit from execution time.

✅ Say this out loud

"We bound the ingestion window explicitly during backfills — delta_column BETWEEN ingestion_time AND ingestion_time + INTERVAL '1 HOUR' — so a replay never silently becomes a full load."

🎯 FAANG pointer

They'll probe on deletes — soft deletes (UPDATE marking removed) or insert-only tables are the two standard answers.

🧱 Databricks angle

Delta Lake's MERGE INTO combined with an insertion_time-filtered source is the standard incremental-upsert shape — same idea applied to ingestion.

P·03

Change Data Capture

ProblemIncremental Loader too slow — need every DB change captured within 30 seconds.
SolutionStream changes off the DB's append-only commit log (Debezium + Kafka Connect, or Delta CDF).
GotchaOutput is data-in-motion — a JOIN against two CDC streams returning nothing may just mean data hasn't arrived yet.
📌 Note

CDC captures every operation type, including hard deletes — producers no longer need soft deletes.

✅ Say this out loud

"CDC gets us the low latency and native delete support Incremental Loader can't, but it costs more in setup complexity — usually needs ops-team involvement to enable the commit log."

🎯 FAANG pointer

Classic trap: "why not just poll more often?" — polling still has query/scheduling overhead that can't reliably hit sub-minute latency; CDC reads the commit log directly.

🧱 Databricks angle

Delta Lake's Change Data Feed (enableChangeDataFeed, readChangeFeed) is a confirmed, far lighter-weight CDC path than standing up Debezium.

P·04

Passthrough Replicator

ProblemNon-idempotent third-party API feeds a reference dataset; dev/staging need the exact same data as prod.
SolutionSimple EL job (or infra replication policy) copying data as-is, zero transformation.
GotchaThe moment the dataset has PII, this pattern is disqualified entirely.
📌 Note

Prefer push (source pushes to targets) over pull, to avoid destabilizing production.

✅ Say this out loud

"Passthrough Replicator only works because there's nothing sensitive to strip — the instant PII enters the picture, this pattern is disqualified by design, not by policy."

🎯 FAANG pointer

"Why not just re-run the pipeline in staging?" — non-idempotency: a non-idempotent source returns different data per call, so replaying the pipeline ≠ reproducing the dataset.

🧱 Databricks angle

No dedicated product feature here beyond standard cloud-storage replication (e.g. S3 replication via Terraform) or a plain Spark EL job — it's an infra/job-design pattern, not Databricks-specific.

P·05

Transformation Replicator

ProblemNeed production data in staging for realistic testing, but it contains PII that can't leave prod.
SolutionSame EL shape, plus a transformation layer (mapping fn or SQL SELECT) stripping/replacing sensitive fields.
GotchaSchema-based transforms can silently corrupt data — e.g. a datetime mismatch dropping timestamp columns.
📌 Note

PII definitions drift over time — tie the transformation to a governed data catalog/contract, not a hardcoded list.

✅ Say this out loud

"We route PII removal through governance-tagged fields rather than a hardcoded column list, so a newly-classified PII attribute doesn't silently leak into staging."

🎯 FAANG pointer

"How do you keep anonymization correct as schema evolves?" — strong answer references a data catalog/contract driving the transform, not a manual list.

🧱 Databricks angle

Unity Catalog's column-level tagging/access controls are the natural governed-field mechanism here, though the book's own examples (SELECT * EXCEPT, .drop()) are framework-level, not Unity-Catalog-specific.

P·06

Compactor

ProblemStreaming-to-object-store job accumulates so many small files that batch jobs spend 70% of runtime listing files.
SolutionMerge small files into fewer big ones — OPTIMIZE (Delta), rewrite action (Iceberg), Hudi merge, or Kafka log compaction.
GotchaCompaction alone can leave original small files in place — needs a separate VACUUM cleanup job.
📌 Note

No universally correct compaction frequency — it's a deliberate cost-vs-performance trade-off, not a solved problem.

✅ Say this out loud

"We treat compaction and cleanup as two separate jobs — compaction alone doesn't remove pre-compaction files, so we always pair OPTIMIZE with a scheduled VACUUM."

🎯 FAANG pointer

"How often do you compact?" — the strong answer names the trade-off explicitly (rare compaction saves compute but denies uncompacted jobs the benefit), not a single "correct" cadence.

🧱 Databricks angle

OPTIMIZE and VACUUM on Delta tables are directly confirmed by the book as the compaction and cleanup mechanism — one of the most concretely Databricks-native patterns in the chapter.

P·07

Readiness Marker

ProblemHourly Silver-layer job feeds other teams' ML/BI work, who keep consuming incomplete datasets.
SolutionFlag file (e.g. Spark's _SUCCESS) as the last pipeline step, or a time-partition convention (N+1 implies N is done).
GotchaNeither implementation is enforced — a consumer can read mid-write, and late data breaks the partition convention.
📌 Note

The readiness marker must always be generated as the last step in a pipeline, after the final transformation.

✅ Say this out loud

"Readiness Marker is pull-based and convention-only — so we either treat partitions as immutable once closed, or explicitly share and communicate the mutability rules with consumers."

🎯 FAANG pointer

"What if late data lands in an already-closed partition?" — distinguish immutable-partition design from explicit mutability contracts, not silently overwriting a "closed" partition.

🧱 Databricks angle

Delta Lake's commit log acts as a built-in readiness signal — readers only see committed, complete writes, a stronger guarantee than a bare _SUCCESS file on raw formats.

P·08

External Trigger

ProblemFeature releases happen irregularly (at most weekly); daily refresh wastes compute reloading unchanged data.
SolutionSubscribe to a notification channel, react to events, push-trigger ingestion only when something changed.
GotchaA bare "ping" trigger with no execution context (version, event time) becomes very hard to debug on failure.
📌 Note

Push-based triggers beat pull-based polling — polling wastes resources finding nothing new most of the time.

✅ Say this out loud

"We always enrich the trigger payload with metadata — trigger version, notification envelope, processing and event time — because a bare ping-to-orchestrator becomes undebuggable the first time it misfires."

🎯 FAANG pointer

"What happens if the trigger event itself gets lost?" — strong answer routes back to Dead-Letter handling (Chapter 3), since the pipeline's only entry point is the event stream.

🧱 Databricks angle

No dedicated trigger primitive is confirmed in the book's own examples (it uses AWS Lambda + Airflow's REST API) — Databricks Workflows' file-arrival triggers are a plausible real-world fit, but treat that as [verify against source page] rather than asserted fact.

Before You Close The Laptop

Every pattern here answers one of two questions: "how much data do I pull?" (Full → Incremental → CDC, in order of decreasing latency and increasing setup cost) or "how do I know it's safe to act?" (Readiness Marker for scheduled data, External Trigger for unscheduled data). If a follow-up question stumps you, ground your answer in who controls the timing — the consumer (pull / Readiness Marker) or the producer (push / External Trigger / CDC) — that's the axis the book keeps returning to.
