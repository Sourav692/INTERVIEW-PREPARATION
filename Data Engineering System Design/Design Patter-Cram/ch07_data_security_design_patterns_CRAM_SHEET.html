Data Security Design Patterns

Last-minute interview review — 9 patterns, scan not read

The connecting thread

Data security in this chapter moves through four layers — comply (delete on request), restrict (fine-grained access), protect (make stolen data useless), connect (authenticate without leaking credentials). Each layer assumes the previous one can fail, so it doesn't rely on it alone — access control exists even though removal patterns exist; encryption exists even though access control exists.

#PatternProblemFix#1 Gotcha
1 Vertical Partitioner Immutable PII repeated in every record bloats removal cost Split rows into mutable/immutable stores, joined by a merge key Extra join hurts read performance
2 In-Place Overwriter Legacy system, no removal design, must still comply Delete/filter in place; stage-then-promote for raw formats Reads + rewrites the entire dataset — costly
3 FGA for Tables Table-level grants aren't granular enough GRANT, catalog tags, masking, or row policies Row policies limited to session attributes
4 FGA for Resources Cloud jobs have overly broad resource permissions IAM resource- or identity-based least-privilege policies Many narrow policies = maintenance burden; hard quotas
5 Encryptor Data at rest/in transit could be intercepted or stolen Server/client-side encryption + TLS via a key management service Lost key = lost data (soft delete mitigates)
6 Anonymizer Dataset has PII users haven't consented to share externally Remove, perturb, or synthetically replace sensitive columns Destroys analytical value (information loss)
7 Pseudo-Anonymizer Fully anonymized data is too degraded for analytics Mask, tokenize, hash, or encrypt while preserving structure Re-identifiable when joined with other datasets
8 Secrets Pointer Credentials risk leaking from Git/code Store in a secrets manager; fetch by reference at runtime Cached credentials go stale (streaming jobs)
9 Secretless Connector Team wants zero credentials to manage at all IAM-role-based or certificate-based authentication Setup and cert rotation still require real work

Pattern Flashcards

1

Vertical Partitioner

ProblemImmutable PII (birthday, ID number) repeats in every record, making removal expensive.
SolutionSplit each row into a mutable store and an immutable/PII store, linked by a merge key (e.g. user_id).
GotchaReads now need a join across the split — query performance and complexity go up for consumers.
📌 Note

This is a security specialization — Chapter 8 reuses the same mechanic purely for storage/performance, not compliance.

✅ Say this in interview

"We isolate PII into a single-occurrence store so a deletion touches one row instead of thousands — we trade that for a read-side join, hidden behind a view."

🎯 FAANG pointer

Expect "how would you make GDPR deletes cheap at scale?" — the answer is reduce what a deletion touches, not "make deletion faster."

🧱 Databricks

Confirmed — build the immutable-attribute store as a Delta table and use MERGE INTO to upsert user context, exactly as the book's example does.

2

In-Place Overwriter

ProblemLegacy system, terabytes of data, no removal strategy, but new regulation forces compliance now.
SolutionDELETE ... WHERE if natively supported (+ vacuum for table formats); otherwise filter the whole dataset and stage-then-promote.
GotchaTouches all rows, not just the target — 2,000 records to remove one user, vs. 1 with Vertical Partitioner.
📌 Note

Two delete strategies in table formats — deletion vectors (side-file marker, reader-filtered) vs. full rewrite (writer-heavy, reader-clean).

✅ Say this in interview

"When we can't redesign storage, we fall back to filter-and-rewrite — expensive, but universal — and batch multiple removal requests into one run."

🎯 FAANG pointer

If compared against Vertical Partitioner, lead with cost-at-scale, and mention "impossible rollback" if you skip staging.

🧱 Databricks

Confirmed — Delta Lake DeltaTable.delete() + VACUUM is the exact mechanism; skip vacuum and time travel still exposes "deleted" data.

3

Fine-Grained Accessor for Tables

ProblemWhole-table grants aren't enough — need column- and row-level restriction within an authorized table.
SolutionGRANT on columns, catalog policy tags, or masking functions for columns; dynamic WHERE-injecting policies for rows.
GotchaRow policies typically only condition on session attributes (user, group, IP) — not arbitrary business logic.
📌 Note

Nested/complex column types can't take simple column policies directly — unnest first, or expose via a materialized view.

✅ Say this in interview

"We layer row-level security on session-derived predicates, and fall back to a permission-scoped materialized view if policy evaluation overhead hurts latency."

🎯 FAANG pointer

"Hide a column from some users but not others in the same table?" → masking (modern answer) or GRANT(cols) (classic SQL answer).

🧱 Databricks

Confirmed — Unity Catalog supports column masking functions and ROW FILTER for row-level security, exactly as the book shows.

4

Fine-Grained Accessor for Resources

ProblemAudit finds a job can overwrite all datasets in an object store — permissions are too broad.
SolutionAt-least-privilege via IAM — resource-based (policy on the bucket) or identity-based (role on the job/user).
GotchaStrict least-privilege creates many small policies; IAM services cap them (AWS 1,500 policies; GCP 300 custom roles/project).
📌 Note

Wildcard prefixes (visits*) reduce sprawl but weaken the guarantee for future resources — flag this trade-off with security explicitly.

✅ Say this in interview

"We prefer identity-based IAM roles for application jobs — permissions travel with the role rather than needing per-bucket edits."

🎯 FAANG pointer

"Resource-based vs identity-based IAM — when do you pick each?" Resource-based = few consumers, one resource; identity-based = one identity, many resources.

🧱 Databricks

Not a dedicated Databricks feature — standard cloud IAM that Databricks compute assumes via service principals/instance profiles; Unity Catalog adds its own grants on top.

5

Encryptor

ProblemStakeholders worry about interception in transit and physical data theft at rest.
SolutionServer/client-side encryption at rest (via KMS/Key Vault) + TLS in transit.
GotchaLosing the key locks out authorized users too — mitigated by soft-delete/restore-window on key deletion.
📌 Note

Server-side encryption fully abstracts the encrypt/decrypt exchange — you just manage access to the store and the key service.

✅ Say this in interview

"Encryption doesn't replace access control — it's the layer that protects you if access control is bypassed, since stolen ciphertext is useless without the key."

🎯 FAANG pointer

"What happens if you lose the encryption key?" → name the real risk (data loss) and the real mitigation (KMS soft-delete window), not "you shouldn't lose it."

🧱 Databricks

Confirmed at platform level — Databricks integrates with cloud KMS/Key Vault for customer-managed keys; same server-side encryption the book describes.

6

Anonymizer

ProblemSharing a dataset externally, but some users never consented to sharing their PII.
SolutionRemove, perturb (add noise), or synthetically replace (e.g. via Faker) sensitive columns.
GotchaReal information loss — technical consumers can't rely on those columns; risks bad downstream models.
📌 Note

Anonymized data stays unidentifiable even combined with other datasets — the key distinction from pseudo-anonymization.

✅ Say this in interview

"Anonymization is the strong guarantee — irreversible and join-safe — but it costs real analytical value, so we only apply it where consent or regulation actually requires it."

🎯 FAANG pointer

"Anonymize vs pseudo-anonymize for a data-sharing deal?" → depends whether the recipient needs residual business signal or true opacity.

🧱 Databricks

No dedicated feature — ordinary column transforms (.drop(), .withColumn()) in a Spark/Databricks job, same as the book's PySpark + Faker example.

7

Pseudo-Anonymizer

ProblemFully anonymized data removed too much — analysts can't answer basic business questions anymore.
SolutionMask, tokenize (vault-backed), hash, or encrypt values to preserve structure/business meaning.
GotchaFalse sense of security — combining two pseudo-anonymized tables can re-identify a person ("John Doe in San Marino").
📌 Note

Tokenization's security is only as strong as the token vault — compromise the vault, tokens become reversible.

✅ Say this in interview

"Pseudo-anonymization preserves usability but not safety under joins — we treat it as a usability trade-off, not compliance-grade anonymization, and we're explicit about that with partners."

🎯 FAANG pointer

"Is masking an SSN's last 4 digits enough for compliance?" → no — combined with other quasi-identifiers it can still re-identify someone.

🧱 Databricks

Confirmed — Unity Catalog column masking can implement masking directly (same mechanism as pattern #3); tokenization/hashing are just UDFs.

8

Secrets Pointer

ProblemCredentials in Git/code risk leaking (book's example: a leak spiked API billing).
SolutionStore credentials in a secrets manager (AWS/GCP); consumers fetch by name at runtime.
GotchaCached credentials can go stale — especially painful for long-running streaming jobs.
📌 Note

Two protection layers stack — access to the secrets manager itself, and the credential's own validity.

✅ Say this in interview

"We never hardcode credentials — jobs resolve a secret name against a managed store at runtime, so rotation never touches consumer code."

🎯 FAANG pointer

"Handle credential rotation for a long-running streaming job?" → let it fail and restart to reload fresh creds, paired with idempotency (async refresh risks mid-flight writes).

🧱 Databricks

Confirmed — Databricks Secrets (dbutils.secrets.get(...)) is the platform-native version of this pattern, backed by managed or Azure Key Vault-backed scopes.

9

Secretless Connector

ProblemA team wants zero credentials to manage at all — no API keys anywhere in code.
SolutionIAM-role-based access (assume-role/service account) or certificate-based authentication.
GotchaNot actually "workless" — assume-role/STS setup and certificate rotation both require real ongoing effort.
📌 Note

Certificate-based auth swaps IAM for a certificate authority (CA) in the same four-step validation workflow.

✅ Say this in interview

"Secretless is strictly better than Secrets Pointer where supported — nothing to leak — but not zero-effort; someone still owns the IAM role or cert lifecycle."

🎯 FAANG pointer

"Most secure way to connect a Spark job to a database?" → certificate/IAM-role-based (Secretless) beats "use a secrets manager" (Secrets Pointer is second-best).

🧱 Databricks

Confirmed — Databricks jobs commonly run under a cloud service principal / instance profile to reach storage with zero stored credentials.

Before you close the laptop

Four layers, each assuming the last one can fail: removal (Vertical Partitioner cheap-but-narrow vs. In-Place Overwriter universal-but-costly) → access control (table-level vs. resource-level fine-grained IAM) → protection (Encryptor keeps data usable-but-locked; Anonymizer/Pseudo-Anonymizer trade safety for usability) → connectivity (Secrets Pointer good, Secretless Connector better). If you remember one line per pattern, remember the Gotcha column — that's what interviewers probe.
