Data Engineering Design Patterns — Chapter 3

Error Management Design Patterns

Nothing is certain except errors and data quality issues. Seven patterns for handling unprocessable records, duplicates, late data, filter regressions, and streaming fault tolerance — with the exact trade-offs the book won't let you forget.

Source: Data Engineering Design Patterns, Bartosz Konieczny (O'Reilly, 2025)
Dead-Letter Windowed Deduplicator Late Data Detector Static Integrator Dynamic Integrator Filter Interceptor Checkpointer Cheat Sheet

Chapter Framing

Error management is the pipeline stage right after data ingestion (Chapter 2). Once data flows into your system, you inherit every upstream problem: unreliable networks causing late delivery, retries causing duplicates, and plain bad records breaking your logic outright. This chapter groups patterns into four problem areas — unprocessable records, duplicated records, late data, and filtering errors — plus a fifth on fault tolerance for long-running streaming jobs.

📌 Note

Error management does not guarantee perfectly valid data. It gives you the feeling of exactly-once delivery — true exactly-once semantics require the Idempotency patterns in Chapter 4.

01 — Data Quality Unprocessable Records

Bad records often cause fatal failures that stop the job entirely — a fail-fast approach that's unworkable for long-running streaming jobs.

📌 Note — Transient vs. nontransient errors

Transient errors are temporary and recover automatically (e.g., brief DB unavailability fixed by connection retries). Nontransient errors never self-recover — unprocessable "poison pill" records are the classic case, requiring manual intervention.

P·01

Dead-Letter

Problem

A stream processing job writes visit events from a Kafka topic to an object store. Data producers started generating unprocessable records, and the job began failing. For three consecutive days, the fix was manual: relaunching the job and altering processed offsets in checkpoint files. Not sustainable.

Solution

Identify likely fail spots in the code and wrap them with a safety control — a try-catch block for mapping functions, an if-else for error-safe transformations. Attach the failed message as metadata for post-analysis, then route erroneous events to a different destination.

When choosing that destination, weigh: resiliency (don't need a dead-letter strategy for your dead-letter store), monitoring ease (know when/how much you're dropping), and writing performance (extra writes cost job time). Optionally close the loop with a replay pipeline that re-ingests fixed records — skip this if you don't care about past data.

Figure — Dead-Letter architecture & the snowball backfilling effect
flowchart LR Src[("Kafka Topic\nvisit events")] --> Job["Stream Job\ntry-catch guard"] Job -->|valid| Main[("Main Output")] Job -->|failed| DL[("Dead-Letter Store\n+ failure metadata")] DL --> Mon["Monitoring\nvolume + rate"] DL -.optional.-> Replay["Replay Pipeline"] Replay -.re-ingests.-> Main Main --> C1["Consumer A"] Replay -. triggers backfill .-> C1 C1 --> C2["Consumer B"] C1 -. cascades .-> C2
Consequences
Snowball backfilling effect Replaying dead-lettered records via the replay pipeline can hit partitions consumers already processed, forcing their own backfill — which can cascade further downstream.
Ordering and consistency Replaying a failed delivery out of order breaks ordering. Example: 10:00, 10:01, 10:02 — if the middle record fails and gets replayed last, the store returns 10:00, 10:02, 10:01.
Implementation for error-safe functions Error-safe functions return NULL instead of throwing. You must compare output to input instead of catching exceptions — and each function's error-safety semantics differ, making this harder.
Hidden errors Keeping the job alive hides errors — potentially masking a fatal failure that should stop the pipeline. Pair with an alerting layer that can still hard-stop on excessive drops.
🧩 Case Study

The book's running example: a stream job writing Kafka visit events to an object store, failing repeatedly on unprocessable records until Dead-Letter is applied.

✅ Say this out loud

"Dead-Letter keeps my pipeline running through bad records, but it trades that resilience for hidden-error risk and a potential snowball backfilling effect on consumers — so I pair it with dead-letter volume monitoring and an alerting threshold that can still stop the job if things go systemically wrong."

02 — Delivery Semantics Duplicated Records

Exactly-once delivery is rare in distributed systems — at-least-once is far more common. If your logic must process each occurrence only once, you need deduplication.

P·02

Windowed Deduplicator

Problem

A batch job processes visit events synchronized from a streaming layer, exposed directly to business users. It must guarantee exactly-once processing per distinct record — but the streaming layer frequently duplicates events via automatic producer retries.

Solution

Identify deduplication attributes that guarantee uniqueness, then define the deduplication scope. For batch, that's usually the current dataset (extending to past data costs more compute). For streaming, which is unbounded, the pattern simulates "completed datasets" via time-based windows, retaining seen keys in a state store for the window's duration.

📌 Note — Windows in batch

Batch has no explicit window API — it relies on an implicit global window over the whole dataset. The pattern name reflects dataset framing, not a literal windowing call.

Batch dedup uses DISTINCT or a WINDOW function with row_number(). Streaming must query the state store per record.

📌 Note — Three types of state store

Local (memory only, fastest, loses state on failure) · Local with fault tolerance (memory + remote persistence — trades speed for consistency depending on persistence frequency) · Remote (naturally fault tolerant, but can hurt latency/cost).

Figure — Windowed Deduplicator (streaming) state store interaction
sequenceDiagram participant Kafka as Kafka Topic participant Job as Streaming Job participant State as State Store participant Out as Output Store Kafka->>Job: record (visit_id, visit_time) Job->>State: has key been seen in window? alt key not seen State-->>Job: no Job->>State: record key (TTL = window) Job->>Out: write record else key already seen State-->>Job: yes (duplicate) Job->>Job: drop record end
Consequences
Space vs. time trade-off Streaming dedup only looks within a time window. Short windows miss dupes but save resources; long windows catch more but need more state-store capacity.
Idempotent producer — not enough for exactly-once delivery Correct deduplication ≠ exactly-once delivery. Transient-error retries can still reprocess already-successful writes. Pair with a Chapter 4 idempotency pattern.
✅ Say this out loud

"Windowed Deduplicator gives me exactly-once processing within a bounded window, not exactly-once delivery — for the latter I pair it with an idempotency pattern, since dedup and idempotency solve different parts of the duplication problem."

03 — Time & Arrival Late Data

Late data sounds innocent but has serious pipeline impact — three patterns handle detecting it and, if valuable, folding it back in.

P·03

Late Data Detector

Problem

Blog visitors normally generate visit events within 15 seconds — but when users lose connectivity, they buffer visits locally and flush them once reconnected. The pipeline needs to detect these late events to apply a per-use-case strategy (e.g., ignore them).

Solution

Define a time-based attribute for lateness (the event time, vs. processing time which is never late). Aggregate it per-partition using a monotonically increasing strategy — MAX is standard; MIN risks a stuck-in-the-past situation. Then aggregate across all partitions using MIN (follow the slowest source, buffer more), MAX (follow the fastest, risk skipping slow sources), or a combination. Finally subtract an allowed lateness value: watermark = MAX(event time) − allowed lateness.

Interactive: Watermark & Late Record Detection

Drag the allowed-lateness slider — events left of the watermark line turn red (late).
On time (≥ watermark) Late (< watermark)
Consequences
Late data capture support varies Spark Structured Streaming detects/ignores late events but doesn't expose a capture API; Flink supports both detecting and capturing.
MIN strategy, stuck-in-the-past, and stateful jobs MIN-based tracking risks an open-close-open infinite loop (reopening already-emitted "completed" states when the watermark moves back) or, worse, getting stuck in the past permanently if late data keeps arriving.
Max strategy and event skew MAX can be too aggressive under skew — e.g., 4 of 5 sources delayed 40 minutes means their records get dropped as late. No silver bullet; mitigate with monitoring and the Late Data Integrator patterns.
Figure — Watermark progression & late record routing
flowchart TD A["Incoming events per partition"] --> B["Per-partition MAX\n(monotonic)"] B --> C["Cross-partition MIN/MAX/combined"] C --> D["watermark = MAX(event time) minus allowed lateness"] D --> E{"event time >= watermark?"} E -->|yes: on time| F["Accept into pipeline"] E -->|no: late| G["Late Data Detector fires"] G --> H{"Is late data valuable?"} H -->|no| I["Ignore"] H -->|yes| J["Late Data Integrator"]
✅ Say this out loud

"I use MAX for per-partition event-time tracking to guarantee monotonicity and avoid a stuck-in-the-past situation, but under high event skew, MAX can aggressively drop records from lagging sources — so I pair it with late-event monitoring rather than trusting the watermark blindly."

P·04

Static Late Data Integrator

Problem

A daily job generates blog-referral statistics, "approximate" for 15 days — the maximum allowed late-data delay. Records older than that are skipped. The team wants late data folded into the daily pipeline without running 15 individual jobs separately each day.

Solution

Use a fixed lookback window: replay the last N days as part of every run so late data folds back in automatically.

📌 Note — Easy solution for you, not for others

Switching to processing-time partitions is the easy fix — but if event time matters anywhere downstream, this just relocates the problem (e.g., a 9:00 processing-time partition might silently be 80% 9:00 data, 10% 8:00, 10% 7:00 data).

Consequences
Snowball backfilling effect Same risk as Dead-Letter — consistency-conscious consumers must replay affected partitions, which can cascade further downstream.
Overlapping executions and backfilling Naively replaying multiple executions with a static window creates overlap. With a 4-day window, replaying 2024-10-10 through 2024-10-12 individually reprocesses overlapping date ranges — only the last execution needs replaying.
Pipeline trigger Backfill tasks must live inside the main pipeline — separate pipelines reintroduce the overlapping-execution problem.
Waste of resources Fixed lookback periods don't always contain late data. Gate with a control task, or switch to the Dynamic variant.
Time requirement No time-partitioning concept means no ability to detect or integrate late data at all with this pattern.
🧩 Case Study

A daily job generating blog-referral statistics, treated as "approximate" for 15 days — the book's concrete anchor for this pattern.

Examples

Apache Airflow — Dynamic Task Mapping generates one backfill task per lookback day:

python
@task
def generate_backfilling_runs():
    dr: DagRun = get_current_context()['dag_run']
    backfilling_dates = []
    days_to_backfill = 2
    start_date_to_backfill = (dr.execution_date
        - datetime.timedelta(days=days_to_backfill))
    for days_to_add in range(0, days_to_backfill):
        date_to_backfill = start_date_to_backfill + datetime.timedelta(days=days_to_add)
        backfilling_dates.append(date_to_backfill.date().strftime('%Y-%m-%d'))
    return backfilling_dates

@task
def integrate_late_data(late_date: str):
    copy_file(late_date)
    # ....

integrate_late_data.expand(late_date=generate_backfilling_runs())
P·05

Dynamic Late Data Integrator

Problem

The Static Integrator's 15-day window isn't enough anymore — the product owner wants all late data included, even beyond 15 days, without blindly replaying a fixed two-week window.

Solution

Use a dynamic lookback window driven by a state table tracking, per partition, the last processed time and last update time:

PartitionLast processed timeLast update time
2024-12-172024-12-17T10:202024-12-17T03:00
2024-12-182024-12-18T09:552024-12-20T10:12
sql
SELECT partition FROM state_table WHERE
`Last update time` > `Last processed time` AND `Partition` < `Processed partition`

Some stores expose per-partition update metadata natively (BigQuery's INFORMATION_SCHEMA.PARTITIONS, Iceberg's last_updated_at) — else you generate it yourself.

📌 Note — Not whole partitions

If you can isolate the entities impacted by late data, overwrite just those entities instead of full partitions — better resource use, more implementation complexity.

Figure — Static vs. Dynamic Late Data Integrator flow
flowchart TD subgraph Static["Static Late Data Integrator"] S1["Run today's job"] --> S2["Always replay fixed\nN-day lookback"] S2 --> S3["Backfill regardless of\nwhether late data exists"] end subgraph Dynamic["Dynamic Late Data Integrator"] D1["Run today's job"] --> D2["Query state table"] D2 --> D3{"Late data found?"} D3 -->|yes| D4["Backfill only affected\npartitions"] D3 -->|no| D5["Skip — no wasted backfill"] end
Consequences
Concurrency Concurrent runs can double-trigger backfills for the same partition. Mitigation: add an Is processed flag, filter on it, and gate steps on the previous run's success.
sql
SELECT partition FROM state_table WHERE
`Last update time` > `Last processed time` AND
`Partition` < `Processed partition` AND
`Is processed` = false
⚠️ Warning

If the partition-generating task fails, its dependency on the previous run means future executions won't run either — the pipeline gets stuck in-progress, requiring manual intervention.

Stateful pipelines and very late data For stateful pipelines (e.g., Incremental Sessionizer), extremely late data can force regenerating a long chain of past executions for correctness — the dynamic window alone doesn't prevent heavy backfills on very late records.
Scheduling complexity Coordinating state-table updates, task generation, and concurrency-safe flags adds real complexity versus the static approach.
✅ Say this out loud

"Static Late Data Integrator trades simplicity for wasted resources and a fixed lookback ceiling; Dynamic fixes both by tracking real arrival in a state table, at the cost of scheduling complexity and a concurrency hazard I have to explicitly guard with an 'is processed' flag."

Comparison Static vs. Dynamic Late Data Integrator

PatternWhen to UseTrade-off
Static Late Data Integrator Late data has a known, fixed maximum delay (e.g., "arrives within 15 days") Simple to reason about, but wastes resources on empty backfills, risks overlapping-execution bugs, and can't handle late data beyond the fixed window
Dynamic Late Data Integrator Late-data timing is unpredictable or exceeds any reasonable fixed window Only backfills partitions that truly changed, but adds a state table, scheduling complexity, and a concurrency hazard requiring explicit locking

04 — Human & Logic Errors Filtering

Not every error is technical — a bad filter condition can silently drop good data, and optimizers can hide which condition is to blame.

P·06

Filter Interceptor

Problem

A batch job on a distributed framework was recently updated. After release, filtered data volume spiked from 15% to 90%. Unclear if it's a data issue or software regression — the execution plan doesn't help, because the optimizer collapses multiple filter expressions into one, hiding per-condition statistics.

Solution

Wrap each filter condition with counter logic that increments when the condition filters a record out, instead of expressing the raw condition alone. Gather all counters at job end.

In SQL, this is more work: use a subquery/temp table exposing each condition as its own column (e.g., a_is_not_null), then use those columns as filter predicates in the main query.

📌 Note — Stay pragmatic

Use the right tool for the job — programmatic API or SQL, whichever suits the task better, even if you've been writing only SQL so far.

Consequences
Runtime impact Small overhead from counter wrapping — local accumulators are cheap. The SQL variant costs more (may need a temp table to both extract stats and filter).
Declarative languages SQL is less powerful here — the programmatic API produces easier-to-maintain code for this specific pattern.
Streaming May require turning a stateless job stateful (added state-management overhead), plus defining time boundaries for meaningful stats — otherwise you can't relate counts to "now" or spot currently active filters.
✅ Say this out loud

"When a filter's selectivity suddenly jumps, the execution plan alone won't tell me which condition is responsible if the optimizer collapsed them — Filter Interceptor wraps each condition with its own counter so I can isolate which rule changed behavior, at the cost of small runtime overhead."

Examples

PySpark — accumulator-wrapped filter conditions:

python
@dataclasses.dataclass
class FilterWithAccumulator:
    name: str
    filter: Callable[[Any], bool]
    accumulator: Accumulator[int]

filters_with_accumulators = {
    'type': [
        FilterWithAccumulator('type is null', lambda device: device['type'] is not None,
            spark_context.accumulator(0)),
        FilterWithAccumulator('type is too short (1 chars or less)',
            lambda device: len(device['type']) > 1, spark_context.accumulator(0))
    ],
    # ...
}
python
def filter_null_type(devices_iterator: Iterator[pandas.DataFrame]):
    def filter_row_with_accumulator(device_row):
        for device_row_attribute in device_row.keys():
            for filter_with_accumulator in filters_with_accumulators[device_row_attribute]:
                if not filter_with_accumulator.filter(device_row):
                    filter_with_accumulator.accumulator.add(1)
                    return False
        return True

    for devices_df in devices_iterator:
        yield devices_df[devices_df.apply(lambda device:
            filter_row_with_accumulator(device), axis=1) == True]

valid_devices = input_dataset.mapInPandas(filter_null_type, input_dataset.schema)
valid_devices.write.mode('append').format('delta').save(output_dir)

SQL — filter conditions exposed as columns:

sql
SELECT * FROM (
    SELECT
        CASE
            WHEN (type IS NOT NULL) IS FALSE THEN 'null_type'
            WHEN (LEN(type) > 2) IS FALSE THEN 'short_type'
            WHEN (full_name IS NOT NULL) IS FALSE THEN 'null_full_name'
            WHEN (version IS NOT NULL) IS FALSE THEN 'null_version'
            ELSE NULL
        END AS status_flag,
        type, full_name, version
    FROM input)
-- creates temp view input_with_flags, then:
SELECT COUNT(*), status_flag FROM input_with_flags WHERE
status_flag IS NOT NULL GROUP BY status_flag
-- and the valid-record output:
SELECT type, full_name, version FROM input_with_flags WHERE status_flag IS NULL

05 — Recovery Fault Tolerance

Long-running streaming jobs need a way to resume without reprocessing everything after a crash — an append-only log has no partition structure to lean on.

P·07

Checkpointer

Problem

A streaming job counts unique visits in 10-minute windows. A fatal failure would stop the job and force reprocessing from the very beginning. Progress needs to persist as the query moves forward.

Solution

Track the most recent position in the data source plus computed state, in storage more durable than the job's own runtime.

Where progress is recorded: framework-based (Spark Structured Streaming / Flink manage it in a resilient object store) or data-store-based (Kafka SDK persists offsets to __consumer_offsets; Kinesis Client Library writes to DynamoDB).

How it executes: configuration-driven (you set frequency, the library handles it) or intentional/code-driven (your code explicitly commits after processing, e.g., a custom Kafka consumer).

Figure — Checkpoint timing and delivery mode
flowchart LR subgraph AL["At-Least-Once"] AL1["1. Process & write"] --> AL2["2. Checkpoint"] end subgraph AM["At-Most-Once"] AM1["1. Checkpoint"] --> AM2["2. Process & write"] end subgraph EO["Exactly-Once (needs Ch.4 idempotency)"] EO1["Checkpoint + write\nas one idempotent unit"] --> EO2["Consistent output\nregardless of retries"] end
Consequences
Delivery guarantee vs. latency trade-off Position tracking alone is cheap. But checkpointing state (e.g., user sessions) can be much larger, with real latency impact. More frequent checkpoints → slower job, less reprocessing on failure. Less frequent → faster job, more reprocessing on failure.
"Exactly-once feeling," not exactly-once delivery Distributed, asynchronous parallel tasks mean a failure mid-work before checkpointing can still trigger retries that reprocess already-successful records. True exactly-once delivery needs an idempotency pattern from Chapter 4 — checkpointing alone isn't enough.
📌 Note — Delivery modes

Exactly once — the ideal, via Chapter 4 idempotency patterns. At least once — checkpoint after write; retries can duplicate. At most once — checkpoint before write; failures can lose data.

✅ Say this out loud

"Checkpointer gives me fault tolerance and an 'exactly-once feeling,' but distributed, asynchronous task execution means a mid-checkpoint failure can still replay already-successful writes — for true exactly-once delivery I'd combine it with an idempotency pattern from Chapter 4."

Apache Flink — time-based checkpointing:

python
checkpoint_interval_30_sec = 30000
env.enable_checkpointing(checkpoint_interval_30_sec, mode=EXACTLY_ONCE)
(env.get_checkpoint_config().enable_externalized_checkpoints(RETAIN_ON_CANCELLATION))

RETAIN_ON_CANCELLATION keeps checkpoint files after failure (Flink normally ties them to job-instance lifecycle). EXACTLY_ONCE checkpoint mode guarantees each input record reflects in state exactly once, so a restart won't double-count.

📌 Note

Spark 3.4.0 introduced experimental asynchronous checkpoints not tied to microbatches; as of the book's writing (2024), open source Spark doesn't support state store for this feature.

Roundup Gotchas by Pattern

Every Consequence from this chapter, gathered in one scannable place.

Dead-Letter Snowball backfilling · ordering/consistency breaks on replay · error-safe functions are harder to wrap · hides errors unless paired with alerting.

Late Data Detector Capture support varies by framework · MIN risks stuck-in-the-past · MAX risks dropping skewed/slow sources.
