Data Observability Design Patterns

Detection and tracking patterns that close the gap left by data-quality controls — knowing when something's wrong, and knowing who to ask.

🔍 Detection 🧭 Tracking
Why this chapter matters: The Data Quality patterns from Chapter 9 (like Audit-Write-Audit-Publish) protect what's inside your datasets. But even a perfect AWAP job is worthless if it silently never ran — say, due to an upstream flow interruption nobody noticed. Data observability patterns close that gap with two pillars: detection (spotting data or time problems) and tracking (understanding dataset, column, and team-level dependencies). Data Detectors

📌 Note Data detectors analyze system health from the data standpoint — is data arriving at all, and is the volume what you'd expect?
Pattern

Flow Interruption Detector

Problem

A streaming job synchronizing data to an object store — the source for many batch jobs owned by different teams — ran fine for seven months. Then one day it processed input records without writing them. The job didn't fail, so nobody noticed until a consumer complained. Relying on consumer feedback is bad for reputation — the goal is proactive detection of data unavailability.

Solution

Implementation varies by mode. For streaming:

  • Continuous delivery — expect ≥1 record per time unit; alert on silence.
  • Irregular delivery — interruptions are expected, so a fixed threshold is less appropriate.

Detection strategies by layer:

  • Metadata layer — enrich with a modification-time column, or compare row counts across periods (e.g. no change across two consecutive hourly runs).
  • Storage layer — works with any file format; monitor time since last file write.

Consequences

  • Threshold — hard to tune; historical-volume thresholds cause false positives during real spikes (e.g. marketing campaigns).
  • Metadata — cheap but imperfect; may not exist for your store, or may reflect schema-only changes with no new rows.
  • False positives for storage — compaction creates new files but not new data — exclude it from the check.
✅ Say this out loud "I chose a storage- or metadata-layer signal for flow interruption, but explicitly excluded compaction-driven file writes, because compaction creates activity without creating new data."

Pattern

Skew Detector

Problem

After deploying the Flow Interruption Detector, consumers complained again — the batch job ran successfully but on a half-empty dataset. The data provider had a generation issue on their side. The goal: always process a complete dataset.

Solution

Three steps: (1) identify the comparison window (e.g. today vs. yesterday), (2) set a tolerance threshold (e.g. ±50%), (3) implement the calculation via either:

  • Window-to-window comparison — percentage difference between two values.
  • Standard-deviation ratio — STDDEV(x)/AVG(x), ideal for partitioned stores like Kafka or PostgreSQL.
🧩 Case Study The Skew Detector fits naturally into the Audit stage of the AWAP pattern (Chapter 9) — acting as a guard that blocks partial datasets before Write/Publish.

Consequences

  • Seasonality — a fixed ±50% band breaks under real seasonal or campaign-driven variance; requires business knowledge and exceptions.
  • Communication — mitigating false positives needs cross-team synchronization, not just code.
  • Fatality loop — comparing against yesterday's broken run makes today's correct (larger) dataset look "skewed" too. Mitigation: compare against the last known-good run instead.

Examples

SQL — PostgreSQL stddev ratio
SELECT
  NOW() AS "time", (STDDEV(n_live_tup) / AVG(n_live_tup)) * 100 AS value
FROM pg_catalog.pg_stat_user_tables
WHERE relname != 'visits_all_range' AND relname LIKE 'visits_all_range_%';
PromQL — Kafka partitions
stddev(sum(kafka_log_size{topic='visits'}) by (partition)) /
avg(kafka_log_size{topic='visits'}) * 100

Time Detectors

📌 Note Time detectors operate purely in the time dimension — they help spot latency issues that are often the earliest warning sign of upcoming data problems.
Pattern

Lag Detector

Problem

A streaming job processed 30% more data than usual a week ago; the alert email was missed. Now a downstream consumer complains about slower delivery. Before scaling, the team needs to actually measure how far the consumer lags the producer.

Solution

  1. Define the lag unit — record position/append time (Kafka), commit number (Delta Lake), partition timestamp (time-partitioned store).
  2. Compute lag = last_available_unit − last_processed_unit.
  3. Aggregate per partition: MAX for worst case, or percentile (P90/P95) for overall behavior — or both.
⚠️ Warning — The Average Trap Per-partition lags of 10, 5, 30, 2, 3, 5, 3 seconds average to 8s, but P90 is 18s — 90% of data is processed within 18 seconds, not 8. Averages can make an unhealthy job look fine. Percentiles are more reliable for lag detection.

Consequences

  • Data skew — MAX-based reporting can blame the consumer for what's actually an uneven partition. Fix distribution at write time, not the consumer.

Examples

Python — Spark Structured Streaming listener
class BatchCompletionSlaListener(StreamingQueryListener):
    def onQueryProgress(self, event: "QueryProgressEvent") -> None:
        latest_offsets_per_partition = self._read_last_available_offsets()
        visits_end_offsets = json.loads(event.progress.sources[0].endOffset)
        visits_offsets_per_partition: Dict[str, int] = visits_end_offsets['visits']
Python — Lag calculation + push
registry = CollectorRegistry()

    metrics_gauge.labels(partition=partition).set(lag)

Pattern

SLA Misses Detector

Problem

A batch job at 6:00 a.m. must finish within 40 minutes so consumers can produce business stats by 8:00 a.m. The job is well optimized, but the team wants automatic notification the day the SLA is broken.

Solution

  • Batch job — simplest: end_time − start_time vs. threshold.
  • Streaming, windowed mode — same subtraction, per iteration.
  • Streaming, non-windowed mode — measure read→write delay per record; aggregate MAX or percentile via the Online/Offline Observer (Ch. 9).
📌 Note Lag Detector and SLA Misses Detector are complementary, not interchangeable. A throughput-limited consumer can meet its SLA every run while lag against a skewed partition keeps growing — and a scheduled daily job can start with zero lag yet still miss its SLA.

Consequences

  • Late data and event time — processing-time SLAs are simple but blind to true delivery delay; event-time SLAs capture it but can be missed for reasons that aren't your fault (disconnected producer, buffered delivery). Monitor both — they measure different things.

Examples

Python — Apache Airflow
@task(sla=datetime.timedelta(seconds=10))
def processing_task_2():
    ...
⚠️ Warning In Airflow 2.10.2, SLA is computed from the DAG's execution start time, not the task's own start. A task scheduled after 08:00:10 in an 08:00 DAG is already "late" — even without having run long. (SLA refactoring planned in AIP-57.)
Python — Apache Flink decoration
def map_json_to_reduced_visit(json_payload: str) -> str:

        start_processing_time_unix_ms=time.time_ns() // 1_000_000, ...).to_dict())
SQL — Flink table + processing-time diff
CREATE TEMPORARY TABLE reduced_visits (
  `start_processing_time_ms` BIGINT,
  `append_time` TIMESTAMP METADATA FROM 'timestamp' VIRTUAL
) WITH ('connector' = 'kafka', ...)

SELECT
  append_time,
  ((1000 * UNIX_TIMESTAMP(CAST(append_time AS STRING)) +
    EXTRACT(MILLISECOND FROM append_time)) -
   start_processing_time_ms) AS time_difference,
  FLOOR(append_time TO MINUTE) AS visit_time_minute
FROM reduced_visits

Data Lineage (Tracking)

📌 Note Detection tells you that something's wrong. Lineage tells you who to ask when the root cause isn't yours — e.g. a late upstream event breaking your event-time SLA.
Pattern

Dataset Tracker

Problem

A consumed dataset has poor quality — a field's data type has been inconsistent over time. The immediate upstream provider isn't the root cause: it's relaying data generated by yet another team further upstream. The team needs to see the full dependency chain across teams to find who actually owns the bug.

Solution

Build a family tree of datasets — dependencies between tables, folders, topics, and queues, and by extension between the teams that own them.

🧩 Case Study The book's example: an orders dataset built from two other tables, which are in turn built on a Kafka topic — each dataset annotated with its owning team, making cross-team ownership visible at a glance.
  • Fully managed — Databricks Unity Catalog lineage, GCP Dataplex (BigQuery, Dataproc) — transparent, no extra work.
  • Self-managed — identify inputs/outputs at the orchestration layer (pipelines report to a lineage service) or the database layer (parse executed queries into a dependency tree).

Consequences

  • Vendor lock — managed solutions typically only see within their own ecosystem; mixing open-source stores or other clouds gives only a partial view.
  • Custom work — orchestration frameworks auto-deduce lineage for built-in task types only; custom task types need manual input/output resolution logic.
✅ Say this out loud "We chose [managed lineage service] within its own ecosystem, but we know it gives only a partial view once data crosses into open source stores or another cloud — so we scoped our lineage guarantees accordingly."

Examples

OpenLineage + Marquez (open source) with Apache Airflow: set OPENLINEAGE_URL=http://localhost:5000 and install apache-airflow-providers-openlineage — native operators like PostgresOperator need no further code.

Python — Spark + OpenLineage

Pattern

Fine-Grained Tracker

Problem

A team applied the Denormalizer pattern (Ch. 8) and the resulting table grew past 30 columns over three years. New team members constantly ask which upstream columns feed each output column — a question the Dataset Tracker can't answer, since it only covers table-level dependencies.

Solution

Column level — some platforms support it natively (Databricks Unity Catalog's system.access.column_lineage, Azure Purview). Self-built: analyze the execution plan. Example: in SELECT CONCAT(u.first_name, d.delivery_address) AS user_with_address FROM users u JOIN addresses d ON d.user_id = u.id, user_with_address traces to users.first_name and addresses.delivery_address. OpenLineage often supports this natively for Spark.

Row level — track which job produced each row, typically via an extra attribute/column using the Data Decoration patterns (Chapter 5).

Consequences

  • Custom code — execution-plan analysis works for standard SQL; custom programmatic transforms are opaque boxes the lineage tool can't interpret.
  • Row-level visualization — useful for debugging but doesn't integrate with standard lineage visualization tools; needs a separate query layer.
  • Evolution management — transformation logic changes over time; lineage must track that evolution or it will report stale/incorrect origins.

Examples

Python — Row-level lineage via Kafka headers
# visits_decorator_job
(visits_to_save.withColumn('headers', F.array(
    F.struct(F.lit('job_version').alias('key'), F.lit(job_version).alias('value')),
    F.struct(F.lit('job_name').alias('key'), F.lit(job_name).alias('value')),
    F.struct(F.lit('batch_version').alias('key'), F.lit(str(batch_number)
        .encode('UTF-8')).alias('value'))
)))

# visits_reducer_job
(visits_to_save.withColumn('headers', F.array(
    # same as for visits_decorator_job, plus the parent's lineage
    F.struct(F.lit('parent_lineage').alias('key'), F.to_json(F.col('headers'))
        .cast('binary').alias('value'))
)))

The visits_reducer_job carries a parent_lineage attribute pointing back to visits_decorator_job's headers — making the upstream source traceable and speeding up debugging with data producers.

⚠

Gotchas — Chapter Round-Up

  • Flow Interruption Detector — threshold tuning is genuinely hard; historical-volume thresholds cause false positives during real spikes; compaction fakes storage-layer "activity."
  • Skew Detector — seasonality invalidates fixed tolerance bands; false positives need cross-team communication; fatality loops from comparing against a broken prior run (compare to last known-good instead).
  • Lag Detector — MAX-based reporting can misattribute partition skew to the consumer; averages hide the real worst-case tail — use percentiles.
  • SLA Misses Detector — event-time SLAs can be missed for reasons outside your control; Airflow measures SLA from the pipeline's start time, not the task's.
  • Dataset Tracker — managed lineage gives only partial coverage across cloud/OSS boundaries; custom task types need manual wiring.
  • Fine-Grained Tracker — custom transformation code is a black box; row-level lineage doesn't fit standard visualization tooling; lineage must track transformation evolution over time.
