Chapter Framing

Why storage design, not just more compute

"Have you ever waited for a query or job longer than two minutes in a big data environment? Many of you will answer yes."

Latency has two fixes: add compute (fast, reactive, expensive, usually done under pressure once users complain) or organize storage wisely up front — the preemptive path, and this chapter's subject. It follows Chapter 7 (Security) and sits before Chapters 9–10 (Quality & Observability): storage optimizes access to data that quality and observability will make trustworthy.

Group 1 · Partitioning

Dividing datasets so processing touches only what's relevant

1

Horizontal Partitioner

Partitioning
Problem

A batch job computing rolling 4-day aggregates ran fine for months, then slowed as storage grew — the filtering step (dropping records older than 4 days) got expensive. Adding compute masked it but raised cost.

Solution

Identify a partitioning attribute (distribution key). The store then physically isolates each value. Time-based keys are most common, sourced from either the job execution context (all rows in a run share one partition) or the dataset's event time (late data can spread writes across several partitions). Business keys (customer ID, region) work too, and keys can nest, e.g. event time + country.

✅ Say this out loud

"I partition by a low-cardinality, frequently-filtered attribute — usually event time rounded to the hour or day — because that's what lets the query engine skip irrelevant partitions without exploding the metadata layer."

Consequences
  • Granularity/metadata overhead — 1M unique users partitioned by username = 1M partitions = slow listing + small files. Mitigation: use low-cardinality attributes; reach for Bucket instead.
  • Skew — one unbalanced partition blocks a whole microbatch (blocking execution model). Mitigation: a backpressure buffer stores skewed overflow for the next microbatch, at the cost of extra latency for that partition.
  • Mutability — changing the key needs moving all existing data. Apache Iceberg supports metadata-only partition evolution: old data stays put, new data uses the new scheme.
📌 Note

Sharding is a special, physical/hardware-layer case of horizontal partitioning — it doesn't require moving data across machines by itself, but sharding always does.

Examples
python · Apache Spark
partitioned_users = (input_users
    .withColumn('year', functions.year('change_date'))
    .withColumn('month', functions.month('change_date'))
    .withColumn('day', functions.day('change_date'))
    .withColumn('hour', functions.hour('change_date')))

(partitioned_users.write.mode('overwrite').format('delta')
    .partitionBy('year', 'month', 'day', 'hour').save(output_dir))
sql · PostgreSQL
CREATE TABLE visits_all (
  visit_id CHAR(36) NOT NULL,
  event_time TIMESTAMP NOT NULL,
  user_id TEXT NOT NULL,
  page VARCHAR(20) NULL,
  PRIMARY KEY(visit_id, event_time)
) PARTITION BY RANGE(event_time);

CREATE TABLE visits_all_20231124 PARTITION OF visits_all
  FOR VALUES FROM('2023-11-24 00:00:00') TO ('2023-11-24 23:59:59');

Vertical Partitioner

Partitioning
📌 Note

This is data storage's version of vertical partitioning. Chapter 7 covers a security-focused specialization of the same idea.

Problem

The visits dataset mixes mutable attributes (visit time, page — change every visit) with immutable ones (IP address — same all visit). Storing them together duplicates the immutable data on every row.

Solution

Classify attributes into groups, pick a combining key (here, visit_id), and write each group to its own location. Beyond storage savings, splitting lets you apply different retention or access policies per group. Unlike Horizontal Partitioner (moves whole rows), Vertical Partitioner splits a row across locations.

Consequences
  • Domain split — related attributes now live apart; documentation becomes essential.
  • Querying — reconstructing a full row is harder. Mitigation: expose a combining view via Dataset Materializer.
  • Data producer impact — producers must implement split-write logic and pay a higher network cost for multiple writes.
Examples
python · Apache Spark
input_dataset.persist()  # avoid reading input twice

user_context = input_dataset.drop('browser', 'os_version', 'device_id')
technical_context = input_dataset.select('visit_id', 'browser', 'os_version', 'device_id')

user_context.write.mode('overwrite').format('delta').save(user_context_dir)
technical_context.write.mode('overwrite').format('delta').save(technical_context_dir)

Group 2 · Records Organization

Colocation for high-cardinality data partitioning can't handle

3

Bucket

Records Organization
Problem

A high-cardinality attribute (unique user ID) drives 80% of query predicates — too high-cardinality for Horizontal Partitioner without hitting metadata limits.

Solution

Colocate groups of rows via modular hashing: hash(key) % buckets_number. Fewer buckets = bigger buckets; more buckets = smaller ones. Enables two optimizations: bucket pruning (eliminate whole buckets that can't match a predicate) and shuffle-free joins (identically bucketed tables join without network exchange).

✅ Say this out loud

"Bucketing is my answer when a high-cardinality column is central to my query and join patterns and partitioning would blow up the metadata layer — the cost is that the bucket count is essentially a one-way door."

Consequences
  • Mutability — bucketing schema is effectively immutable; changing column or count needs a costly backfill.
  • Bucket size — no clean sizing strategy; sizing for today = big future buckets, predicting the future risks being wrong.
Examples
sql · AWS Athena
CREATE EXTERNAL TABLE visits (...) ...
CLUSTERED BY (`user_id`) INTO 50 BUCKETS
TBLPROPERTIES ('bucketing_format' = 'spark')
python · Apache Spark
input_dataset.write.bucketBy(50, 'user_id').saveAsTable(table_name)
4

Sorter

Records Organization
Problem

Weekly tables (for the Fast Metadata Cleaner idempotency strategy) helped maintenance but did nothing for query time. Most queries filter or sort by event_time.

Solution

Declare sort column(s) at table creation; the database organizes rows accordingly, letting queries skip whole data blocks. Z-order ("curved sort") colocates rows across multiple dimensions instead of lexicographically — in the book's two-column example, lexicographical order read 9 blocks vs. Z-order's 7. Native to Delta Lake / Apache Iceberg; Redshift has interleaved sort keys; BigQuery/Snowflake use classical clustered tables.

📌 Note

Z-order is often called "clustering" — but mechanically it's still a sort on disk, which is why the book classifies it under Sorter rather than as its own pattern.

Consequences
  • Unsorted segments — new writes create unsorted blocks until compaction runs.
  • Composite sort keys — queries must reference columns in the declared key order to benefit; filtering only on a later key still scans most blocks.
  • Mutability — changing sort keys may require re-sorting the entire table.
Examples
sql · GCP BigQuery
CREATE TABLE `dedp.visits.raw_visits`
PARTITION BY DATE(event_time)
CLUSTER BY visit_id, page
python · Delta Lake
DeltaTable.forPath(spark, output_dir).optimize().executeZOrderBy(['visit_id', 'page'])

Metadata Enhancer

Read Performance
Problem

New analysts query a small subset of rows from a large partition but always load the full dataset before filtering — driving up latency and pay-as-you-go cost.

Solution

Persist statistics about stored records. Columnar formats (Parquet) carry a per-file footer with min/max stats computed automatically at write time — the engine checks the small footer instead of opening the large data block. Table formats (Delta Lake, Iceberg, Hudi) add commit-log-level stats (row counts, column min/max, null counts). Databases/warehouses maintain equivalent stats for the query planner.

Consequences
  • Overhead — extra write-time step to compute and keep stats current.
  • Out-of-date statistics — threshold-based auto-refresh can leave stats stale after many small changes. Mitigation: manual ANALYZE TABLE — adds temporary read overhead.
Examples

Dataset Materializer

Read Performance
Problem

A view simplifying multi-week partitioned tables still frustrates consumers — because it re-runs its query on every access.

Solution

Materialize instead of recomputing: write the `SELECT`, store the result as a materialized view (some warehouses auto-refresh, e.g. Redshift's AUTO REFRESH YES, though timing isn't immediate) or a table (manual refresh, but gains partitioning/bucketing/sorting).

🧩 Case Study

The book's incremental example keeps dedp.visits_counter fresh via MERGE-ing only rows with insertion_time after the previous run — combining the Incremental Loader and Merger patterns.

Consequences
  • Refresh cost — full re-runs are expensive. Mitigation: incremental refresh for insert-only workloads (Databricks/BigQuery support this, but not for every SQL operation).
  • Data access — consistent access/retention policy across combined source tables is hard; consider the Fine-Grained Accessor pattern.
  • Data storage overhead — trades storage for speed. Mitigation: materialize only some source datasets.
Examples
sql · GCP BigQuery
CREATE MATERIALIZED VIEW dedp.visits.visits_enriched
OPTIONS (enable_refresh = true, refresh_interval_minutes = 15)
AS SELECT ...
sql · Incremental MERGE
MERGE INTO dedp.visits_counter AS target
USING (
  SELECT user_id, COUNT(*) AS visits FROM dedp.visits
  WHERE insertion_time > '2024-11-09T03:27:32' GROUP BY user_id
) AS input
ON target.user_id = input.user_id
WHEN MATCHED THEN UPDATE SET count = count + input.visits
WHEN NOT MATCHED THEN INSERT (user_id, count) VALUES (input.user_id, input.visits)

Manifest

Read Performance
Problem

A fast Parquet-on-object-store dataset gets slow once exposed through a data warehouse layer — the bottleneck is the listing operation discovering files.

Solution

List files once, or not at all. Table file formats write each transaction's file list to the commit log, so readers skip storage listing entirely. Manifests help writing too — Redshift's COPY can take a manifest tied to a specific job run, making loads idempotent on replay.

Consequences
  • Complexity — an extra (simple) creation step, easier to accept than repeated slow listing.
  • Size — manifests can hit multiple GB with many small files or streaming producers. Early Spark Structured Streaming manifests grew so large jobs couldn't restart (fixed — SPARK-27188).
Examples
python · Delta Lake
devices_table = DeltaTable.forPath(spark_session, DemoConfiguration.DEVICES_TABLE)
devices_table.generate('symlink_format_manifest')
sql · Amazon Redshift
COPY customer
FROM 's3://devices/manifest_20250601_1031'
...
MANIFEST;
-- manifest_20250601_1031
{"entries": [
  {"url":"s3://devices/dataset_1","mandatory":true},
  {"url":"s3://devices/dataset_2","mandatory":true}]}

Normalizer

Data Representation
Problem

The visits table mixes event-driven attributes with immutable device/OS attributes, which repeat on every row — bloating storage and slowing updates.

Solution

Represent each fact once. Two implementations:

  • Normal Forms (NF) — 1NF (atomic values, unique PK), 2NF (non-key columns depend on the whole key), 3NF (no transitive dependencies between non-key columns).
  • Snowflake schema — a fact table (an observation) described by dimension tables, which can describe further dimensions (date → month → quarter).
📌 Note

The Normalizer's overarching goal: prioritize data consistency over performance — an update is reflected once and is immediately visible everywhere.

Consequences
  • Query cost — more joins, costly in distributed environments. Mitigation: colocate small dimension tables with big ones, or use broadcast joins (spark.sql.autoBroadcastJoinThreshold).
  • Archival — dimension tables can be time-sensitive (e.g. price changes). Mitigation: apply SCD (see Static Joiner, Ch. 5).
Examples
python · Apache Spark
context = (visits_context
    .join(ads, visits_context.ads_id == ads.id, 'left_outer').drop('id')
    .join(browser, visits_context.browsers_id == browser.id, 'left_outer').drop('id')
    .join(device, visits_context.devices_id == device.id, 'left_outer').drop('id'))

full_visit = (visits
    .join(context, visits.visit_id_event == context.visit_id, 'left_outer')
    .join(users, visits.users_id == users.id, 'left_outer').drop('id')
    .join(page_with_category, visits.pages_id == page_with_category.id, 'left_outer'))
9

Denormalizer

Data Representation
Problem

A fully relational warehouse model worked at low volume, then 80% of queries needed to join eight tables once the product took off.

Solution

Flatten joined tables into a single row — One Big Table (regular top-level columns) or nested structures (STRUCT-typed columns). A star schema is the dimensional-model version: like snowflake, but dimensions can't describe other dimensions.

📌 Note

Normalizer and Denormalizer aren't exclusive — build a normalized model for consistency, then a denormalized copy on top for querying, synced with a Ch. 6 sequence pattern. The snowflake layer can even stay private.

✅ Say this out loud

"I'd reach for One Big Table or a star schema when read latency dominates and the source data is closer to append-only — the update cost is the real bill you're paying for that speed."

Consequences
  • Costly updates — duplicated attributes mean one logical update touches many rows. Mitigation: treat the table as an immutable snapshot.
  • Storage — duplication grows the footprint.
  • Row consistency after updates — partial updates can leave the table internally inconsistent.
Examples
python · One Big Table (write once, read cheap)
full_visit = (fact_visit
    .join(page_w_category, fact_visit.dim_page_id == page_w_category.page_id, 'left_outer')
    .join(date_w_month_quarter, fact_visit.dim_date_id == date_w_month_quarter.date_id, 'left_outer'))

full_visit.write.mode('overwrite').format('delta').save(get_one_big_table_dir())

# reading — no joins needed
visits_table = spark_session.read.format('delta').load(get_one_big_table_dir())

Tool Quirks & Further Reading

Special notes

  • Amazon Athena implements Bucket only at the logical level — it never writes data, so INSERT INTO on a bucketed table errors out.
  • Early Apache Spark Structured Streaming manifests grew unbounded until fixed (SPARK-27188).
  • Databricks and BigQuery support incremental materialized-view refresh, but not for every SQL operation.
  • Redshift's AUTO REFRESH and BigQuery's refresh interval are both best-effort, not guaranteed-immediate.

Further reading: The Cloud Data Lake by Rukmani Gopalan (O'Reilly, 2023) — small-files background relevant to bucketing/partitioning; dimensional modeling references for fact/dimension fundamentals; Static Joiner (Ch. 5) for SCD; sequence patterns (Ch. 6) for syncing Normalizer/Denormalizer outputs.
