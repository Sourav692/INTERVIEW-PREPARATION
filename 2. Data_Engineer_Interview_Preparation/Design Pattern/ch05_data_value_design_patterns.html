Data Engineering Design Patterns — Chapter 5

Data Value Design Patterns

Nine ways to turn raw, disconnected records into something a business stakeholder can actually use — enrichment, decoration, aggregation, sessionization, and ordering, all grounded in the book's blog-analytics case study.

Book Data Engineering Design Patterns, Bartosz Konieczny (O'Reilly, 2025) Case study Blog analytics platform · Bronze/Silver/Gold Medallion Patterns in this chapter 9

Raw ingested data is not a real asset on its own. Take the book's running example: the visit-events stream. A browser producer can report browser version, language, or OS — but each visit lands as a distinct, disconnected item. Correlating "what do visitors using a specific browser have in common?" is impossible without extra effort.

That's the job of data value design patterns: augment a dataset to make it more useful for end users. This chapter sits right after Idempotency (Chapter 4) and right before Data Flow (Chapter 6) — once you can safely ingest and retry, you generate business value, and the next chapter covers how that value flows to the rest of the organization.

  • Data EnrichmentStatic Joiner, Dynamic Joiner — combine two datasets
  • Data DecorationWrapper, Metadata Decorator — compute extra attributes
  • Data AggregationDistributed & Local Aggregator — summarize volume
  • SessionizationIncremental & Stateful Sessionizer — group into sessions
  • Data OrderingBin Pack Orderer, FIFO Orderer — guarantee delivery order

01 Data Enrichment

Raw events are technically precise but contextually poor. Data enrichment patterns bring a second dataset alongside the primary one to fill that gap.

Static Joiner: reference data at rest, joined by key (+ optional SCD time bounds). Dynamic Joiner: both sides streaming, joined with watermark buffers.

Pattern: Static Joiner

Data Enrichment
Problem

A team's datasets are used heavily by business stakeholders. A new project needs a dataset linking a user's registration date to day-to-day activity — but the raw activity data lacks user context, which lives only in a static user reference dataset.

Solution

The at-rest reference dataset is the perfect condition for the Static Joiner — and it also works for streaming pipelines, not just batch.

  • Requires a list of shared key attributes across both datasets (e.g. user_id).
  • May need time constraints when the enrichment dataset implements slowly changing dimensions (SCD).
  • Usually a plain SQL JOIN; universal across processing frameworks and warehouses.
  • Can also enrich from a programmatic API — materialize as a table first if idempotency matters.
📌 Note — SCD Types SCD type 2 tracks validity with start_date/end_date columns on one table. SCD type 4 splits current value and full history into two tables. Only the implementation differs.
Consequences
Late data and consistency — The reference stream rarely evolves in perfect lockstep with the main stream. Fix: Dynamic Joiner for streaming, or orchestrator-level readiness waiting for batch.
Idempotency — Backfills need to ask whether the enrichment side must be idempotent too. If the provider can't do time-based queries, bring the data into your own layer and use SCD.
🧩 Case Study Joining streaming visit events with a static (or slowly changing) users reference dataset to answer "how does registration date relate to daily activity?"
✅ Say this out loud "I chose Static Joiner because the enrichment dataset is at-rest — but for idempotent backfills I implemented it as SCD type 2, so replaying a run always sees the same historical state of the reference data."
Examples
SCD type 2 tables + joinsql
CREATE TABLE dedp.users (
  id TEXT NOT NULL,
  login VARCHAR(45) NOT NULL,
  start_date TIMESTAMP NOT NULL DEFAULT NOW(),
  end_date TIMESTAMP NOT NULL DEFAULT '9999-12-31'::timestamp,
  PRIMARY KEY(id, start_date)
);

SELECT v.visit_id, v.event_time, v.page, u.id, u.login, u.email
FROM dedp.visits v JOIN dedp.users u ON u.id = v.user_id
AND NOW() BETWEEN start_date AND end_date;
Stream-to-batch joinpython
devices: DataFrame = spark.read.format('delta').load(...)
visits: DataFrame = (spark.readStream.format('kafka').load()...)

(visits.join(devices_table, [visits.device_type == devices.type,
    visits.device_version == devices.version], 'left_outer'))
⚠️ Warning The streaming job doesn't wait for the static dataset to update. With a raw file format (JSON/CSV) instead of a transactional table format, a full rewrite could momentarily join against an empty reference table.

Pattern: Dynamic Joiner

Data Enrichment
Problem

Static Joiner is implemented for users-to-visits, but with thousands of new users weekly, profile changes make the enriched dataset stale. Each user change now arrives via Change Data Capture on a streaming broker — both sides are moving.

Solution

The Dynamic Joiner shares Static Joiner's key logic but adds time boundaries, since the two streams may have different latencies.

  • Time-bounded buffers on both streams — the faster source waits for the slower one to catch up.
  • A GC watermark expires old buffered records so the buffer doesn't grow unbounded.
  • Frameworks like Spark Structured Streaming and Flink implement this buffering natively.
Consequences
Space vs. exactness trade-off — Bigger buffers catch more joins but cost more hardware; smaller buffers save resources but miss matches when latency skew is large. No one-size-fits-all formula.
Late data — Once the GC watermark advances past a buffered key, a very late match is silently dropped. Needs the late-data tracking techniques from Chapter 3.
✅ Say this out loud "For streaming-to-streaming enrichment I use Dynamic Joiner with watermarked buffers — the watermark size is a direct trade-off between join completeness and hardware cost, tuned to the observed latency skew between the two streams."
Examples
Watermarked time-bound joinpython
visits_from_kafka = (visits_data_stream
    .withWatermark('event_time', '10 minutes'))
ads_from_kafka = (ads_data_stream
    .withWatermark('display_time', '10 minutes'))

visits_with_ads = visits_from_kafka.join(ads_from_kafka, F.expr('''
    page = visit_page AND
    display_time BETWEEN event_time AND event_time + INTERVAL 2 minutes
'''), 'left_outer')

PatternWhen to useTrade-off
Static JoinerEnrichment dataset is at-rest / slowly changingLate-data consistency risk; idempotent backfills need SCD
Dynamic JoinerBoth datasets are streams (e.g. CDC-fed reference data)Space-vs-exactness buffer trade-off; late data still missed

02 Data Decoration

Adds value by computing attributes from within the record itself — no second dataset required. Either wrap the record (Wrapper) or hide extras in the metadata layer (Metadata Decorator).

Pattern: Wrapper

Data Decoration
Problem

A streaming layer processes visits from different providers with different output schemas. A job must extract fields into a uniform structure for downstream consumers, while clearly separating computed values from originals — keeping the original structure available for debugging.

Solution

The Wrapper adds an envelope at the record level, wrapping original values and referencing computed attributes (from the data itself or execution context).

Four wrapping implementations
#LayoutDescription
1Raw flat, computed nestedOriginal row flat; computed columns as one nested struct
2Computed flat, raw nestedOpposite of #1
3Fully flatAll columns at the same level (normalized)
4Two tablesJoined later by a unique key
Consequences
Domain split — An entity's fields end up split across raw and computed structures, complicating retrieval. Mitigation: treat wrapped data as an early layer (e.g. Silver), not the final user-facing exposure.
Size — Decorated values are part of the record, so they inflate size and network traffic. Mitigation: use a storage format with column/data-source projection.
Examples
Wrapping with PySparkpython
visits_w_processing_context = (visits.withColumn('processing_context', F.struct(
    F.lit(job_version).alias('job_version'), F.lit(batch_number).alias('batch_version')
)))
visits_to_save = (visits_w_processing_context.withColumn('value', F.to_json(
    F.struct(F.col('value').cast('string').alias('raw_data'),
    F.col('processing_context')))))
Wrapping in SQLsql
SELECT *, NAMED_STRUCT(
  'is_connected',
  CASE WHEN context.user.connected_since IS NULL
  THEN false ELSE true END,
  'page_referral_key', CONCAT_WS('-', page, context.referral)
) AS decorated FROM input_visits

Pattern: Metadata Decorator

Data Decoration
Problem

Streaming jobs release almost weekly with little visibility into how each version affects the generated data. Technical context (like job version) needs attaching to each record — but must stay invisible to end users.

Solution

Use the storage layer's metadata layer directly rather than the Wrapper:

  • Native metadata support (e.g. Kafka record headers) — straightforward.
  • Object stores — apply metadata as file-level tags.
  • No native support (relational/NoSQL) — simulate with a hidden column/table behind a view or permissions.
📌 Note — Wrapper vs. Metadata semantics Structurally similar to Wrapper, but metadata is never meant for business users — it's data about data, while Wrapper explicitly decorates business attributes too.
⚠️ Warning Never put business-related attributes (shipment address, invoice amount) in the metadata layer — most consumers never think to query it.
Consequences
Implementation — Storage support for metadata is the biggest limit. Amazon Kinesis Data Streams doesn't support headers at all. Table datasets need an extra column/table.
Examples
Kafka header metadatapython
visits_with_metadata = (visits_to_save.withColumn('headers', F.array(
    F.struct(F.lit('job_version').alias('key'), F.lit(job_version).alias('value')),
    F.struct(F.lit('batch_version').alias('key'),
        F.lit(str(batch_number).encode('UTF-8')).alias('value'))
)))
(visits_with_metadata.write.format('kafka')
    .option('kafka.bootstrap.servers', 'localhost:9094')
    .option('includeHeaders', True).option('topic', 'visits-decorated')
    .save())

PatternWhen to useTrade-off

Metadata DecoratorPurely technical/debugging context, not for end usersLimited by storage's native metadata support

Pattern: Distributed Aggregator

Data Aggregation
Problem

Combining datasets and grouping records that live across different physical nodes or stores — records sharing a key aren't guaranteed to be colocated.

Solution

The classic MapReduce-style approach: group, then reduce. Requires a shuffle — exchanging records across the network so the reduce step can operate on collocated rows.

  • Aggregations supporting partial generation (e.g. COUNT) can pre-aggregate locally before the shuffle, shrinking what's exchanged.
  • Works across physically isolated stores — e.g. Spark joining PostgreSQL with local JSON, or BigQuery querying external GCS tables.
Consequences
Additional network exchange — Two exchanges: bringing input data to nodes, and the shuffle itself.
Data skew — One overloaded key makes moving/processing it the most expensive part. Mitigation: salting — add a random value to the key, aggregate twice.
Scaling — A finished node may stay held for fault tolerance. A shuffle service (Spark's External Shuffle Service, GCP Dataflow's Shuffle) frees nodes mid-job.
✅ Say this out loud "When I see data skew in a distributed aggregation, my first lever is salting the grouping key and re-aggregating in two passes — it trades a bit of extra shuffle for avoiding a single overloaded reducer."
Examples
Cross-store aggregationpython
visits = spark_session.read.json(f'{base_dir}/input-visits')
devices = spark_session.read.jdbc(url='jdbc:postgresql:dedp',
    table='dedp.devices', properties={'user': 'dedp_test',
    'password': 'dedp_test', 'driver': 'org.postgresql.Driver'})

visits_with_devices = visits.join(devices,
    [devices.type == visits.context.technical.dev_type,
     devices.version == visits.context.technical.dev_version], 'inner')
Salting a skewed keypython
dataset.withColumn('salt', (rand()*3).cast("int"))
    .groupBy('group_key', 'salt').agg(...)
    .groupBy('group_key').agg(...)

Pattern: Local Aggregator

Data Aggregation
Problem

A streaming job generates windows over visits in a partitioned streaming broker. Volume is static and the partition count never changes — the job needs to drop the automatic grouping shuffle.

Solution

With static partitioning and related attributes already colocated, the Local Aggregator aggregates with only the input-read exchange — no shuffle.

  • Producer side must guarantee a key always lands in the same partition.
  • Kafka Streams' groupByKey recognizes pre-partitioned data natively.
  • Spark uses mapPartitions/foreachPartition manually, or avoids shuffle for matching bucketed datasets.
Consequences
Scaling — Breaks if partition assignment ever changes; reorganizing storage is costly and needs a stop-the-world event in streaming.
Grouping keys — Expects one shared grouping-key logic across all consumers of the partitioned data.
Examples
Kafka Streams groupByKeyjava
KStream<String, String> visitsSource = streamsBuilder.stream("visits");
KGroupedStream<String, String> groupedVisits = visitsSource.groupByKey();
KStream<String, AggregatedVisits> aggregatedVisits = groupedVisits
    .aggregate(AggregatedVisits::new, new AggregatedVisitsAggregator(),
        Materialized.with(Serdes.String(), new JsonSerializer<>())).toStream();

PatternWhen to useTrade-off
Distributed AggregatorData not guaranteed colocated by keyShuffle cost; data skew; scaling/reclaiming compute
Local AggregatorInput statically partitioned by the grouping keyFrozen/costly rescale; one shared grouping key required

04 Sessionization

A specialized aggregation: group events into user sessions, adapted to incremental batch workloads or real-time streaming.

Pattern: Incremental Sessionizer

Sessionization
Problem

Visit events are stored hourly partitioned. Sessions start at first visit, end after two hours of inactivity. Typical duration: minutes to three hours, so one session can span up to three partitions — analysts struggle reprocessing many consecutive partitions per user.

Solution

Builds on the Incremental Loader pattern (Chapter 2) using three storage spaces:

StoragePurpose
Input datasetRaw hourly-partitioned events
Completed sessionsFinished sessions, publicly exposed
Pending sessionsSessions still spanning partitions; private, may carry internal fields

Sessionization logic applies three states: Initialization (session starts), Accumulation (session is live, data folds in), Finalization (session ends on event type or inactivity).

Consequences
Inactivity period — Longer periods capture more late data but cost more compute/storage. Emitting partial sessions early risks consumers treating an interim state as final.
Data freshness — Batch-bound insight lag; partial-session emission is the main mitigation.
Late data / backfilling — Sessions are forward dependent: 09:00's session affects 10:00's, which affects 11:00's. Backfilling one partition means backfilling all subsequent ones.
🧩 Case Study The blog platform's two-hour inactivity window, spanning up to three hourly partitions per session, is the concrete numeric example used throughout this pattern.
Examples
Session merge logicsql
CREATE TEMPORARY TABLE sessions_to_classify AS
SELECT
  COALESCE(p.session_id, n.session_id) AS session_id,
  LEAST(p.start_time, n.start_time) AS start_time,
  GREATEST(p.last_visit_time, n.start_time) AS last_visit_time,
  ARRAY_CAT(p.pages, n.pages) AS pages,
  CASE WHEN n.user_id IS NULL THEN p.expiration_batch_id
       ELSE '{{ macros.ds_add(ds, 2) }}' END AS expiration_batch_id
FROM (SELECT ... FROM visits_{{ ds_nodash }}) AS n
FULL OUTER JOIN (SELECT ... FROM dedp.pending_sessions
  WHERE execution_time_id = '{{ prev_ds }}') AS p ON n.session_id = p.session_id;

Pattern: Stateful Sessionizer

Sessionization
Problem

Stakeholders want lower latency than the hourly-bound Incremental Sessionizer can offer. Visits are available on the stream within seconds — the pipeline needs to run near real time.

Solution

Uses a state store — in-memory for speed, checkpointed regularly to fault-tolerant storage. Two abstractions: session windows (fixed gap duration per key) or arbitrary stateful processing (dynamic gap logic, more implementation effort, more flexibility — supported by Spark, Flink, GCP Dataflow).

Consequences
At-least-once processing — Checkpointing is irregular, so restarts resume from the last checkpoint. Avoid session-key logic tied to values that change between runs (e.g. wall-clock time).
Scaling — Capacity changes trigger state rebalancing — costlier than stateless jobs.
Inactivity period time — Event-time expiration is reliable; processing-time expiration risks expiring sessions too early under unexpected latency (e.g. write retries).
✅ Say this out loud "I picked event-time-based expiration over processing-time for the session state — processing time ties correctness to wall-clock latency, and any retry-induced delay would expire sessions prematurely."
Examples
Stateful mappingpython
grouped_visits = (visits_from_kafka.withWatermark('event_time', '1 minute')
    .groupBy(F.col('visit_id')))

sessions = grouped_visits.applyInPandasWithState(
    func=map_visits_to_session,
    outputStructType=StructType([...]),
    stateStructType=StructType([...]),
    outputMode="update", timeoutConf="EventTimeTimeout"
)
Trade-off — Sessionization
PatternWhen to useTrade-off
Incremental SessionizerBatch pipelines, hourly-partitioned inputLatency bounded by partition size; expensive forward-dependent backfills
Stateful SessionizerNear-real-time session availability requiredAt-least-once semantics; state rebalancing complicates scaling

05 Data Ordering

Guaranteeing chronological delivery order downstream — easy to say, hard to guarantee at scale against data stores with partial commit semantics.

📌 Note — Partial commits Some bulk writes can partially succeed — ingesting only a subset of records. Of three records timestamped 10:00, 10:10, 10:20, a store might write only 10:20; retrying the rest leaves the dataset out of order. Seen in AWS Kinesis's PutRecords, DynamoDB's BatchWriteItem, and Elasticsearch's bulk operation.

Pattern: Bin Pack Orderer

Data Ordering
Problem

External sites embed the platform's pages; embed visit events must reach an external API for partner analytics. The sync job must build a 10-minute window with per-minute aggregates and flush individually per minute/provider, in event-time order — but the destination broker has partial commit semantics.

Solution

The Bin Pack Orderer uses bulk operations while guaranteeing order under partial commits:

  1. Sort all related events by grouping key and event time.
  2. Pack sorted rows into bins — one grouping key per bin.
  3. Emit bins sequentially — retries stay local to a bin; the next bin waits for the current one to finish.
Consequences
Retries — Order is guaranteed only within a single execution; a full pipeline retry can break overall ordering across runs.
Complexity — Needs custom sort-and-bin logic, more than a classical sort call.
Examples
Local sort + bin packingpython
(events.sortWithinPartitions([F.col('visit_id'), F.col('event_time')])
    .foreachPartition(lambda rows: write_records_to_kinesis(...)))

def write_records_to_kinesis(output_stream, visits_rows):
    delivery_groups = []
    groups_index = 0
    last_visit_id = None
    for visit in visits_rows:
        if visit.visit_id != last_visit_id:
            last_visit_id = visit.visit_id
            groups_index = 0
        if len(delivery_groups) <= groups_index:
            delivery_groups.append([])
        delivery_groups[groups_index].append(visit)
        groups_index += 1

Pattern: FIFO Orderer

Data Ordering
Problem

A streaming job must forward detected events, in processing order, to a different stream — as soon as possible, so buffering isn't an option.

Solution

The simpler FIFO Orderer: issue delivery requests and wait for each acknowledgment before sending the next.

  • Single-record API (Kinesis PutRecord, or Kafka send() + sync flush()).
  • Bulk API only with full commit semantics, bounded concurrency (Kafka max.in.flight.requests.per.connection=1, or the idempotent producer, up to 5 concurrent).
Consequences
I/O overhead and latency — One network request per record. Mitigation: multithreading with per-entity process scoping to keep ordering intact per entity.
FIFO is not exactly-once — A send-then-ack loop can silently redeliver records if the ack fails after a successful send. Needs one of the idempotency patterns from Chapter 4.
⚠️ Warning producer.send(message) immediately followed by consumer.ack(message) is not safe for exactly-once — if ack() fails after a successful send, a restart resends already-delivered records.
✅ Say this out loud "FIFO Orderer gives me delivery order, not delivery guarantees — for exactly-once I still need to layer one of the idempotency patterns from Chapter 4 on top."
Examples
Idempotent producerpython
producer = Producer({
    'max.in.flight.requests.per.connection': 5,
    'enable.idempotence': True,
    'queue.buffering.max.ms': 2000
})
producer.produce(...)

PatternWhen to useTrade-off
Bin Pack OrdererDestination has partial-commit semantics; bulk throughput mattersOrder guaranteed per-execution only; nontrivial bin logic
FIFO OrdererLow volume, latency-sensitive, order over throughputPer-record I/O overhead; not exactly-once alone

06 Gotchas — By Pattern

Static Joiner — Late data breaks consistency between enrichment and enriched datasets; idempotent backfills may require SCD.
Dynamic Joiner — Space-vs-exactness trade-off from the GC watermark buffer; late data can be silently dropped past the watermark.
Wrapper — Domain split across raw/computed structures; payload size grows since decorated values are part of the record.
Metadata Decorator — Fully dependent on storage's native metadata support (e.g. Kinesis has no headers); scope must stay metadata-only.
Distributed Aggregator — Network exchange (shuffle) cost; data skew on hot keys; reclaiming compute after the reduce phase.
Local Aggregator — Frozen/costly scaling tied to static partitioning; requires one shared grouping key across all consumers.
Incremental Sessionizer — Inactivity period trades cost against completeness; forward-dependent sessions make backfills expensive.
Stateful Sessionizer — At-least-once processing from irregular checkpointing; state rebalancing complicates scaling.
Bin Pack Orderer — Ordering guarantee only holds within a single execution, not across pipeline-level retries.
FIFO Orderer — Per-record I/O overhead and latency; FIFO order is not the same thing as exactly-once delivery.
