Lakehouse & Table Formats

A lakehouse table format is a clever bookkeeping system sitting on top of a pile of plain files, whose whole job is to make that pile behave like a real, trustworthy table.

Printed as "Chapter Eight" in the book's own running heads — see the numbering note in Chapter 3. This guide cites it as Chapter 9.
The Simple Version, First

A huge shared spreadsheet hundreds of people need to read and update at once — except instead of one file, it's millions of separate files in cloud storage, which has a rule: you can't edit a file in place, and there's no built-in guarantee everyone reading it sees a consistent version.

A lakehouse format is just clever bookkeeping on top of that pile of files — making it behave like a real table, where changes appear all at once, past versions are instantly queryable, and adding a column doesn't mean rewriting everything.

Why Picking "By Popularity" Cost One Team Six Months

Two teams migrate from an older system to a modern lakehouse format. Both need: all-or-nothing changes, columns added without rewriting everything, past versions for compliance, and multiple tools querying the same tables.

Team A picks a Spark-first format in a week because they're heavy Databricks users. Shipping is fast. Team B picks a writer-neutral format in three weeks because they run several query engines against the same tables.

Six months later, Team A's dashboards on a different engine are slow — edge cases around streaming updates cause inconsistent reads across engines. They only now realize the format they picked was fundamentally built around one engine.

Both teams "picked a format." One picked by popularity. The other picked by actually checking which tools would be writing. That's the entire difference.

Idea 1: Making a Pile of Files Behave Like a Real Table

You can't directly edit a file in cloud storage the way you'd edit a database row. Without coordination, there's no guarantee everyone reading a table made of thousands of files sees a consistent version.

💡 The one idea to remember

A lakehouse format solves this with a tiny pointer file swapped atomically. Every update creates new files, then does one instant, all-or-nothing swap of a pointer saying "the current version is over here now." Nobody ever sees a half-finished update.

❌ Anti-Pattern

Picking a format by popularity or familiarity instead of by what's actually writing to the table. "We're picking Delta because everyone uses it" is the most common wrong answer to this chapter's core question.

⚠️ War Story

A data platform team at an ad company picked Hudi because they'd read it was "best-in-class for updates" and their pipelines included some CDC data. Six months in, they measured their actual workload: 92% append-only event tables, with only nightly updates on a handful of small dimension tables. Hudi's "fast write" mode was rewriting entire data files to handle even small updates, inflating storage costs by roughly 8x. They migrated to Iceberg over one quarter. Storage costs dropped by a third; query planning time dropped by half. The lesson wasn't that Hudi is bad — it was that the team hadn't measured their real workload before picking based on a marketing claim.

✅ Pattern

Schedule lakehouse maintenance like any other production concern — a nightly compaction job and a weekly snapshot-expiration job from day one. Catching bloat proactively costs minutes a quarter. Diagnosing it reactively costs days.

Idea 5: Time Travel Is a Compliance Feature, Not Just a Debugging Trick

Every past version stays queryable until explicitly expired — instantly, at almost no cost, because it resolves against existing bookkeeping rather than reconstructing anything.

sql-- src/code-examples/ch08/iceberg_time_travel.sql
-- Hidden partitioning: derived from a source column, not a
-- separately maintained column.
CREATE TABLE warehouse.events (...)
USING iceberg
PARTITIONED BY (days(event_ts));

-- Time travel resolves against the metadata tree, not raw files.
SELECT COUNT(*) FROM warehouse.events VERSION AS OF 3847219478234;
SELECT COUNT(*) FROM warehouse.events TIMESTAMP AS OF '2024-06-15 14:30:00';

If a regulator asks "show me exactly what this looked like on December 31st at 11:59 PM," a lakehouse answers in seconds. Without it, you're restoring a backup — hours, plus auditor coordination.

The retention window is a legal decision, not just a technical one. Privacy rules (GDPR's "right to be forgotten") require deleting a person's data within a set window — meaning any snapshot still containing it must expire within that window. Financial audit rules can separately require keeping records for years. These two pressures genuinely pull in different directions.

A Real Interview, Walked Through Simply

A rich, two-part example — migrating a huge legacy warehouse, then picking a format from scratch at a fresh build.

Part 1 — Migrating a 50 PB legacy warehouse, zero downtime
Interviewer

Migrate a 50 petabyte legacy Hive warehouse to a lakehouse format. Zero downtime. Thousands of active consumers across batch, interactive analytics, streaming, and BI.

Candidate

What's actually writing to these tables today — one dominant engine, or multiple? And what's the mix of table shapes — mostly append-only, or lots of updates?

Interviewer

Multiple engines. Mostly append-only fact tables, some slowly-changing dimensions, some CDC-derived tables with a higher update rate.

Candidate

Multiple writers rules out the Spark-first option — one engine's support would lag. I'd lean writer-neutral. (pauses) Let me actually check that instead of asserting it — how frequently are those CDC tables updated, what percentage of rows per day?

Interviewer

Call it 5 to 10% per day on the heaviest one.

Candidate

Comfortably within range for the writer-neutral format with nightly compaction. At 20%+ per day, the update-optimized format would genuinely win instead — better to confirm before committing. I'd standardize on one format across the warehouse rather than run two for the sake of a handful of tables.

Interviewer

What breaks first at this scale?

Candidate

Three things. Metadata bookkeeping bloat with 730 daily partitions and thousands of files each. The small-file problem from streaming writers killing read parallelism. And cloud storage rate limits by file-path prefix — a nightly writer landing everything under one date-based path hits that ceiling and gets throttled a couple hours in. The fix is spreading the partition value early in the path across many prefixes. Teams that skip this discover it during their first big backfill.

Interviewer

What's the point of no return?

Candidate

The moment the first consumer switches to reading only from the new format. Before that, rollback just means turning off dual-writes. After, it means re-migrating everyone who already switched. I'd mark that milestone explicitly and require written sign-off before crossing it.

Part 2 — A fresh build: picking a format from scratch
Interviewer

Why this format specifically, and not one of the other two?

Candidate

Writer neutrality. Several engines write to these tables, and adding a new tool next year should work without a migration. The Spark-first option makes other engines second-class here. The update-optimized option is tuned for update-heavy workloads, and we're mostly append-only, so it costs more than it buys. The writer-neutral option is the default for exactly this situation — its maintenance overhead is real, but every format has some version of that cost under a different name.

Common Mistakes People Make

  1. Picking a format for a multi-engine warehouse based on one team's favorite tool. Excellent for Spark-only shops, a liability the moment a second engine writes.
  2. Skipping maintenance with "we'll get to it later." Later is when the incident hits — bloat causes slowdowns hard to trace back to their cause.
  3. Treating time travel as purely a debugging convenience. It's a compliance feature, and retention is a legal decision.
  4. Underestimating the small-file problem when migrating. The old system's file-size patterns are usually wrong for a lakehouse. Compaction starts day one.
  5. Trying to cut over in a single step. Petabyte migrations succeed as a 6-to-9-month rollout, never a single flip-the-switch event.
Cheat Sheet
Built to be photographed before your interview.

The Three Formats

  • Iceberg — writer-neutral, default for multi-engine
  • Delta Lake — Spark-first, default for Databricks
  • Hudi — update-optimized, default for CDC-heavy

The Metadata Tree

catalog → snapshot → manifest list → manifest → data files

Every commit: new manifests, one atomic swap of the catalog pointer.

Four Maintenance Jobs

  1. Expire old snapshots — daily, keep 7–30 days
  2. Compact small files — daily/nightly, 128–512 MB target
  3. Rewrite manifests — weekly
  4. Remove orphaned files — weekly

Time Travel

A compliance feature. Retention in days is a legal decision.

VERSION AS OF / TIMESTAMP AS OF

Schema Evolution

Columns tracked by ID, not name — add/rename/drop are all metadata-only, no rewrite.

Migration Pattern (Petabyte Scale)

Scaffolding → dual-write + validate (4–6 wks) → progressive reader switch → decommission. Total: 6–9 months.

Three Lines Worth Memorizing

  • "Pick by workload composition, not by popularity."
  • "Maintenance on the lakehouse is mandatory, not optional."
  • "Time travel retention is a legal decision."
A Couple of Extra Ideas — from the older 2025 edition
  • Serialization format depends on how data will be read: columnar (Parquet) wins for analytics, since queries want a few columns out of a huge dataset; row-based (Avro) makes more sense for individual events through a message system, since each is read as a whole record and Avro's schema enforcement catches problems early.
  • A lakehouse format is one piece of a bigger pattern vocabulary: medallion/layered lake patterns, event-driven vs. scheduled pipelines, and how state/CDC patterns interact with correctness — this is what separates operating a tool from actually architecting a platform. These patterns repeat across analytics, fraud detection, identity resolution, and traditional reporting alike.
