System Design for Data Engineers · Chapter 16 · Case Study 2

Recommendation Serving

Out of millions of possible items, the system has to find the best handful for this specific person, right now, cheaply enough to do it billions of times a day.

Chapter 16 is printed as "Chapter Fifteen" in the book's own running heads — see the numbering note in Chapter 3. This is the second of four full case studies.
The Simple Version, First

A librarian has ten million books but only three seconds to hand you the ten you'd actually enjoy. She can't read every description in that time — so she grabs a rough armful of about a thousand books that seem in your interest area first, then takes a closer look at just those to pick the best ten.

Where fraud detection was a write-heavy problem with a hard latency wall, this is a read-heavy problem with both a latency budget and a real cost ceiling.

The Prompt

"Design the feature-serving pipeline for a recommendation system at a large consumer platform. Peak traffic is around 35,000 ranking requests per second. Ten million items in the catalog. The end-to-end response budget is 200 milliseconds. This isn't strictly blocking the way fraud scoring is, but it still needs to be fast and affordable at this scale."

Idea 1: Five Questions, Asked in a Very Deliberate Order

  1. "What kind of ranking are we doing?" — decides if a similarity-search index is needed at all.
  2. "What happens for a brand-new user?" — shapes how the serving path branches for cold start.
  3. "Is 200ms end-to-end, or service-only?" — a 50-80ms swing in the real internal budget.
  4. "How often do features need refreshing?" — the online-vs-offline split.
  5. "What's the cost ceiling?" — asked upfront here specifically, unlike in fraud, because recommendation infra is often the single largest DE cost at a consumer company.
🚩 FAANG Signal

Asking about cost upfront for a recommendation prompt specifically signals real operational experience. Fraud-focused prep rarely emphasizes cost the same way, so candidates who only prepared with the fraud playbook tend to skip this question here — and it's noticeable.

Idea 3: Naming Two Weak Points Together — On Purpose

✅ Say this out loud

"Feature-store tail latency, because 3.5 billion lookups per second leaves a razor-thin margin. And cost, because the cost-per-impression number determines which business decisions are even feasible."

🚩 FAANG Signal

Fraud was latency-first because the blocking path was a hard stop. Recommendation is latency-and-cost because the budget is softer but the cost-per-impression number directly shapes business viability. Naming only latency here is just re-applying the fraud playbook without adjusting it — naming both shows the toolkit is matched to the actual problem.

Idea 4: The Architecture, in Plain Terms

  • Candidate generation narrows the catalog to ~1,000 candidates per user via a similarity index.
  • The re-ranker scores those candidates, combining fast session features with slower baseline features.
  • A fast in-memory store holds only what genuinely changes fast — ~20 features/user, ~50GB total at 100M active users.
  • A columnar store holds everything else, refreshed on different schedules (daily/hourly/weekly) and pre-joined ahead of time.
  • Every impression gets logged — the audit trail and next model's training data.

Idea 5: Handling a Brand-New User

Under a threshold of prior sessions, a new user routes to popularity-ranked items blended with contextual signals, using a model trained specifically on minimal-history users. As real history accumulates, cold-start scores blend gradually into fully personalized ones.

The subtle design choice: cold start isn't a separate pipeline — it's the same serving architecture, fed different feature values and a different model variant. That keeps the operational footprint small.

Idea 7: What Breaks First Under Load

  1. Fast-store tail latency drifting under bursty load — primary alert: p99.9 sustained above 3ms for 30 seconds.
  2. Candidate-generation quality degrading silently — no alarm fires, just slowly worsening engagement over days. The most dangerous one because it's ambiguous.
  3. Query anti-patterns creeping into analytics — the function-on-partition- column trap from the query engines chapter, showing up again here.

The 30-Second Closing Summary

✅ What I'd build

A two-stage ranking pipeline — fast similarity search to narrow to ~1,000 candidates, then a richer model to re-rank. Session features in a fast store with a 1ms target, everything slower pre-joined into columnar storage. Cold start as a variant, not a separate system.

✅ What I'd sacrifice

The fast store is a single point of failure for the whole latency target — invest in its observability first. Candidate-generation quality can drift silently, so it needs a dedicated quality metric, not just an uptime check.

✅ What I'd watch, in order

Fast-store p99.9 above 3ms (primary). Candidate-generation recall trending down week over week (the slow, silent one). Cost-per-impression drift.

What This Case Study Is Really Teaching

The pattern from Case Study 1 is visible here, wearing different clothes: skew shows up as item popularity instead of merchant concentration; the feature store shows up identically (fast online tier + slower offline tier); "exactly-once" becomes "impression-log exactly-once." The moves transfer across domains — the specifics don't.

Common Mistakes People Make

  1. Skipping the "score everything" math. Without it, two-stage ranking sounds arbitrary instead of mathematically necessary.
  2. Naming only latency as the weak dimension. Cost matters just as much here.
  3. Treating cold start as a separate system. Should be a variant of the same pipeline.
  4. Forgetting feature-store tiering is the biggest cost lever. In-memory is 10-50x pricier per GB than columnar.
  5. Not asking about cost upfront. A strength signal here specifically.
Cheat Sheet

The "Score Everything" Math

10M × 35,000/sec = 350B ops/sec naively. Two-stage ranking cuts this by 4 orders of magnitude.

Two Weak Dimensions

Feature-store tail latency (3.5B lookups/sec) and cost (determines business viability).

  1. Feature-store tiering (biggest — 10-50x pricier in-memory)
  2. Gateway result caching (20-40% fewer calls)
  3. Candidate-gen index choice (ML-team call)

What Breaks First

  • Fast-store tail latency under burst
  • Candidate-gen quality, silently
  • Query anti-patterns in analytics

Cold Start Rule

Same pipeline, different inputs — never a separate system.

Three Lines Worth Memorizing

A Couple of Extra Ideas — from the older 2025 edition
  • Upload-time enrichment fixes cold start more cleanly: a dedicated event at content-creation time triggers an enrichment pipeline extracting content and author features before any engagement data exists — so the model never sees a truly blank slate.
  • Time-decayed features (a recent action counting more than an old one) benefit from a true streaming engine's per-event control rather than a micro-batch framework's coarser cadence.
  • Online/offline feature consistency is its own design question — a feature computed slightly differently in the real-time path versus batch training can cause the model to train on one distribution and serve on another.
