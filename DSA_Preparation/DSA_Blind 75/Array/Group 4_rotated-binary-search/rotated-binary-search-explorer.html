The core flip

A rotation breaks full sortedness, but at any midpoint, at least one half is still fully sorted. Detect which half that is by comparing endpoints, range-check the target against that sorted half, and recurse into whichever half must contain it. Each step still halves the search space — O(log n) survives the rotation.

Decision rule: if nums[lo] <= nums[mid], the left half [lo..mid] is sorted — check if target falls in [nums[lo], nums[mid]). If so, search left; otherwise the target (if present) must be in the right half, so search there. Mirror the logic when the right half is the sorted one instead.

Optimal Solution — Modified Binary Search · O(log n) time, O(1) space

def search_rotated(nums: list[int], target: int) -> int:
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:        # LEFT half [lo..mid] is sorted
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1              # target in that sorted left half
            else:
                lo = mid + 1              # otherwise it's on the right
        else:                             # RIGHT half [mid..hi] is sorted
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1              # target in that sorted right half
            else:
                hi = mid - 1              # otherwise it's on the left
    return -1

Search space halves every step → O(log n) time. Only two/three integer pointers → O(1) space.

The core flip

We're not hunting a value this time — we're hunting the rotation point (the dip where the array resets). Compare nums[mid] to nums[hi]: if nums[mid] > nums[hi], the dip must be strictly to the right of mid (mid is still on the "high" side of the rotation); otherwise the dip is at mid or to its left.

Why hi = mid, not mid - 1? When nums[mid] <= nums[hi], mid itself could be the minimum — discarding it with mid-1 risks skipping the answer. Using hi = mid keeps it in play; the loop still terminates because lo only ever moves strictly forward (mid+1) in the other branch.

Optimal Solution — Binary Search on the Rotation Point · O(log n) time, O(1) space

def find_min(nums: list[int]) -> int:
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:   # mid is on the "high" side -> dip is to the RIGHT
            lo = mid + 1
        else:                       # dip is at mid or to the LEFT
            hi = mid
    return nums[lo]                 # lo == hi lands exactly on the minimum

Search space halves every step → O(log n) time. Two integer pointers → O(1) space.
