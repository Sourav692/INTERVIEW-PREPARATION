4. Downstream of a Failure (Blast Radius)

Medium · Graphs / BFS · DFS

The problem, in plain words

Services depend on each other (an arrow u → v means v depends on u). If u fails, everything reachable from it — directly or through a chain — is affected. Find that whole "blast radius."

Auth(0) → API(1), Auth(0) → Billing(2) API(1) → Notif(3), API(1) → Dashboard(4) Billing(2) → Dashboard(4), Dashboard(4) → Reports(5) API (1) fails → affected = {Notif(3), Dashboard(4), Reports(5)}

Approach 1 — Rescan every edge until stable (the slow way)

Keep a "reached" set starting with the failure. Repeatedly scan all edges: if one starts at a reached node, its endpoint becomes reached too. Repeat until a full pass changes nothing. Correct, but you re-walk every edge every round → O(nodes × edges).

Approach 2 — Single BFS/DFS sweep (the fast way)

The idea: build a lookup once (who depends on each node), then walk outward from the failure with a queue, marking each node visited exactly once. That's what the animation above does. Each node and edge is touched once.

Speed & memory: O(nodes + edges) time and space. The visited set is what makes this safe even if the graph has a cycle — without it you could loop forever.

When you'd reach for this

"Who is affected / blast radius / cascading failure / everything downstream of X" — incident impact analysis, dependency graphs. Reverse the arrows to instead trace upstream (root cause: what did this task wait on?).
