🧩 DevRev DSA Patterns — Interview Cheat Sheet

Six problems, six reusable ideas — each one a real DevRev platform concern. Learn to spot which one a question is asking for, and what to say out loud.

🧮 Prefix Sum + Hash Map

Running totals turn any stretch-sum into one subtraction; a memory of totals makes the match instant.

The tell (how to spot it): Count/among contiguous subarrays that hit a target sum — especially with negative values (no sliding window).

How it works: Walk once keeping a running total; for each position ask “have I seen total = current − k before, and how often?” Seed the memory with total 0.

Problems here that use it: Subarray Sum Equals K

Say this in the interview:
“I’ll keep prefix sums in a hash map and count earlier prefixes equal to current − k — that’s one linear pass.”

🌊 Monotonic Deque (rolling extreme)

A line of candidates kept in order so the winner is always at the front.

The tell (how to spot it): You need the max/min over every sliding window, or a rolling peak.

How it works: Keep candidate positions in a deque, biggest at the front. A bigger newcomer evicts smaller older ones from the back; the front drops when it slides out of the window.

Problems here that use it: Sliding Window Maximum

Say this in the interview:
“I’ll keep a decreasing deque of indices so the window max is the front — each index enters and leaves once, so O(n).”

🔥 Reachability from a Source (BFS / DFS)

Start at one node and fan out to everything you can reach, chalk-marking as you go.

The tell (how to spot it): You need the blast radius of a failure, everything downstream of X, or a cascade / who-is-affected set.

How it works: Build an adjacency list, then BFS (queue) or DFS (stack) from the source with a visited set. BFS also gives hop-distance = impact order. Reverse the arrows to trace upstream (root cause).

Problems here that use it: Downstream of a Failure

Say this in the interview:
“It’s reachability from the failed node, so I’ll BFS/DFS with a visited set — O(V+E), and cycle-safe.”

🔗 Topological Waves (Kahn by level)

Do chores in dependency order — and do all the currently-unblocked ones at once.

The tell (how to spot it): You must order tasks under prerequisites, run independent ones in parallel, or detect a scheduling cycle.

How it works: Count each task’s remaining prerequisites (in-degree). Emit the whole zero-prerequisite frontier as one wave; finishing it lowers dependents’ counts, exposing the next wave. Leftovers = a cycle.

Problems here that use it: Topological Wave Scheduling

Say this in the interview:
“These are dependencies, so I’ll run Kahn’s and emit each in-degree-0 frontier as a parallel wave; leftover tasks mean a cycle.”

🗂️ Hash-Map Index, then One Pass

Look everything up by id first, so linking is instant instead of a search.

The tell (how to spot it): You must turn flat {id, parent_id} rows into a tree, or join records that reference each other.

How it works: Build a map id → node in one pass, then a second pass attaches each node under its parent in O(1). Handles rows that arrive before their parent; no-parent rows are roots.

Problems here that use it: Build Tree from Flat List

Say this in the interview:
“I’ll index the rows by id in a dict, then one linear pass links each node to its parent in O(1) — absent parents become roots.”

🔀 DFS That Returns a Signal Upward

Ask each node “do you contain what I’m looking for?” and let the answer bubble up.

The tell (how to spot it): You need something about two nodes in a tree — a common ancestor, a path, a shared property — with no ordering to exploit.

How it works: One post-order DFS: a node returns itself if it is a target or if a target was found below it. The node that gets a non-null from both sides is where the paths split (the LCA).

Problems here that use it: Lowest Common Ancestor

Say this in the interview:
“I’ll DFS returning a node if it holds either target; the node whose left and right both come back non-null is the LCA — O(n).”

🗄️ Hash Map + Doubly Linked List

One structure to find things fast, another to track order — together, everything is O(1).

The tell (how to spot it): A fixed-size cache with O(1) get/put that must evict the least-recently-used item.

How it works: The map gives instant lookup by key; the doubly linked list keeps items in recency order. On access, splice the node to the front; when full, drop the node before the tail sentinel and delete its key.

Problems here that use it: LRU Cache

Say this in the interview:
“Hash map for O(1) lookup, doubly linked list for O(1) reorder and eviction — front is most-recent, evict the node before the tail.”

Talking through any of these

1. State the approach and complexity first — the prep doc flags “needed hints” as a negative signal.

2. Name the DevRev tie-in: task trees, workflow DAGs, rolling metrics, caches — connect the algorithm to real orchestration/integration work.

3. Narrate edge cases out loud: empty input, single element, cycles, duplicate/absent keys, negative values.
